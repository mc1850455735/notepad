
# 发送者可靠性

### 发送者重连

**概述**
- 有的时候由于网络波动, 可能出现发送者连接 MQ 失败的情况.
- 通过配置我们可以开启连接失败后的重连机制
```yaml
spring:  
  rabbitmq:  
    connection-timeout: 1s  
    template:  
      retry:  
        enabled: true
        initial-interval: 1000ms # 失败后初始等待时间
        multiplier: 2    # 等待倍率
        max-attempts: 3  # 最大重试次数
```

**注意**
- 当网络不稳定时, 使用重试机制可以有效提高消息发送的成功率. 但是 `SpringAMQP` 提供的重试机制是**阻塞式**的重试, 等待过程中, 线程是阻塞的, 会影响业务的性能
- 如果对业务性能有要求, 建议禁用重试机制. 如果要用, 需要**合理配置**等待时长和重试次数. 也可以考虑异步线程执行发送消息的代码, 避免当前线程阻塞

### 发送者确认
- `SpringAMQP` 提供了 `Publisher Confirm` 和 `Publisher Return` 两种确认机制.
- 开启确认机制后, 当发送者发送消息给 MQ 后, MQ 会返回确认结果给发送者
- 返回结果有以下几种情况
	1. 消息投递到了 MQ, 但是**路由失败**, 此时会通过 `PublisherReturn` 返回路由异常原因, 并返回 ACK, 告知投递成功
	2. **临时消息**投递到了 MQ, 并且入队成功, 返回 ACK, 告知投递成功
	3. 持久消息投递到了 MQ, 并且入队**完成持久化**, 返回 ACK, 告知投递成功
	4. 其他情况都会返回 **NACK**, 告知投递失败
- 由于发送者确认机制需要与 MQ 进行通信与确认, 会影响消息发送效率, 大多数情况下不建议开启, 除非对业务可靠性要求很高

**实现**
1. 在 `publisher微服务` 的 `application.yaml` 中添加配置
- `publisher-comfirm-type` 中有三种类型可选
	- `none`: 关闭 confirm 机制
	- `simple`: 同步阻塞并等待 MQ 的回执消息
	- `correlated`: MQ 异步回调方式返回回执消息 (通常使用)
```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated
    publisher-returns: true
```
2. 每个 RabbitTemplate 只能配置一个 ReturnCallback, 因此需要在项目启动过程中配置
```java
@Slf4j  
@Configuration  
@RequiredArgsConstructor  
public class MqConfig {  
    private final RabbitTemplate rabbitTemplate;  
    @PostConstruct  
    public void init() {  
        rabbitTemplate.setReturnsCallback(returnedMsg -> {  
            log.error("监听到了消息ReturnCallback");  
            log.debug("交换机: {}", returnedMsg.getExchange());  
            log.debug("routingKey: {}", returnedMsg.getRoutingKey());  
            log.debug("message: {}", returnedMsg.getMessage());  
            log.debug("replyCode: {}", returnedMsg.getReplyCode());  
            log.debug("replyText: {}", returnedMsg.getReplyText());  
        });  
    }  
}
```
3. 发送消息, 指定消息 ID 和消息 ConfirmCallback
- 通常只会收到 `ACK` 或者 `NACK`, 二者都代表 `Success`, `Failure` 指的是程序内部发生异常的情况, 基本不会触发
```java
// 需要确保消息ID的唯一性  
CorrelationData cd = new CorrelationData(UUID.randomUUID().toString());  
cd.getFuture().addCallback(new ListenableFutureCallback<CorrelationData.Confirm>() {  
    @Override  
    public void onFailure(Throwable ex) {  
        // 内部处理MQ结果过程中出现异常, 发生直接记录日志  
        log.error("spring amqp 处理确认结果异常", ex);  
    }  
  
    @Override  
    public void onSuccess(CorrelationData.Confirm result) {  
        // 判断是否成功  
        if (result.isAck()) {  
            // MQ成功接收到消息  
            log.debug("收到ConfirmCallback ack, 消息发送成功");  
        } else {  
            // MQ接收消息失败
            log.error("收到ConfirmCallback nack, 消息发送失败. reason: {}", result.getReason());  
        }  
    }  
});
```

# MQ可靠性

- 在默认情况下, RabbitMQ 会将接收到的消息保存在内存中以降低消息收发的延迟, 但是这样会导致一些问题
1. 一旦宕机, 内存中的消息会丢失
2. 内存空间有限, 当消费者故障或处理过慢时, 会导致消息积压, 引起 MQ阻塞
- 通常使用 **数据持久化** 或 **LazyQueue** 进行解决

### 数据持久化

- RabbitMQ的数据持久化包括3个方面
	1. 交换机持久化 (Durable, 默认开启)
	2. 队列持久化 (Durable, 默认开启)
	3. 消息持久化, 默认消息构建器构建的消息都是持久化的
- 非持久化消息写入磁盘的问题在于, 每次向磁盘中写入消息时, MQ 都是阻塞的, 此时向内存中写入消息的速度为 0, 即无法写入消息
- 当消息开启持久化后, 会在写入内存的同时也写入磁盘, 不会出现阻塞内存写磁盘的情况, 从而提高了 MQ 的性能
- 由于默认构建器都是持久化的, 所以想要发送非持久化消息必须自己构建
```java
@Test  
void testSendMessage() {  
    Message message = MessageBuilder.withBody("Hello SpringAMQP".getBytes(StandardCharsets.UTF_8))  
            .setDeliveryMode(MessageDeliveryMode.NON_PERSISTENT)  
            .build();  
    for (int i = 0; i < 1000000; i++) {  
        rabbitTemplate.send(message);  
    }  
}
```

### LazyQueue

**概述**
- 数据持久化的问题在于, 每次向 MQ 传输消息时, 都必须在内存和磁盘中同时写入, 提高了消息处理的耗时, 影响并发能力
- 从 `RabbitMQ 3.6.0` 开始, 引入了 `Lazy Queue` 的概念, 即**惰性队列**, 特征如下
1. 接收到消息后直接存入磁盘, 不再存入内存, 且写磁盘时进行了优化
2. 消费者要消费消息时才会从磁盘中读取并加载的内存
	- 可以**提前缓存**部分消息到内存中, 最多可提前缓存2048条
- 在 `Rabbit MQ 3.12` 版本后, 所有队列都是 `Lazy Queue` 模式, **无法更改**; 无论持久化消息还是非持久化消息, 都会直接保存到磁盘
- 开启持久化和生产者确认时, MQ 只会在消息**持久化完成**后才会给生产者返回 ACK 回执

**Lazy Queue 声明**
- 在低版本, 要设置一个队列为 `Lazy Queue`, 如果在控制台添加, 直接在声明队列时指定其中的 `x-queue-mode` 属性为 `lazy`
- 使用代码添加时, 在 `Queue Builder` 的调用链中添加 `.lazy()`
- 使用注解添加时, 使用注解参数 `arguments=@Argument(name="x-queue-mode", value="lazy")`

# 消费者可靠性

### 消费者确认机制

**概述**
- 消费者确认机制 (`Consumer Acknowledgement`) 是为了确认消费者是否成功处理消息. 当消费者处理消息结束后, 应该向 `RabbitMQ` 返回一个回执, 告知 `RabbitMQ` 自己的消息处理状态
1. ack: 成功处理消息, `RabbitMQ` 从队列中删除该消息
	- 确认处理成功后, 再返回 `ACK`
2. nack: 消息处理失败, `RabbitMQ` 需要再次投递消息
	- 确认处理失败后, 再返回 `NACK`, 表示处理失败
3. reject: 消息处理失败并拒绝该消息, `RabbitMQ` 从队列中删除该消息
	- 当消费者认为当前消息存在问题时, 返回 `REJECT`, 并从队列中删除消息

**实现**
- SpringAMQP 已经实现了消息确认功能, 并允许通过配置文件选择 ACK 处理方式, 具体处理方式有如下三种
1. `none`: 不处理. 消息投递给消费者后立刻 ack, 消息会立即从 MQ 中删除. 非常不安全, 不建议使用
2. `manual`: 手动模式. 需要手动在业务代码中调用相关api, 进行发送 **ACK** 或者 **REJECT**, 存在业务入侵的可能, 但是更灵活
3. `auto`: **自动模式**. SpringAMQP 利用 **AOP** 对消息处理逻辑进行环绕增强, 当业务正常执行时自动返回 ack, 业务出现异常时, 根据异常类型返回不同结果
	- 如果是业务异常, 会自动返回 nack
	- 如果是消息处理或校验异常, 自动返回 reject

**配置**
- 消息确认模式配置如下
- 相关配置应在消费者中进行配置
```yaml
spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 1
        acknowledge-mode: none
```

### 失败重试策略

**概述**
- SpringAMQP提供了消费者失败重试机制, 在消费者出现异常时**利用本地**重试, 而不是无限 requeue 到 mq. 可以在配置中开启重试机制
```yaml
spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 1
        retry:
          enabled: true   # 是否开启失败重试
          initial-interval: 1000ms  # 初始失败等待时间
          multiplier: 1   # 失败等待时长倍率
          max-attempts: 3 # 最大重试次数
          stateless: true # 有无状态, 业务使用事务时应该有状态
```
- 默认重试次数耗尽后丢弃消息, 导致消息队列可靠性降低
- 开启重试模式后, 重试次数耗尽后若消息依然失败, 则需要 `MessageRecover` 接口来处理, 它包含三个不同的实现
1. `RejectAndDontRequeueRecover` : 重试耗尽后, 直接 `reject` 丢弃消息, **默认**
2. `ImmediateRequeueMessageRecover` : 重试耗尽后, 返回 `nack`, 消息重新入队
3. `RepublishMessageRecover` : 重试耗尽后, 将失败消息投递到指定的交换机

**代码实现**
- 将失败处理策略改为 RepublishMessageRecover
- 首先, 定义接收失败消息的交换机, 队列, 及其绑定策略
- 然后, 定义 RepublishMessageRecover, 修改消息处理处理并绑定交换机
- 在对应的错误消息队列中, 不仅会包含原消息信息, 还会包含错误堆栈信息
```java
private final RabbitTemplate rabbitTemplate;
@Bean  
public MessageRecoverer messageRecoverer() {  
    return new RepublishMessageRecoverer(
        rabbitTemplate, 
        "error.direct", 
        "error"
    );  
}
```

### 业务幂等性

**概念**
- 在某些情况下, 可能出现业务成功接收到消息并处理, 但是发送的 ACK 没有成功被消息队列接收到, 导致消息队列将处理过的消息再次发送给消费者
- **幂等**是一个数学概念, 即 $f(x)=f(f(x))$ . 在程序开发中, 业务幂等性指的是同一个业务, 执行一次或多次, 对业务状态的影响是一致的

**唯一消息id** 
- 给每个消息都设置一个唯一id, 利用id区分是否是重复消息
1. 每一条消息都对应一条唯一id, 与消息一起投递给消费者
2. 消费者接收到消息后处理自己的业务, 处理成功后将消息id保存到数据库
3. 下次收到相同消息, 去数据库判断id是否存在, 存在视为重复消息, 放弃处理
- 缺点: 需要做无关业务的判断, 同时存取数据库会影响业务性能
- 发送消息时, 配置消息转化器
```java
@Bean  
public MessageConverter messageConverter() {  
    Jackson2JsonMessageConverter converter = 
        new Jackson2JsonMessageConverter();  
    converter.setCreateMessageIds(true);  
    return converter;  
}
```
- 接收消息时, 接收 Message 格式的消息
```java
@RabbitListener(queues = "simple.queue")  
public void listenSimpleQueue(Message message) {  
    String msg = new String(message.getBody());  
    String messageId = 
        message.getMessageProperties().getMessageId();  
    log.info("监听到simple.queue的消息id: " + messageId);  
    log.info("监听到simple.queue的消息: " + msg);  
}
```

**业务判断**
- 结合业务逻辑, 基于业务本身做判断
- 如: 对订单修改为已支付, 仅在订单本身未支付时进行
```java
public void listenSuccess(Long orderId) {  
    // 1. 查询订单状态  
    Order order = orderService.getById(orderId);  
    // 2. 判断订单状态是否为未支付  
    // 订单状态1: 未支付  
    if(order == null || order.getStatus() != 1) {  
        return;  
    }  
    // 3. 标记订单状态为已支付  
    orderService.markOrderPaySuccess(orderId);  
}
```

# 延迟消息

**概念**
- 延迟消息: 发送者发送消息时指定一个时间, 消费者不会立刻收到消息, 而是在指定时间之后才会收到消息
- 延迟任务: 设置在一定时间之后才执行的任务
- RabbitMQ 默认不支持延迟消息, 所有的延迟方案都是基于 MQ 模拟出来的
- RabbitMQ 的过期消息内部是通过时钟维护的, 需要占用 CPU 进行处理, 如果队列内过期消息过多, 可能对服务器造成较大压力, 所以延时时间不宜过长

### 死信交换机

- 当一个队列中的消息满足下列情况时, 就会成为 **死信** (dead letter)
1. 消费者使用 `reject` 或 `nack` 声明消费失败, 且消息 `requeue` 参数设为 `false`
2. 消息是一个过期消息 (达到了队列或消息设置的过期时间), 超时无人消费
3. 要投递的队列已满, 最早的消息可能会成为死信
- 如果某队列通过 dead-letter-exchange 属性指定了一个交换机, 那么该队列中的死信就会不会被直接丢弃, 而是投递到这个交换机中, 这个交换机就被称为 **死信交换机** `Dead Letter Exchange, DLX`
- 利用消息过期和死信交换机, 就可以模拟实现延迟消息的效果

**代码示例**
- 死信交换机与死信队列
```java
@RabbitListener(bindings = @QueueBinding(  
        value = @Queue(name = "dlx.queue", durable = "true"),  
        exchange = @Exchange(name = "dlx.direct"),  
        key = "hi"  
))  
public void listenDlxQueue(String message) {  
    // 死信交换机  
    log.info("消费者监听到: " + message);  
}
```
- 普通交换机与普通队列定义, 并与死信交换机绑定
- 死信交换机与普通交换机应该与队列绑定相同的 `routing key`
- 因为消息发送到死信交换机时, 所使用的 `routing key` 是一开始传输过来的 `routing key` , 如果不相同, 则死信交换机无法路由到死信队列
```java
@Configuration  
public class NormalConfiguration {  
    @Bean  
    public DirectExchange normalExchange() {  
        return new DirectExchange("normal.direct");  
    }  
    @Bean  
    public Queue normalQueue() {  
        return QueueBuilder.durable("normal.queue")  
                .deadLetterExchange("dlx.direct").build();  
    }  
    @Bean  
    public Binding normalQueueBinding(Queue normalQueue, DirectExchange normalExchange) {  
        return BindingBuilder.bind(normalQueue)  
                .to(normalExchange)  
                .with("hi");  
    }  
}
```

**带过期时间的消息发送**
```java
@Test  
void testSendDelayMessage() {  
    rabbitTemplate.convertAndSend(  
            "normal.direct",  
            "hi",  
            "hello",  
            message -> {  
                message
                    .getMessageProperties()
                    .setExpiration("10000");  
                return message;  
            });  
}
```

### 延迟消息插件

**概述**
- 该插件可以将普通交换机改造成为支持延迟消息功能的交换机, 当消息投递到交换机后可以暂存一段时间, 到期后再投递到队列
- 由于是社区插件, 需要额外下载并安装, 加入 `RabbitMQ` 的 `mq-plugins` 目录
- 使用 `docker volume inspect mq-plugins` 查看该目录对应的数据卷
- 加入目录后执行命令: `docker exec -it mq rabbitmq-plugins enable rabbitmq_delayed_message_exchange` 安装插件
- 安装完毕后, 需要重启 RabbitMQ

**代码示例**
- 创建交换机时, 通过设置交换机 `delayed` 属性指定为延迟交换机
```java
@RabbitListener(bindings = @QueueBinding(  
        value = @Queue(name = "delay.queue", durable = "true"),  
        exchange = @Exchange(name = "delay.direct", 
                             delayed = "true"),  
        key = "hi"  
))  
public void listenDelayQueue(String message) {  
    // 死信交换机  
    log.info("消费者监听到: " + message);  
}
```
- 发消息时, 通过消息头 `x-delay` 设置过期时间
```java
@Test  
void testSendDelayMessageByPlugin() {  
    rabbitTemplate.convertAndSend(  
            "delay.direct",  
            "hi",  
            "hello",  
            message -> {  
                message.getMessageProperties().setDelay(10000);  
                return message;  
            });  
}
```


# 业务改造

**发送延迟消息**
```java
@Override  
@GlobalTransactional  
public Long createOrder(OrderFormDTO orderFormDTO) {  
    ...
    // 5. 发送延迟消息, 检测订单支付状态  
    rabbitTemplate.convertAndSend(  
            MqConstants.DELAY_EXCHANGE_NAME,  
            MqConstants.DELAY_ORDER_KEY,  
            order.getId(),  
            message -> {  
                message.getMessageProperties()  
                        .setDelay(10000);  
                return message;  
            }  
    );  
    return order.getId();  
}
```
**接收延时消息**
```java
@Component  
@RequiredArgsConstructor  
public class OrderDelayMessageListener {  
    private final IOrderService orderService;  
    private final PayClient payClient;  
    @RabbitListener(bindings = @QueueBinding(  
            value = @Queue(value = MqConstants.DELAY_ORDER_QUEUE_NAME),  
            exchange = @Exchange(name = MqConstants.DELAY_EXCHANGE_NAME),  
            key = MqConstants.DELAY_ORDER_KEY  
    ))  
    public void listenOrderDelayMessage(Long orderId) {  
        // 1. 查询本地数据库订单  
        Order order = orderService.getById(orderId);  
        // 2. 检查支付状态  
        if(order == null || order.getStatus() != 1) {  
            // 2.1 订单不存在或已支付, 直接返回  
            return;  
        }  
        // 3. 查询支付流水, 使用 OpenFeign        
        PayOrderDTO payOrder = 
            payClient.queryPayOrderByBizOrderNo(orderId);  
        // 4. 判断是否支付  
        if(payOrder != null && payOrder.getStatus() == 3) {  
            // 4.1 已支付, 则更新订单状态为已支付  
            orderService.markOrderPaySuccess(orderId);  
        } else {  
            // 4.2 未支付, 取消订单, 恢复库存  
            orderService.cancelOrder(orderId);  
        }  
    }  
}
```
