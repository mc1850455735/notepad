
# 基础

- 使用如下命令在Docker中创建网络
```shell
docker network create hm-net
```
- 使用如下命令在Docker中安装MySQL
```shell
docker run -d \
--name mysql \
-p 3306:3306 \
-e TZ=Asia/Shanghai \

```

### 架构

**单体架构**
- 将业务的所有功能集中在一个一个项目中开发, 打包成一个包部署
- 优点:
	- 架构简单
	- 部署成本低
- 缺点:
	- 团队协作成本高
	- 系统发布效率低
	- 系统可用性差
- 总结: 适合开发功能相对简单, 规模较小的项目

**微服务架构**
- 微服务架构是服务化思想指导下的一套最佳实践架构方案. 服务化, 就是把单体架构中的功能模块拆分成为多个独立项目, 拆分时, 粒度小, 团队要自治, 服务要自治
- 微服务框架: SpringCloud
- SpringCloud是目前国内使用最广泛的微服务框架, 其集成了各种微服务功能组件, 并基于SpringBoot实现了这些组件的自动装配, 从而提供了良好的开箱即用体验
- SpringCloud对SpringBoot的版本有要求, SpringBoot对Spring版本有要求, Spring对Java版本有要求, 必须做到版本的匹配
- 服务注册发现: Eureka, Nacos, Consul
- 统一配置管理: SpringCloudConfig, Nacos
- 远程服务调用: OpenFeign, Dubbo
- 统一网关路由: SpringCloudGateway, Zuul
- 服务链路监控: Zipkin, Sleuth
- 流控, 降级, 保护: Hystix, Sentinel

# 微服务拆分

### 概述

**拆分时机**
- 创业型项目: 先采用单体架构, 快速开发, 快速试错. 随着规模扩大, 逐渐拆分
- 确定的大型项目: 资金充足, 目标明确, 可以直接选择微服务架构, 避免后续拆分的麻烦

**拆分目标**
- 高内聚: 每个微服务的职责要尽可能单一, 包含的业务互相关联度高, 完整度高
- 低耦合: 每个微服务的功能要相对独立, 尽量减少对其他微服务的依赖

**拆分方式**
- 纵向拆分: 按照业务模块进行拆分
- 横向拆分: 抽取公共服务, 提高复用性

**工程结构**
- 独立Project: 对于每个微服务, 都创建一个独立的Project, 相互之间没有任何关联, 通常使用一个目录包含所有的微服务Project. 相互耦合程度低, 但是由于过于独立, 可能造成管理困难等问题, 适用于巨型项目
- Maven聚合: 整个项目作为一个单独的Project, 每一个微服务模块都作为该项目的Module模块进行管理, 所有的模块受双亲项目的管理, 适用于中小型项目

### 实践

**配置**
- 每个微服务都需要在yaml文件中声明自己的服务名称
- 对于每一个不同的微服务, 都需要有一台完整的MySQL服务器用以增删改查(项目经费有限, 使用一台MySQL的多个数据库替代)
- 在knife4j(API文档工具)中, 同样也需要修改对应的描述(`title`, `description`), 同时对应接口文档扫描位置也需要进行更改
	- 通过`url/doc.html`就可以访问自动生成的接口文档
- 进行拆分时, 要注意源代码中的包位置, 文件路径等信息, 并及时进行修改

**依赖**
- SpringCloud依赖管理
- 管理了SpringCloud以及SpringCloudAlibaba所用的各种依赖的版本
```xml
<!--spring cloud-->  
<dependency>  
    <groupId>org.springframework.cloud</groupId>  
    <artifactId>spring-cloud-dependencies</artifactId>  
    <version>${spring-cloud.version}</version>  
    <type>pom</type>  
    <scope>import</scope>  
</dependency>  
<!--spring cloud alibaba-->  
<dependency>  
    <groupId>com.alibaba.cloud</groupId>  
    <artifactId>spring-cloud-alibaba-dependencies</artifactId>  
    <version>${spring-cloud-alibaba.version}</version>  
    <type>pom</type>  
    <scope>import</scope>  
</dependency>
```

### 远程调用
- 虽然各个模块之间的物理连接消失了, 但是各个模块之间依然存在网络连接, 对于依赖某模块的功能, 可以通过网络进行调用
- Spring提供了`RestTemplate`工具, 可以方便的实现Http请求的发送
- 注入RestTemplate到Spring容器
```java
@Bean  
public RestTemplate restTemplate() {  
    return new RestTemplate();  
}
```
- 发起远程调用
```java
public <T> ResponseEntity<T> exchange(
    String url,  // 请求路径
    HttpMethod method,  // 请求方式
    @Nullable HttpEntity<?> requestEntity, // 请求实体
    Class<T> responseType,  // 返回值类型
    Map<String, ?> uriVariables  // 请求参数
)
```

**示例**
- 对于参数注入, 虽然 `@Autowired` 可以进行按类型自动注入, 但是是不推荐的做法, 推荐的做法是使用构造函数进行注入, Spring同样可以进行管理
- 但是当参数过多时, 构造函数的书写和维护就会遇到相当的挑战, 此时可以考虑使用lombok注解进行构造函数的自动生成
- 然而, 如果直接使用`@AllArgsConstructor`, 会导致对于某些不希望进行构造函数初始化的变量也加入构造函数参数中
- 所以可以将希望被注入的变量前加`final`修饰符进行修饰, 表示使用前必须被初始化且不可被修改, 然后使用 `@RequiredArgsConstructor` 注解进行构造函数生成, 对于不希望加入构造函数的final变量, 手动赋初值即可
```java
@Service  
@RequiredArgsConstructor  
public class CartServiceImpl extends ServiceImpl<CartMapper, Cart> implements ICartService {  
    private final RestTemplate restTemplate;
}
```
- 利用RestTemplate发起Http请求, 得到Http响应并进行解析
```java
// 2.查询商品  
ResponseEntity<List<ItemDTO>> response = restTemplate.exchange(  
    "http://localhost:8081/items?ids={ids}",  
    HttpMethod.GET,  
    null,    
    new ParameterizedTypeReference<List<ItemDTO>>() {},  
    Map.of("ids", StrUtil.join(",", itemIds))
);  
if(!response.getStatusCode().is2xxSuccessful()) {  
    return;  
}  
List<ItemDTO> items = response.getBody();
```


### 扩展

**DTO, PO, VO的区别**
- `PO` ( `Presistent Object` ): 持久化对象
	- 来源: 数据库中的表记录, 与数据库高度对应
	- 特点: 
		- 一般是ORM框架映射的实体类
		- 字段与数据库几乎一一对应
		- 可能包含数据库相关的注解(如`@TableName`)
	- 作用: 数据持久化, 用以与数据库进行交互
- `DTO` ( `Data Transfer Object` ): 数据传输对象
	- 来源: 用来封装服务之间, 层与层之间的数据传输
	- 特点: 
		- 与数据库不对应, 可能是多个表的组合, 也可能是PO的子集
		- 一般用于表现层到服务层的数据传输, 或者远程调用RPC/REST
		- 常用于参数校验, 减少无关字段的传递
	- 作用: 
		- 用于在网络/接口上传输数据, 解耦持久层和表现层
		- 可以理解为前端传输给后端的数据格式
- `VO` ( `View Object` / `Value Object` ): 视图对象
	- 来源: 接口返回给客户端或前端的数据封装
	- 特点:
		- 面向前端或接口调用者
		- 可以是PO/DTO的裁剪与混合
		- 可能会隐藏敏感信息(如密码)
	- 作用: 展示层使用, 用以给前端传输数据


# 服务治理

**问题**
- 使用RestTemplate根据url访问微服务模块, 在对应模块存在多实例部署的情况时, 只能访问一个固定的实例, 无法做到负载均衡, 且无法做到在对应实例宕机时转移访问的实例
- 即, 无法感知到服务状态的变更, 这个问题就叫做服务治理问题
- 服务治理中存在三个角色
	- 注册中心
	- 服务提供者: 暴露服务接口, 供其他服务调用
	- 服务消费者/服务调用者: 调用其他服务提供的接口
	- 注册中心: 记录并监控微服务各个实例状态, 推送服务变更信息

### 注册中心原理

- 服务提供者启动后, 首先向注册中心提供自己的服务信息
- 服务消费者需要使用服务时, 对应项目向注册中心中订阅服务提供者的信息
- 服务提供者可能存在多个实例, 则服务提供者进行**负载均衡**的调用
- 服务消费者选定一个实例, 向服务提供者发送请求进行远程调用
- 服务提供者注册完成服务信息后, 需要与注册中心之间形成心跳, 每隔一段时间, 向注册中心发送一条请求报告自己的状态信息
- 若服务提供者中某个实例宕机, 由于心跳机制, 注册中心将该实例信息删除, 一旦注册表中信息发生变更, 无论删除还是新增, 注册中心都会将该变更推送给该服务的服务调用者

### Nacos注册中心
- Nacos是目前国内企业中占比最多的注册中心组件. 它是**阿里巴巴**的产品, 目前已经加入SpringCloudAlibaba中
- 官方文档: https://nacos.io/docs/latest/quickstart/quick-start/

**安装与配置**
- Nacos本身需要数据源进行支持, 在这里使用MySQL
- 完成配置文件后, 使用Docker进行部署
```shell
docker run -d \
--name nacos \
--env-file ./nacos/custom.env \
-p 8848:8848 \
-p 9848:9848 \
-p 9849:9849 \
--restart=always \
nacos/nacos-server:v2.1.0-slim
```

**访问与管理**
- 使用 http://192.168.199.200:8848/nacos 访问nacos管理系统
- 默认用户名: nacos
- 默认密码: nacos

### 服务注册

**步骤**
- 引入`nacos discovery`依赖(服务注册&发现)
```xml
<!-- nacos相关依赖 -->  
<dependency>  
    <groupId>com.alibaba.cloud</groupId>  
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>  
</dependency>
```
- 配置Nacos地址
```yaml
spring:  
  application:  
    name: item-service # 微服务名称  
  cloud:  
    nacos:  
      server-addr: 192.168.199.200:8848
```

### 服务发现

**步骤**
- 引入nacos dependency依赖 (略)
- 配置nacos地址 (略)
- 服务发现
- SpringCloud定义了一套统一的接口, 对于服务消费者, 使用 `DiscoveryClient` 接口从注册中心拉取和订阅服务
- 根据服务名称获取实例
```java
private final DiscoveryClient discoveryClient;
private void handleCartItems(List<CartVO> vos) {  
    ... 
    // 从nacos中获取实例  
    List<ServiceInstance> instances = 
        discoveryClient.getInstances("item-service");  
    if(CollUtils.isEmpty(instances)) {  
        return;  
    }  
    // 手写负载均衡, 从实例列表中挑选一个实例  
    ServiceInstance instance = 
        instances.get(RandomUtil.randomInt(instances.size()));  
    // 解析实例, 获取相关信息  
    URI uri = instance.getUri();  
    // 发起网络请求  
    ResponseEntity<List<ItemDTO>> response = restTemplate.exchange(  
        uri + "/items?ids={ids}",  
        ...
    );  
    ...
}
```

# OpenFeign

### 快速入门

**概述**
- OpenFeign是一个声明式的http客户端, 是SpringCloud在Eureka公司开源的Feign基础上改造而来.
- 官方地址: https://github.com/OpenFeign/feign
- 其作用就是基于SpringMVC的常见注解, 实现http请求的快捷发送

**快速入门**
- OpenFeign已被SpringCloud自动装配, 实现起来非常简单
- 引入依赖, 包括 `OpenFeign` 和负载均衡组件 `SpringCloudLoadBalancer`
- 早期使用 `Ribbon` 实现负载均衡, 目前大都使用 `LoadBalancer`
```xml
<!-- openFeign -->  
<dependency>  
    <groupId>org.springframework.cloud</groupId>  
    <artifactId>spring-cloud-starter-openfeign</artifactId>  
</dependency>  
<!-- 负载均衡器 -->  
<dependency>  
    <groupId>org.springframework.cloud</groupId>  
    <artifactId>spring-cloud-starter-loadbalancer</artifactId>  
</dependency>
```
- 通过 `@EnableFeignClients` 注解, 启动OpenFeign功能
```java
@MapperScan("com.hmall.cart.mapper")  
@SpringBootApplication  
@EnableFeignClients  
public class CartApplication {  ...  }
```
- 编写 `FeignClient` 接口
```java
@FeignClient("item-service")  
public interface ItemClient {  
    @GetMapping("/items")  
    List<ItemDTO> queryItemByIds(@RequestParam("ids") Collection<Long> ids);  
}
```
- 使用 `FeignClient` , 实现远程调用
```java
private final ItemClient itemClient;
private void handleCartItems(List<CartVO> vos) {  
    Set<Long> itemIds = 
        vos.stream()
           .map(CartVO::getItemId)
           .collect(Collectors.toSet());
    List<ItemDTO> items = itemClient.queryItemByIds(itemIds);
    ...
}
```

### 连接池

- 由OpenFeign底层代码可知, 与微服务建立连接使用的是`HttpURLConnection`, 这个工具类每次访问都必须重新建立连接, 效率较低
- OpenFeign对Http请求进行了伪装, 不过其底层发起的http请求依赖于其他的框架, 这些框架可以自行选择, 包括以下三种
	- HttpURLConnection: 默认实现, 不支持连接池
	- Apache HttpClient: 支持连接池
	- OKHttp: 支持连接池
- 具体源码参照FeignBlockingLoadBalancerClient类中的delegate成员变量

**整合OKHttp步骤**
- 引入依赖
```xml
<!-- okhttp依赖 -->  
<dependency>  
    <groupId>io.github.openfeign</groupId>  
    <artifactId>feign-okhttp</artifactId>  
</dependency>
```
- 开启连接池功能
```java
feign:  
  okhttp:  
    enabled: true
```

### 最佳实践

**两种实践**
- 在原有微服务的基础上, 再对模块进行拆分, 将经常被使用到的功能独立成为单独的模块, 由相应项目组的人员进行维护. 优点是项目耦合度低, 代码结构更加合理; 缺点是项目结构更加复杂
- 单独创建一个新的通用模块, 不属于任何一个微服务, 在其中创建client, config, dto包, 将所有重合的功能放入该通用模块中. 优点是在工作量较低的基础上同样实现了重复功能的拆分, 且项目结构更加简单; 缺点是项目耦合度增加了

**建议与注意事项**
- 本身就是多项目结构的, 使用微服务模块拆分; 本身就是单项目结构的, 使用独立通用模块进行拆分
- 项目拆分后, 原有的注入可能不再生效, 这是因为SpringBoot的扫描是基于当前模块的所有包的, 所以必须手动指定对应bean的位置
- 有两种方式解决
	- 指定FeignClient所在的包
	- `@EnableFeignClients(basePackages = "com.hmall.api.client")`
	- 指定FeignClient的字节码
	- `@EnableFeignClients(clients = {ItemClient.class})`

### 日志

- OpenFeign只会在FeignClient所在的包的日志级别为DEBUG时, 才会输出日志, 而其日志级别有4级:
	- NONE: 不记录任何日志信息, 此为**默认值**
	- BASIC: 仅记录请求的方法, URL以及响应状态码和执行时间
	- HEADERS: 在BASIC的基础上, 额外记录了请求和响应的头信息
	- FULL: 记录所有请求和响应的明细, 包括头信息, 请求体, 元数据
- 要自定义日志级别需要声明一个类型为 `Logger.Level` 的Bean, 在其中定义日志级别
```java
public class DefaultFeignConfig {  
    @Bean  
    public Logger.Level feignLoggerLevel() {  
        return Logger.Level.BASIC;  
    }
}
```
- 此时配置未生效, 可以通过在`@FeignClient`注解中声明来配置日志级别
```java
@FeignClient(configuration = DefaultFeignConfig.class)
```
- 如果想要全局配置, 则需要在`@EnableFeignClients`注解中声明
```java
@EnableFeignClients(defaultConfiguration = DefaultFeignConfig.class)
```
