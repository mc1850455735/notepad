
# 雪崩问题

**概念**
- 微服务调用链路中的某个服务故障, 引起整个链路中所有微服务都不可用, 这就是微服务的雪崩, 服务雪崩问题有以下可能原因
	- 微服务相互调用, 服务提供者出现故障或阻塞
	- 服务调用者没有做好异常处理, 导致自身同样出现了故障
	- 调用链中的所有服务级联失效, 导致整个微服务集群出现故障
- 为避免雪崩问题的出现, 有以下思路
	- 尽量避免服务出现故障或阻塞
	- 服务调用者做好远程调用异常的后备方案, 避免异常扩散

**服务保护方案**
- **请求限流**: 使用限流器, 限制访问微服务请求的并发量, 避免服务因流量激增出现故障, 这种方式又被称为**流量整形**
- **线程隔离**: 也叫做**舱壁模式**, 模拟船舱隔板的防水原理, 通过限定每个业务能使用的线程数量而将故障业务隔离, 避免故障扩散
- **服务熔断**: 由断路器统计请求的异常比例或慢调用比例, 如果超出阈值, 则会熔断该业务, 拦截该接口的请求; 熔断期间, 所有请求快速失败, 全部进行fallback逻辑, 返回默认数据或者友好提示

# Sentinel

### 概述

**概念**
- Sentinel是阿里巴巴开源的一款微服务流量控制组件
- 官网地址: https://sentinelguard.io/zh-cn/index.html
- **簇点链路**: 就是单机调用链路, 是一次请求进入服务后经过的每一个被Sentinel监控的资源链. 默认Sentinel会监控SpringMVC中的每一个Endpoint (http接口). 限流, 熔断等操作都是针对簇点链路中的资源设置的, 而资源名默认就是接口的请求路径
- RESTful风格的API请求路径一般相同, 这会导致簇点资源名称重复. 因此, 需要在配置中设置簇点资源名称为 **请求方式+请求路径**
```yaml
spring:  
  cloud:  
    sentinel:  
      # 是否设置请求方式作为资源名称
      http-method-specify: true
```


**启动命令**
- 默认账号密码都是: `sentinel`
```shell
java -Dserver.port=8090 -Dcsp.sentinel.dashboard.server=localhost:8090 -Dproject.name=sentinel-dashboard -jar sentinel-dashboard.jar
```

**整合微服务**
- 引入依赖
```xml
<!-- 引入sentinel依赖 -->  
<dependency>  
    <groupId>com.alibaba.cloud</groupId>  
    <artifactId>spring-cloud-starter-alibaba-sentinel</artifactId>  
</dependency>
```
- 在yaml文件中配置, 连接到控制台
```yaml
spring:  
  cloud:  
    sentinel:  
      transport:  
        dashboard: localhost:8090
```

### 请求限流

- 对于Sentinel, 可以直接在控制台中进行各种配置, 无需编码
**步骤**
- 在簇点链路后面点击流控按钮, 即可对其做限流配置
- 选择阈值类型为QPS, 即可设置限流的类型为控制请求流量大小

### 线程隔离

**步骤**
- 在簇点链路后面点击流控按钮, 即可对其做线程隔离
- 选择阈值类型为并发线程数, 即可限制单一接口的最大线程数量

### Fallback

**步骤**
- 通过配置将FeighClient作为Sentinel的簇点资源
- 通过这种方式, 不再将整个业务作为限流目标, 而是只把feigh远程调用作为簇点资源进行管理
```yaml
feign:  
  sentinel:  
    enabled: true
```
- FeighClient的Fallback有两种配置方式
	- 方式1: FallbackClass, 无法被远程调用的异常做处理
	- 方式2: FallbackFactory, 可以对远程调用的异常做处理, 通常选用这种
- 自定义类, 实现FallbackFactory, 编写对某个FeignClient的fallback逻辑
```java
@Slf4j  
public class ItemClientFallbackFactory implements FallbackFactory<ItemClient> {  
    @Override  
    public ItemClient create(Throwable cause) {  
        return new ItemClient() {  
            @Override  
            public List<ItemDTO> queryItemByIds(Collection<Long> ids) {  
                log.error("查询商品失败: ", cause);  
                return CollUtils.emptyList();  
            }  
  
            @Override  
            public void deductStock(List<OrderDetailDTO> items) {  
                log.error("修改商品数据失败: ", cause);  
                throw new RuntimeException(cause);  
            }  
        };  
    }  
}
```
- 将自定义的UserClientFallbackFactory注册为一个bean
```java
@Bean  
public ItemClientFallbackFactory itemClientFallbackFactory() {  
    return new ItemClientFallbackFactory();  
}
```
- 在UserClient接口中使用UserClientFallbackFactory
```java
@FeignClient(value = "item-service", fallbackFactory = ItemClientFallbackFactory.class)  
public interface ItemClient {...}
```

### 服务熔断

**概念**
- 熔断是解决雪崩问题的重要手段
- 由**断路器**统计服务调用的异常比例或慢调用比例, 如果超出阈值, 则会**熔断**该业务, 拦截该接口的请求, 熔断期间所有请求快速失败, 全部进行fallback逻辑
- 当服务恢复后, 断路器会放行访问该服务的请求
![[后端/SpringCloud/Inbox/Pasted image 20251001154724.png]]

**配置**
- 点击控制台中簇点资源后的熔断按钮, 即可配置熔断策略
- 熔断策略分为: 慢调用比例, 异常比例, 异常数 三种策略
- 熔断时长: 控制当熔断时间达到多少以后, 尝试关闭断路器
- 最小请求数&统计时长: 控制当统计时长内, 达到最小请求数及以上时, 计算其中超过最大RT的请求数量

# 分布式事务

**概念**
- 在分布式系统中, 如果一个业务需要多个服务合作完成, 而且每个服务都有事务, 多个事务必须同时成功或者失败, 这样的事务就是**分布式事务**
- 其中的每个服务的事务就是一个**分支事务**, 整个业务称为**全局事务**

### Seata
- Seata是蚂蚁金服和阿里巴巴共同开源的分布式事务解决方案, 致力于提供高性能和简单易用的分布式事务服务, 为用户打造一站式分布式解决方案
- 官网地址: http://seata.io/

**分布式事务解决思路**
- 解决分布式事务, 就要求各个子事务之间必须能够感知到彼此之间的事务状态, 才能保证状态一致性
- 添加一个事务协调者, 使各个子事务可以借由事务协调者感受到彼此的状态

**架构**
- TC (Transaction Coordinator): 事务协调者, 负责维护**全局和分支事务**的状态, 协调全局事务提交或回滚
- TM (Transaction Manager): 事务管理器, 定义**全局事务**的范围, 开始全局事务, 提交或回滚全局事务
- RM (Resource Manager): 资源管理器, 管理分支事务, 与TC交谈以注册分支事务和报告分支事务的状态

### 部署TC服务

- 由于TC运行过程中需要保存各个事务信息等, 所以需要空间保存相应信息, 在此使用MySQL数据库存储Seata相关信息
- 将相关配置文件添加到虚拟机 `/root` 目录下, seata容器将直接使用docker网络与nacos进行通信, 直接通过容器名即可访问
- 同理, MySQL也直接使用Docker容器网络进行通信
- 在/root目录下使用Docker中部署相关服务, 使用 `docker update --restart=always seata` 设置开机自启
```shell
docker run --name seata \
-p 8099:8099 \
-p 7099:7099 \
-e SEATA_IP=192.168.199.200 \
-v ./seata:/seata-server/resources \
--privileged=true \
--network hm-net \
-d \
seataio/seata-server:1.5.2
```
- 使用 `url:7099` 访问对应控制台
- 用户名: admin, 密码: admin

### 微服务集成Seata

- 引入Seata依赖
```xml
<!-- nacos配置依赖 -->
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
</dependency>
<!-- 读取bootstrap文件 -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-bootstrap</artifactId>
</dependency>
<!-- seata依赖 -->
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-seata</artifactId>
</dependency>
```
- 配置TC服务地址, 使用注册中心类型nacos
- 先找命名空间, 再找分组, 在分组中找服务, 最后确定使用哪个集群
- 对于同一个全局事务涉及的微服务, 通常希望他们使用同一个集群中的微服务, 减少延迟等, 所以需要配置事务组名称及其与tc集群的映射关系
- 由于配置较复杂, 通常将其抽取为共享配置在配置中心
```yaml
seata:
  registry: 
    type: nacos
    nacos:
      server-addr: 192.168.199.200:8848
      namespace: ""
      group: DEFAULT_GROUP
      application: seata-server
      username: nacos
      password: nacos
  tx-service-group: hmall
  service:
    vgroup-mapping:
      hmall: "default"
```

### XA模式
- XA规范是X/Open组织定义的分布式事务处理(DTP, Distributed Transaction Processing)标准, XA规范描述了全局的TM与局部的RM之间的接口. 
- 几乎所有的主流关系型数据库都对XA规范提供了支持

**步骤**
- 这种分布式事务实现方法又被称为二阶段分布式事务
- 一阶段工作
	- RM注册分支到TC
	- RM执行分支业务sql但不提交
	- RM报告执行状态到TC
- 二阶段工作
	- TC检测各分支事务指定状态
	- 如果都成功, 通知所有RM提交事务
	- 如果有失败, 通知所有RM回滚事务
	- RM接收到指令, 提交或回滚事务
- 优点: 实现了事务的ACID, 通过等待确保了事务的强一致性
- 缺点: 通过等待的方式确保一致性存在性能损失
![[后端/SpringCloud/Inbox/Pasted image 20251002144609.png]]

**实现**
- 修改yaml文件, 开启XA模式
```yaml
seata:
  data-source-proxy-mode: XA
```
- 给发起全局事务的入口方法添加`@GlobalTransactional`注解
```java
@Override
@GlobalTransactional
public Long createOrder(OrderFormDTO orderFormDTO) { ... }
```

### AT模式
- Seata主推AT模式, 其同样是一个分阶段提交的事务模型, 但是弥补了XA模型中资源锁定周期过长的缺点
- AT模式中, 各个分支事务执行完成后立即提交, 但是在业务提交前需要生成一个**undo log**记录更新前后快照, 由于立即提交, 不会因等待导致性能损失
- 全局事务结束后, 检查各个分支事务, 如果全部成功, 则直接删除undo log即可; 如果存在事务失败, 则根据log恢复数据到更新前
- 缺点: 若全局事务最终失败, 则在分支事务提交后, log数据恢复前, 存在数据不一致的风险窗口
![[后端/SpringCloud/Inbox/Pasted image 20251002152121.png]]

**实现**
- 将 `seata-at.sql` 添加到需要使用AT模式Seata的微服务对应的数据库中
- 修改application.yml文件, 将事务模式修改为AT模式
- Seata的默认事务模式即为AT, 实际上无需设置事务模式

**区别**
- XA一阶段不提交事务, 锁定资源; AT一阶段提交事务, 不锁定资源
- XA依赖数据库机制实现回滚; AT使用数据快照实现数据回滚
- XA模式强一致; AT模式最终一致
