# 概述

Kafka 是一个分布式的、基于发布/订阅模式的消息队列。

Kafka 在消息保存时根据消息的 Topic 进行分类，其中消息发送者称为 Producer，消息接收者称为 Consumer。Kafka 集群由多个 Kafka 实例组，每个实例称为 broker。消息队列保存在一个个 Topic 主题中。

无论是 Kafka 集群，还是 Consumer，都依赖于 Zookeeper 集群保存 Meta 信息，以保证系统的可用性。

## 应用场景

**异步处理请求**

通过消息队列将处理过程异步化，从而提升系统的吞吐能力和稳定性。
具体而言，业务系统在接收到请求后，只需将需要处理的任务封装成消息并投递到消息队列中，即可立即返回响应。
后续的业务处理由一个或多个消费者服务异步完成。

**将项目中各个组件进行解耦**

通过使用消息队列，可以让调用方直接将任务信息存入消息队列当中完成持久化，随后直接返回用户任务完成；在服务方中，通过推拉模式，获取消息队列中的任务。
由此实现调用方和服务方之间的解耦操作。

## Cluster
在 Kafka 架构中，由 Zookeeper 总管整个 Kafka Cluster，在 Kafka Cluster 中：
- Kafka 集群由多个 Broker 组成，一个 Broker 可以被视为一个独立的 Kafka 服务器；
- 一个 Kafka Broker 中可以存在多个 Kafka Topic，Topic 可以被理解为消息队列的主题，类似于 MySQL 中的表，一个 Topic 可以被拆分为多个 Partition；
- Partition 作为 Kafka 的核心，负责实现消息队列的功能。通过 Topic 的拆分，可以提高 Kafka 的并发处理能力；
- 同一个 Partition 在不同的 Topic 中拥有不同的角色。其中会存在一个 Leader Partition 和多个 Follower Partition；Leader Partition 负责消息的接收和消费，Follower Partition 只负责消息的备份。

## Producer
对于 Producer，发送消息时通过 topic + value + key 进行指定。Topic 由 Producer 手动指定，而具体接收消息的 Partition 也可以由 Producer 显式指定，或者根据 Key 经过 Partitioner 计算得到。Producer 会通过 Kafka 集群 Metadata 找到该 Partition 的 Leader Broker，然后将消息发送给 Leader。

## Consumer
Consumer 负责消费消息，多个 Consumer 可以组织成为 Consumer Group，Consumer Group 负责多个 Consumer 的协同消费，一个 Partition 在同一个 CG 内只能被一个 Consumer 消费。

不同 Consumer Group 可以独立消费同一个 Topic，因为 Kafka 中使用 offset 定位消息位置，且不同的 CG 独立保存自己的 Offset，消费消息时只会修改 offset 中的值，而不会实习删除队列中的元素。

当 CG 中的 Consumer 数量发生变化时，就会触发 Consumer Rebalance。

# Offset

## Offset 基础概念

Offset 表示消息在一个 Partition 中的**位置编号**。Kafka 中的 Topic 由多个 Partition 组成，每个 Partition 内部的消息都有自己的 Offset 编号。Offset 是 Partition 内唯一的，但不是 Topic 内唯一的。

Consumer 消费时，通过 Offset 获取自己消费位置的信息。Kafka 内的 Offset 与 Consumer Group 是关联的；具体来说，Offset 绑定 Consumer Group + Topic + Partition。所以说，不同的 CG 可以消费同一个 Partition，因为要使用的 Offset 不同。

Consumer 中通过 Position 确定要读取的 offset 的位置。

## Offset 的提交

Offset 的提交分为**手动提交和自动提交**。通常情况下，Consumer 通过 poll() 将消息拉下后自动提交 Offset，随后进行处理；但是如果处理失败，由于 Offset 已经提交，导致消息丢失，虽然失败也没有办法再进行重试。

因此，可以采用手动提交 offset 的方式，也就是用户手动确认是否提交本地的 Offset。当 Consumer 使用 poll() 拉下消息后，先进行处理而不提交 Consumer，确认业务成功后，再提交 Offset。

通过手动提交的方式可以做到消息的不漏，但是 Kafka 中很难做到消息的不重。也就是说，Kafka 很难做到 exactly once 的消费。对于以下情况：消费成功 -> offset 提交失败 -> 重新消费，从而导致业务被执行两次。

因此，需要通过[[幂等处理]]的方式解决这个问题。

## Offset 存储

Kafka 中 Offset 的位置存储在特殊的 `__consumer_offsets` Topic 中。

# Kafka术语

1. Producer：消息生产者，负责向 Kafka Broker 中发送消息的客户端。
2. Consumer：消息消费者，负责从 Kafka Broker 中取消息的客户端。
3. Topic：可以理解为一个队列，Producer 和 Consumer 都面向队列进行处理。
4. Broker：一台 Kafka 服务器就是一个 Broker，一个 Kafka Cluster 由多台 Kafka Broker 组成，一个 Broker 内可以容纳多个 Topic。
5. Partition：分区，为实现扩展性，一个非常大的 Topic 可以分布到多个 Broker 服务器中，每个 Topic 可以分为多个 Partition，每个 Partition 都是一个有序的队列。Partition 中的每条消息都会被分配一个有序的 id，Kafka 只保证 Partition 内的消息顺序将消息发送给 Consumer，而不保证 Topic 整体的顺序。
6. Consumer Group (CG)：消费者组，是 Kafka 中用来实现一个 Topic 内消息的广播和单播的手段。对于一个 Topic，可以有多个 CG，Topic 中的消息会复制到其中所有的 CG 当中，但对于 CG 中的 Partition，Partition 只会将消息发送给 Parition 内某个 Consumer。如果需要实现单播，只需要将所有 Consumer 加入同一个 CG；如果需要实现广播，则可以将每一个 Consumer 都单独分配一个 CG。使用 CG 还可以灵活的将 Consumer 按照功能进行分组，避免多次发送消息到不同的 Topic 中。
7. Offset：Kafka 的存储文件都以 offset.kafka 的格式命名，这样做的优势是方便查找。
8. Replication：副本。为保证集群中某个节点发生故障时，节点上的 Partition 数据不丢失且 Kafka 仍可以继续工作，Kafka 提供了副本机制，一个 Topic 的每个 Partition 分区都有若干个副本，分为一个 Leader 和若干个 Follower。Kafka 保证同一个 Partition 的不同 Replication 一定不会被分配给同一个 Broker，否则备份就不存在意义。
9. Leader：每个分区中有多个副本，Leader 为副本中的主副本。生产者发送数据的对象以及消费者消费数据的对象都是 Leader。Follower 仅作为备份使用。
10. Follower：每个分区中有多个副本，Follower 为副本中的从副本。Follower 会实时从 Leader 中同步数据，保持和 Leader 数据的同步。当 Leader 出现故障时，某个 Follower 会称为新的 Leader。Follower 只能用于同步数据，消费者不能通过 Follower 进行消费。

# Zookeeper

### Broker注册

Kafka 的 Broker 的分布式部署且相互之间独立的，但是需要有一个注册系统管理整个集群中的 Broker，此时就需要 Zookeeper。Zookeeper 上会有一个专门用于记录 Broker 服务器列表记录的节点。记录位置位于 `/brokers/ids`。

Kafka 依赖全局唯一的数字指代每一个 Broker，不同的 Broker 必须使用不同的数字进行表示。每个 Broker 在启动时都会在 Zookeeper 中的 `/brokers/ids` 位置创建自己的节点，节点中存储 Broker 自身的 IP 地址和端口信息。Broker 创建的节点类型是临时节点，Broker 下线后该临时节点也会被自动删除。

Kafka 集群中的一个 Broker 会被选举成为 Controller，负责集群中 Broker 的上下线、所有 Topic 的分区副本分配和 Leader 选举等工作。Controller 的管理工作依赖于 Zookeeper。

### Topic 注册

在 Kafka 中，同一个 Topic 的消息会被分成多个分区并将其分布在多个 Broker 上，这些分区信息以及与 Broker 的对应关系也存储在 Zookeeper 中，由专门的节点记录，如 `/brokers/topics`。

Kafka 中的每一个 Topic 都会以 `/brokers/topics/[name]` 的格式记录在 Zookeeper 中。Broker 启动后，会到对应的 Topic 节点中注册自己的 Broker ID 节点，并在节点中记录针对该 Topic 的分区数量。该节点同样是临时节点。

### 负载均衡

由于同一个 Topic 消息会被分区并将其分布到多个 Broker 上。因此，生产者需要通过负载均衡，将消息合理地发布到分布式的 Broker 上；同时，消费者也需要进行负载均衡，实现多个消费者合理的从对应的 Broker 服务器上接受消息。

Kafka 支持传统的四层负载均衡或 Zookeeper 方式实现负载均衡。
