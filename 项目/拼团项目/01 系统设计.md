# 概述

### 产品设计
- 互联网公司中, 需求首先是从业务侧出发发起的盈利目标, 拆分成为不同的运营策略, 再把对应策略由产品经理设置成为可以支撑市场运营操作, 完成盈利目标的具体项目
- 在设计过程中一般有三个角色, 分别是业务人员, 运营人员, 产品经理, 三者分别在自己的岗位产生不同的文档

**文档分类**
- **市场需求文档** (MRD): MRD 是从市场的角度出发, 描述目标市场的需求和机会, 通常包括目标客户群, 市场趋势, 竞争分析, 市场定位, 产品定位以及产品应该实现的市场目标等. MRD 通常由产品经理或市场分析师编写, 目的是定义产品应该解决的**市场问题**和满足用户的需求
- **业务需求文档** (BRD): BRD更侧重于业务角度, 描述业务目标, 业务流程, 业务规则, 业务问题以及业务需求. 他是从组织的业务视角来定义需求, 包括业务背景, 业务目标, 影响分析, 风险评估等. BRD 通常由业务分析师编写, 目的是确保项目解决了正确的**业务问题**, 并与公司的业务战略保持一致
- **产品需求文档** (PRD): PRD是更详细的文档, 他是根据MRD和BRD中确定的需求, 具体描述产品的功能性和非功能性需求. PRD 包括用户故事, 用力, 功能列表, 性能要求, 界面设计, 用户体验等. PRD 通常由产品经历编写, 目的是为设计团队和开发团队提供一个明确详细的产品实现指南

### 项目背景
- 对于商城项目等, 在长期运营的基础上, 可能出现商品购买交易同比增速放缓, 需要引入新的营销策略促进商品交易量. 为盘活沉睡用户, 需要适当降低商品价格, 为达到传播效果, 可以引入拼团模式
- 通过拼团, 可以做到以客带客, 靠用户自身传播的方式进行交易拉新, 相比于 KOL, 即关键意见领袖, 可以做到让利商品价值给用户自身的效果

# 需求分析

**前端页面**
- 进入商品页后, 查询是否配置了拼团活动, 并进行优惠试算, 拼团成团价, 最低优惠展示等
- 拼团页面展示参与首次拼团和参与拼团中拼团. 拼团完成则不展示此拼团
- 所有参与中的拼团统计拼团人员

**运营管理**
- 提供配置, 包括拼团人数, 拼团时长, 商品名称, 人群标签等信息
- 人群标签为提前设定的标签类型, 产生对应的人群数据

**功能流程**
- 首先, 由运营配置商品拼团活动, 增加折扣方式. 同时, 根据预先设置的拼团人群标签, 控制哪些用户可以参加拼团
- 之后, 用户可见拼团商品并参与拼团. 用户可以自主分享拼团或者等待拼团. 因为拼团折扣较大, 刺激用户自主分享, 由此节省营销推广费用
- 最后, 拼团完成, 商品发货. 商品拼团方式通常分为两种, 一种是拼团成团稀有性, 必须达成拼团人数条件才拼团成功; 另一种是虚拟拼团, 无论条件是否满足, 到达对应拼团结束时间后自动成团

# 拼团库表设计

### 概要
- 编码逻辑的实现都是算法对数据结构的处理, 库表即为根据业务和算法需求设计出的数据结构, 用于存储业务数据
- 数据库表设计的好坏决定了编码的难易程度

**拼团活动表**
- 商品拼团活动对应一个拼团活动表, 其中包含拼团时间, 人数, 价格等等. 
- 同时, 根据用户标签的不同, 消费动作的不同等, 还需要设置不同的用户的人群标签; 人群标签经过计算得出, 标记某用户是否为某种特定消费群体的一员
- 人群数据通常存储与 Redis 中, 访问速度快, 吞吐量高

**拼团用户账户**
- 用户试图通过拼团购物时, 首先会给用户展示可以成团的拼团数据, 其中可能只是在前端展示的机器人团, 通常为高频商品的拼团策略

# 研发系统设计

### 用户用例图
- 用例图是用户与系统交互的**最简表示形式**, 展现了用户和与他相关的用例之间的关系. 通过用例图, 可以获知系统不同种类的用户和用例. 用例图也经常与其他图表配合使用
- **用例图**, 也可以等同于**用户故事**, 主旨是以日常语言或者商务用语撰写句子, 是一段简单的功能表述. 以客户或使用者的观点撰写下有价值的功能, 引导和框架来与使用者进行互动, 从而推进工作进程.
- 可以被认为是一种规则文件, 代表着客户的需求与方向. 以该用户故事反应对象在组织内其工作职责, 范围, 需要进行的任务等. 用户故事在敏捷开发中用来定义系统需要提供的功能和实现需求管理
- 尽管用例本身存在大量细节和各种可能, 但用例图可以提纲挈领地让人了解系统概况, 为系统做什么提供了简化的图形表示.

### 四色建模图

**建模方法**
- DDD的建模过程是一个以用户为起点, 通过行为命令, 发起行为动作, 串联整个业务. 而这个用户的起点最初来自于用例图的分析. 用例图是用户与系统交互的最简表达形式, 展现了用户和与他相关的用例之间的关系, 通过用例图, 可以分析出所有的行为动作
- 在 DDD 中用于完成用户的行为命令和动作分析的过程, 是一个四色建模的过程, 也称作风暴模型. 在使用DDD标准对系统建模之前, 要先了解DDD的操作手段, 才能使项目的各个阶段开发人员在同一个语言下完成系统建模
- 下图为四色建模的指导图, 通过寻找领域事件, 扎起事件命令, 完成领域事件的过程, 完成 DDD 工程建模
	- 蓝色 - 决策命令: 用户发起的行为, 如查看额度
	- 黄色 - 领域事件: 过去时态, 表示该领域要完成的终态, 如签到完成
	- 粉色 - 外部系统: 系统需要调用外部接口完成的流程
	- 红色 - 业务流程: 串联决策命令到领域事件的业务流程
	- 绿色 - 只读模型: 做读取数据的动作, 没有写库的操作
	- 棕色 - 领域对象: 每个决策命令的发起, 都有一个相对应的领域对象
![[项目/拼团项目/Inbox/Pasted image 20251101212215.png]]

**寻找事件**
- 寻找领域事件的过程, 就是寻找系统中流程节点的结果态, 即什么完成了, 什么结束了, 什么终止了等等
- 通过寻找事件, 做到目标结果启动, 使系统设计过程基于要实现的目标制定
- 如果后续再迭代新功能, 可以继续引入其他领域事件
![[项目/拼团项目/Inbox/Pasted image 20251101213730.png]]

**划分领域**
- 领域的划分基于寻找领域事件之后, 所有的领域事件都应该有一个对应的发起方, 这个发起方称为决策命令
- 用户维度发起的所有决策命令, 都需要有与之对应的结果态承接
- 如果复杂业务需要进行一系列流程, 则还应通过业务流程进行处理. 业务流程中可以通过设计模式完成功能的设计

### 系统架构

**概述**
- DDD是软件开发的一套指导思想, 但是并不直接决定如何进行编码, 而是提供了对需求设计为研发提供编码指引的手段.
- DDD建模后, 既可以使用 MVC 三层架构开发, 也可以使用六边形架构, 整洁架构, 菱形架构开发等
- DDD 只是指导思想, 而六边形架构, 整洁架构, 菱形架构等是对指导思想的具体实现; MVC虽然可以实现DDD架构, 但是其并不适应分布式微服务资源模块的承载和领域思想的处理, 新的架构形态可以更好的承载DDD指导思想

**差别**
- MVC基本把所有内容实现都使用服务层Service进行承接, 无论是自身服务还是外部服务, 长此以往会导致维护困难, 迭代成本增加
- 六边形架构把MVC的劣势进行了针对性架构处理, 合理划分了各项资源在不同层的承载, 同时 domain 也更专注于领域功能的实现
