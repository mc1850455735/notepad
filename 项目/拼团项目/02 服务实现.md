### 工程解释

**工程设计**
- 该工程是一个 `六边形/菱形架构` , 相当于对 MVC 三层结构进行了优化设计, 使每一层更好的关注自身业务, 减少互相调用
- 在六边形架构中, 对于外部的调用不直接产生, 而是在包内定义一个相关接口, 并使外部相关基础设置对接口进行实现, 注入时将外部实现注入定义的接口, 实现依赖倒置的设计模式, 减少组件实现变更对调用者的影响
- 这种设计是一种 `ACL` 防腐设计

**层级结构**
- `api` 用于定义为外部提供服务的接口标准, 包括 `http`, `rpc` 等
- `app` 为该项目的应用, 如工程配置, 工程打包, 工程启动等设置
- `domain` 负责处理业务逻辑, 包括 `service` 服务, `adapter` 适配器, `model` 数据模型等信息; 实现了每个 `service` 所需要的类和工具都位于同一个包下, 划分了不同包的职责, 进行了隔离操作
- `infrastructure` 基础设施层, 用于实现连接数据库, 连接网关, 连接缓存等一系列对基础设施的操作. 同时添加适配器用于管理基础设施层的各种实现
- `trigger` 可以视为 controller 的高级版本, 其中提供 `http`, `job`, `listener` 等多种服务提供方式
- `types` 层, 类似 common 层, 其中包含枚举类, 异常类, 常量接口, Util工具包等, 供给项目内部调度使用
- 对于模块间的相互使用, 基于 maven 中依赖引入的方式进行

# 规则树模型

### 规则树模板概述

**概述**
- 对于某些设计模式, 如责任链, 是一种对于编程时工程实现的指导思想, 具体的实现方法通常因人而异; 项目中如果需要使用责任链, 不加管理的情况下会对同一个功能进行多次实现, 即增加了成本, 又增大了系统复杂度和维护难度
- 所以通过设计抽象模板的方式, 将常用的组件式的功能进行抽象和封装, 不同的模块中使用同样的模板进行开发, 提高了代码复用率

**规则树**
- 规则树相比较责任链, 灵活性更好, 可以展现不同节点之间功能逻辑的串联关系, 实现功能较复杂情况下的场景
- 其中需要一个策略映射器, 一个策略处理器, 以及一个策略路由抽象类. 
- 策略映射器相当于使用 dao 数据库操作时对节点的 mapper 映射, 每次会映射到要处理的下一个节点
- 策略处理器相当于每一个节点内部的方法, 在其中进行具体功能的实现
- 策略路由抽象类实现了策略映射器和策略处理器两个接口, 但是内部不做具体的编码; 其内部定义的是路由结构, 负责路由的分发; 其泛型参数分别代表入参类型, 动态上下文类型, 返回结果类型
- 动态上下文用于上下节点的沟通, 如将上一个节点查到的数据用于下一个或者更后面节点使用

### 规则树模板实现
- `StrategyMapper<T, D, R>` : 策略映射器, 其中实现一个get方法, 该方法接收参数为 `T requestParameter, D dynamicContext`, 即请求参数和动态上下文, 返回 `StrategyHandler<T, D, R>`, 即策略处理器
- `StrategyHandler<T, D, R>` : 策略处理器, 其中实现一个apply, 用于接收请求并进行处理, 接收参数为 `T requestParameter, D dynamicContext`,  返回值类型为泛型参数类型 `<R>`
- `StrategyHandler DEFAULT = (T, D) -> null` 为默认处理器类型, 默认接收一个函数并返回对应的策略处理器, 目前置为空, 不作实现
- `AbstractStrategyRouter<T, D, R>` : 路由抽象类, 其中实现 `StrategyHandler` 和 `StrategyMapper` 两个接口; 实现一个 `R router(T requestParameter, D dynamicContext)` 方法, 该方法的作用是通过传入的参数和上下文信息映射到一个合适的策略处理器并做处理
- 如果没找到对应的策略处理器, 则使用事先在 `StrategyHandler` 接口中定义好的默认策略处理器 `StrategyHandler.DEFAULT` 进行处理

# 多线程异步数据加载

### 概述

**概述**
- 在业务节点中, 通常需要其他数据支撑进行业务的查询等操作, 将没有上下文关联的查询等操作使用并行, 可以减少数据准备过程中的耗时
- 在代码实现的过程中, 先添加一个带有多线程处理功能的策略路由抽象类, 并使原本继承自普通策略路由抽象类的实现类继承自该类, 拓展原路由类功能
- 在多线程加载路由类中, 分三个区块进行, 分别是异步数据加载区, 功能逻辑受理区, 节点路由流转区.

**功能**
- 在新增的 `AbstractMultiThreadStrategyRouter` 中, 对于 `apply()` 方法, 先调用 `multiThread()` 方法异步加载可能需要加载的数据, 再通过 `doApply()` 方法通过加载后数据实现业务功能逻辑
- 将domain领域包中的拼团购买节点抽象类 `AbstractGroupBuyMarketSupport` 调整继承为 ` ` 抽象类, 并将 `multiThread()` 方法实现为一个缺省方法, 使有需要的实现类自行实现, 不必要每个节点都对该方法进行实现

**其他节点功能**
- 在各个节点的 `doApply()` 中, 实现该节点应有的逻辑
- 在 `RootNode` 中进行传入参数的检验, 对于失败的情况, 新增自定义异常, 并返回常量枚举类中定义的错误码 `ILLEGAL_PARAMETER`, 检查无误后, 进行流转, 进入下一个节点 `switchNode`
- `switchNode` 为流转节点, 用于处理降级等场景, 即根据传入的参数对请求链进行分叉处理, 比如用户权限不足或用户标签不满足条件等

**营销节点**
- 在营销节点中进行异步数据的处理, 为进行处理, 新增 thread 包, 并在其中增加线程方法, 实现 Callable 接口, 为线程池提供任务. 该任务负责查询活动优惠的配置以及商品的sku, 即原始信息
- 新增sku表, 其中包含商品的各种信息, 如商品id, 商品名称, 商品原始价格等
- 线程池对象的配置在app层进行声明和配置
- 最后, 在app层中进行决策树链条的 test 测试

### 实现

**多线程数据加载抽象类**
- 对于原 `StrategyHandler` 中的 `apply()` 方法, 为其添加多线程异步加载数据的功能, 相当于先执行异步数据加载方法, 再执行原 `doApply()` 方法
- 新建 `AbstractMultiThreadStrategyRouter` 抽象类, 其中实现 `router()` 方法进行路由, 并重写 `apply()` 方法, 将其分解成为 `multiThread()` 多线程异步加载数据和 `doApply()` 方法; 在其中定义超时时间参数 `timeout`
- 使 `AbstractGroupBuyMarketSupport` 继承自新添加的多线程异步策略路由器抽象类, 分别后续实现抽象类中的异步加载方法, 对异步加载方法在抽象类中进行缺省实现, 简化节点代码;
- 同时注入仓储接口 `IActivityRepository`, 分别实现类调用仓储功能; 在节点中同样实现新抽象类中新增的方法

**RootNode与SwitchNode**
- 在 `RootNode` 中进行基础功能的实现和路由操作. 主要实现 `get()` 方法返回下一个节点, 以及 `doApply()` 对传入上下文信息及参数的处理功能, `doApply()` 处理完成后, 通过 `router()` 执行 `Node` 中定义好的 `get` 获取下一个 `Handler` 或者获取默认 `Handler`; `Root` 中主要进行对参数的检查操作
- `SwitchRoot` 暂不处理, 直接路由到 `MarketNode`

**MarketNode与EndNode**
- 营销节点 `MarketNode` 重点处理, 其中需要实现异步数据的加载, 所以需要重写 `multiThread` 方法. 为实现多线程异步, 需要 `ThreadPoolExecutor` 线程池. 
- 该节点路由到 `EndNode` 节点, `multiThread` 中通过事先定义好的 `ThreadTask` , 使用 `FutureTask` 类封装多线程异步调用查询过程, 并使用线程池执行该异步任务; `Future Task` 的 `get() `方法, 设置最大超时为父类中的 timeout 参数
- 对于 `EndNode`, 取出动态上下文中的数据, 将其封装为 `doApply()` 对应的返回值类型, 即结果对象, 并返回, 结束调用

**多线程任务**
- 创建对应的 thread 包, 在其中添加对应的多线程任务类, 使其实现 Callable 接口, 设置接口的泛型参数为对应的查询类型
- 在多线程查询任务类中, 添加活动信息仓储查询接口 `IActivityRepository`, 该接口中需要声明 dao 中实现的各类查询方法, 并在 `infrastructure` 包中增加该接口对应的实现类, 通过实现声明好的 dao 层方法进行查询

**仓储接口**
- 在 `adapter.repository` 包中增加仓储适配器接口, 并在相应的 `model.valobj` 包中添加要查询的值对象 `GroupBuyActivityDiscountVO`, 该对象大致与数据对象相同;
- 折扣相关部分由类内的折扣静态对象代替, 主要起防腐的作用; 在业务变化时不需要改变对应的数据库对象. 在 `GroupBuyActivityDiscountVO` 类中, 配置静态内部类 `GroupBuyDiscount` , 存储拼团活动的具体折扣信息
- 在 `infrastructure` 项目中添加商品库 `sku` 的数据库对象, `ISkuDao` 接口 (注意添加 `@Mapper` 注解), 以及对应的 `mapper xml` 文件; 在 `GroupBuyActivity` 的查询拼团活动 `queryValidGroupBuyActivity` 方法中, 根据给定的 `source` 和 `channel` 查询一个拼团信息

# 策略模式折扣计算

### 概述

- 在 Service 中创建折扣计算相关包 discount, 在包中增加设计模式计算逻辑, 并在其中定义 `IDiscountCalculateService` 接口用于外部的调用
- 增加抽象类实现接口, 在抽象类中实现人群标签的过滤和折扣计算, 由于目前未实现人群标签, 所以直接返回 true 即可.
- 对于折扣计算部分, 将抽象类实现多个不同的折扣计算相关类, 每个类中都实现一种相关的优惠策略折扣计算模式. 折扣后最低价格设为 `0.01` 元
- 折扣策略完成后, 在营销节点中进行调用. 将折扣计算策略根据策略名, 作为 Map 形式进行注入; 通过这种形式, Spring将自动注入项目中所有实现了折扣计算接口的 Bean, 并根据 Bean 名称组织为一个 Map; Bean 名称与数据库中的折扣计算模式名称是相同的;
- 通过从数据库中获取的 Bean 名称, 在 Map 中查找对应的实现, 并使用该实现进行折扣计算. 将计算后的价格结果保存在动态上下文信息中

### 实现

**修改**
- 将 `GroupBuyActivityDiscountVO` 中表示拼团方式的 `groupType` 由 `Byte` 类型改为 `Enum` 枚举类型, 增强程序的可读性; 将原代码中, 与数据库交互的类中存储 `discountType` 的字段改为 Integer 类型, 其他系统内部的 `discountType` 也由 `Byte` 类型改为枚举类型
- 枚举类型中定义了一个静态的 `get()` 方法, 可以通过 `code` 快速获取到对应的枚举类型
- 增加新的 `ResponseCode`, 当拼团信息中存储的折扣方式在 Map 中无法找到时, 返回对应的 code 和 info, 表示不存在对应的折扣计算服务

**折扣计算接口与抽象类**
- 数据库折扣表中, 如果人群标签 `tag_id` 不为 `null`, 说明该优惠是基于特定人群使用的, 则做折扣计算时, 需要过滤掉对应的人群标签
- 新增 discount 包, 包含折扣信息的计算服务. 在包内增加折扣服务策略接口`IDiscountCalculateService` , 其中关键方法为 `calculate` 计算折扣价格, 参数为 原始价格, 用户id, 折扣策略.
- 使用抽象类继承该接口, 其中实现折扣类型针对特定人群标签的过滤. 该抽象类中实现了 `calculate()` 方法, 用于查看某折扣是否存在人群标签. 
- 如果存在, 则实现针对人群标签的过滤, 不满足人群标签时直接返回原价, 满足人群标签时, 通过 `doCalculate()` 方法返回计算后的折扣价格. 
- 抽象类中定义了方法 `filterTagId()` 和 `doCalculate()` , 分别用于进行人群标签过滤和折扣计算. 人群标签过滤方法目前先只返回true, 折扣计算方法定义为抽象类, 供子类进行实现

**满减折扣计算**
- 定义 `MJCalculateService` 实现抽象类. 
- 添加 `@Service` 注解, 并将服务名定义为 `MJ`. 
- 在类中实现折扣计算方法 `doCalculate()`, 实现满减策略. 获取满减策略公式 `marketExpr`, 使用分隔符对其拆分后, 转为 x 和 y 两个参数. x 即为满多少元触发满减, y 为减多少元
- 计算原始价格是否满足满减条件, 即最低价格, 否则不触发满减条件. 如果进行满 x 减 y 后价格低于或等于 0, 则返回最低价格 0.01
- 如果无异常, 则返回满减后的价格

**其他折扣计算**
- 分别创建其他折扣模式对应的类, 如 N元购, 直减, 折扣等.
- 根据折扣模式, 分别在对应的 `doCalculate()` 方法中实现折扣策略

**折扣计算实现**
- 定义好相关的折扣计算策略后, 在 MarketNode 中使用 Map 容器类进行注入; 该 Map 容器的 Key 为折扣计算策略服务的服务名, Value 为对应服务接口类型的实现, 需要使用时, 直接根据折扣名称在 Map 中 `get()`
- 数据库中存储着折扣相关的服务名, 折扣id, 以及某个拼团活动使用的折扣策略id等信息, 通过修改数据库, 可以进行拼团折扣类型的修改
- 在动态上下文中, 通过对应的get方法, 获取上下文信息中存储的拼团信息, 折扣信息以及商品信息, 通过 Map 中存储的折扣策略对拼团进行处理
- 在 MarketNode 内部, 经预处理(获取拼团信息和折扣策略)后, 进行折扣计算, 通过传入的 `request` 参数以及上下文, 调用折扣计算策略的 `calculate` 方法获取折扣后的价格, 并将价格写入上下文当中
- 在 EndNode 中, 通过上下文获取折扣后价格作为返回值价格部分

# 人群标签节点过滤

**概述**
- 加入人群标签节点, 在该节点中, 根据人群标签库表以及拼团活动表中定义的策略, 实现根据人群标签规则进行可见限制或参与限制等内容. 

**人群标签检查**
- 新建 `TagNode` 为人群标签节点, 进行人群标签的处理, `MarketNode` 直接进入 `TagNode`. 在其中获得拼团活动的配置信息, 并在其中进行各项检查. 如果该活动未设置 `tagId`, 说明该活动不进行人群标签过滤, 设置为 true 后放行; 否则通过 `isTagCrowdRange` 进行人群标签判断, 判断是否属于该人群, 并与默认的人群标签启动设置进行或操作, 得到最终的结果
- `isTagCrowdRange` 方法中通过 `Redis` 的 `BitMap` 进行对应用户是否存在于指定人群标签范围的判断. 首先根据对应的 `tagId` 获取对应的 `BitMap`, 如果不存在这种 `BitMap`, 说明不需要进行人群标签判断, 直接返回 `true`; 如果存在对应 `BitMap`, 则通过相关函数判断其是否存在于 `BitMap`

**活动默认范围检查**
- 拼团活动类中新建两个方法用来检查当前活动是否可见和可用. 在拼团活动类中的两个方法中, 以 tagScope 字段为标准进行判断该活动是否启用了对人群标签的限制, 如果 tagScope 未启用, 即使不在范围内的用户也可以参加该活动. 如果tagScope 设置了对应的值, 且对应字段为 "1" 时, 默认设置其不可见; 同理, 也根据此逻辑对活动是否可使用进行判断
- 对于通过 tagScope 返回的 boolean 类型, 定义一个枚举值, 提高程序可读性
- 如果人群标签配置为空, 则走默认值直接路由; 否则通过 `BitSet` 判断当前用户是否在拼团活动规定的人群标签中. 该节点最终路由到 `EndNode` 节点, 在 `EndNode` 中将 `TagNode` 中得到的可见和可用信息加入返回结果中

**人群标签注意事项**
- 公司中 Redis 集群非常大, 专门为营销活动作准备, 同时需要的 BitMap 也非常大, 甚至以 Redis 的性能都会存在性能不足, 此时会涉及 JVM 的**堆外内存**, 使用堆外内存设计一种 BitMap 人群标签结构进行处理

# 动态配置开关操作

**概述**
- 动态开关配置用途: 在开关节点中实现动态配置, 如切量, 白名单, 开关等. 其实现方式是将对应的配置刷新到配置类属性中, 需要修改配置时直接与本地配置中心进行交互即可. 
- 动态变更配置组件不仅可以通过 Redis 的 发布订阅 机制进行实现, 也可以通过 SpringCloud 的消息总线(EventBus), 配置(Config), 以及 ZooKeeper 等技术进行实现

**注解与配置字段**
- 在基础类型层 types 中新增注解 `DCCValue` ( `Dynamic Config Controller` ), 对添加该注解的对象进行管理操作. 该注解的保留策略为 `运行时`, 目标为 `Field` 字段. 运行时保证了在代码运行阶段 JVM 也可以获取到注解的信息
- 在基础设施层中添加对 DCC 动态配置的服务. 该服务中配置了降级开关和切量开关, 使用 key:value 作为注解中值的格式, 默认分别是 `downgradeSwitch:0` 和 `cutRange:100`; `downgradeSwitch` 值为0表示不进行降级
- DCC 动态配置服务中, 使用 `isDowngradeSwitch` 和 `isCutRange` 进行是否进行降级操作和切流操作的判断. 

**配置字段检索与值填充**
- 在 app 层下的 config 包中, 定义 `DCCValueBeanFactory` 配置类加载对应的服务. 该类实现了 Spring 的 `BeanFactory` 接口. 通过实现初始化后处理方法 `postProcessAfterInitialization` , 拿到当前项目所有的 Bean 后, 通过 `AOP` 检查其是否为代理对象, 如果是, 则通过 AOP 获取其代理对象. 
- 获取Bean中的属性信息, 取出其中所有的字段, 并对其中标注了 `DCCValue` 注解的字段进行处理; 取出注解中的 value 值, 拆解并配置其中的设置
- 获取相应字段中注解内的值, 并对该值进行处理. 获取到对应的 key 和 default value, 从 redis 中获取 key 对应的 value, 如果不存在, 则以 default 作为当前的 value 值, 并将该值通过反射填充到对象中, 随后记录该对象

**配置信息监听**
- 在 `DCCValueBeanFactory` 配置类中添加 Redis 监听器, 当 Redis 中相关配置发生变化后, 获取到相应的变化信息, 并将最新值设置到记录的对象中; 更新时, 同时更新本机中存储着的配置对象列表和远程 Redis 配置列表
- 在 api 层下, 设置一个对外的接口, 用于向监听器中发送消息; 在 trigger 层的 `http` 包中实现这个接口, 接收到用户发送的 http 配置更改请求后, 由 `publisher` 发送一个相关的配置变更信息

**动态配置使用**
- 在 SwitchNode 节点中, 调用是否降级和是否处于切量范围内的判断, 如果判断成立, 则返回对应的错误信息

# 责任链抽象模板设计

**概述**
- 责任链抽象模板是一个重要的用于解耦业务流程的思想, 是处理复杂业务场景常用的解耦手段. 本节实现了一个通用的责任链模板
- 责任链实际上就是一个双向链表, 每个节点会关联其下一个节点和上一个节点. 为了实现责任链中每个功能节点的可复用性, 会通过多实例链路连接各个链路节点. 

**责任链**
- types 层中的 link 包中, 添加关于责任链的设计模式.

**model1**
- 第一种模型为单实例的责任链模型. `ILoginChainArmory` 为责任链的节点, 含有 `next()` 获取下一个节点和 `appendNext()` 设置下一个节点; 在接口 `ILogicLink` 中继承 `ILoginChainArmory` , 通过 `apply()` 方法实现节点功能.
- 单实例链的填充和执行都在同一个节点进行, 是一种单链结构, 无法更改. 如果想要实现多个相同节点的创建, 则应将相关节点设置为多例模式, 使每一次获取的节点都是新的对象, 组装完成对应的责任链后存储责任链.
- 创建抽象类实现对应的接口, 并在抽象类中实现添加下一个节点和获取下一个节点的方法; 同时, 提供了执行下一个节点中方法的过程

**model2**
- 将逻辑和用于执行的链进行解耦. 该模型使用双向链表进行实现.
- 在 `BusinessLinkedList` 业务链路类中, 对责任链进行遍历执行操作. 如果责任链中的某个节点返回值不为空, 说明此节点结束了向下执行操作, 直接返回该节点的结果即可.
- 最后声明一个 `LinkArmory`, 初始化时传入责任链名称以及一系列处理方法, 将这些方法加入到 `BusinessLinkedList` 中作为节点, 需要使用时, 直接返回对应的 `BusinessLinkedList`

# 交易规则责任链过滤

**概述**
- 实现对活动有效性的检验, 如: 活动是否过期, 用户是否已参与过活动, 用户是否已在某个拼团中等. 为了实现该目标, 新增了一系列用户, 需要将其添加到人群标签中, 同时在 order_list 中新增了用于检测用户是否参与过对应活动的业务id `biz_id`, 是业务的唯一标识
- 由于数据库表发生了一系列变动, 所以应该调整对应的 mapper 文件; 同时对于折扣金额 deductionPrice, 将其清晰化, 作为该活动剪掉的金额而不是实际支付的金额; 在优惠计算中, 添加人群标签验证, 如果用户不在对应的人群标签中, 则返回原价
- 通过查看原项目分支提交明细记录可以获取代码的变更位置等信息

**支付金额调整**
- `MarketNode` 节点中区分好支付金额和折扣金额
- 在决策树上下文信息中添加对支付金额的存储
- `EndNode` 中填充 `payPrice`, 在返回实体类中添加 `payPrice` 字段
- 在 `trigger` 层中的 `MarketTradeController` 内, 对于返回值类型, 增加支付价格相关信息, 并在返回值中填充支付价格
- 在 `Repository` 中, 修改返回的支付价格 `payPrice`, 取传入的折扣信息的值

**人群标签过滤**
- 在优惠试算抽象服务类中, 添加根据 `tagId` 和 `userId` 对人群标签的过滤功能

**交易责任链**
- 在 domain 层的 trade 包下增加规则节点, 通过责任链进行过滤操作; 在其中的 service 包下新建 filter 和 factory 分别用于存储过滤节点和各个责任链
- 增加两个实体类 `TradeRuleCommandEntity` 和 `TradeRuleFilterBackEntity`, 用于表示交易规则命令实体和交易规则过滤结果实体; 在责任链中分别作为参数类型和返回值类型
- 创建工厂类 `TradeRuleFilterFactory`, 其中包含上下文等信息, 动态上下文中存储活动信息等
- 在 filter 中添加两个过滤节点. `ActivityUsabilityRuleFilter` 用于检测活动是否可用; `UserTakeLimitRuleFilter` 用于检测当前用户是否可以参与该活动. 
- 在活动可用检测中, 需要先获取活动的信息, 对于相关的状态码, 定义对应的枚举类, 该枚举类为活动状态的枚举类, 作用范围较广, 应抽象到最上层的 types 层中. 依次检查活动是否生效, 活动是否处于有效期, 如果没有问题, 将查询到的活动存入上下文, 并路由到下个节点.
- 在用户可参与检测中, 检测用户的拼单数量是否大于等于最大单用户拼单数量, 若无问题, 则返回交易规则过滤结果

**工厂拼装责任链**
- 在 `TradeRuleFilterFactory` 内部定义函数 `tradeRuleFilter`, 将其作为一个 Bean 进行处理, Bean 名称即为责任链的名称. 将定义好的两个规则节点注入该 Bean 作为依赖进行使用. 使用注入的规则节点, 利用定义的构造函数创建对应 `BusinessLinkedList`
- 将定义的链路对象 `Bean` 注入到 `TradeOrderService` 中进行使用. 在锁单操作时, 先使用责任链对传入的参数进行过滤, 获取结果. 检查结果是否存在问题, 对于不存在问题的, 再进行下一步操作.
- 在耦合对象中加入当前用户的订单次数, 便于后续执行. 在 Dao 层的锁单操作 `lockMarketPayOrder` 中, 拼接活动id+用户id+用户拼单次数作为事务id. 

# 拼团组队结算统计

**概述**
- 该部分用于拼团结算操作. 与小型电商等系统进行对接
- 在处理拼团锁单完成后, 等待用户进行支付并记账; 支付后, 判断当前订单是否为锁单订单. 如果是, 则在事务内查询并更新拼团记录, 如果当前订单支付后拼团达到目标量, 则认为拼团完成. 如果订单不是锁单订单, 则直接结束
- 当拼团完成, 即整个拼团内所有订单都已支付, 则将当前订单写入回调任务表, 根据订单进行回调, 对拼团内订单进行发货

**库表**
- 增加了 `notify_task` 回调通知任务库表. 对应的, 添加基础设施层库表类和库表相关 Dao 操作, 并配置对应的 mapper 文件

**单一职责**
- 在 domain 层的 trade.service 中, 进行单一职责设计, 把每一个职责都拆分为单独的包, 目前拆为 lock 包和 settlement 包. 单一职责即为对任务流程的拆解, 确保每个服务都只完成单个任务目标
- 将锁单操作与结算操作拆分为两个不同的 Service.
- 在 lock 包功能返回类型 MarketPayOrderEntity 中, 添加当前锁单的拼团id

**结算操作**
- 如果拼团顺利完成, 则查询拼团完成时的外部单号列表, 并将拼团完成的一系列信息, 包括外部单号列表, 写入回调任务记录表中, 供处理发货使用
- 进行结算操作时, 传入支付成功的消息对象, 并返回结算操作结果对象. 先根据外部单号进行拼团信息查询, 再以拼团信息进行组团信息查询, 并使用查询出的组团信息进行拼团交易的结算, 最后返回结算信息
- 进行仓储操作时, 需要分别进行 `订单状态的更新`, `拼团完成订单数量的更新`, `拼团是否完成的判断`. 结算时, 首先根据用户id和外部订单号查询用户的拼团订单信息, 并判断当前信息是否正确; 确认用户拼团订单无误后, 通过仓储接口进行拼团对象的查询. 
- 通过查询的拼团信息创建对应的聚合对象, 使用该聚合对象通过仓储接口完成结算操作. 在仓储接口的结算方法中, 使用事务保证数据库操作的同成功同失败. 先对用户拼团订单状态进行更新, 更新无误后, 对拼团订单的完成数量加1. 最后检查, 如果该订单提交前, 拼团内只有一个需要完成的订单, 则说明该拼团已完成, 修改该拼团状态并将对应操作加入回调任务表中

# 交易结算责任链过滤

**概述**
- 在交易结算过程中, 需要考虑到拼团活动的有效期, 渠道的管控, 外部单号的有效性等信息, 对用户的支付行为构建责任链, 通过责任链进行过滤
- 对于锁单操作, 修改锁单相关操作的类名称, 以便于与结算操作相关类名称作区分, 便于更好理解
- 在 trade 领域下, 在结算 statement 中, 使用责任链模板实现营销交易规则的过滤. 
- 责任链中实现如下节点: `SCRuleFilter` 黑名单管控过滤, `OutTradeNoRuleFilter` 外部交易单号有效性过滤, `SettableRuleFilter` 交易时间是否在拼团有效时间内过滤, `EndRuleFilter` 结束节点封装返回数据
- 交易服务调用责任链返回相关的数据信息. 在结算时, 直接使用责任链返回的数据, 不再需要再到数据库中进行查询
- 在 `settlementMarketPayOrder` 结算操作下, 对 `updateOrderStatus2COMPLETE` 更新时增加 `outTradeTime` 时间

**库表**
- 在拼团活动表中, 存在有效支付时间字段, 拼团在成立后必须在规定时间内支付, 否则认定为结算失败.
- 在拼团订单表中, 添加 `valid_start_time` 和 `valid_end_time` 字段, 用于标识该拼团的有效参与时间范围.
- 在用户拼团订单表中, 添加 `out_trade_time` 用于保存用户的锁单时间等信息
- 在相关数据库表类中, 添加相关的字段信息, 并修改对应的 mapper; 对于拼团活动的开始和结束时间, 在仓储层中根据当前时间和拼团活动预先设置的有效时间进行计算; 对于外部服务时间, 在进行结算时, 设置为结算成功时设置的时间, 在本节中, 通过测试方法设置外部订单结算时间

**结算责任链**
- 在trade领域下结算 statement 中添加对应的 filter 与 factory, 定义多个用于过滤的节点, 并使用责任链抽象模板串联这些节点
- 创建责任链对应的入参和出参. 在 factory 中构建责任链, 并定义上下文结构
- 在 `SCRuleFilter` 中实现根据黑名单过滤对应的 source 和 channel. source 和 channel 是否属于黑名单作为配置的一部分由动态配置控制 DCC 进行管理. 在 DCCService 中添加对应的变量, 并添加 `isSCBlackIntercept` 方法, 用于检查传入的source 和 channel 组合是否位于黑名单中
- 在 `OutTradeNoRuleFilter` 中用于检查传入的外部单号是否符合要求, 是否存在对应的外部单号及其状态是否正常, 取结算相关服务时的单号检测部分
- 在 `SettableRuleFilter` 中用于检测用户结算时间是否处于有效时间内. 
- 在 `EndRuleFilter` 中组装责任链最终数据并返回给用户
- 在 `settlementMarketPayOrder` 方法中添加责任链,, 通过责任链进行交易结算阶段的过滤

# 拼团回调通知任务

**概述**
- 拼团已经完结, 回调通知其他微服务(如商城)组队已完成, 进行发货等处理.
- 通过 `GroupBuyNotifyJob` 进行批量处理回调, 并通过 okhttp 框架调用外部接口, 对回调进行处理, 同时更新回调任务的状态; 可以在拼团组队完结时即时性的发起回调通知, 避免了对定时扫描的依赖, 同时使用定时扫描作为补偿机制, 避免因网络故障等原因导致的即使处理失败. 定时回调处理有时间限制, 如果一定次数的回调后仍处理失败, 则不再进行尝试, 通知人工介入
- 用户锁单动作开始前, 由外部传入 `notify_url`, 并将 `notify_url` 写入拼团组队表中; 结算时, 取出 `notify_url` 构建拼团组队信息; 拼团完成后, 将 `notify_url` 写入回调任务表, 并通知回调进程进行处理

**库表**
- 拼团组队表  `group_buy_order` 中增加回调地址 `notify_url`, 用于回调处理
- 修改相应库表类中的字段, 并修改对应的 dao 与 mapper 操作

**notifyUrl写入数据库**
- 在锁单操作的参数对应的 DTO 类中加入回调地址, 用于将回调地址传入锁单操作, 同时应判断该值不为空, 否则抛出异常;
- `PayDiscountEntity` 中储存着和折扣相关的外部信息, 在其中添加 `notify_url` 回调地址字段
- 在 `MarketTradeController` 的锁单操作中, 通过 `PayDiscountEntity` 对象接收 `notify_url` 回调地址传入仓储操作中; 在仓储操作中, 使回调地址写入拼团组队表 `group_buy_order` 
- 在结算操作中, 将锁单记录中的 `notify_url` 传入 `GroupBuyTeamEntity` 中, 并在责任链的 `EndRuleFilter` 节点的 `TradeSettlementRuleFilterBackEntity` 返回值中将 `notify_url` 填入并返回
- 在交易结算服务中, 在拼团信息中填入责任链返回的 `notify_url`; 在仓储接口的 `settlementMarketPayOrder` 中, 写入 `notify_url`, 并将该 `notify_url` 加入回调任务对象中, 并将该对象写入 `notify_task` 表

**回调处理**
- 回调状态控制应使用枚举标识回调的状态, 应在 `ResponseCode` 中定义回调异常时的异常码; 同时创建枚举类  `NotifyTaskHTTPEnumVO` 表示 http 回调操作的返回结果状态.
- 在交易结算处理接口中, 定义回调处理方法 `execSettlementNotifyJob`, 用来通知指定的处理回调任务. 在该方法中使用 port 进行回调功能的执行, 并返回结果, 同时记录回调成功, 重试, 失败次数. 根据返回的结果更新回调任务表的状态, 将各种状态的回调次数记录在 Map 中并返回.
- 增加一系列方法, 允许指定一个或一组 teamId 进行立即回调.
- 回调通知分为两个阶段: 拼团后立即执行或任务补偿. 立即执行是为了保证任务的时效性, 但是由于服务可能受网络和服务的波动影响导致失败, 所以增加了定时任务进行补偿.

**接口配置**
- 在 trigger 包中定义 http 接口 `TestApiClientController`, 该接口用来测试交易回调功能, 传入一个 `NotifyRequestDTO` 对象, 该对象内含有组队id以及需要进行回调的外部单号列表. 通过 PostMan 对该接口进行测试, 并生成对应的 okhttp 接口调用代码.
- 在基础设施层引入 okhttp 依赖, 并在 app 层增加 okhttp 的 config. 在基础设施层的 gateway 包中加入拼团回调服务 `GroupBuyNotifyService`, 使用 okhttp 发起 http 请求, 代码部分取 PostMan 生成的代码

**接口使用**
- 在 domain 域的 trade 包下的适配器中, 定义 port 包作为 http 请求的适配器. 一般来说, repository 用来进行本地调用, 而 port 用来进行远程调用.
- 创建 `NotifyTaskEntity` 用于记录回调任务本身的参数等信息. 在基础设施层中创建对适配器接口的实现. 在实现中调用写好的 `GroupBuyNotifyService` 进行 http 请求的发送;
- 使用 Redisson 分布式锁对发送请求的过程进行抢占, 在 `NotifyTaskEntity` 中添加 getKey 方法, 用来提供回调处理过程中分布式锁的 key, 每个拼团订单对应一个 key, 确保同一时间相同的订单只会存在一次处理

**定时回调任务**
- 在 Application 中添加 `@EnableScheduling` 注解, 允许定时任务的执行
- 在 trigger 层 job 包下定义回调任务 `GroupBuyNotifyJob`, 将结算服务作为依赖进行注入. 在类中添加 exec() 方法作为回调任务, 为其添加 `@Scheduled` 注解, 并定义执行时间间隔为 `0/15 * * * * ?`
