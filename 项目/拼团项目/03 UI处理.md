# 根据UI展示封装接口

**UI所需信息**
- 对于商品的支付信息和降价信息等, 属于拼团商品信息
- 对于有x人在抢等信息, 属于拼团的统计信息
- 对于当前有什么拼团, 拼团内有几人, 属于拼团信息
- 对于开团购买和参与拼团, 属于拼团锁单接口部分
- 对于扫码支付, 属于拼团结算接口部分
- 用户能看到的信息由营销首页接口组装返回

**代码组织**
- 添加 `IMarketIndexService` 接口, 用于查询对应商品的拼团营销配置; 该接口返回 `GoodsMarketResponseDTO` 类型的对象, 其中会存储商品信息, 拼团组队信息 (一个个人置顶拼团信息, 两个随机抽取的拼团信息, 从10个获取到的拼团配置中抽两个), 组队统计信息.
- 在 `IMarketTradeService` 接口中添加营销结算接口, 直接调用营销结算服务中的相关方法即可.

**IMarketIndexService接口实现**
- `IMarketIndexService` 中主要需要实现三个功能: 查询对应 goodsId 的商品信息; 随机返回指定数量的拼团详情; 返回该拼团活动的成单量和当前正在进行的拼团数量信息.
- 为获取经拼团优惠后的商品信息, 需要使用优惠试算决策树对传入的 用户id, 商品id, sc 值进行处理, 得到商品对应的拼团相关信息, 并将该信息封装到商品类 `goods` 对象中
- 对于页面展示的拼团详情, 分为以下两个部分: 用户自身已参与的拼团和随机的用户没有参与的拼团. 为此, 在查询方法中设置本人拼团数量和随机拼团数量, 并使用不同的 SQL 进行查询, 最终将查询到的两个列表合并为最终返回的结果列表
- 由于对查询的结果有数量限制的存在, 为此在基础设施层 po 包中添加一个 base 包, 并在其中定义分页相关类 `Page`, 在其中定义一次查询的数量. 使拼团订单详情类继承 `Page` 类, 实现分页限定数量查询的相关字段
- 在 mapper 中查询尚未完成的拼团订单明细, 并根据拼团订单明细完成获取对应的拼团订单id; 共需实现两个查询: 1.查询用户参加的拼团订单明细信息 2.查询非用户参与的其他拼团订单明细; 通过 limit 条件对返回的查询数量进行控制. 非本用户参与的拼团明细同时要求该拼团必须正在进行中, 否则获取已完结拼团正在进行中的拼团订单详情无任何意义.
- 通过获取的拼团订单号集合, 在 mapper 中查询拼团订单的信息, 如拼团中有几人参与, 共需几人, 还差几人, 还有多少时间结束等, 并返回给前端

# Deepseek 处理接口对接

**概述**
- 告诉ai相应的页面信息和接口信息, 并告诉ai页面中的信息从何处获取, 使ai自动处理完成前端页面与接口的对接处理

**话术**
```
(html 代码)
根据要求修改以上 html 代码； 
1. 对接接口 (给出接口代码) 
2. 接口返回 json 为；(json)
3. 直降60元，从 deductionPrice 获取 
4. 76人再抢，从 allTeamUserCount 获取 
5. 参与拼团的列表数据从 teamList 获取，其中仅剩1人、2人这样的数据，从 targetCount - lockCount 获取。倒计时从 validTimeCountdown 获取。
6. 单独购买 金额从 originalPrice 获取，开团购买金额从 payPrice 获取 
7. 如果 teamList 为 null 的时候，则在页面展示 小伙伴，赶紧去开团吧，做村里最靓的仔。
```
