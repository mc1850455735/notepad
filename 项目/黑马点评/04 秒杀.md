
# 全局唯一ID

**前置问题**
- 当用户抢购时, 就会生成订单并保存到tb_voucher_order表中, 而如果订单表使用数据库自增ID, 就会出现一些问题
	- id规律性太过于明显
	- 受单表数据量的限制
- 常见生成策略
	- Redis自增
	- UUID
	- snowflake算法
	- 数据库自增

**全局ID生成器**
- 是一种在分布式系统下用来生成全局唯一ID的工具, 一般需要满足以下特性:
	- 唯一性: 生成的id必须是一个全局唯一的id
	- 高可用: 在任何时候, 全局id生成器都必须保持可用
	- 高性能: 保证随时可生成id的基础上, 生成id速度够快
	- 递增性: 创建的id必须总体是自增的, 有利于数据库创建索引
	- 安全性: 不能太过于有规律等, 使用户可以根据id猜测系统内部
- 为了增加生成id的安全性, 可以不直接使用redis产生的自增数值, 而是拼接一些其他信息
- ID组成
	- 符号位: 1bit, 永远为0
	- 时间戳: 31bit, 以s为单位, 可以使用69年
	- 序列号: 32bit, 秒以内的计数器, 最多可以支持2^32个不同id

**代码实现**
- 每天一个key, 方便统计订单量, 同时限定每天key的值
```java
public long nextId(String keyPrefix) {  
    // 生成时间戳  
    LocalDateTime now = LocalDateTime.now();  
    long nowSecond = now.toEpochSecond(ZoneOffset.UTC);  
    long timestamp = nowSecond - BEGIN_TIMESTAMP;  
    // 生成序列号  
    // 获取当前日期, 精确到天  
    String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));  
    long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + date);  
    // 拼接并返回  
    return timestamp << COUNT_BITS | timestamp;  
}
```


# 优惠券秒杀下单

**概述**
- 优惠券分为平价券和特价券, 平价券可以任意购买, 特价券需要秒杀抢购
- 表关系如下
	- tb_voucher: 优惠券基本信息, 优惠金额, 使用规则等
	- tb_seckill_voucher: 优惠券库存, 开始抢购时间, 结束抢购时间等, 供给特价优惠券使用
- 实现秒杀下单功能时有两点需要注意
	- 秒杀是否开始或已经结束, 如果未开始或已结束则无法下单
	- 库存是否充足, 如果库存不足则无法下单
	- 由于先扣减库存后下单, 应该为对应功能添加事务, 确保执行的原子性

**示例**
```java
@Override  
@Transactional  
public Result seckillVoucher(Long voucherId) {  
    // 查询优惠券  
    SeckillVoucher voucher = 
        seckillVoucherService.getById(voucherId);  
    // 查询秒杀是否已经开始  
    if (voucher.getBeginTime().isAfter(LocalDateTime.now())) {  
        return Result.fail("秒杀尚未开始");  
    }  
    // 查询秒杀是否已经结束  
    if (voucher.getEndTime().isBefore(LocalDateTime.now())) {  
        return Result.fail("秒杀已经结束");  
    }  
    // 判断库存是否充足  
    if(voucher.getStock() < 1) {  
        return Result.fail("库存不足");  
    }  
    // 扣减库存  
    boolean isSuccess = seckillVoucherService.update()  
            .setSql("stock = stock - 1")  
            .eq("voucher_id", voucherId).update();  
    if(!isSuccess) {  
        return Result.fail("库存不足");  
    }  
    // 创建订单  
    VoucherOrder voucherOrder = new VoucherOrder();  
    long orderId = redisIdWorker.nextId("order");  
    voucherOrder.setId(orderId);  
    voucherOrder.setVoucherId(voucherId);  
    voucherOrder.setUserId(UserHolder.getUser().getId());  
    save(voucherOrder);  
    return Result.ok(orderId);  
}
```

# 超卖问题

- 超卖问题是典型的多线程安全问题, 针对这一问题, 常见的解决方法就是加锁
- 悲观锁
	- 认为线程安全问题一定会发生, 因此在操作数据之前先获取锁, 确保线程串行执行
	- 悲观锁只能允许线程在临界区内一个个执行, 运行效率较差
	- 例如synchronized , Lock都属于悲观锁
- 乐观锁
	- 认为线程安全问题不一定会发生, 因此不加锁, 只是在**更新数据**时去判断有没有其他线程对数据做了修改
	- 如果没有修改则认为是安全的, 自己才更新数据
	- 如果已经被其他线程修改, 说明发生了安全问题, 此时可以重试或抛出异常
	- 所以乐观锁性能相对较好, 在高并发场景下通常使用乐观锁
	- 乐观锁由于容易发生冲突, 存在成功率低的问题, 在库存高并发场景下通常通过修改乐观锁条件对其进行调整

**乐观锁实现**
- 版本号法
	- 为需要被修改的数据添加版本号字段, 基于版本号判断数据是否有修改, 每修改一次, 就对数据的版本号字段+1
![[项目/黑马点评/Inbox/Pasted image 20250919135222.png]]
- CAS法 (Compare And Save)
	- 在修改前, 先对数据进行查询
	- 修改时, 判断要修改的数据和之前查询到的数据是否一致, 若已不一致, 说明被人修改过(SQL中加入where stock = 1)
- 缺点
	- 如果直接使用 `stock = 查询到的stock` 的方案, 会导致大量查询失败, 原因是因为很多时候库存确实大于0, 但是由于stock数量不匹配导致失败
	- 可以通过调整乐观锁条件, 不在要求其stock必须与先前查询到的值相等, 只要求stock大于0, 保证其可操作性即可
	- 对于不具有库存特征的需要加乐观锁的表, 通常使用分表加乐观锁的方法, 通过对小批次数据分别上锁, 降低乐观锁冲突几率

**代码示例(CAS法)**
- 使用MyBatisPlus实现
```java
boolean isSuccess = seckillVoucherService.update()  
        .setSql("stock = stock - 1")  
        .eq("voucher_id", voucherId)  
        .gt("stock", 0)  
        .update();
```

# 一人一单

**要求**
- 对于相同的秒杀商品, 一个用户只能下一单
- 由于下单操作属于插入数据, 无法对数据使用乐观锁, 只能对其使用悲观锁
- 悲观锁的使用亦有要求: 由于一人一单操作是对同一个用户的要求, 所以插入操作时的同一把锁不需要对所有用户添加, 只需要对相同的用户添加即可
- synchronized修饰符是对相同的对象加锁, 对于相同的用户的id, 其用于存储id的String对象或Integer对象在每一次都是不同的, 所以需要使用方法获取一个稳定的, 与id绑定的对象
- synchronized应该加在方法上, 因为方法由于存在多个SQL操作, 必须设置其事务, 但是如果使用synchronized块, 则会在事务结束前释放锁, 从而导致其他线程在数据更新前查询数据, 从而因数据不一致而引发超卖
- String类的intern方法, 可以返回对应字符串对象的规范表示, 即返回其在字符串池中的对象

**代码注意事项**
- Spring中的`@Transactional`事务操作是在反射的代理对象的基础上实现的
- this关键字指的是当前对象的非代理对象, 没有事务功能 (Spring事务失效几种经典场景之一)
- 通过获取事务代理方法获取代理对象并调用事务函数以解决, 该解决方法需要添加 `aspectjweaver` 依赖, 并在SpringBoot启动类中添加 `@EnableAspectJAutoProxy(exposeProxy = true)` 以暴露代理对象

# 分布式锁

**概念**
- 当使用分布式布局时, 由于会存在多个JVM, 导致 synchronized 锁失效
- synchronized 锁监视器是基于JVM常量池实现的, 当使用多个JVM实现分布式时, 就会存在多个常量池, 使得监视器失效
- 此时就需要一个独立于JVM存在的锁监视器, 使得无论是哪个JVM, 都可以获得相同的锁状态
- 分布式锁: 在满足分布式系统或集群模式下多进程可见并且互斥的锁
	- 多线程可见
	- 互斥
	- 高可用
	- 高性能
	- 安全性

 **常见实现方式**
 - 使用Redis实现分布式锁的两个方法
	 - 获取锁: 
		 - 互斥, 确保只有一个线程能够获取锁
		 - 为保证原子性, 可以只使用 `set k v ex x nx` , 同时添加key, 设置过期时间, 并在已有记录情况下不添加
		- 非阻塞式, 尝试一次, 成功返回true, 失败返回false
	 - 释放锁: 
		 - 手动释放, 删除对应记录即可
		 - 超时释放, 规定时间不删除则自动过期
![[项目/黑马点评/Inbox/Pasted image 20250919201105.png]]

**代码实现**
- 定义一个类, 实现ILock接口, 利用Redis实现分布式锁功能
```java
public interface ILock {  
    /**  
     * 尝试获取锁  
     * @param timeoutSec 锁持有的超时时间, 过期自动释放  
     * @return true代表获取锁成功, false代表失败  
     */  
    boolean tryLock(long timeoutSec);  
    /**  
     * 释放锁  
     */  
    void unlock();  
}
```
- Redis分布式锁实现类
```java
@Override  
public boolean tryLock(long timeoutSec) {  
    long threadId = Thread.currentThread().getId();  
    // 获取锁  
    Boolean success = stringRedisTemplate.opsForValue().setIfAbsent  
            (KEY_PREFIX + name, threadId + "", timeoutSec, TimeUnit.SECONDS);  
    return Boolean.TRUE.equals(success);  
}  
@Override  
public void unlock() {  
    stringRedisTemplate.delete(KEY_PREFIX + name);  
}
```
- 分布式锁的使用
```java
Long userId = UserHolder.getUser().getId();  
SimpleRedisLock simpleRedisLock = new SimpleRedisLock("order:" + userId, stringRedisTemplate);  
if (!simpleRedisLock.tryLock(5L)) {  
    return Result.fail("不可重复下单");  
}  
try {  
    IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();  
    return proxy.createVoucherOrder(voucherId);  
} catch (IllegalStateException e) {  
    throw new RuntimeException(e);  
} finally {  
    simpleRedisLock.unlock();  
}
```


### 分布式锁误删问题

**问题**
- 对于超时释放, 可能出现以下情况
- 当线程A获取到锁, 进行业务过程中发生了长时间阻塞, 以至于超过了超时时间, 由于超时, 锁被直接释放
- 锁被释放后, 线程B重新拿到了锁, 在线程B执行过程中, 线程A阻塞完成, 执行了释放锁的命令, 导致线程B的锁被释放
- 锁被释放后, 线程C重新拿到了锁, 此时线程B未执行完成, 出现同一时间线程B和线程C同时执行业务的问题

**解决**
- 解决问题的关键在于, 不要让线程能够任意的删除锁, 确保一个线程只能删除自己对应的锁
- 需求
	- 获取锁时, 存入线程标识(可以用UUID表示)
	- 释放锁时, 先获取锁中的线程标示, 判断是否与当前线程标示一致
		- 如果一致则释放锁, 不一致则不释放锁
	- 由于JVM之间线程id的生成相互独立, 所以使用随机UUID标示不同JVM
```java
private static final String KEY_PREFIX = "lock:";  
private static final String ID_PREFIX = UUID.randomUUID().toString(true) + "-";

@Override  
public void unlock() {  
    String threadId = ID_PREFIX + Thread.currentThread().getId();  
    String id = stringRedisTemplate.opsForValue().get(KEY_PREFIX + name);  
    if (threadId.equals(id)) {  
        stringRedisTemplate.delete(KEY_PREFIX + name);  
    }  
}
```

### 分布式锁释放阻塞

- 当判断分布式锁是否为本线程之后, 如果确认为本线程, 则开始执行删除操作
- 如果在删除操作之前, JVM A产生了阻塞, 如进行垃圾回收, 则会导致较长时间的延迟
- 如果在该JVM A阻塞时间内, 分布式锁过期并删除, 另一台JVM B试图获取锁并成功, 在持有锁的情况下进行业务操作
- 此时JVM A阻塞完成, 由于已经判断过, 则直接进行删除操作, 此时就会导致线程虽然了判断锁, 但是仍会删除JVM B获取的锁
- 想要解决这个问题, 实际上就是要保证判断和删除的原子性, 虽然可以使用乐观锁和Redis事务实现, 但是操作过程相对复杂, 所以在此使用Lua脚本进行操作

### Lua脚本
- Redis提供了Lua脚本的功能, 在一个脚本中编写多条Redis命令, 可以保证多条命令执行时的原子性
- Redis提供了用来调用命令的Lua函数
	- `redis.call('命令名称', 'key', '其他参数', ...)`
	- 如: `redis.call('set', 'name', 'Jack')`
- Redis提供了用来执行Lua脚本的命令
	- `eval 脚本 key参数数量`
	- 如果脚本中的key value不想写死, 可以作为参数传递
	- key类型参数会放入keys数组中, 其他参数会放入argv数组, 在脚本中, 可以通过这两个数组中获取参数(lua中下标从1开始)
	- 如: `EVAL "return redis.call('set', KEYS[1], ARGV[1])" 1 name Rose`
- 在RedisTemplate中, 使用如下API调用Lua脚本
	- `public <T> T execute(RedisScript<T> script, List<K> keys, Object... args)`

**释放锁脚本**
```lua
-- 获取锁中的线程标识
if(redis.call('get', KEYS[1]) == ARGV[1]) then
    -- 释放锁
    return redis.call('del', KEYS[1])
end
return 0
```

**基于Lua脚本的Java代码**
```java
private static final DefaultRedisScript<Long> UNLOCK_SCRIPT;  
static {  
    UNLOCK_SCRIPT = new DefaultRedisScript<>();  
    UNLOCK_SCRIPT.setLocation(new ClassPathResource("unlock.lua"));  
    UNLOCK_SCRIPT.setResultType(Long.class);  
}
@Override  
public void unlock() {  
    // 调用lua脚本  
    stringRedisTemplate.execute(  
            UNLOCK_SCRIPT,  
            Collections.singletonList(KEY_PREFIX + name),  
            ID_PREFIX + Thread.currentThread().getId());  
}
```



# Redisson分布式锁

- 基于Redis的setnx实现的分布式锁还存在以下问题
	- 不可重入: 同一个线程无法多次获取同一把锁(一个线程内获取到某锁后, 按理说该线程不再会被该锁阻拦, 但实际上仍会被阻止)
	- 不可重试: 获取锁只尝试一次就返回false, 没有重试机制
	- 超时释放: 锁超时释放虽然可以避免死锁, 但是如果是业务执行耗时较长导致的锁释放, 同样会造成安全隐患
	- 主从一致性: 如果Redis提供了主从集群, 主从同步存在延迟, 当主宕机时, 如果从并同步主中的锁数据, 则会出现锁实现
- Redisson是一个在Redis基础上实现的Java驻内存数据网络(In-Memory Data Grid). 
- 它不仅提供了一系列的分布式的Java常用对象, 还提供了许多分布式服务, 其中就包括了各种分布式锁的实现
	- 官网地址: https://redisson.pro GitHub地址: https://github.com/redisson/redisson

### 基础使用

- 使用Redisson分布式锁

```java
}
```

### Redisson锁可重入原理
- 可重复锁的基本原理, 就是在加锁时进行一个判断, 如果锁中记录的线程与当前试图获取锁的线程一致, 则直接放行
- 同一个线程多次进入锁时, 内部计数器会进行递增, 每次释放锁计数器递减, 直到计数器为0时, 对锁进行销毁
- Redisson中采用类似的原理, 使用Hash结构对变量进行存储, 分为field和value进行记录, field表示当前持有锁的线程, value表示锁的调用次数
- 整体流程复杂, 为保证原子性, 需要在lua脚本中进行实现, 详见Redisson源码
- 重入锁时需要对锁生存时间进行重置

### Redisson重试等待原理
- 在Redisson中, 如果传入了超时等待时间, 那么执行tryLock时, 在tryLock内部, 如果锁已被占用, 那么会返回一个剩余有效时间
- 通过该剩余有效时间, 会通过get函数进行阻塞等待, 等待完成后返回`ttl` , `ttl` 是该锁的剩余过期时间, 如果`ttl`为`null`, 说明获取锁成功, 否则检查剩余等待时间
- 如果还未超时, 则订阅释放锁的消息(unlock时会进行publish), 并进行剩余获取锁时间的等待, 如果在规定时间内没有等到该信号, 则取消对该信号的订阅, 并返回false
- 如果等到了该信号, 则首先对超时等待时间进行验证, 确保当前没有超时, 确保没有超时后, 进入循环尝试获取锁, 得到其`ttl` , 如果为null, 说明成功获取锁, 否则检查更新等待时间是否用完
- 如果第一次获取锁失败, 那么使用`ttl`和`time`中的较小量对释放锁信号做监听, 因为如果ttl小于time, 只需要等待锁过期时间即可, 否则就等待自己的time时间(锁可能由于释放而在ttl之前被销毁)
- 最后检查time, 确保未超时, 进入下一轮while循环重新尝试获取锁

### Redisson解决阻塞过期
- 在上锁时, 如果锁未设置过期时间, 则默认给予一个30s的过期时间, 调用`scheduleExpirationRenewal`函数, 只有不设置过期时间才能触发看门狗
将当前线程的唯一名称(通过函数生成)试图存入内部的`ConcurrentMap`中, 如果该线程是第一次加入, 则同时执行`renewExpiration`
- 在`renewExpiration`中, 主要创建了一个定时任务, 该任务的定时是锁释放时间的三分之一, 在该任务中, 会对锁的过期进行更新
- 当定时任务执行完毕后, 会触发函数`renewExpiration`, 即该函数本身, 从而实现持续刷新锁释放时间的目的 (**看门狗机制**)
- 当锁释放时, 会进行执行`cancelExpirationRenewal`函数, 对锁的定时更新进行取消, 会将该线程表示从内部的`ConcurrentMap`中移除, 以保证函数`renewExpiration`不再满足执行条件, 从而退出定时循环
- 即使因并发导致在函数中没能检查到不符合条件, 最终也会因不符合Lua原子操作中的if检查而返回0, 从而结束定时循环

### Redisson主从一致性问题
- Redis的主从模式, 本质上就是创建了多台Redis, 将其中一台作为主节点(Master), 其余服务器作为从节点(Slave)
- 主节点主要负责处理写操作, 从节点只负责处理读操作, 为保证主节点和从节点数据一致, 主节点会不断地向从节点发送数据, 这个过程即为主从同步
- 主从同步之间延时很短但是存在, 如果主Redis节点在主从同步时发生了宕机, 就会导致主从一致性问题的出现

**解决**
- Redisson通过取消主从关系的方式解决了主从一致性问题, 即不再设置主节点和从节点, 而是将所有节点都作为主节点使用, 客户端发送请求时, 必须依次向所有的节点发送相关信息, 从而避免了主从不一致
- 当某一台Redis节点宕机后, 其他Redis节点依然保存着完整的信息, 并且该体系的可靠性会随着加入Redis集群的节点数量的增多而提升, 对于一个试图获取锁的线程, 只有在每一个节点都获取到锁才算获取锁成功
- 如果想要进一步提高Redis集群的可用性, 还可以为每一台作为主节点的Redis主机都配备Redis从节点
- 这套方案在Redisson中被称为Multilock联锁
	- 在RedissonConfig中配置多个RedissonClient Bean
	- 使用不同的Bean分别创建多个锁
	- 使用 `redissonClient.getMultiLock(lock1, lock2, lock3)` 创建联锁

# Redis消息队列
- 消息队列 (Message Queue) , 字面意思就是存放消息的队列
- 最简单的消息队列包括三个角色
	- 消息队列: 存储和管理消息, 也被称为消息代理(Message Broker)
	- 生产者: 发送消息到消息队列
	- 消费者: 从消息队列获取消息并处理消息
- Redis消息队列的实现是独立于JVM的第三方, 不受JVM内存的限制, 并且消息会实现消息的持久化, 确保数据的安全, 且投递消息后要求消费者确认, 确保消息至少被消费一次
- Redis中提供了三种不同的方式实现消息队列
	- list结构: 基于List结构模拟消息队列
	- PubSub: 基本的点对点消息模型
	- Stream: 比较完善的消息队列模型

### 基于List模拟消息队列
- 消息队列是一个队列, 而Redis的list数据结构是一个双向链表, 很容易模拟出队列的效果
- 队列的入口和出口不在一边, 因此可以利用`LPUSH`结合`RPOP`或者`RPUSH`结合`LPOP`实现队列的效果
- 值得注意的是, 当队列中没有消息时进行RPOP或LPOP操作会直接返回null, 并不像JVM阻塞队列一样阻塞并等待消息, 因此应该使用`BRPOP`或者`BLPOP`实现阻塞的效果

**优点**
- 利用Redis存储, 不受限于JVM内存上限
- 基于Redis的持久化机制, 数据安全性有保证
- 可以满足消息的有序性
**缺点**
- 无法避免消息丢失
- 只支持单消费者

### 基于PubSub消息队列
- PubSub (发布订阅) 是Redis2.0版本后引入的消息传递模型
- 顾名思义 , 消费者可以订阅一个或多个channel, 生产者向对应channel发送消息后, 所有订阅者都可以收到相关消息
- `SUBSCRIBE channel [channel]` : 订阅一个或多个频道
- `PUBLISH channel msg` : 向一个频道发送消息
- `PSUBSCRIBE pattern [pattern]` : 订阅与pattern格式匹配的所有频道
- `SUBSCRIBE` 命令天生就是阻塞的

**优点**
- 采用发布订阅模型, 支持多生产, 多消费
- 支持阻塞读取数据
**缺点**
- 不支持数据持久化
- 没有确认机制, 无法避免消息丢失
- 无法进行消息回溯
- 消息堆积有上限, 超出时数据丢失

### 基于Stream的消息队列
- Stream是Redis5.0引入的一种新数据类型, 可以实现一个功能非常完善的消息队列

**特点**
- 消息可回溯
- 一个消息可以被多个消费者读取
- 消息可以阻塞读取
- 有漏读消息的风险

##### 基础

**命令**
- 写入消息队列: `XADD key [NOMAKESTREAM] [MAXLEN|MINID [=|~] threshold [LIMIT count]] *|ID field value [field value...]`
	- `NOMAKESTREAM` : 如果队列不存在, 是否创建队列, 默认不创建
	- `[MAXLEN|MINID [=|~] threshold [LIMIT count]]` : 设置消息队列的最大消息数量
	- `*|ID` : 指定消息的唯一ID, `*` 代表由Redis自动生成, 格式为 `时间戳-递增数字`, 建议使用 `*` , 由Redis自动生成
	- `field value...` : 发送到队列中的消息, 称为Entry, 格式就是多个键值对
	- 示例 : `XADD users * name jack age 21`
- 读取消息队列: `XREAD [COUNT count] [BLOCK milliseconds] STREAM key [key ...] ID [ID ...]`
	- `[COUNT count]` : 读取消息的最大数量
	- `[BLOCK milliseconds]` : 没有消息时是否阻塞, 0为永久阻塞
	- `key [key ...]` : 从哪个队列读取, key为队列名
	- `ID [ID ...]` : 起始id, 只返回大于该ID的消息
		- `0` : 代表从第一个消息开始
		- `$` : 代表从最新的消息开始
- Stream中的消息读完以后不会删除, 永久存在在队列中
- 当队列中所有值都读过以后, `$` 符指向的消息为 `nil` , 如果处理一条消息的过程中同时有多个消息到达, 就可能出现漏读消息的情况

##### 消费者组

**概述**
- 消费者组 : 将多个消费者划分到一个组中, 监听同一个队列, 具有以下特点
	- 消息分流: 队列中的消息会**分流**给组内的不同消费者, 而不是重复消费, 从而加快消息处理的速度
	- 消息标示: 消费者组会维护一个标示, 记录最后一个被处理的消息, 即使消费者宕机重启, 也会从标示之后读取消息. 确保每一个消息都会被消费
	- 消息确认: 消费者获取消息后, 消息处于pending状态, 并存入一个pending-list. 当消费者处理完消息后, 需要使用XACK确认消息, 标记该消息已处理, 随后才会从pending-list移除

**特点**
- 优点
	- 支持消息持久化
	- 消息可回溯
	- 可以多消费者争抢消息, 加快消费速度
	- 可以阻塞读取
	- 没有消息漏读风险
	- 有消息确认机制, 确保消息至少被消费一次
- 缺点
	- 消息持久化基于Redis实现, 无法保证持久化万无一失
	- 消息确认机制只支持消费者, 不支持生产者
	- 不支持消息的事务机制
	- 无法解决多消费者情况下的消息有序性

**命令**
- 创建消费者组: `XGROUP CREATE key groupName ID [MKSTREAM]`
	- `key`: 队列名称
	- `groupName`: 消费者组名称
	- `ID`: 起始ID标示, `$`标示队列中最后一个消息, `0`代表队列中第一个消息
	- `MKSTREAM`: 队列不存在时自动创建队列
- 删除指定的消费者组: `XGROUP DESTORY key groupName`
- 给指定的消费者组添加消费者: `XGROUP CREATECONSUMER key groupname consumername`
- 删除消费者组中的指定消费者: `XGROUP DELCONSUMER key groupname consumername`
- 从消费者组读取消息: `XREADGROUP GROUP consumer [COUNT count] [BLOCK milliseconds] [NOACK] STREAM key [key ...] ID [ID ...]`
	- `group`: 消费组名称
	- `consumer`: 消费者名称, 消费者不存在, 会自动创建一个消费者
	- `count`: 本次读取消息的最大数量
	- `BLOCK milliseconds`: 当没有消息时最长等待时间
	- `NOACK`: 无需手动ACK, 获得消息后自动确认 (不建议设置)
	- `STREAM key`: 指定队列名称
	- `ID`: 获取消息的起始ID
		- `>` : 从下一个未消费的消息开始(建议使用)
		- `其他` : 根据指定id从pending-list中获取已消费但未确认的消息, 例如0, 即为从pending-list中的第一个消息开始
- 确认消息: `XACK key group ID [ID...]`
- 查看pending-list中的消息: `XPENDING key group [[IDLE min-idle-time] start end count [consumer]]`
	- `[IDLE min-idle-time]` : 在pending-list中的等待时间
	- `start end` : 范围, `-` 代表最小, `+` 代表最大
	- `count` : 获取消息的数量
