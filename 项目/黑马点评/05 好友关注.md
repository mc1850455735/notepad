
# 关注和取关

- 对于关注功能, 前端需要两个接口
	- 判断是否关注用户
	- 尝试关注/取关用户
- 关注是User与User之间的关系, 需要使用一个中间表tb_follow记录

**代码实现**
- 判断是否关注
```java
@Override  
public Result isFollow(Long id) {  
    Long userId = UserHolder.getUser().getId();  
    // 1. 查询是否关注  
    Long count = query().eq("user_id", userId).eq("follow_user_id", id).count();  
    return Result.ok(count > 0);  
}
```
- 关注/取关
```java
@Override  
public Result follow(Long id, Boolean isFollow) {  
    UserDTO user = UserHolder.getUser();  
    // 判断是关注还是取关  
    if(isFollow) {  
        // 关注, 新增数据  
        Follow follow = new Follow();  
        follow.setUserId(user.getId());  
        follow.setFollowUserId(id);  
        save(follow);  
    } else {  
        // 取关, 删除数据  
        remove(new QueryWrapper<Follow>().eq("user_id", user.getId()).eq("follow_user_id", id));  
    }  
    return Result.ok();  
}
```

# 共同关注

- 利用Redis中恰当的数据结构实现共同关注功能
- 使用集合存储后取交集

**代码实现**
- 需要实现关注后同时加入Redis和MySQL数据库, 此处略
- 还需要使用Set交集获取交集用户id并查询, 代码如下
```java
@Override  
public Result followCommons(Long id) {  
    String keyPrefix = "follows:";  
    Long userId = UserHolder.getUser().getId();  
    Set<String> intersect = stringRedisTemplate.opsForSet().intersect(keyPrefix + userId, keyPrefix + id);  
    if(intersect.isEmpty() || intersect == null) {  
        return Result.ok(Collections.emptyList());  
    }  
    // 解析集合  
    List<Long> ids = intersect.stream().map(Long::valueOf).toList();  
    List<UserDTO> users = userService.listByIds(ids)  
            .stream()  
            .map(user -> BeanUtil.copyProperties(user, UserDTO.class))  
            .toList();  
    return Result.ok(users);  
}
```

# 关注推送

- 关注推流也叫Feed流, 为用户提供持续的沉浸式体验, 通过下拉获取新的信息
- 有两种常见的实现模式
- Timeline: 不做内容筛选, 简单的按照内容发布时间排序, 常用于好友或者关注, 比如朋友圈
	- 优点: 信息全面, 不会有丢失, 且实现相对简单
	- 缺点: 信息噪音较多, 用户不一定感兴趣, 获取内容效率低
- 智能排序: 利用智能算法屏蔽掉违规的, 用户不感兴趣的内容, 推送用户感兴趣信息来吸引用户
	- 优点: 投喂用户感兴趣信息, 用户粘度高, 容易沉迷
	- 缺点: 如果算法不精确, 可能起到反作用

**TimeLine实现方案**
- 拉模式: 读扩散, 每个人有一个发件箱和一个收件箱
	- 用户发出的内容存在发件箱中, 当用户查看关注的人信息时, 从关注的人的发件箱中拉取消息到收件箱
	- 该模式只保存一份消息, 比较节省内存空间
	- 但是每次读取都需要重新拉取消息并排序, 耗时较多
- 推模式: 写扩散, 每个用户都有一个收件箱
	- 当一个用户发消息时, 该消息会直接发送到关注他的用户的收件箱中, 所以又叫推模式
	- 优点是读取时直接取自己的收件箱即可, 耗时较低
	- 缺点是每个人都要存储对应的消息副本, 占用内存较多
- 推拉模式: 读写混合模式, 兼具推和拉两种模式的优点. 
	- 将发件人按粉丝数量分为两类, 对于粉丝较多的(以下称大V)用户创建单独的发件箱, 对于普通用户不创建发件箱, 大V发消息时, 直接发到发件箱中, 普通用户推模式推到粉丝收件箱中. 
	- 将收件人按活跃程度分为两类, 对于普通用户, 仅当试图读取时, 再从大V的发件箱中读取, 对于活跃粉丝, 则直接将大V发送的消息推送到收件箱中, 保证了活跃粉丝读取时的低延迟

**代码实现推模式**
- 修改新增探店笔记的业务, 在保存blog到数据库的同时, 推送到粉丝的收件箱
- 收件箱满足可以根据时间戳排序, 必须使用Redis的数据结构实现
- 查询收件箱数据时, 可以实现分页查询

**滚动分页**
- 由于Feed流中的数据会不断更新, 所以数据的角标也在时刻变化, 所以不能使用传统的分页方式, 需要使用滚动分页, 不按角标查询, 而是按分数查询
- 对于按时间排序的队列, 其最大值就是当前时间戳, 使用如下命令求前5个值: `zrevrangebyscore z1 now 0 withscores limit offset count`
- 对于时间戳重复的推文, 不能直接设置offset为1, 而是要对上一页查询中最小值数量进行统计, 有几个最小值, 就将offset设为几

**推送**
```java
@Override  
public Result saveBlog(Blog blog) {  
    // 获取登录用户  
    UserDTO user = UserHolder.getUser();  
    blog.setUserId(user.getId());  
    // 保存探店博文  
    boolean isSuccess = save(blog);  
    if(!isSuccess) {  
        return Result.fail("新增笔记失败");  
    }  
    // 将博文推送到粉丝的收件箱中  
    // 获取粉丝列表  
    List<Follow> follows = followService.query().eq(  
            "follow_user_id", user.getId()  
    ).list();  
    for (Follow follow : follows) {  
        Long fanId = follow.getUserId();  
        // 推送笔记  
        String key = "feeds:" + fanId;  
        stringRedisTemplate.opsForZSet().add(key, blog.getId().toString(), System.currentTimeMillis());  
    }  
    // 返回id  
    return Result.ok(blog.getId());  
}
```

**请求**
- 参数: 上次查询的最小时间戳, 偏移量offset
- 返回值: 笔记集合, 本次查询的最小时间戳, 偏移量offset(根据最小时间戳推文的数量进行确定)
```java
@Override  
public Result queryBlogOfFollow(Long max, Long offset) {  
    // 获取当前用户  
    UserDTO user = UserHolder.getUser();  
    String key = FEED_KEY + user.getId();  
    // 查询收件箱  
    Set<ZSetOperations.TypedTuple<String>> typedTuples =  
            stringRedisTemplate.opsForZSet()  
                    .reverseRangeByScoreWithScores(key, 0, max, offset, 2);  
    // 非空判断  
    if(typedTuples == null || typedTuples.isEmpty()) return Result.ok();  
    // 解析数据: blogId, minTime, offset  
    List<Long> ids = new ArrayList<>(typedTuples.size());  
    long minTime = 0;  
    int newOffset = 1;  
    for (ZSetOperations.TypedTuple<String> tuple : typedTuples) {  
        // 获取id  
        String idStr = tuple.getValue();  
        ids.add(Long.valueOf(idStr));  
        long time = tuple.getScore().longValue();  
        if(time == minTime) {  
            newOffset++;  
        } else {  
            newOffset = 1;  
            // 最后一个元素时间一定是最小值  
            minTime = time;  
        }  
    }  
    // 根据id查询blog  
    String idStr = StrUtil.join(",", ids);  
    List<Blog> blogs = query().in("id", ids).last("order by field(id, " + idStr + ")").list();  
    // 填充blog内容  
    blogs.forEach(blog -> {  
        queryBlogUser(blog);  
        isBlogLiked(blog);  
    });  
    // 封装并返回  
    ScrollResult result = new ScrollResult();  
    result.setList(blogs);  
    result.setOffset(newOffset);  
    result.setMinTime(minTime);  
    return Result.ok(result);  
}
```
