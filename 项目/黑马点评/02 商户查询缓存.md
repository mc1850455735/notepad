
## 概述

- 缓存是数据交换的缓冲区(Cache) , 是存储数据的临时地点 , 一般读写性能较高
- 缓存的作用
	- 降低后端负载
	- 提高读写效率, 降低响应时间
- 缓存的成本
	- 数据一致性成本
	- 代码维护成本
	- 运维成本

**代码**

- 使用String存储
```java
@Override  
public Result queryById(Long id) {  
    String redisKey = RedisConstants.CACHE_SHOP_KEY + id;  
    // 1. 从redis查询商户缓存  
    String shopJson = redisTemplate.opsForValue().get(redisKey);  
    if(StrUtil.isNotBlank(shopJson)) {  
        // 2. 存在则直接返回  
        Shop shop = BeanUtil.toBean(shopJson, Shop.class);  
        return Result.ok(shop);  
    }  
    // 3. 不存在, 根据id查数据库  
    Shop shop = getById(id);  
    if(shop == null) {  
        // 4. 不存在, 返回错误  
        return Result.fail("商铺不存在");  
    }  
    // 5. 存在, 写入redis并返回  
    shopJson = JSONUtil.toJsonStr(shop);  
    redisTemplate.opsForValue().set(redisKey, shopJson);  
    return Result.ok(shop);  
}
```
- 使用List存储
```java
@Override  
public Result queryList() {  
    String shopTypeListKey = RedisConstants.CACHE_SHOP_KEY + "list";  
    // 1. 从redis查询商户缓存  
    List<String> shopTypeJsonList = 
    stringRedisTemplate.opsForList()
                       .range(shopTypeListKey, 0, -1);  
    if(!shopTypeJsonList.isEmpty()) {  
        // 2. 存在则直接返回  
        List<ShopType> shopTypeList = 
        shopTypeJsonList.stream()
        .map(json -> JSONUtil.toBean(json, ShopType.class))
        .collect(Collectors.toList());  
        return Result.ok(shopTypeList);  
    }  
    // 3. 不存在则查询数据库  
    List<ShopType> shopTypeList = list();  
    // 4. 数据库中不存在则报错(不太可能)  
    if(shopTypeList == null) {  
        return Result.fail("不存在任何商户类型");  
    }  
    // 5. 数据库中存在, 则保存到Redis并返回  
    for(ShopType shopType : shopTypeList) {  
        String jsonStr = JSONUtil.toJsonStr(shopType);  
        stringRedisTemplate.opsForList()
            .rightPush(shopTypeListKey, jsonStr);  
    }  
    return Result.ok(shopTypeList);  
}
```

# 缓存更新策略

- 如果数据库中的数据发生了变化, 而缓存中没有对此做出反应, 就会导致缓存与数据库中产生数据不一致的问题

**常见策略**
- 内存淘汰
	- 不用自己维护, 利用redis内存淘汰机制, 当内存不足时主动淘汰部分数据, 下次查询时更新缓存
	- 一致性差, 维护成本无
- 超时剔除
	- 给缓存数据添加TTL时间, 到期后自动删除缓存, 下次查询时更新缓存
	- 一致性一般, 维护成本低
- 主动更新
	- 编写业务逻辑, 在修改数据库的同时, 更新缓存
	- 一致性好, 维护成本高

**业务场景**
- 低一致性场景 : 使用内存淘汰机制, 如店铺类型查询缓存
- 高一致性场景 : 主动更新, 并以超时机制进行兜底, 如店铺详情查询的缓存

**主动更新策略**
- Cache Aside Pattern (常用)
	- 由缓存的调用者在更新数据库的同时更新缓存
	- 尽管需要调用者自己编码进行同步, 但是可控性好, 可靠性高
- Read/Write Through Pattern
	- 缓存和数据库整合成为一个服务, 由服务来维护一致性
	- 调用者只需要调用服务, 无需关心缓存一致性问题
- Write Behind Caching Pattern
	- 调用者只操作缓存, 由其他线程**异步的**将缓存数据持久化到数据库, 最终保持一致

**缓存与数据库同步**
- 删除缓存还是更新缓存
	- 更新缓存 : 每次更新数据库的同时更新缓存, 可能包含无效写操作
		- 无效写操作 : 
		- 对缓存更新了, 但是缓存不被读, 导致对缓存的更新没有意义; 
		- 对数据库多次更新, 多次更新中缓存不被访问, 对缓存的写没有意义
	- 删除缓存 : 每次数据库更新时, 直接删除对应条目的缓存, 待下次查询后, 再对缓存进行更新
- 如何保证更新数据库和更新缓存的同成功或同失败
	- 单体系统 : 将缓存和数据库操作放在一个事务
	- 分布式系统 : 利用TCC等分布式事务方案
- 先操作缓存还是先操作数据库
	- 先删缓存再操作数据库
	- 先操作数据库再删缓存 (最佳)
	- 二者都可能会导致数据库和缓存不一致的情况, 但是其概率是不同的
	- 数据库操作慢, 缓存操作快, 导致先操作数据库不同步概率远低于先删除缓存

# 缓存穿透

**概念**
- **缓存穿透**指的是客户端请求的数据在缓存中和数据库中都不存在, 这样的缓存永远都不会生效, 所有请求都会达到数据库

**解决**
- 缓存空对象 (常用)
	- 优点 : 实现简单, 维护方便
	- 缺点 : 额外消耗内存, 可能造成短期内的数据不一致(比如刚缓存完空就插入了一个真正存在的记录)
- 布隆过滤
	- 在客户端与缓存之间添加一个中间层布隆过滤器 , 过滤器查询id不存在则直接拒绝, 只有确定id存在, 才会真正在缓存中进行查询
	- 布隆过滤器并不一定是100%准确, 如果认为不存在那么必定不存在, 但是认为存在则不一定真实存在
	- 优点: 内存占用少, 没有多余key
	- 缺点: 实现复杂, 存在误判可能
- 增强id复杂度, 避免被猜测id规律
- 做好数据的基础格式校验
- 加强用户权限校验
- 做好热点参数限流

**示意图**
![[项目/黑马点评/Inbox/Pasted image 20250917123013.png]]

**代码**
```java
@Override  
public Result queryById(Long id) {  
    String redisKey = RedisConstants.CACHE_SHOP_KEY + id;  
    String shopJson = redisTemplate.opsForValue().get(redisKey);  
    if(StrUtil.isNotBlank(shopJson)) {  
        // 2. 存在则直接返回  
        Shop shop = BeanUtil.toBean(shopJson, Shop.class);  
        return Result.ok(shop);  
    }  
    // 如果查询到的结果为空字符串, 则直接返回  
    if(shopJson != null) {  
        return Result.fail("店铺信息不存在");  
    }
    // 3. 不存在, 根据id查数据库  
    Shop shop = getById(id);  
    if(shop == null) {  
        // 4. 不存在  
        // 将空值写入redis  
        redisTemplate.opsForValue().set(redisKey, "", RedisConstants.CACHE_NULL_TTL, TimeUnit.MINUTES);  
        // 返回错误信息  
        return Result.fail("商铺不存在");  
    }  
    // 5. 存在, 写入redis并返回  
    shopJson = JSONUtil.toJsonStr(shop);  
    redisTemplate.opsForValue().set(redisKey, shopJson, RedisConstants.CACHE_SHOP_TTL, TimeUnit.MINUTES);  
    return Result.ok(shop);  
}
```

# 缓存雪崩

**概念**
- 缓存雪崩是指在同一时间段内大量的缓存key同时失效或者Redis服务器直接宕机, 导致大量请求直接到达数据库, 为数据库带来巨大压力
- 详情见SpringCloud相关课程

**解决方案**
- 给不同的key的TTL添加随机值
- 利用Redis集群提高服务的可用性
- 给缓存业务添加降级限流策略
- 给业务添加多级缓存

# 缓存击穿

**概念**
- 缓存击穿也叫热点Key问题, 就是一个被高并发访问且缓存重建业务较复杂的Key突然失效, 导致大量请求访问瞬间给服务器带来巨大冲击

**解决方案**
- 互斥锁
	- 设置锁, 使只有一个线程可以重建缓存, 其他线程循环等待
	- 优点 : 逻辑清晰, 实现简单, 没有额外内存消耗, 一致性强
	- 缺点 : 阻塞过程线程必须循环等待, 性能受影响, 存在死锁风险
- 逻辑过期
	- 不为关键Key设置真正的过期时间, 而是为其设置逻辑过期字段
	- 查询时, 如果发现已经逻辑过期, 则设置锁, 建立一个新的线程用来对其进行重建, 原线程直接返回旧的数据
	- 如果发现重建缓存已经被上锁, 则也返回过期数据
	- 优点 : 线程无需等待, 性能较好
	- 缺点 : 不保证一致性, 有额外内存消耗且实现复杂

**互斥锁代码示例**
- 对缓存操作的锁与Java中的默认锁概念不同, 所以应该由用户自定义
- 可以借助Redis中的 `setnx` 命令进行上锁操作, 该命令只会在key不存在时进行操作, 如果存在则不执行任何操作
- 通常会给锁字段添加一个TTL, 保证锁即使在相关线程出现故障而无法释放的情况下依然可以自动强制释放
- `Spring` 中的setnx函数为 `setIfAbsent`
```java
private Boolean tryLock(String key) {  
    Boolean aBoolean = 
        redisTemplate.opsForValue().setIfAbsent(key, "1", RedisConstants.LOCK_SHOP_TTL, TimeUnit.SECONDS);  
    return BooleanUtil.isTrue(aBoolean);  
}  
  
private void unlock(String key) {  
    redisTemplate.delete(key);  
}  
  
private Shop queryWithMutex(Long id) {  
    String redisKey = RedisConstants.CACHE_SHOP_KEY + id;  

    String shopJson = redisTemplate.opsForValue().get(redisKey);  
    if(StrUtil.isNotBlank(shopJson)) {  
        return BeanUtil.toBean(shopJson, Shop.class);  
    }  
    if("".equals(shopJson)) {  
        return null;  
    }  
  
    // 实现缓存重建  
    String lockKey = RedisConstants.LOCK_SHOP_KEY + id;  
    Shop shop = null;  
    try {  
        // 退避自旋锁
        while(!tryLock(lockKey)) {  
            // 进行延时退避, 提高CPU利用率
            Thread.sleep(50);  
        }  
        // 如果重新获取到锁了, 则应重新检查一下redis中是否已有记录  
        // 因为可能在尝试获取锁的同时redis更新完毕  
        shopJson = redisTemplate.opsForValue().get(redisKey);  
        if(StrUtil.isNotBlank(shopJson)) {  
            return BeanUtil.toBean(shopJson, Shop.class);  
        }  
        if("".equals(shopJson)) {  
            return null;  
        }  
        shop = getById(id);  

        // 模拟重建延时  
        Thread.sleep(200);  
  
        if(shop == null) {  
            redisTemplate.opsForValue().set(redisKey, "", RedisConstants.CACHE_NULL_TTL, TimeUnit.MINUTES);  
            return null;  
        }  
        shopJson = JSONUtil.toJsonStr(shop);  
        redisTemplate.opsForValue().set(redisKey, shopJson, RedisConstants.CACHE_SHOP_TTL, TimeUnit.MINUTES);  
    } catch (InterruptedException e) {  
        throw new RuntimeException(e);  
    } finally {  
        // 释放互斥锁  
        unlock(lockKey);  
    }  
    return shop;  
}
```
