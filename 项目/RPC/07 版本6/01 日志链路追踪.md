# 概述

### 概念
- 在分布式系统中, 一个业务请求往往需要通过多个 RPC 服务节点进行处理, 当出现下列需求时
	- 跨服务异常定位
	- 请求响应时间突增, 需定位性能瓶颈
	- 需要分析完整调用链路行为
- 传统离散的日志记录方式难以满足需求, 需要一种贯穿调用链路的处理方案

### TraceId

**定义**
- TraceId 是一个全局唯一的标识符, 用于标识一个完整的请求链路. 
- 当一个请求进入分布式系统后, 系统会为该请求生成一个唯一的 TraceId, 并将其在整个请求处理过程中传递下去
- 无论这个服务在分布式系统中经过了多少个服务节点, 只要是处理同一个请求, 就会使用相同的 `traceId`

### SpanId

**定义**
- SpanId 是一个局部唯一标识符, 用于标识一个请求在某个服务节点内的一次调用. 一个 Trace 内可以包含多个 Span, 每个 Span 代表了请求在某个服务节点内的一个操作或子任务

# 链路信息生成与保存

### 生成原则

- 在分布式追踪系统中, TraceId 时用于唯一标识一个完整调用链的全局标识符
- **TraceId设计原则**
	1. 全局唯一性: 整个分布式系统中, 每个 TraceId 都必须唯一
	2. 高效生成: 生成 id 算法性能要搞, 避免成为系统性能瓶颈
	3. 可读性: 尽量保证 TraceId 生成的字符串可读

### 常见生成算法

**UUID**
- 利用 `UUID` 算法生成全局唯一的字符串
- **优点**
	- 简单, 无需额外依赖项, 满足唯一性
- **缺点**
	- 字符串较长, 可能影响日志可读性

**Snowflake**
- Twitter 开源的分布式 ID 生成算法, 生成64位长整型, 可转为16位
- `1 + 41位时间戳 + 10位机器ID + 12位序列号`
- **优点**
	- 高性能, 有序, 分布式唯一
- **缺点**
	- 需分配机器Id, 需处理时钟回拨

### 定义结构保存链路信息

- 对于日志链路中的 TraceId, SpanId 等信息, 应该使用一个数据结构, 使在存储信息的同时, 保证不同线程和链路中各自独立的稳定保存和传递
- 常用的解决方案是使用 SLF4J 的 MDC (Mapped Diagnostic Context), 是一个线程本地的映射, 用于在日志记录时提供额外的上下文信息
- MDC内部维护了一个 ThreadLocal 变量, 存储每个线程的MDC上下文信息

# 日志链路数据上报与可视化

### 概述
- 实现调用链可视化时, 需要先将日志追踪数据发送到一个分布式追踪系统, 如 Zipkin 或者 Jaeger, 通过这些系统UI界面查看调用链可视化结果

### 设计思路

- **数据格式**
	- 调用链数据需要符合分布式追踪系统的数据格式 (如 Json)
	- 每个调用链的节点需要包含以下信息
		- traceId: 调用链全局唯一id
		- spanId: 当前 Span 节点唯一id
		- parentId: 父 Span 节点的id
		- name: 当前 Span 名称
		- timestamp: Span 开始调用时的时间戳
		- duration: Span 持续时间
		- tags: 附加信息, 如请求参数, 响应状态等
- **数据上报**
	- 每个 Span 结束后, 将数据发送到分布式追踪系统
	- 可以通过 Http 或 消息队列 (如 Kafka) 来实现这个过程
- **调用链可视化**
	- 使用 Zipkin 或者 Jaeger 的 UI界面 查看调用链的可视化信息
	- UI中会展示调用链内每个服务的调用顺序, 耗时, 层级关系等信息

### 数据上报与拦截器

**定义ZipkinReport类**
- 在 core 项目中的 trace 包下, 创建 ZipkinReporter 类, 封装与 Zipkin 的交互

**定义客户端和服务端拦截器类**
- 定义在在 core 项目中的 trace.interceptor 包下
- 对于客户端
	- `beforeInvoke()` 调用函数前, 用于初始化和保存日志链路数据
	- `afterInvoke()` 调用函数后, 用于上报日志链路数据
- 对于服务端
	- `beforeHandler()` 处理请求前, 用于获取和生成链路数据
	- `afterHandler()` 处理请求后, 用于上报链路数据

**调用拦截器**
- 无论是客户端还是服务端, 都可以在其 Netty 处理链中的自定义 Handler 的实现中, 添加对应的拦截器方法
- 对于客户端, 在发起请求前设置 TraceId 和 SpanId, 请求返回时上报日志数据
- 对于服务端, 在接收请求的入口获取数据, 返回响应数据前上报日志数据

### 日志传递

**概述**
- 在客户端生成的 TraceId 等信息, 需要被传递到服务端, 服务端获取后在 TraceContext 中持有对应的 TraceId.
- 对应的 C-S 之间的传递, 可以通过 netty 中的编解码器实现, 类似于 Http, 在消息头增加一段 trace 消息头, 并存放到 TraceContext 中
- 在 common 项目下的 serializer.mycoder 包中. 在 MyEncoder 中获取当前的 traceId 和 spanId, 存入消息头; 在 MyDecoder 中按格式解析写入的 traceId 和 spanId, 将其存放到服务端的 TraceContext 中

**问题**
- Netty 是一个多线程网络通信框架. 在 Netty 中, 用于发起请求的主线程和用于建立和维护网络 IO 的 Channel 不属于同一个线程, 而 MDC 将其 TraceId 和 SpanId 存储在其维护的 ThreadLocal 中.
- 所以, 为了在发送数据时也可以使用 MDC 中的数据, 应当在主线程中手动将 MDC 的数据同步给 netty 发送的 MDC, 从而达到传递 Netty 信息的目的
- 使用 Netty 中 Channel 的属性将不同线程的 MDC 进行传递
