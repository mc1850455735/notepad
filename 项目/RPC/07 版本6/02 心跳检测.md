
# 概念

### 问题
- 在 Client 进行请求发送时, 不能在发送完毕后直接关闭 eventLoop, 否则接下来所有的请求都将无法处理
- 但是也需要及时维护 C-S 直接的连接, 避免客户端和服务端之间出现大量的连接资源占用浪费情况
- 因此引入 Netty 心跳检测实现动态资源维护

### 概念
- 心跳检测时用于保障服务端与客户端之间通信连接状态的实时监控
- 客户端不断向服务端中发送心跳包, 服务端在一定时间范围内如果能够正常接收客户端的心跳包, 就认为连接正常活跃
- 如果服务端一段时间内没有接收到客户端心跳包, 认为连接出现中断或异常, 则进行连接断开, 释放资源等操作, 节省了服务端连接资源

### 相关 Netty 类

**IdleStateHandler**
- 主要有三个关键参数
	- 读空闲时间: `readerIdleTime / readerIdleTimeSeconds`
	- 写空闲时间: `writerIdleTime / writerIdleTimeSeconds`
	- 读写空闲时间: `allIdleTime / allIdleTimeSeconds`
- 如果对某一个参数不感兴趣, 只需要将对应参数设置为0即可

**触发事件**
- 当通道有一段时间没有执行读取或写入时, 即一段事件未满足内条件时, 触发预先设置好的 `IdleStateEvent`
- 没有读操作, 触发 `IdleState.READER_IDLE` 事件
- 没有写操作, 触发 `IdleState.WRITER_IDLE` 事件
- 没有读写操作, 触发 `IdleState.ALL_IDLE` 事件

**处理事件**
- 当触发上述对应事件后, 需要对其接收并进行处理
- 通过重写 `handler` 中的 `userEventTriggered` 方法, 进行事件处理

# 优化关闭逻辑

**概述**
- 将 `NettyRpcClient` 中 `finally` 模块的 `shutdown` 方法移除
- 无需在流程内部执行关闭逻辑, 而是外部执行 `close` 后统一关闭所有资源
- 对 `ZKServiceCenter` 和 `ClientProxy` 也通过 `close` 方法实现外部关闭客户端, `ClientProxy` 的 close 中调用 `NettyRpcClient` 和 `ZKServiceCenter` 的 `close`

**步骤**
- 首先, 在 `RpcClient` 接口中新增 `close` 方法
- 在 `NettyRpcClient` 中以 `eventLoopGroup.shutdownGracefully().sync()` 的调用为核心, 实现 `close` 方法, 优雅的关闭 `eventLoopGroup`
- 在调用端结束前, 手动调用 `clientProxy.close()` 关闭

# Handler实现

**服务端Handler**
- 服务端关注读空闲事件和写空闲事件, 即如果服务端10秒之内没有收到客户端的心跳包, 或者20秒之内没有发送数据, 则关闭与客户端的连接
- 首先, 新定义一个 `HeartbeatHandler` 类, 用于处理 `IdleStateEvent` 事件, 服务端关注读空闲事件和写空闲事件, 触发事件时, 关闭与客户端之间的连接
- 在 `NettyServerInitializer` 中, 添加触发事件处理器 `IdleStateHandler` , 并添加处理事件处理器 `HeartbeatHandler` 

**客户端Handler**
- 客户端只关注写空闲事件, 如果8秒内没有写操作, 则触发写空闲事件, 向服务端发送心跳包
- 客户端中, 同样新增 `HeartbeatHandler` 类, 若超8秒没有写数据, 则向服务端发送心跳包, 维持与服务端之间的联系
- `NettyClientInitializer` 中添加 `HeartbeatHandler` 和 `IdleStateHandler`

# 心跳消息类型

- 为 Request 添加属性 type, 表示该请求是一个心跳包还是普通包
- 在 common.message 包中新添加枚举类 `RequestType` 表示请求的类型
- 服务端中, 通过请求类型, 判断其作为心跳包或是普通包, 如果是心跳包, 则不作处理
