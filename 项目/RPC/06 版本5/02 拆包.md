# krpc-api

**概述**
- 将原本pojo包内的服务调用相关的类拆分到此包中
- 即 User 类和 UserService 类

# krpc-common

**概述**
- 将共性的工具类放置在该项目中
- 通常包括: 序列化类, 工具类, 消息类型, 异常类型等

**概述**
- 将核心功能类放置在该项目中
- 通常包括: 缓存类, 熔断类, 网络类, 代理类, 重试类等

# krpc-consumer

**概述**
- 将 TestClient 抽取出来, 并更名为 ConsumerTest
- 将 api 和 core 作为依赖导入
- 将其中的并发测试部分由新建线程类改为使用线程池

**线程池优势**
- **避免频繁创建和销毁线程**: 每次调用 `new Thread()` 都会额外的创建一个新的线程并启动, 操作系统和 JVM 每次都要为该线程分配一次资源;
	- **性能开销**: 线程的创建和销毁都需要系统的资源, 这可能会带来性能问题, 尤其是在高并发的场景下
	- **资源浪费**: 频繁创建和销毁线程会占用大量的内存和CPU时间, 尤其是线程数量非常多的时候, 可能导致系统资源枯竭
	- **线程池**: 通过复用线程避免了每次创建新的线程, 更高效的利用系统资源, 减少了线程创建和销毁的开销
- **控制并发量**
	- 当并发请求的数量过多时, 直接创建大量线程可能导致系统过载. 线程池可以通过控制最大线程数来限制并发量, 避免系统崩溃或响应变慢
	- 线程池还可以根据任务的执行情况动态调整线程数, 实现高效资源利用
	- 线程池允许通过参数 `nThread` 设置一个最大线程数, 从而避免超出系统的并发能力, 保证系统的稳定性
- **更好的资源管理**
	- 线程池会管理线程的生命周期, 包括线程的创建, 销毁和调度等.
	- 通过对线程池的配置, 可以实现对线程的精细控制, 避免线程数量过多而导致的系统资源被耗尽等问题
- 若不使用线程池, 如果不能合理的控制线程数量, 可能导致
	1. 线程饥饿: 系统可能无法及时处理所有线程, 导致线程一直处于等待状态
	2. 线程阻塞: 系统资源耗尽时, 线程会一直阻塞等待, 导致响应超时
