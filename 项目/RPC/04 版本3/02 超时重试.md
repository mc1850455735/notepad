# 概述

**概念**
- 对于一次RPC调用, 可能因网络波动出现丢包等问题, 导致请求失败, 此时的RPC应该具有失败重试机制, 保证系统的容错率

**实现**
- Java 中存在多种重试方式, 如手动重试, Spring Retry, Guava Retry等
- 这里选择使用 Guava Retry 进行超时重试操作

**白名单实现幂等性**
- 幂等性, 指的是同一个操作无论执行多少次, 最终产生的业务结果都完全相同
- 在因各类原因进行的请求重新发送的过程中, 保证业务幂等性是重要一环, 否则在处理因网络波动而导致的两次相同请求时, 其结果会与正常情况不同
- 在本项目中, 使用白名单机制进行幂等性标记. 在服务端进行节点注册时, 将幂等性的服务添加到白名单中, 客户端请求服务时, 先查看该服务是否是一个幂等服务, 如果是, 则使用重试机制进行调用

# guavaRetry

### 重试机制设置

**重试时机**
- `retryIfExpection()` : 设置对所有异常进行重试
- `retryIfRuntimeExpection()` : 设置对所有 RuntimeException 进行重试
- `retryIfExceptionOfType()` : 设置对指定类型异常进行重试
- `retryIfResult()` : 设置对不符合预期的结果进行重试

**重试策略**
- `withRetryListener()` : 设置重试监听器, 执行额外的处理工作
- `withWaitStrategy()` : 重试等待策略
- `withStopStrategy()` : 停止重试策略
- `withAttemptTimeLimiter()` : 设置任务单次执行的时间限制, 超时则抛出异常
- `withBlockStrategy()` : 设置任务阻塞策略, 即当前重试完成, 下次重试开始的时间间隔内需要进行的任务

### 异常重试实现

**作用**
- 异常重试机制主要通过 `sendServiceWithRetry` 函数进行定义, 该方法用来发送一个RPC请求, 并在发生某些特定情况时自动进行重试
- 该函数封装了发送请求的过程, 并通过 Guava Retry 库实现了重试机制, 方法接收两个参数: `RpcRequest` 表示要发送的请求, `RpcClient` 表示使用的客户端

**实现**
- 使用 Guava Retry 库实现对 RPC 请求的重试机制. 通过设置重试策略, 可以在发生异常或者服务器返回特定错误时, 尝试重新发起请求
- `retryer` 是 `Retryer<RpcResponse>` 类型的变量, 通过 `RetryerBuilder` 中提供的 `newBuilder()` 方法配置重试的策略
- 通过 `retryer.call` 方法, 执行实际的 RPC 请求, 并进入重试. 传入的 Lambda 表达式表示要执行的操作, 表达式的返回值类型与 `retryer` 的泛型类型一致; 如果请求成功且返回结果不满足重试条件, 则 `call` 方法返回该结果
- 通过 catch , 捕获 call 方法执行过程中的异常, 如达到最大重试次数且所有重试都失败, 并将报错的堆栈信息打印输出; 且当所有操作执行完毕没有返回正确的结果时, 则通过 `RpcResponse.fail()` 静态方法返回失败

### 重试策略构建

- 通过 builder, 创建一个新的 Retryer 构建器, 用于配置重试逻辑
```java
RetryerBuilder.<RpcResponse>newBuilder()
```
- 当RPC请求抛出任何异常时进行重试. 如果希望指定限制特定类型的异常进行重试, 则可以使用 `retryIfExceptionOfType()` 指定具体类型异常
```java
retryIfException()
```
- 当RPC请求的响应结果响应码为 `500`, 即服务器错误, 则认为该请求出现了问题, 需要进行重试. 此处使用 Lambda 表达式进行响应的条件判断
```java
retryIfResult(response -> Objects.equals(response.getCode(), 500))
```
- 设置重试等待策略, `fixedWait(2)` 表示每次重试后固定等待2s
```java
withWaitStrategy(WaitStrategies.fixedWait(2, TimeUnit.SECONDS))
```
- 设置重试停止策略. `stopAfterAttempt(3)` 表示重试次数最大为3次
```java
withStopStrategy(StopStrategies.stopAfterAttempt(3))
```

### 监听器
- 这段代码为 `Guava Retry` 库 的 `Retryer` 类型对象配置了一个重试监听器, 即 `RetryListener` 重试监听器. 
- `withRetryListener` 用于为 `Retryer` 配置重试监听器, 重试监听器允许每次重试时执行自定义操作, 如记录日志, 统计重试次数等
- `RetryListener` 是一个接口, 内部实现一个 `onRetry` 方法.
- `onRetry` 方法在每次重试时被触发, 并传递一个 `Attempt` 类型的对象作为参数. `Attempt<V>` 是 `Guava Retry` 库中表示一次尝试的对象, V 表示重试操作返回的类型. 其中包含重试次数, 是否成功, 上次请求结果等
```java
withRetryListener(new RetryListener() {
    @Override
    public <V> void onRetry(Attempt<V> attempt) {
        System.out.println("RetryListener: 第" + attempt.getAttemptNumber() + "次调用");
    }
})
```

# ZKServiceCenter部署重试

### 设置白名单
- 服务端中注册服务节点时, 在注册函数中手动传入该服务是否实现幂等性
- 若服务是幂等的, 则在 `Zookeeper` 的 `RETRY` 节点中加入对应的服务名
- 需要判断幂等时, 从 `zookeeper` 中访问对应路径, 查看是否存在对应的服务名称, 借助 `zookeeper` 实现远程白名单功能

### checkRetry方法
- 传入欲检查的服务名, 使用该方法, 判断这个服务是否是一个幂等性方法, 如果是, 则使用异常重试机制对其进行检查, 一定程度提高服务可靠性
- 从 Zookeeper 中使用 `client.getChildren().forPath("/" + RETRY)` 取出维护的可重试服务列表, 查找列表中是否存在与传入服务名称参数对应的服务
- 如果找到对应服务, 则直接返回 true, 遍历一趟后不存在, 则返回false

# ZKServiceRegister

### 简单设置
- 在 `ZKServiceRegister` 中设置白名单路径名常量 `RETRY`
- 在 `ServiceRegister` 的 `register` 方法中添加标识参数 `boolean canRetry`
- 通过 `ServiceProvider` 进行服务注册时, 同时传入 `canRetry` 参数

### 白名单添加
- 在 `ZKServiceRegister` 的 `register` 方法中判断是否加入重试白名单; 若 `canRetry` 为 `true`, 则在加入服务注册表的同时加入 retry 白名单中
- 服务加入白名单, 表示该服务是幂等的, 允许调用方失败后重试
- 拼接白名单路径, 格式为 `/RETRY节点/服务名`, 并根据 path 在 zookeeper 中注册节点, 节点模式为临时节点, 在服务实例销毁后, 节点自动删除

# ClientProxy

**ServiceCenter**
- 在代理类中添加服务管理中心, 并直接指定使用的 rpcClient 为 Netty 实现
- 将 ServiceCenter 作为类成员变量进行存储, 使用其中的 `checkRetry` 在发送请求时判断所请求的服务是否支持重试机制

**invoke调用**
- 在代理类的invoke调用中, 加入对是否支持重试的判断, 流程如下
- 用户通过代理调用方法时, 由代理接管传入的方法和传入的参数, 并根据用户使用的方法构建一个请求类对象
- 检查欲使用的接口名是否支持重试机制, 如果支持重试, 则使用定义的 `guava retry` 进行重试调用, 否则直接调用
- 接收服务端结果并返回
