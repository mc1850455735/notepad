# 概述

### 限流的意义
- 假如目前发布了一个 RPC 服务, 当作为服务端接收调用端发送的请求时, 服务端某个节点负载压力过高, 服务器可能出现宕机等问题, 影响用户体验
- 此时应对此节点进行限流操作, 对能试图到达服务节点的请求进行限制, 使请求到达速度低于服务处理速度, 以降低服务器的负载压力
- 限流是一个比较通用的功能, 当调用端发送请求过来时, 服务端在执行业务逻辑之前先执行限流逻辑, 如果发现访问量大且超过了限流阈值, 则让服务端直接抛回给调用段一个限流异常, 否则执行正常的业务逻辑
- 对于软件系统, 限流就是对请求速率进行限制, 避免瞬时大量请求击垮软件系统, 但限流也会导致用户请求无法正常被处理或者无法被立即处理, 所以限流应该是软件系统中权衡了稳定性后的最优解

### 限流算法

**固定窗口计数器算法**
- 固定窗口, 即时间窗口, 原理是将时间划分为固定大小的窗口, 每个窗口内限制请求的数量或者速率, 即规定了系统单位时间处理的请求数量
- **优点**
	- 实现简单
- **缺点**
	- 限流不够平滑. 如果时间窗口内前半部分达到了限制数量, 则后半部分用户将完全不能访问服务, 用户体验极差
	- 无法保证限流速率, 不能处理激增流量. 如果在极短时间内就达到了限制数量, 虽然固定时间段内用户请求数不变, 但是瞬时QPS极大, 仍造成压力

**滑动窗口计数器算法**
- 相当于固定窗口计数器算法的升级版, 限流的颗粒度更小
- 其优化在于: 把时间以一定的比例进行分片, 将要限制的请求数量平摊到更小的时间单位中, 比如1min最多60请求改为1s最多1请求
- 当滑动窗口格子划分的越多, 滑动窗口的滚动就越平滑, 限流统计就越精确
- **优点**
	- 相比较固定窗口, 滑动窗口算法可以应对激增流量
	- 相比较固定窗口, 滑动窗口算法颗粒度更小, 可以提供更精确的限流控制
- **缺点**
	- 仍存在限流不够平滑的问题
	- 实现和理解相对更复杂

**漏桶算法**
- 将调用端的请求动作看作注水到桶中, 服务端处理请求的动作看作桶漏水. 向桶中以任意速率流入水, 以固定速率流出水.
- 当水超过桶流量就抛弃, 因为桶容量是不变的, 保证了整体的速率
- 对于实现, 可以准备一个队列用来保存请求, 并定期从队列中拿出请求执行
- 实际业务场景中基本不使用漏桶算法
- **优点**
	- 实现简单, 便于理解
	- 可以控制限流速率, 避免网络拥塞和系统过载
- **缺点**
	- 只能以固定速率处理请求, 无法应对激增流量, 对系统资源利用不够友好
	- 桶入水速率如果一直大于桶出水速率, 那么桶一直是满的, 会一直有一部分请求被丢弃, 会导致服务质量下降

**令牌桶算法**
- 类似漏桶算法, 但是桶中存储的是令牌, 请求被处理之前需要拿到一个令牌, 请求处理完毕后, 将这个令牌丢弃. 根据需要的限流大小, 控制向桶中添加令牌的速率, 如果桶中装满, 则不能继续向其中添加令牌
- **优点**
	- 可以限制平均速率和激增流量
	- 可以动态调整生成令牌的速率
- **缺点**
	- 如果令牌产生速率和桶容量设置不合理, 可能出现各种问题, 比如大量请求被丢弃, 系统过载等
	- 相比于其他限流算法, 实现更复杂

# RateLimit
- 接口, 用于定义限流机制, `getToken()` 表示是否允许获取访问许可
- 即用来表示本次请求是否可以被处理

# TokenBucketRateLimitImpl

### 概述
- 该类为 `RateLimit` 的实现类, 即令牌桶限流方法
- 实现的 `getToken()` 方法使用 `synchronized` 关键字进行修饰, 是一个线程安全的方法

### 字段
- `RATE` : 令牌产生速率. 表示每个 RATE 毫秒生成一个令牌. 值越小, 令牌产生速度越快, 流量限制也就越宽松. 默认情况下, 令牌生成速度是固定的.
- `CAPACITY` : 桶容量, 表示令牌桶的最大容量, 生成的令牌数超过该容量则丢弃
- `curCapacity` : 当前桶容量, 表示当前令牌桶剩余令牌数量, 初始为 `CAPACITY`
- `timeStamp` : 时间戳, 记录上次消费令牌的时间, 用来记录自上次消费令牌以来经过的时间

### getToken方法

**如果桶中有令牌**
- 消耗一个令牌, 返回 true
```java
if (curCapacity > 0) {
    curCapacity--;
    return true;
}
```

**如果桶中无令牌**
- 获取当前的时间戳, 计算现在与上次消费令牌的时间差
- 如果时间差大于 RATE, 说明在中间这段时间会产生一定数量的令牌, 令牌分配应该成功, 且进行令牌产生操作
- 否则, 说明时间间隔过小, 不足以产生新令牌, 直接返回 false 即可
```java
long current = System.currentTimeMillis();
if (current - timeStamp >= RATE) {
    ...
}
return false;
```
- 在大于 RATE 的情况下, 当前请求可以获得Token, 并计算这段时间产生了多少令牌, 如果产生的令牌数量大于1, 则还应该向桶中加入对应数量的Token
- 应加入的 token 数量由时间间隔中存在几个 RATE 决定, 同时计算得出的结果还需要减去当前请求用到的一个 token
```java
if ((current - timeStamp) / RATE >= 2) {  
    curCapacity += (int) (current - timeStamp) / RATE - 1;  
}
```
 - 如果当前时间间隔过长, 导致 curCapacity 大于令牌桶最大容量, 则应直接将 `curCapacity` 设置为最大令牌桶容量 `CAPACITY`
 - 更新时间戳为本次请求时间, 并返回 true 表示成功获取到令牌
```java
if (curCapacity > CAPACITY) curCapacity = CAPACITY;  
// 刷新时间戳为本次请求  
timeStamp = current;  
return true;
```

# RateLimitProvider

**作用**
- 实现了 RateLimit 接口, 提供了 Rate Limiting 限流的相关服务

**Map<String, RateLimit> rateLimitMap**
- rateLimitMap 是一个 HashMap 类型的成员变量, 用于存储每一个接口的速率限制器实例. `String, RateLimit` 表示键为 String 类型的接口名, 值为对应的速率限制器实例
- 通过这种设计, 可以让 RateLimitProvider 在调用时根据不同的接口名称返回对应的速率限制器, 使不同的接口有不同的速率限制策略

**getRateLimit**
- 该方法将会通过接口名称返回对应的速率限制器实例
- 如果 `rateLimitMap` 中已经包含该接口名称的速率限制器实例, 直接返回该实例; 否则创建一个新的速率限制器实例并存入 `rateLimitMap`
- 默认新建的速率限制器设置是相同的, 如有修改可后期自行设置
