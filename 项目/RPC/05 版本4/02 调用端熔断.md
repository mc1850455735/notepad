# 概述

### 概述
- 服务端处理请求时, 可能出现负载过大, 此时通过限流的方式进行自我保护
- 调用端发送请求等待相应的过程中, 若服务端响应超时, 则调用端在等待服务端的过程中, 调用端本身也在接收请求, 大量请求堆积导致调用端本身也出现宕机, 层层调用下, 可能导致整个调用链都出现宕机, 导致整个服务失效
- 调用端为了保证服务端即使出现问题也不会影响本服务, 利用熔断机制进行自我保护

### 熔断机制
- 熔断器类比电路中的熔断器, 在调用请求多次失败时, 主动熔断与对应之间的连接, 直到满足特定条件, 如一段时间后, 再尝试重新建立连接
- 熔断器通常需要实现三个状态: 闭合, 断开, 半断开; 分别对应于 正常, 故障, 故障后检测故障是否已被修复
- **闭合**: 正常情况下, 后台会对调用失败次数进行计数, 当到达一定阈值或一定比例时启动熔断机制
- **断开**: 一旦对某个服务调用的失败次数达到一定阈值, 熔断器就会启用; 熔断器启用后, 所有对该服务的调用都将直接返回一个固定的错误信息, 而不进行实际的网络调用. 同时, 熔断器还需要设置一个固定的时间间隔, 当处理请求达到这个时间间隔时, 进入半熔断状态
- **半断开**: 在半断开状态下, 熔断器会对通过它的部分请求进行处理, 如果这部分请求成功返回结果, 则熔断器认为该服务已恢复正常, 熔断器关闭; 否则, 重新打开熔断器, 并刷新时间间隔

# CircuitBreaker

### 作用
- 实现了一个熔断器模式, 主要用于保护系统的高可用性. 它用于监控一段时间内的服务调用失败情况, 当失败次数超过一定阈值时, 熔断器会切换到 `OPEN` 状态, 从而避免继续调用可能导致错误的服务
- 当失败恢复或满足一定条件时, 熔断器会进入 `HALF_OPEN` 状态进行小范围测试, 放入少量请求, 如果测试中的少量请求全部成功, 则恢复到 `CLOSED` 状态

### 字段
- `failureCount` : 失败计数, 记录失败请求的数量
- `successCount` : 成功计数, 记录成功请求的数量
- `requestCount` : 请求计数, 记录当前半开状态下的请求次数
- `failureThreshold` : 失败次数阈值, 超过该值后, 熔断器启动, 进入 `OPEN` 状态
- `halfOpenSuccessRate` : 半开状态下需要的成功率阈值, 只有当成功请求的占比达到该阈值后, 才会切换到 `CLOSED` 状态
- `resetTimePeriod` : 熔断器状态为 `OPEN` 时, 等待进入 `HALF_OPEN` 的时间
- `lastFailureTime` : 上次切换为 `OPEN` 的时间, 帮助判断是否进入 `HALF_OPEN`

### CircuitBreakerState
- 记录熔断器当前的状态
- `CLOSED` : 闭合, 正常发送请求
- `OPEN` : 断开, 服务出现大量失败, 所有请求都不允许
- `HALF_OPEN` : 半断开, 熔断器尝试恢复状态, 允许一些请求进入

### 方法详解

**allowRequest**
- 用于检查当前的熔断器状态, 并决定是否允许新的请求
- 如果熔断器处于 `CLOSED`, 则直接通过该请求
- 如果熔断器处于 `OPEN`, 则检查自上次失败以来是否已经过了指定的重置时间. 如果过了, 则将熔断器设为 `HALF_OPEN` 状态并允许请求. 否则阻止请求
- 如果熔断器处于 `HALF_OPEN` 状态, 则允许请求并记录该请求, 判断是否应该将熔断器恢复到 `CLOSED` 状态

**recordSuccess**
- 该方法用于记录一个成功的请求
- 如果熔断器处于 `HALF_OPEN` 状态, 会增加成功计数. 如果成功计数超过设定的成功率阈值, 熔断器会切换回 `CLOSED` 状态
- 如果熔断器不处于 `HALF_OPEN` 状态, 则不检查成功率, 直接重置计数器

**recordFailure**
- 该方法用于记录一个失败的请求
- 当方法调用时, 对应的失败计数器+1
- 如果此时熔断器处于 `HALF_OPEN` 状态, 失败后会切换到 `OPEN` 状态
- 如果此时失败数超过了设定的阈值, 则熔断器直接切换到 `OPEN` 状态

# CircuitBreakerProvider

**作用**
- 根据服务名 `Service Name`, 提供一个对应的熔断器 `Circuit Breaker`.
- 使用 `Map` 类型存储每个服务的熔断器实例, 并在请求时返回对应的熔断器. 如果熔断器不存在, 则会创建一个新的熔断器并将其加入 `Map`
