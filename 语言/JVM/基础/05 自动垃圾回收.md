
# 概述

**概述**
- 在C/C++这类没有自动垃圾回收机制的语言中, 一个对象如果不再使用, 需要手动释放, 否则就会出现 **内存泄漏**. 内存泄露指的是不再使用的对象未在系统中被回收, 内存泄漏的积累可能导致**内存溢出**
- 对于释放不再使用的内存的过程, 称其为垃圾回收, 对于需要程序员编写代码进行垃圾回收的过程, 称为**手动垃圾回收**
- Java中为了简化对象的释放, 引入了自动 **垃圾回收** (Garbage Collection, **GC**) 机制. 通过**垃圾回收器**对不再使用的对象完成自动的回收, 垃圾回收器主要负责对**堆**上的内存进行回收
- 如果需要**手动触发垃圾回收**, 可以调用 `System.gc()` 方法; 该方法调用后, 并不一定立刻回收垃圾, 仅仅是向Java虚拟机中发送垃圾回收的**请求**, 具体是否需要执行垃圾回收, Java虚拟机会自行判断

**对比**
- 自动垃圾回收: 根据对象是否使用由虚拟机回收对象
	- 优点: 降低程序员实现难度, 降低对象回收Bug的可能性
	- 缺点: 程序员无法控制内存回收的及时性
- 手动垃圾回收: 由程序员编程实现对象的删除
	- 优点: 回收及时性高, 由程序员把控回收的时机
	- 缺点: 编写不当容易出现悬空指针, 重复释放, 内存泄漏等问题

# 方法区的回收

**概述**
- 线程不共享的部分, 都是伴随着线程的创建而创建, 线程的销毁而销毁, 而方法的栈帧在执行完后就会自动弹出栈并释放掉对应的内存
- 正常开发中很少会执行方法区的回收, 也就是类的卸载, 主要出现在如 `OSGi`, `JSP` 的热部署等引用场景中.
	- 如JSP的立即重加载就是为每个 JSP 文件分配一个唯一的类加载器, 当某个 JSP 文件被修改了, 则直接**卸载**这个类加载器, 并重新创建类加载器, 重新加载 JSP 文件
- 方法区中能回收的内容主要就是**不再使用的类**

**类的卸载**
- 通过参数 `-XX:+TraceClassLoading` 和 `-XX:+TraceClassUnloading` , 可以实现追踪与打印类的加载与卸载过程
- 判定一个类可以被卸载, 需要同时满足下面三个条件
	1. 此类的所有**实例对象**都已经被回收, 在堆中不存在任何该类的实例对象以及其子类对象
	2. 加载该类的**类加载器**已经被回收
	3. 该类对应的 **java.lang.Class 对象**没有在任何地方被引用

# 堆回收

- 在Java中, 一个对象是否能被回收, 是根据对象是否被引用来决定的. 如果对象可以通过栈中的引用被访问到, 则说明该对象还有可能被使用
- 如果想要查看垃圾回收的信息, 可以使用 `-verbose:gc` 虚拟机参数
- 分析某对象是否被引用有两种方法: 引用计数法 和 可达性分析法(java使用)

##### 引用计数法
- 引用计数法会为每个对象维护一个引用计数器, 对象被引用时加1, 取消引用时减1
- 优点是实现简单, C++的智能指针就采用了引用计数法
- 缺点
	- 每次引用和取消引用时都需要维护计数器, 对性能存在影响
	- 存在循环引用问题, 使存在对象无法回收, 导致内存泄漏

##### 可达性分析法
- Java使用的是**可达性分析算法**来判断对象是否可以被回收. 
- 可达性分析将对象分为两类: 垃圾回收的**根对象**(GC Root)和**普通对象**, 对象与对象之间存在引用关系
- 可达性分析算法是指, 如果从某个节点到GC Root对象是可达的, 对象就不可被回收

**GC Root对象**
- 线程**Thread对象**, 引用线程栈帧中的方法参数, **局部变量**等
- **系统类加载器**加载的java.lang.Class对象, 引用类中的**静态变量**
- 监视器对象, 用来保存同步锁synchronized关键字持有的对象
- 本地方法调用时使用的全局对象

**查看GC Root**
- 通过arthas和eclipse Memory Analyzer (MAT) 工具可以查看GC Root
- MAT工具是eclipse推出的Java堆内存检测工具
1. 使用arthas的heapdump命令将**堆内存快照**保存到本地磁盘中, 文件后缀名为 `.hprof` , 命令如下 `heapdump 路径\文件名.hprof`
2. 使用MAT工具打开堆内存快照文件
3. 选择GC Roots功能查看所有的GC Root

##### 软引用
- 可达性算法中描述的对象引用, 一般指的是**强引用**, 即GC Root对象对普通对象有引用关系, 只要存在这种引用, 普通对象就不会被回收
- 除了强引用外, 还包含其他4种引用方式
- 软引用, 弱引用, 虚引用, 终结器引用

**概念**
- 软引用相对于强引用是一种比较弱的引用关系, 如果一个对象只有软引用关联到他, 则程序**内存不足**时, 就会将软引用中的数据进行回收
- JDK1.2版本之后, 提供了 SoftReference类对象 实现软引用, 软引用的特征决定了其不能用于引用重要数据, 故其常用于缓存中
- SoftReference类对象中用于定义需要被软引用的对象, 但是SoftReference类对象本身需要被GC Root关联到, 否则其本身同样会被垃圾回收

**软引用队列机制**
- 当软引用中的对象被回收时, SoftReference对象本身也需要被回收.
- 为了确保在软引用的对象回收的同时回收SoftReference对象, SoftReference中提供了一套队列机制
1. 软引用创建时, 通过构造器传入引用队列
2. 在软引用中包含的**对象被回收时**, 该软引用对象会被自动放入引用队列
3. 通过代码遍历引用队列, 将 SoftReference 的强引用删除
```java
ArrayList<SoftReference> softReferences = new ArrayList<>();  
ReferenceQueue<byte[]> queues = new ReferenceQueue<byte[]>();  
for (int i = 0; i < 10; i++) {  
    byte[] bytes = new byte[1024 * 1024 * 100];  
    SoftReference studentRef = new SoftReference<byte[]>(bytes,queues);  
    softReferences.add(studentRef);  
}
```

**使用**
- 将对象使用软引用进行包装 - `new SoftReference<对象类型>(对象)`
- 内存不足时, 虚拟机尝试进行垃圾回收
- 如果垃圾回收后, 仍然不能解决内存不足问题, 则回收软引用中的内容
- 如果内存仍不足, 则抛出 `OutOfMemory` 异常

##### 弱引用
- 弱引用机制与软引用基本一致, 区别在于弱引用包含的对象在垃圾回收时, 不论内存足够与否, 都会直接进行回收.
- 在JDK1.2版本后, 使用 WeakReference类实现弱引用, 弱引用主要用于 ThreadLocal 当中, 其本身也可以使用引用队列进行回收

##### 虚引用
- 一般开发不使用
- 虚引用也称为幽灵引用/幻影引用, 不能通过虚引用获取到包含的对象, 其唯一的用途就是当对象被垃圾回收器回收时, 可以接收到对应的通知
- Java中使用 PhantomReference 实现了虚引用, 直接内存中, 为了及时知道直接内存对象不再被使用从而进行内存回收, 使用了虚引用进行实现

##### 终结器引用
- 一般开发不使用
- 终结器引用指的是在对象需要被回收时, 终结器引用会关联对象并放置在 Finalizer 类中的引用队列中. 
- 之后由 FinalizerThread 线程从队列中获取对象, 然后执行对象的 finalize方法, 在对象第二次被回收时, 该对象才会被真正的回收.
- finalize方法只会调用一次, 第二次回收时不再调用该方法, 直接回收
- 在这个过程中, 可以在 finalize方法 中再次将该对象与强引用关联, 实现对象的自救, 但是不建议这样做

# 垃圾回收算法

**概述**
- 标记清除算法和复制算法是最早发布的算法, 后续所有垃圾回收算法, 都是在这两种算法的基础上优化而来
- 常见垃圾回收算法有4种, 分别是
	- 标记-清除算法
	- 复制算法
	- 标记-整理算法
	- 分代GC

**核心思想**
1. 找到内存中存活的对象
2. 释放不再存活的对象, 使得程序能够再次使用这部分空间

**评价标准**
- 通过虚拟机参数 `-verbose:gc` 可以打印垃圾回收的日志
- Java垃圾回收过程会通过单独的GC线程来完成, 但是不管使用哪一种GC算法, 都会有部分阶段需要停止所有用户线程
- 这个过程称为 Stop The World, 简称 **STW**. 如果STW过长会影响用户的使用
- 判断GC算法可以从三个方面考虑
	- **吞吐量**, 即执行用户代码时间和CPU总执行时间的比值
	- **最大暂停时间**, 即垃圾回收过程中STW的最大值
	- **堆使用效率**, 不同垃圾回收算法对堆使用方式不同, 导致使用效率不同
- 三个评价标准不可兼得, 一般来说, 堆内存越大, 最大暂停时间就越长. 如果想要减少最大暂停时间, 就会降低吞吐量
- 所以, 没有最好的垃圾回收算法, 不同的垃圾回收算法**适用于不同的场景**

##### 标记清除算法

**步骤**
- 标记阶段: 将所有存活对象进行标记. 在Java中使用可达性分析算法, 从GC Root开始通过引用链遍历出所有存活对象
- 清除阶段: 从内存中删除所有没有被标记的对象, 即非存活对象

**优缺点**
- 优点: 
	- **实现简单**, 只需要在第一阶段维护每个对象标志位, 第二阶段删除对象
- 缺点: 
	- **碎片化问题**. 由于内存连续, 对象删除后可能留下过小的可分配单元. 当需要较大连续内存空间时, 可能存在多个细小零碎空间无法使用
	- **分配速度慢**. 由于内存碎片的存在, 需要维护空闲链表保存可用内存. 试图获取内存空间时, 需要遍历链表才能找到可用内存

##### 复制算法

**思路**
- 准备两块空间 (From空间和To空间), 在对象分配阶段, 只使用其中一块空间
- 在垃圾回收阶段, 将From中的存活对象复制到To空间. 
	- 完整步骤如下: 先将GC Root搬运到To空间中, 再根据GC Root, 将其关联的对象搬运到To空间
- 清理From空间, 并将两块空间的From和To名字互换

**优缺点**
- 优点
	- **吞吐量高**: 只需要遍历一次存活对象, 将其复制到To空间即可. 相比较**标记整理**算法, 少了一次遍历的过程, 但是不如**标记清除**算法, 因为标记清除算法不需要进行对象的移动
	- **无碎片化问题**: 复制算法复制对象后就会将对象按顺序放入To空间, 所以除To以外区域都是可用空间, 不存在碎片化内存空间
- 缺点
	- **内存使用效率低**: 每次都只能使用一半内存空间创建对象使用

##### 标记整理算法
- 标记整理算法, 也叫标记压缩算法, 是对标记清除算法中易产生内存碎片问题的一种解决方案

**思路**
- 标记阶段: 使用Java可达性算法对所有存活对象进行分析
- 整理阶段: 将存活对象移动到堆的一段, 清理掉存活对象的内存内容

**优缺点**
- 优点: 
	- **内存使用效率高**: 整个内存空间都可用
	- **不会发生碎片化**: 整理阶段将对象向内存一侧移动, 剩下的空间都可用
- 缺点
	- **整理阶段效率不高**: Lisp2算法需要对整个堆中对象扫描搜索多次, 性能不佳. 可以通过Two-Finger, 表格算法, ImmixGC等算法优化此阶段性能

##### 分代GC算法

**概述**
- 分代GC算法是目前应用最广的垃圾回收算法, 结合了上述多种算法使用
- 分代GC算法将整个内存区域划分为 **年轻代**(新生代, Young) 和 **老年代**(Old)
- 年轻代: 存放存活时间比较短的对象, 其中又分为几个区域
	- Eden区: 对象刚创建时, 加入该区域
	- Survivor幸存区: 共有两块幸存区, 分别记为S0和S1, 用来实现复制算法
- 老年代: 存放存活时间比较长的对象

**执行流程**
- 分代回收时, 创建出来的对象, 首先会被放入Eden区
- 当Eden区满后, 新创建的对象无法放入, 会触发 年轻代GC, 称为 Minor GC 或者 Young GC
- **MinorGC** 会回收 Eden区 和 幸存者From区 中的垃圾对象, 并将没有回收的对象放入 幸存者To区, 同时幸存者S0区和S1区身份互换; 再次MinorGC后, 仍会将存活对象加入新的To存活区
- 每次MinorGC后, 都会记录该对象的年龄, 初始值为0, 每次加1
- 如果MinorGC后对象年龄达到阈值 (最大15, 默认与**垃圾回收器**有关), 则将该对象**晋升**至老年代 (或者幸存者区存满而老年代未满时, 也会放入老年代)
- 当老年代中空间不足, 无法存放新对象时, 会先尝试进行 MinorGC, 如果还是不足, 则触发 **FullGC**, 对整个堆进行垃圾回收
- 如果FullGC后, 依然无法回收掉老年代对象, 则当对象继续放入老年代时, 会抛出 `OutOfMemory` 异常

**工具**
- 在JDK8中, 添加 `-XX:+UseSerialGC` 参数使用分代回收的垃圾回收器
	- 其他JDK版本中, 垃圾回收器可能存在不同
- 在arthas中, 使用memory命令查看内存, 显示三个区域内存情况
- 通过以下参数, 可以用来调整堆大小并观察结果 (添加 `-XX:+UseSerialGC` 后) 
- `Xms` : 设置堆初始大小, 大于1MB
- `Xmx` : 设置堆最大大小, 大于2MB
- `Xmn` : 设置新生代大小, 通过新生代大小可以得出老年代大小 
- `-XX:SurvivorRatio` : Eden区与幸存者区的大小比例, 默认为8
	- 既如果有1GB内存, 则800MB给Eden区, 两个100MB给两个幸存者区
- `-XX:+PrintGCDetails / verbose:gc` : 打印GC日志

# 垃圾回收器

**为什么分代GC要把堆分为新生代和老年代**
- 系统中的大部分对象, 都是创建出来之后很快就不再被使用, 可以回收. 如用户获取订单数据, 订单数据返回给用户后, 就可以进行释放
- 老年代中会存放长期存活的对象, 比如Spring中的大部分Bean对象, 在程序启动后就不会被回收
- 在虚拟机**默认设置**中, 新生代大小要远小于老年代大小

**设计原因**
1. 可以通过调整年轻代和老年代的比例来适应不同类型的应用程序, 提高内存的**利用率和性能**
2. 新生代和老年代使用不同的垃圾回收算法, 新生代一般使用选择复制算法, 老年代使用标记清除和标记整理算法, 由程序员选择, 灵活度高
3. 分代的设计中, 通过 MinorGC 回收新生代, 如果可以满足对象分配要求, 就不需要对整个堆进行 FullGC, 减少了 STW 时间

### 组合关系

##### 概述
- 垃圾回收器是垃圾回收算法的具体实现
- 使用 `dashboard -n 1` 并观察使用的垃圾回收算法, 就可以得出对应使用的垃圾回收器是哪一个组合
- 由于垃圾回收器分为新生代和老年代, 除了G1之外的其他垃圾回收器必须成对组合进行使用. JDK9之后, 主流推荐使用 G1垃圾回收器

##### 总结
- 垃圾回收器版本虽然有很多, 但是针对几个特定版本, 比较好的组合如下
- JDK8及之前
	- ParNew+CMS - 关注暂停时间, 需要**经过测试**选出最佳暂停时间
	- ParallelScavenge+ParallelOld - 关注吞吐量
	- G1 - JDK8不建议, 较大堆且关注暂停时间
- JDK9及之后
	- G1 - 默认使用
	- 从JDK9之后, 由于G1日趋成熟, JDK默认垃圾回收器已经修改为G1, 所以强烈建议在生产环境上使用G1

### Serial与SerialOld
- `-XX:+UseSerialGC` : 新生代, 老年代都使用串行回收器

**Serial**
- Serial是一种**单线程串行**回收**年轻代**的垃圾处理器
- 回收年轻代, 使用复制算法
- 优点: 单CPU处理器下, 吞吐量非常出色
- 缺点: 多CPU下吞吐量不如其他垃圾回收器, 年轻代堆偏大时会让用户线程处于长时间等待
- 适用场景: Java编写的**客户端程序**或者硬件配置**有限**的场景
![[语言/JVM/Inbox/Pasted image 20251018214853.png]]

**SerialOld**
- SerialOld是Serial的老年代版本, 使用**单线程串行**回收**老年代**
- 回收老年代, 使用标记整理算法
- 优点: 单CPU处理器下, 吞吐量非常出色
- 缺点: 多CPU下吞吐量不如其他垃圾回收器, 老年堆偏大时会让用户线程处于长时间等待
- 适用场景: 与Serial垃圾回收器配合使用, 或者在CMS特殊情况下使用

### ParNew与CMS
- `-XX:+UseParNewGC` : 新生代使用ParNew回收器, 老年代使用SerialOld串行回收器
- `-XX:+UseConcMarkSweepGC` : 使用CMS垃圾回收器

**ParNew**
- ParNew垃圾回收器本质上是对Serial在**多CPU**下的优化, 使用**多线程**进行垃圾回收
- 回收年轻代, 使用复制算法
- 优点: 多CPU处理器下停顿时间较短
- 缺点: 垃圾回收时用户线程无法执行, 吞吐量和停顿时间不如G1, 在JDK9之后不建议使用
- 适用场景: JDK8及其之前版本, 与CMS老年代垃圾回收器配合使用
![[语言/JVM/Inbox/Pasted image 20251018214802.png]]

**CMS**
- CMS (Concurrent Mark Sweep) 垃圾处理器关注的是系统的**暂停时间**, 允许用户线程和垃圾回收线程在某些步骤中**同时执行**, 减少用户线程的等待时间
- 回收老年代, 使用标记清除算法
- 优点: 系统由于垃圾回收出现的停顿时间较短, 用户体验好
- 缺点: 1. 内存碎片化问题 2. 退化问题 3. 浮动垃圾问题
- 适用场景: 大型互联网系统中用户请求数据量大, 频率高的场景, 如订单接口, 商品接口等

**缺点**
- CMS使用了标记清除算法, 垃圾回收结束后会出现大量内存碎片, CMS会在FullGC 时进行碎片的整理, 这样会导致用户线程暂停
	- 可以通过 `-XX:CMSFullGCsBeforeCompaction=N(默认0)` 来设置N次FullGC后再进行内存整理
- 无法处理在并发清理过程中产生的**浮动垃圾**, 不能做到完全的垃圾回收
- 如果老年代中内存不足无法分配对象, CMS就会**退化成SerialOld**单线程回收老年代

**CMS执行步骤**
1. 初始标记: 用短时间标记出GC Roots能直接关联到的对象
2. 并发标记: 标记所有对象, 用户线程不需要暂停
3. 重新标记: 由于并发标记阶段对象可能发生变化, 存在漏标, 错标的可能, 需要通过多线程进行重新标记
4. 并发清理: 清理死亡的对象, 用户线程不需要暂停

### ParallelScavenge与ParallelOld
- JDK8默认使用该组合
- `-XX:+UseParallelGC` 或 `-XX:+UseParallelOldGC`: 使用ParallelScavenge + ParallelOld组合

**ParallelScavenge**
- ParallelScavenge是JDK8默认的年轻代垃圾回收器, 多线程**并行回收**, 关注的是系统吞吐量. 具备**自动调整堆内存大小**的特点
- 回收年轻代, 使用复制算法
- 优点: 吞吐量高, 且**手动可控**. 为了提高吞吐量, 虚拟机会动态调整堆的参数
- 缺点: 不能保证单次的停顿时间
- 适用场景: 后台任务, 不需要与用户交互, 并且容易产生大量数据的对象. 如: 大数据的处理, 大文件的导出等
![[语言/JVM/Inbox/Pasted image 20251019081931.png]]

**使用**
- ParallelScavenge允许手动设置最大暂停时间和吞吐量
- Oracle官方建议使用该组合时, 不要设置堆内存的最大值, 该垃圾回收器会通过最大暂停时间和吞吐量自动调整内存大小
- 最大暂停时间: `-XXMaxGCPauseMillis=n` , n为毫秒数
- 吞吐量: `-XX:GCTimeRatio=n`, 设置吞吐量为n, 则用户线程执行时间占比 `n/n+1`
- 自动调整内存大小: `-XX:+UseAdaptiveSizePolicy`
- 通过 `-XX:+PrintFlagsFinal` 可以查看虚拟机所有设置的当前值, 包括默认值

**ParallelOld**
- ParallelOld是为ParallelScavenge收集器设置的老年代版本, 利用**多线程**并发收集
- 回收老年代, 使用标记整理算法
- 优点: 并发收集, 在多核CPU下效率较高
- 缺点: 暂停时间较长
- 适用场景: 与 ParallelScavenge配套使用

### G1垃圾回收器

- 同时回收年轻代和老年代, 使用复制算法
- 优点: 对较大的堆, 比如超过6G的堆回收时, 延迟可控; 不会产生内存碎片; 并发标记的 SATB 算法效率较高
- 缺点: JDK8及之前不够成熟
- 适用场景: JDK8最新版本和JDK9之后默认使用该回收器

##### 概述
- JDK9之后默认的垃圾回收器是G1 (Garbage First) 垃圾回收器
- ParallelScavenge关注吞吐量, 允许用户设置最大暂停时间, 但是会减少年轻代可用空间的大小
- CMS关注暂停时间, 但是吞吐量方面会下降
- `-XX:+UseG1GC` : 打开G1的开关, JDK9之后默认自动打开
- `-XX:MaxGCPauseMills=毫秒值` : 最大暂停时间

**特点**
- G1设计目标就是将上述两种垃圾回收器的优点结合
1. 支持巨大的堆空间回收, 并且拥有较好的吞吐量
2. 支持多CPU并行垃圾回收
3. 允许用户设置最大暂停时间
- JDK9之后, 强烈建议使用G1垃圾回收器

##### 内存结构
- G1垃圾回收期出现前, 内存结构一般是连续的, 如下图
![[语言/JVM/Inbox/Pasted image 20251019091936.png]]
- G1的整个堆会被划分为多个大小相等的区域, 称为 区(Region), 各个区域**不要求连续**, 分为 Eden, Survivor, Old
- Region的大小通过 `堆空间/2048` 计算得出, 也可以通过参数进行设置, 参数大小必须是2的指数幂, 取值范围从1M到32M
- `-XX:G1HeapRegionSize=参数`
![[语言/JVM/Inbox/Pasted image 20251019091959.png]]

##### 回收过程
- G1中存在年轻代回收 (YoungGC) 和混合回收 (MixedGC) 两种垃圾回收方式
- 年轻代回收会回收Eden区和Survivor区中不用的对象, 会导致STW
- G1中可以通过参数 `-XX:MaxGCPauseMillis=n (默认200)` 设置每次垃圾回收时的最大暂停时间毫秒数, G1垃圾回收器会尽可能地保证暂停时间
- G1在进行YoungGC时, 会记录每次垃圾回收时每个Eden区和Survivor区的**平均耗时**, 以作为下次回收时的参考依据
- 根据配置的最大暂停时间与每次回收时的平均耗时相除, 可以计算出本次回收最多回收多少个Region

**执行流程**
1. 新创建的对象会存放在Eden区, 当G1判断年轻代区空间不足(默认60%), 无法分配对象时需要回收, 会执行 YoungGC
2. 标记Eden和Survivor区域中的存活对象
3. 根据配置的最大暂停时间**选择某些区域**将存活对象复制到一个**新的**Survivor区中, 同时使年龄+1, 并清空有原来的这些区域
4. 后续YoungGC与之前相同, 只是Survivor区中的存活对象会被搬运到另一个Survivor区
5. 当某个存活对象的年龄到达阈值(默认15), 将被放入老年代当中
6. 部分对象大小如果超过Region的一半, 会直接放入老年代, 这类老年代被称为Humongous区, 如果对象过大, 会横跨多个Region
7. 多次回收后, 会出现很多Old区, 此时总堆占用率达到阈值时, 会触发混合回收机制 MixedGC, 使用 `-XX:InitiatingHeapOccupancyPercent` 设置阈值, 默认阈值大小为 45%. 通过 MixedGC 回收所有年轻代和部分老年代, 以及 `Humongous` 区. 使用复制算法完成该操作

**混合回收**
- 混合回收分为, 初始标记, 并发标记, 最终标记, 并发清理
- G1对老年代的清理会优先选择存活度最低的区域进行回收, 以此保证回收的效率最高, 因此称为 GarbageFirst (G1) 垃圾回收器
- 初始标记: 标记 GcRoots 引用的对象为存活
- 并发标记: 将第一步中标记的对象引用的对象标记为存活
- 最终标记: 只标记引用改变漏标的对象, 不管新创建或者不再关联的对象
- 并发复制清理: 将存活对象复制到其他Region, 不会产生内存碎片, G1只会选择部分存活度比较低的区域进行清理
![[语言/JVM/基础/Inbox/Pasted image 20251019104321.png]]

**FullGC**
- 如果清理过程中发现没有足够的**空Region**存放转移的对象, 则会出现FullGC, 执行单线程标记-整理算法
- 此时会导致用户线程暂停, 所以要尽量保证堆空间中有一定多余内存
