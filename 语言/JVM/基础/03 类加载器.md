
# 概述

- 类加载器 (ClassLoader) 是Java虚拟机提供给应用程序去实现**获取类和接口字节码**数据的技术
- 类加载器只参与加载过程中字节码获取并加载到内存这一阶段
- 本地接口 `JNI` (`Java Native Interface`)运行Java调用其他语言编写的方法. 在hotspot类加载器中, 主要用于调用Java虚拟机中使用C++编写的方法

# 分类

- 类加载器分为两类, 一类是在Java代码中实现的, 一类是在Java虚拟机底层源码中实现的
- 类加载器的详细信息, 可以通过arthas进行查看, 使用 classloader 命令

**虚拟机底层实现**
- 源代码位于虚拟机源码中, 实现语言与虚拟机底层语言一致, 如 Hotspot 使用 C++ 进行实现
- 通常用于加载程序运行时的基础类, 如java.lang.String, 确保基础类的可靠性
**JDK默认提供或自定义**
- JDK中默认提供了多种处理不同渠道的类加载器, 程序员也可以根据自己的需求进行定制
- 所有Java中实现的类加载器都需要继承自**ClassLoader**这个抽象类

**JDK8及之前**
- 虚拟机底层 C++
	- 启动类加载器 **Bootstrap**: 加载Java中**最核心**的类
- Java
	- 扩展类加载器 Extension: 允许扩展Java中**比较通用**的类
	- 应用程序类加载器 Application: 加载应用使用的类
	- 反射类加载器 Delegating: 提升反射加载效率的类加载器 (不重要)

# 启动类加载器
- 启动类加载器 (Bootstrap ClassLoader) 是由Hotspot虚拟机提供的, 使用C++编写的类加载器
- 默认加载Java安装目录`/jre/lib`下的类文件, 如`rt.jar, tools.jar, resources.jar`等等, 其中最重要的是 `rt.jar`, 包含多个核心类的定义
- 启动类加载器存在于虚拟机底层, 处于安全条件考虑, 无法通过常规代码获取到该类加载器
- 在arthas中, 使用 `sc -d 类名`, 可以搜索到某个类, 并展示出该类使用的类加载器, 对于使用启动类加载器的类, 其 `ClassLoader` 为空
- 如果需要拓展Java功能, 有两种做法
	- 放到 `jre/lib` 下去拓展: 不推荐, 可能出现预料之外的异常, 且尽量不要更改jdk安装目录中的内容, 即使加入也有可能因为文件名不匹配而不被正常加载
	- 使用参数进行拓展: 推荐, 使用 `-Xbootclasspath/a:jar包目录/jar包名` 加载用户jar包

# 扩展类加载器

##### 概述
- 扩展类加载器和应用程序类加载器都是 JDK 中提供的, 使用 Java 编写的类加载器
- 他们的源码都位于 `sun.misc.Launcher` 中, 是一个**静态内部类**. 继承自`URLClassLoader` , 具备通过目录或者指定jar包将字节码加载到内存中的能力

**扩展类加载器**
- 扩展类加载器是JDK中提供的, 使用Java编写的类加载器
- 默认加载Java安装目录 `/jre/lib/ext` 下的类文件
- 通过扩展类加载器加载用户jar包也有两种选择
	- 放到 `jre/lib/ext` 下去拓展: 不推荐, 与启动类加载器同理
	- 使用参数进行拓展: 推荐, 使用 `-Djava.ext.dirs=jar包目录` 进行扩展, 这种方式会覆盖掉原始目录, 可以使用 `;` (windows) 或 `:` 追加上原始目录
	- `-Djava.ext.dirs="xxx\jdk1.8.0_202\jre\lib\ext;D:\代码\day02"`
	- 目录中含有特殊字符(空格, 汉字等), 使用双引号进行引用

# 应用类加载器

- 加载 Classpath 下的类文件
- 不论是用户自己创建的类, 还是由maven引入的第三方依赖jar包, 都由应用类加载器进行加载
- 通过arthas中的classloader命令, 可以查看类加载器的hash值, 通过hash值可以查看类加载器的加载路径
- 查看所有类加载器及其hash值: `classloader -l`
- 查看类加载器的加载路径: `classloader -c hash值`
- **应用类加载器**同样会加载启动类加载器和扩展类加载器加载的内容, 这与JVM的**双亲委派机制**有关

# 双亲委派机制

### 概念
- 由于Java虚拟机中有多个类加载器, 双亲委派机制的核心解决的是一个类**到底由谁加载**的问题
- 双亲委派机制指的是: 当类加载器收到加载类的任务时, 会先自底向上查询是否加载过, 再自顶向下进行类加载. 
	- 从最低端加载器开始向上查找, 如果在向上查找的过程中发现加载过, 则直接返回Class对象, 加载过程结束, 从而避免了类的重复加载
	- 如果没有加载过, 则从顶端类加载器开始尝试加载类, 如果该类在加载目录中, 则由该类加载器进行加载, 否则继续向下传递, 直到符合加载目录
	- 如果所有类加载器都无法加载, 则抛出**无法找到对应类异常**
- 向下委派机制起到了**加载优先级**的作用, 越靠上的加载器优先级越高, 由此实现了避免用户替代核心类的作用, 因为上级类加载器总是会有限加载
- 类加载器通常具有**父类加载器**, 如 Application 应用程序类加载器的父类加载器是 Extension 扩展类加载器, Extension 扩展类加载器的父类加载器是 Bootstrap 启动类加载器
- 该父类加载器并非继承, 每个Java实现的类加载器中保存了一个名为 `parent` 的累加载器, 可以理解为他的上级, 并非传统的继承关系
- Application的parent是Extension, 但是Extension的parent为null
- 通过arthas的 `classloader -t` 可以查看所有类加载器之间的父子关系

**作用**
- 保证类加载的安全性: 使用双亲委派机制避免恶意代码替代JDK中的核心类库, 如 java.lang.String, 确保核心类库的完整性和安全性
- 避免重复加载: 双亲委派机制可以避免同一个类被多次加载

### 自定义类加载器

##### 问题
- 一个Tomcat程序中可以运行多个Web应用, 如果这两个应用出现了相同限定名的类, 比如MyServlet类. Tomcat要保证这两个类都能加载并且他们应该是不同的类
- 如果不打破双亲委派机制, 应用类加载器加载完成Web1中的 MyServlet 后, 就无法再通过相同的限定名加载Web2中的 MyServlet 了

##### 解决
- Tomcat 使用**自定义类加载器**的方法来实现应用之间类的隔离, 对每一个不同的Web应用, 都会有一个独立的类加载器来加载对应的类
- 通过自定义类加载器并重写 loadClass 逻辑, 使其不再向上传递, 从而打破双亲委派机制
![[语言/JVM/Inbox/Pasted image 20251015203206.png]]

##### 注意
- 值得注意的是, 即使重新实现了 loadClass 逻辑不再向上传递, 也不能使用自定义类加载器加载名称以 `java.` 开头的类 (因为 defineClass 中会进行检查)
- 即使不给自定义类加载器的 parent 赋值, 其默认值仍为应用程序类加载器 (ApplicationClassLoader), 只是不再实行双亲委派机制的向上和向下的流程
- 正确的去实现一个自定义类加载器的方式是重写 **findClass 方法**, 通过这种方式不会破坏双亲委派机制

##### 分析
- `ClassLoader` 中包含了4个核心方法
- `loadClass` 方法为 **类加载的入口**,包含了双亲委派机制的核心代码, 该方法内部会调用 findClass 方法
- `findClass` 由类加载器的子类实现, **获取二进制数据**并调用 defineClass, 比如 URLClassLoader会根据文件路径去获取类文件中的二进制数据
- `defineClass` 会做一些类名的校验, 并根据二进制数据信息, 调用虚拟机底层方法在对应的JVM内存区域创建类, 使用 C++实现
- `resolveClass` 方法会执行类生命周期中的连接阶段, 使类真正可用
- 两个不同的类加载器加载相同限定名的类并不会冲突, 因为在同一个Java虚拟机中, 只有**相同类加载器+相同类限定名**才会认为是同一个类
- 在arthas中使用 `sc -d 类名` 的方式查看具体情况

### SPI与上下文类加载器

##### 概述
- 利用**上下文类加载器**加载类, 常被JDK用于Java内部的技术, 如 JDBC 和 JNDI
- JDBC 中使用了 `DriverManager` 来管理项目中引入的不同数据库的驱动, 如mysql驱动, oracle驱动等
- DriverManager类位于rt.jar包中, 由**启动类加载器**进行加载; 而该类加载时扫描得到的用户jar包, 其中的驱动需要由**应用类加载器**进行加载, 这样就违反了类加载过程中的双亲委派机制
- 有时也认为没有破坏双亲委派机制, 理由如下: 虽然驱动类确实需要由应用类加载器进行加载, 但是这个提前加载的过程同样是符合双亲委派机制的, 类加载器同样需要进行**自底向下和自顶向上**两个步骤

##### SPI机制
- SPI (Service Provider Interface) 机制, 是JDK内置的一种**服务提供发现机制**
- SPI 使用了**线程上下文**中保存的类加载器进行类的加载, 这个类加载器一般默认就是应用类加载器
- 可以通过 `setContextClassLoader` 手动设置当前线程的类加载器
- spi 的工作原理
1. 在ClassPath路径下的 `META-INF/services` 文件夹中, 以接口的全限定名来命名文件夹, 对应的文件里面写该接口的**实现**
2. 使用 ServiceLoader 中的 `load()` 方法加载实现类, 得到驱动加载器, 由其迭代器遍历jar包中满足条件的类名
3. SPI 的 load 方法中使用线程上下文获取类加载器 (通常是应用程序类加载器), 通过该加载器加载并创建发现的对象

### Osgi框架与热部署

##### 概述
- 历史上, Osgi模块化框架, 存在允许同级之间的类加载器的委托加载
- OSGi还使用类加载器实现了**热部署**的功能, 即在服务不停止的情况下, 动态地更新字节码文件到内存中

##### Arthas热部署
- 在相关服务器中部署arthas并启动
- 使用 `jad -source-only 类名 > 目录/文件名.java` 进行反编译, 并修改源码
- 使用 `sc -d 类名` 查看指定类加载器的 hashcode
- 使用 `mc -c 类加载器hashcode 目录/文件名.java -d 输出目录` 指定一个类加载器, 以便于找到其他类的字节码文件, 共同编译修改过的代码
- 使用 `retransform 目录/文件名.class` 加载新的字节码文件

**注意**
- jar包重启后, 字节码文件就会恢复, 除非将class文件放入jar包共同更新
- 使用 retransform 不能添加方法或字段, 也不能更新正在执行中的方法
- 所以使用 arthas 进行热部署只能用于应急处理, 正常情况仍需重新编译打包

# JDK9之后的类加载器

- JDK8以及之前的版本中, **扩展类加载器**和**应用程序类加载器**的源码位于 `rt.jar` 中的 `sun.misc.Launcher.java`, 二者都继承自 `URLClassLoader`, 基于 jar包的位置寻找字节码文件
- JDK9及其之后的版本, 由于引入了module的概念, 类加载器在设计上发生了很大的变化
1. **启动类加载器**不再使用C++编写, 而是使用Java编写, 存放于名为`jdk.internal.loader.ClassLoader` 的类中, `BootClassLoader` 继承自 **BuiltinClassLoader** , 实现从模块中找到要加载的字节码文件. 启动类加载器依然无法通过java代码获取到, 返回的**依然是null**, 保持了统一
2. **扩展类加载器**被替换为新的**平台类加载器** (`PlatformClassLoader`), 平台类加载器遵循**模块化方式**加载字节码文件, 所以继承关系由 `URLClassLoader` 变成了 `BuiltinClassLoader` , 实现了从模块中加载字节码文件. 平台类加载器的存在主要是为了实现与老版本设计方案的**兼容**, 本身不具有特殊逻辑
3. **应用类加载器**继承关系由 `URLClassLoader` 变为了 `BuiltinClassLoader` , 其他方面变化不大
