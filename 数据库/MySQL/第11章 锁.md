# 概述

**介绍**
- 锁是计算机协调多个进程或者线程并发访问某一资源的机制.
- 在数据库中, 除传统计算资源, 如 `CPU`, `RAM`, `I/O` 等的争用外, 数据也是一种供许多用户共享的资源
- 保证数据并发访问的一致性和有效性是所有数据库必须解决的问题, 锁冲突是影响数据库并发访问性能的一项关键因素

**类型**
- 全局锁 : 锁定该数据库中的所有表
- 表级锁 : 每次操作锁住整张表
- 行级锁 : 每次操作锁住对应的行数据

# 全局锁

**介绍**
- 全局锁是对整个数据库实例进行加锁, 加锁后整个实例处于只读状态, 后续的DML写语句, DDL语句, 已经进行完更新操作事务的提交语句等, 都将被阻塞
- 最典型的使用场景为全库的逻辑备份, 对所有的表进行锁定, 从而保证数据的完整性
- `mysqldump` : MySQL中提供数据备份的工具

**特点**
- 数据库中加全局锁是一个比较重的操作, 存在以下问题
	1. 如果在主库上备份, 那么备份期间无法执行数据库的更新, 业务基本停摆
	2. 如果在从库上备份, 那么备份期间从库无法执行主库同步过来的二进制日志, 导致主从延迟
- 在InnoDB引擎中, 可以通过在备份时加上参数`--single-transaction`完成不加锁的一致性数据备份

**语法**
- 加全局锁
```mysql
flush tables with read lock;
```
- 执行备份 - 在命令行中执行, 不要作为SQL执行
- 将数据库中的信息备份到SQL文件当中
```shell
mysqldump -uroot -p **** itcast > itcast.sql
```
- 解锁
```mysql
unlock tables;
```

# 表级锁

**介绍**
- 表级锁每次操作锁住整张表, 锁定粒度大, 发生锁冲突的概率最高, 并发度最低
- 应用在 `MyISAM`, `InnoDB`, `BDB` 等存储引擎当中

**分类**
- 表锁
- 元数据锁 (Meta data lock, MDL)
- 意向锁

### 表锁

**介绍**
- 对于表锁, 主要分为两类
- 表共享读锁 (read lock)
	- 读锁, 所有客户端都只能读, 不能写
- 表独占写锁 (write lock)
	- 写锁, 加锁的客户端既能读也能写, 其他客户端既不能读, 也不能写

**语法**
- 加锁 : `lock tables 表名... read/write`
- 释放锁 : `unlock tables` / 客户端断开连接

### 元数据锁

**介绍**
- MDL加锁过程是系统自动控制, 无需显式使用, 在访问一张表的时候会自动加上, 表元数据可以理解为**表的结构**
- 在MySQL5.5中引入了MDL, 当对一张表进行增删改查时, 自动加MDL读锁; 当对表结构进行更改时, 自动加MDL写锁
- MDL锁的作用主要是维护表元数据的数据一致性, 在表上有活动事务时, 不可以对元数据进行写入操作
- 避免**DML语句**与**DDL语句**冲突, 保证读写的准确性

**查看元数据锁**
```mysql
select object_type, object_schema, object_name, lock_type, lock_duration from performance_schema.metadata_locks;
```

**SQL与元数据锁的对应**
- 修改表相关SQL的元数据锁与其他所有SQL添加的元数据锁都是互斥的

### 意向锁

**概念**
- 如果表中某一行存在行锁, 此时如果试图对该表添加表锁, 会导致表锁与行锁发生冲突, 所以加锁时需要对表中每一行进行检查, 效率较低
- 为了避免DML在执行时, 所加的行锁与表锁产生冲突, 在InnoDB中引入了意向锁, 使得表锁不用检查每一行数据是否加锁, 使用意向锁来减少表锁的检查
- 当某一个事务A对该表内某行添加了一个行锁的同时, 会对该表加上一个**意向锁**, 事务B试图加入表锁, 只需要检查表中是否有意向锁即可

**分类**
- 意向共享锁 (IS) : 由语句 `select ... lock in share mode` 添加
	- 与表锁共享锁(read)兼容, 与表锁排他锁(write)互斥
- 意向排他锁 (IX) : 由语句 `insert, update, delete, select ... for update` 添加
	- 与表锁共享锁(read)和表锁排他锁(write)都互斥
- 意向锁之间不会互斥

**查看意向锁**
```mysql
select object_type, object_schema, object_name, lock_type, lock_duration from performance_schema.data_locks;
```

# 行级锁

**概述**
- 行级锁, 每次操作锁住对应的行数据
- 锁定粒度最小, 发生锁冲突的概率最低, 并发度最高
- 应用在InnoDB引擎中, InnoDB的数据是基于索引组织的, 行锁是通过对索引上的索引项加锁来实现, 而不是对记录本身加锁

**分类**
- 行级锁主要分为以下三类
- 行锁 (Record Lock)
	- 锁定单个行记录的锁, 防止其他事务对此行进行update和delete
	- 在RC, RR隔离级别下都支持
- 间隙锁 (Gap Lock)
	- 锁定索引记录间隙(不含该记录) , 确保索引记录间隙不变 , 防止其他事务在这个间隙进行insert, 产生**幻读现象**
	- 在RR隔离级别下支持
- 临键锁 (Next-Key Lock)
	- 行锁和间隙锁组合, 同时锁住数据和数据前面的间隙Gap
	- 在RR隔离级别下支持

### 行锁

InnoDB实现了以下两种类型的行锁
- 共享锁 (S) : 允许一个事务去读一行, 阻止其他事务获得相同数据集的排他锁
- 排他锁 (X) : 允许获取排他锁的事务更新数据, 阻止其他事务获得相同数据集的共享锁和排他锁

**演示**
- 默认情况下, InnoDB在`REPEATABLE READ`事务隔离级别运行, InnoDB使用next-key锁进行搜索和索引扫描, 以防止幻读
- 针对唯一索引进行检索时, 对已存在的记录进行等值匹配时, 会自动优化为行锁
- InnoDB的行锁是**针对于索引**加的锁, 不通过索引条件检索数据, 那么InnoDB将对表中所有记录进行加锁, 此时就会升级为**表锁**

### 间隙锁/临键锁

- 默认情况下, InnoDB在 `REPEATABLE READ` 事务隔离级别运行, InnoDB使用next-key键进行搜索和索引扫描, 以防止出现**幻读**
	- 索引上的等值查询 (**唯一**索引) , 给不存在的记录加锁时, 优化为间隙锁
		- 如更新不存在的记录时, 会将该位置所在间隙加间隙锁
	- 索引上的等值查询 (普通索引) , 向右遍历时最后一个值不满足查询需求时, next-key lock退化为间隙锁
		- 如试图向(16,18,23)中加入对18的锁时, 会向后遍历找到23, 然后把16到23之间的所有间隙加锁, 同时也会对18加一个行锁
	- 索引上的范围查询 (唯一索引) , 会访问到不满足条件的第一个值为止
		- 会将范围边界条件上的记录添加行锁, 为其后的每个间隙添加间隙锁
- 间隙锁的唯一目的就是为了防止其他事务插入间隙中, 间隙锁可以共存, 一个事务的间隙锁并不会阻止其他事务在同一间隙上采用间隙锁
