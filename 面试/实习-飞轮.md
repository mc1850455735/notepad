
# 什么场景下会出现数据库记录与云端实际资源状态不一致的问题？你设计的状态对账机制又是如何解决这个问题的？

之所以会出现数据库记录和云端资源不一致的问题，根本原因是因为数据库操作和云端资源操作**无法放到同一个事务**内，一次申请或释放的过程要经过平台、Scale 服务、数据库、云厂商 API 等多个平台，任何一步的中断都会导致状态的不一致。项目中采用的是最终一致性方案，不追求数据库与云资源操作的原子性，而是通过持久化操作记录和周期性状态对账，使异常中断的操作最终**收敛到正确状态**。

具体来说，以下是几种可能的问题场景：
首先，就是云端操作成功，但是没有成功写回到数据库。以申请集群为例，云厂商可能已经创建了对应实例，但是在返回的过程中，由于网络或者进程重启等问题，导致云上存在及其但是数据库中没有对对应机器记录其状态，导致数据库记录和实际云端不一致。
同理，对于多节点集群，或者集群扩缩容的状态，可能会遇到，部分节点申请成功，另外的节点申请时，服务挂掉等，导致数据库中记录和云端记录出现不一致的情况。
为此，我补充了状态对账机制，该机制以持久化操作记录为入口，**定期关联外部任务**，并根据实际执行结果修正状态，必要时对实例进行补充清理。

具体来说，以申请流程为例，对账相关机制如下：
申请实际操作开始前，数据库中会先记录操作记录，同时关联**资源管理服务的 taskid 和 requestid**，即使外部的 taskid 还未来得及保存，也可以根据 requestid 找回任务。

随后，服务启动时，进行一次状态对账，随后每 15 秒扫描一次 pending 和 running 的操作，如果**可以查询到外部记录的结果**，同步操作状态和关联的工作流步骤，如果外部任务缺失或者不存在对应的外部任务，则根据操作类型去查询云端资源，判断云端资源是否存在，如果目标实例确实不存在，则完成本地记录和数据库内容的清理。

对于申请操作，需要进行额外保护。
对于正在执行的申请记录，会直接跳过补偿操作；对于**失去归属**的申请操作，还需要经过宽限期判断。如果**确认需要补偿**，则根据已保存的资源 id 等记录定位到本次申请的资源，清理残留并结束操作。如果出现查询失败、清理失败等操作时，由于无法确认状态，不会在该轮进行操作，而是等待下一轮操作。

# 单集群串行，多集群并行，这套调度机制具体是如何实现的？尤其是调度器使用了什么数据结构来管理不同集群的待执行任务，以及如何保证同一集群不会有两个工作流同时执行？

我在任务提交和 step 执行之间添加了一层按集群组织的调度，核心结构是，一个集群对应一个 Executor，每个 Executor 拥有自己的 1024 大小的缓冲 channel 和 用于消费任务的 goroutine。

代码中使用 map 管理集群到 Executor 之间的关系，集群名作为 map 的 key，value 为一个 `*Executor`。channel 中储存的对象类型是 workflow，也就是用户提交的流水线任务。一个任务提交时，会被持久化为一个 workflow 并存储到数据库中，状态为 pending，随后根据 workflow 中的集群名找到对应的 executor，将任务提交到其中的 channel。

executor 在集群第一次接受请求时创建，采用读写锁进行保护，如果有两个工作流同时提交，且工作流要操作的集群属于同一个，在 Map 中创建 Executor 的相关代码受读写锁保护，同时提交也只能创建一个 executor。同时，由于一个 Executor 中只存在一个用于消费的 goroutine，因此，每个集群在同一时间只能有一个工作流被执行。通过以上上述的两种方案，自然实现了同集群串行。

与此同时，map 的结构也天然保证了跨集群提交的两个工作流，使用的一定是不同的 goroutine，可以并行执行。此外，消费 goroutine 从队列中拿到任务之后，还会进行一次兜底判断，重新读取数据库中的任务记录，如果任务已经被取消或者被执行，则直接跳过对应任务。

# 优雅停机过程中，如果一个 Workflow 的 step 还在执行中，这时候要怎么处理？

通过优雅停机，让任务停在可恢复的位置，并保留已经执行到哪一步的依据。

首先会先判断对应的 step 是否支持恢复。服务进入 Draining 状态后停止派发新的 Workflow，对于正在执行的 Step，通过 Context 通知对应的执行逻辑服务即将退出。

如果该任务已经被提交到外部的 Jenkins、TeamCity 等，实际任务运行在外部系统，那么停机时只是退出本地监听，并保存数据库中的 Step 状态、外部任务 ID 等信息，外部任务继续执行。

服务重启后，会扫描可恢复的 Workflow，先根据数据库中持久化的任务 ID 查询对应的外部任务执行结果，如果还在运行，就继续等待；执行出结果，则更新对应 step 状态并进入下一步的处理。服务重启的恢复，主要恢复的是对外部已有任务的跟踪，而不是重新执行任务。

对于不支持恢复的 step，当前实现会通知取消并等待有限退出时间，超时后进入取消流程。Go 无法强制杀掉某个 goroutine，所以 Step 本身也需要响应 Context。

# 什么是可恢复的 Step，什么是不可恢复的 Step，判断标准是什么？

可恢复和不可恢复的边界在于，服务重启后，是否拥有对应的持久化信息，确定 Step 的执行进度并安全的继续处理。主要看三个条件：
- 执行身份和进度是否持久化；
- 重启后是否可以确认执行结果；
- 继续执行是否安全。

可恢复的情况比如，Deploy Step 会把对应任务推到 Jenkins 中，并保存对应的执行 ID，服务重启后，通过该 ID 就可以查询到对应任务的执行进度。

不可恢复的情况比如，某个本地操作执行到一半，进度并不会持久化，此时服务退出后，相应的 Step 无法继续执行，服务恢复后也无法从刚才的状态继续执行，且无法安全的重试，这种 Step 就无法恢复，只能终止、补偿或人工介入。

在项目中，通过一个方法直接判断当前 workflow 是否是可恢复的：
通过判断当前 Workflow 的下一个 Step 本身是否具备任务续接、检查点或状态对账能力，或是否为 Jenkins、TeamCity、Kestra 任务，或者是手动指定的其他特定任务时，被视为可恢复的 Step，否则该 Step 不可恢复，使对应 WorkFlow 也被视为不可恢复。
