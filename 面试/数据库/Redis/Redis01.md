
# Redis 基础概念

### 概念
- Redis 是一个开源的, 基于内存的非关系型数据库, 以键值对的形式存储数据, 并且支持多种数据结构

### 优缺点
**优点**
- **性能高, 速度快**: 数据存储在内存, 读写速度快, 适合缓存和实时数据处理
- **多数据结构支持**: Redis 支持多种数据结构, 适合各种应用场景.
- **发布-订阅模式**: Redis 支持发布订阅模式, 可应用于消息队列, 实时通信等.
- **持久化**: Redis 支持 RDB 和 AOF 两种持久化方式, 可以定期将内存中的数据保存到磁盘中, 保证数据的可靠性.
- **原子性操作**: Redis 操作的命令是原子性的, 可以保证并发操作时的一致性
- **Lua脚本支持**: Redis 支持 Lua 脚本, 可以通过编写自定义脚本实现复杂逻辑
- **分布式锁支持**: Redis 提供了简单分布式锁实现, 可以解决多个系统实例之间的资源竞争问题.
- **空间与时间效率**: Redis 数据结构设计兼顾空间与时间效率, 可降低对系统资源的占用.
- **易于拓展**: Redis 支持主从同步, Sentinal 集群管理和 Redis Cluster 分布式架构, 可满足水平拓展的场景.

**缺点**
- **内存限制**: Redis 将数据保存到内存中, 受限于物理内存大小, 存储空间有限
- **单线程处理**: 由于单线程的特性, 导致 Redis 的性能受限于单核 CPU 的瓶颈, 无法充分利用多核 CPU 资源, 极端情况下可能导致性能瓶颈.
- **数据安全性**: 相比于存储在磁盘中的数据, Redis 中的数据存储在内存中, 如果出现突然等极端情况, 数据可能丢失最近的更改.
- **存储成本高昂**: 相比于磁盘, 内存存储在大容量长时间存储场景下成本更高昂
- **集群管理复杂**: Redis 虽然支持集群管理, 但与其他分布式数据库相比, 搭建和维护 Redis 集群的复杂度较高.
- **身份验证安全性**: Redis 默认情况下没有内置身份验证机制, 需要进行额外配置来确保数据安全.

### 应用场景
- **缓存系统** : Redis 可以用来作为应用程序和数据库之间的缓存层, 用来存储热点数据或者其他频繁访问的数据, 提高数据的查询速度, 减少数据库服务器的压力.
- **计数器** : 通过 `Redis` 中 `INCR` 和 `DECR` 操作的原子性可以实现各种计数器, 如网页访问量, 社媒点赞数等信息. 
- **消息队列** : 通过 `Redis` 中的 `List` 数据结构可以实现简单的消息队列系统. 通过 `LPUSH` 向队列添加消息, `RPOP` 从队列中取出消息, 利用阻塞操作等待并取出队列中的消息.
- **排行榜** : 利用 `ZSet` 可以维护试试的排行榜数据, 并通过 `zrevrange` 操作获取前N名成员.
- **实时分析** : `Redis` 的高性能和数据结构可以用于监控和分析实时数据.
- **Session共享** : 在分布式系统中, 为实现 `Session` 数据的共享读/写, 通常会将 `Session` 数据存储在 `Redis` 中, 各个服务器之间可以共享 `Session` 数据.
- **分布式锁** : `Redis` 的分布式特征和原子性操作使其适合用作分布式锁的实现, 可以帮助接近分布式系统中的并发访问问题.

# Redis为什么快
- **内存存储** : Redis 将所有数据都保存在内存中, 读写速度远超磁盘.
- **非阻塞IO** : Redis 采用基于多路复用技术的事件处理模型, 可以处理大量并发请求, 即使高并发情况下也可以保持稳定的响应时间.
- **优化数据结构** : Redis 中的数据结构可以更精细的操作数据, 对数据的操作更有针对性, 提高操作的效率.
- **单线程操作** : Redis 操作都是**单线程**的, 避免了传统数据库因多线程引起的各类问题, 如上下文切换, 锁竞争等.
- **复制的特性** : Redis 通过主从复制的方式实现数据备份, 且复制操作是非阻塞的, 除非处于主从复制 (SYNC) 状态, 否则主服务无需阻塞其他操作.
- **持久化设计** : Redis 提供了 RDB 和 AOF 两种持久化策略, 用户可以根据自己的需要选择合适的持久化策略, 以平衡数据安全性和运行效率. 允许 Redis 在保持性能的同时提供数据持久性.

# Redis持久化

### 概念
- Redis 持久化是指将内存中的数据保存到磁盘, 以便在服务重启或故障后可以恢复数据的机制. Redis 本质是内存数据库, 内存中数据在服务器宕机后都会丢失. 持久化用于保证数据不会因进程退出或机器重启而丢失.
- Redis 中主要有 RDB 和 AOF 两种持久化存储方式. `RDB` 通过快照的形式进行持久化存储, 恢复速度快, 对性能影响小, 但是可能丢失最近一次快照记录; `AOF` 通过追加日志实现持久化存储, 数据恢复最完整, 丢失可控制在秒级, 但文件更大, 性能开销相对较高.
- 通常情况下会同时使用 `RDB` 和 `AOF` 两种持久化方法. 让 `RDB` 用于数据备份, `AOF` 用于数据恢复.

### RDB
- `RDB` 方式按照预设规则定期将内存中数据写入磁盘中的二进制文件, 使用 `snapshot` 快照形式写入. `RDB` 文件的保存位置是在 `Redis` 配置文件中指定的.
- `RDB` 的快照规则可以自定义, `Redis` 重启时, 通过读取 `.rdb` 文件恢复数据
- 优点: `RDB` 是一个非常紧凑的数据集的单文件表示形式, 适合用于备份, 全量复制等操作; `Redis` 重载 `RDB` 文件速度快, 适合用于灾难恢复.
- 缺点: 最近操作可能不会被持久化, 从而导致数据丢失; RDB 进行保存操作时, 父进程可能使用 `fork()`, 数据库较大时耗费服务器性能.

### AOF
- `AOF` 方式会记录每一次对 `Redis` 的写操作, `Redis` 重启时会重新执行这些命令用于恢复原始数据. `AOF` 文件的保存位置是在 `Redis` 配置文件中指定的.
- 优点: `AOF` 数据完整性优于 `RDB`, 且可读性好; `AOF` 提供了更多的策略, 如每秒同步一次, 每次写入同步一次, 或不做同步等策略.
- 缺点: 对于相同数据, `AOF` 文件体积通常比 `RDB` 文件体积更大; 根据选用的 `fsync` 策略不同, `AOF` 在某些配置下可能比 `RDB` 更慢一些.

# Redis事务

### 概念
- Redis 中事务的本质就是通过命令 (`MULTI`, `EXEC`, `WATCH`) 一次性, 顺序性地执行一组命令地机制. 事务中所有命令都会被打包后按顺序执行, 不会被其他客户端的命令插入, 从而保证系列操作一定程度的原子性.
- 总结来说, 事务就是一次性, 顺序性, 排他性的执行一个队列中的一系列命令.

### 事务阶段
1. 使用 `Multi` 命令开始一个事务
2. 在使用 `Exec` 执行事务之前, 所有命令都不会立即执行, 而是被入队
3. 通过 `Exec` 执行队列中的所有命令, 标志着事务的执行阶段.
4. `Exec` 执行后, 整个事务被视为已完成, 不做任何操作即可结束事务.
- Redis 中事务不支持回滚, Exec 执行开始后, 即使事务执行过程中出现失败, 也不会终止, 而是继续向下执行.

### 事务 ACID
- **原子性(Atomic)** : Redis 中单条命令是满足原子性的, 但是事务不保证原子性, 且没有回滚操作. 任意命令执行失败, 其余操作依然会继续向下执行.
- **一致性(Consistency)** : Redis 的数据模型不存在复杂的一致性约束, 但是可以藉由单个命令的原子性和 Lua 脚本复杂原子操作, 在业务层面保持一致性.
- **隔离性(Isolation)** : Redis 是单线程模型, 命令之间串行执行, 事务之间互不影响, 满足隔离性需求
- **持久性(Durability)** : 事务只要执行成功, 就可以被通过 RDB 或 AOF 持久化到磁盘中.

# Redis Lua脚本

### 好处
- **原子性保证**: Lua 脚本在 Redis 中会被作为一个整体执行, 中途不会被其他命令插入, 具备天然原子性, 避免并发竞争问题. 同时逻辑集中在 Redis 内部执行, 避免客户端多步操作带来的状态不一致问题.
- **提高系统性能**: 多个命令合并写入 Lua 脚本一次性执行, 避免客户端与 Redis 多次网络往返; 同时在 Redis 内可直接完成部分复杂逻辑, 避免因数据频繁传输导致的执行效率降低, 提高执行效率
- **逻辑可复用**: 脚本可以复用和参数化, 使代码更易维护

### 与事务比较
- **更强的灵活性**: Redis 事务无法依赖于前一个命令的结果来进行后续的处理, 但Lua脚本提供了更强的灵活性. 通过编写脚本, 开发者可以设计出更符合业务需求的事务处理方案
- **提供原子性操作**: 虽然 Redis 的事务可以保证一组命令的原子性执行, 但不能保证在执行过程中数据不被其他客户端修改. 而 Lua 脚本则可以避免这种情况, 所有命令在同一 Lua 脚本中执行, 从而保证数据在执行过程中的一致性
- **减轻服务器压力**: 使用 Redis 内置的事务功能, 每个命令都需要进行网络通信, 增加服务器的压力; 而将命令放入 Lua 脚本执行, 只需要一次通信. 既减轻了服务器压力又提高了执行效率

### 原子性实质
- Redis 中 Lua 脚本保证的原子性并不是数据库层面上的原子性, 而是指 Lua 脚本在执行过程中具有独占性, 操作不会分割.
- Lua 脚本的原子性是一种执行粒度上的原子性, 属于并发控制上的原子性, 而不是 ACID 事务上的原子性. 其原子更多的是原子命令的意思.
- Lua 脚本不具有自动回滚功能, 如果失败整个脚本都会失败, 但是已经修改的数据不会 Rollback.
- Lua 脚本不支持事务隔离等级机制. 其运行于单线程的 Redis 线程中, 没有多事务隔离的概念.
- Lua 脚本不支持事务日志与持久化一致性事务. Redis 中虽然有 AOF/RDB 等持久化策略, 但不是 ACID 风格的事务日志.

# Redis互斥锁

### 实现演进
- 实现1: 直接使用 `SETNX` 加锁, `del` 释放锁. 加锁没有过期时间, 且 `del` 时不区分锁的主人, 可能出现**死锁**现象或**误删锁**等情况.
- 实现2: 使用 `SETNX` 加锁, `del` 释放锁. 通过 `setnx` 加锁后通过 `expire` 设置过期时间, 确保不会出现死锁现象. 设置锁时同时在 `value` 设置锁的拥有者, 防止误删锁的现象发生. 但这种方法加锁和设置过期时间是两条命令, 不是原子操作, 存在中间状态.
- 实现3: 使用 Set 命令/ Lua 脚本同时实现加锁和过期时间的设置, 保证操作的原子性, 同时使用 Lua 可以实现复杂的原子操作. 但当业务执行时间大于锁的过期时间是, 锁会自动过期解锁, 其他客户端可以得到本不应释放的锁, 导致多个客户端同时进入临界区
- 实现4: 在客户端设置看门狗线程, 负责定期给当前客户端持有的锁延长过期时间, 业务结束后, 正常使用 Lua 脚本释放锁.

### 实现机理

##### 单Redis实例互斥锁
- 常用, 思想为实现4, 即使用 setnx + Lua 脚本+看门狗自动续约的方式实现互斥锁. 同时允许客户端逻辑控制实现可重入锁/公平锁. 适用于单机应用或对可靠性要求不极端的场景.
- **优点**: 实现方法简单, 易实现且性能好
- **缺点**: 安全性差, 只能依赖单一 Redis 实例的可靠性, 当该实例宕机时 Redis 锁便会丢失; 同时主从切换的不一致可能导致短时间内锁异常

##### RedLock分布式锁
- 红锁是 Redis 作者提出的一种基于 Redis 的分布式锁算法
- 部署N个相互独立的 Redis 节点 (N通常是奇数) , 客户端依次尝试在每个 Redis 节点中获取同名锁, 统计在时间窗口内成功获得的锁的数量, 如果获取锁成功的节点数超过一般, 则认为获取锁成功. 释放锁时通过 Lua 脚本对所有节点执行解锁操作.
- 作用: 通过多个独立实例提高锁的可用性与安全性, 避免单个节点宕机导致锁完全失效. 是一种提高锁可靠性的方案, 但不是银弹. 如果对锁可靠性有严格要求, 还需要进行高幂等的业务设计等额外方案

##### 第三方依赖
- 使用一些封装好的库, 如 Redisson, Jedis / Lettuce 等

### 达到最大内存
- 当 Redis 内存达到最大限制后, 可以通过实现配置的内存淘汰策略, 对 Redis 中的 key 进行淘汰, 也可以采用额外措施, 对 Redis 进行扩容或压缩等.

#### 淘汰
- `noeviction` (默认): 不淘汰任何数据, 当 Redis 满后, 后续任何写入命令都将直接报错 `OOM`, 适用于只读或者严格内存控制的场景.
- `volatile-*` : 只淘汰设置了 `TTL` 的 key, 共有四种淘汰策略
	- `lru` : 淘汰最近最少使用的
	- `ttl` : 淘汰 `TTL` 最快过期的
	- `lfu` : 淘汰最不常用的
	- `random` : 随机淘汰 (带 TTL)
- `allkeys-*` : 所有 key 都有可能被淘汰, 共有三种淘汰策略
	- `lru` : 淘汰最近最少使用的
	- `lfu` : 淘汰最不常用的
	- `random` : 随机淘汰 (带 TTL)

#### 扩容/压缩
- 增大 maxmemory (常用)
- 扩容/分片 : 在 Cluster 模式中
- 优化 key 大小与 value 结构, 减少内存占用
- 使用 Redis 的数据压缩特性 (如 Redis 7.0 字典共享机制等)

# 缓存问题

### 击穿
- **缓存击穿**也叫热点 Key 问题, 就是一个被高并发访问且缓存重建业务较复杂的 Key 突然失效, 导致大量请求访问瞬间给服务器带来巨大冲击
- **解决策略**
	- **互斥锁**: 当热点 key 失效时, 通过互斥锁, 只允许一个线程查询并重建缓存, 其他并发线程阻塞等待或者返回默认值. 分布式锁必须设置过期时间, 且过期时间需要大于数据库查询+缓存写入的最大耗时之和. 同时设置最大重试次数, 避免无限等待. 适用于可以接收短暂请求阻塞的场景, 且对数据一致性高要求的同时热点 key 更新频繁的场景.
	- **逻辑过期**: 热点 key 是系统核心高频访问的数据. 通过业务逻辑而不是 Redis 过期时间控制, 实现 key 逻辑过期, 逻辑过期时直接取已过期数据. 适用于热点 key 相对稳定, 同时可以接收短期不一致, 以及对性能有高要求的场景.
	- **缓存预热**: 对于某些可预测的热点 key (如秒杀商品, 节日活动等), 在系统启动时主动将热点 key 加载到 Redis 中, 避免首次访问为空导致大量数据库请求; 适用于可提前得知的热点 key, 且系统启动时无大量用户访问, 但无法应对突发热点 (如突发新闻等).

### 穿透
- **缓存穿透**指的是客户端请求的数据在缓存中和数据库中都不存在, 这样的缓存永远都不会生效, 所有请求都会达到数据库
- **解决策略**
	- **缓存空对象**: 对数据库中不存在的数据, 在 Redis 中缓存一个空值, 并设置一个较短的过期时间, 短时间内后续相同请求会直接打到缓存中. 实现简单, 但可能占用过多内存空间.
	- **布隆过滤器**: 是一种概率性数据结构, 可以用来判断某元素是否可能存在于集合中, 且空间占用极小. 缺点是存在误判可能, 认为存在则不一定真实存在, 但认为不存在必定不存在
	- **加强请求参数校验**: 通过配置过滤规则, 过滤明显非法的请求, 如格式错误, 超出合理范围等. 从请求入口处拦截非法请求, 避免无效请求到达缓存或数据库.
	- **限流熔断**: 对于单个IP/用户/接口的请求频率进行限制, 防止短时间内恶意高频请求冲击.

### 雪崩
- **缓存雪崩**是指在同一时间段内大量的缓存 key 同时失效或者 Redis 服务器直接宕机, 导致大量请求直接到达数据库, 为数据库带来巨大压力.
- **解决策略**
	- **打散过期时间**: 雪崩的主要原因就是大量 key 同时过期. 通过给每个 key 过期时间都添加随机偏移量, 打散过期时间, 避免瞬间集体失效, 将数据库压力进行平摊.
	- **构建 Redis 集群**: 通过构建 Redis 集群提高缓存层的可用性, 确保缓存服务层不宕机, 不丢失数据, 防止单体 Redis 因服务器宕机导致的缓存层整体不可用, 核心是数据冗余+故障自动切换.
	- **添加熔断降级策略**: 当 Redis 集群出现故障导致缓存层不可用时, 通过熔断降级策略, 直接拒绝部分请求或返回默认值, 避免所有请求直接穿透导数据库, 保护数据库不被压垮.
	- **配置合理淘汰策略**: Redis 内存满后会触发提前配置好的内存淘汰策略, 如果淘汰策略不合理, 则可能导致大量热点 key 被批量淘汰.
