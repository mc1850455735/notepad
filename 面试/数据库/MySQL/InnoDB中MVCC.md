# MVCC

MVCC 用于控制并发事务执行过程中的数据可见性问题, 保证数据读写过程中的各个事务之间数据的一致性和隔离性. MVCC 通过快照的方式保证各个事务之间数据的独立. 通过MVCC, 实现了不同事务一定程度上的并发执行.

**读操作**
- 当事务执行读操作时, 会使用快照读取的方式. 会截取事务执行时的数据库状态创建快照, 并在该快照的基础上执行查询操作, 因此不会读取到其他事务尚未提交的修改.
- 进行读操作时, 事务会选取符合条件的数据行进行读取, 如果数据行存在多个版本, 则事务会选择不晚于事务开始时间的最新版本, 确保事务读取数据最新的同时保证事务只读取该事务开始前已经存在的数据.

**写操作**
- 当事务执行写操作时, 事务会为要修改的数据行创建一个新版本, 并将修改后的数据存入新版本, 新版本数据会带有当前事务的版本号, 确保其他事务可以正确读取到相应版本的数据. 原始版本的数据仍存在, 供其他事务快照使用, 保证了其他事务不受当前事务写操作的影响.

**事务提交**
- 当一个事务被提交后, 他所做的修改将成为数据的最新版本, 对其他事务可见
- 当事务撤销时,所进行的修改将被撤销, 对其他事务不可见.

**版本回收**
- 为避免MVCC持续增长, MVCC会定期进行版本回收, 删除已经不再需要的旧版本数据.

# InnoDB中MVCC实现

### 隐藏字段
- InnoDB引擎为每行数据添加了3个隐藏字段:
- `DB_TRX_ID` : 表示最后一次插入或更新该行的事务id. delete 操作同样被视为更新, 只是更新记录头 `Record Header` 中的 `deleted_flag` 字段
- `DB_ROLL_PTR` : 回滚指针, 指向该行的 undo log. 如果改行未被更新过则返回空
- `DB_ROW_ID` : 如果该表没有设置主键且该表内没有设置唯一非空索引, InnoDB 将使用该ID生成聚簇索引

### ReadView
- `Readview` 主要用来进行可见性判断, 其中保存了对当前事务不可见的其他活跃事务, 事务的可见性与 ReadView 的创建时机密切相关. 其中主要有以下字段:
- `m_ids` : `ReadView` 创建时记录的当前活跃的其他事务ID集合, 后续即使其中事务修改了记录的值, 对当前事务也是不可见的. `m_ids` 不包含当前事务本身以及其他已提交的事务.
- `m_low_limit_id` : 目前出现过的最大事务id + 1, 大于等于这个事务id的数据版本对当前事务来说都是不可见的.
- `m_up_limit_id` : 当前活跃事务的最小事务id. 任何小于这个事务id的数据版本对当前事务都是可见的. 如果没有正在活跃事务, 则 `m_up_limit_id` 等于 `m_low_limit_id`
- `m_creator_trx_id` : 创建该 `Read View` 的事务 ID

### undo-log
- undo-log 主要用于回滚过程中的数据恢复以及 `MVCC` 中的版本管理. 如果该记录当前版本对该事务不可用, 则可以通过 `undo-log` 获取之前的版本数据, 实现非锁定读
- undo log 分为两种, 分别是 `insert undo log` 和 `update undo log` . 
- 对于 `insert` 操作, 该记录只对事务本身可见, 对其他事务不可见, 所以可以在事务提交后直接删除 `undo log`
- 对于 `update/delete` 操作, 该操作产生的 `undo log` 可能在后续为 `MVCC` 提供支持, 因此不能在事务提交后立即删除, 应在提交后放入 `undo log` 链表待 `purge线程` 进行最后删除

### 可见性算法
- 在 InnoDB 中, 创建一个新事物后, 执行每个 select 语句前, 都会创建一个快照 ReadView. 通过 ReadView, 可以得到记录行是否满足可见性条件以及记录行的哪个版本满足可见性条件.
- `DB_TRX_ID` 为记录的**最新**修改事务id, 具体判断规则如下:
- `DB_TRX_ID < m_up_limit_id` : 该条记录在该ReadView创建前就提交了, 对当前事务是可见的.
- `DB_TRX_ID >= m_low_limit_id` : 该条记录在该ReadView创建后才进行修改, 对当前事务是不可见的.
- `m_ids` 为空, 说明 `ReadView` 创建时数据库中不存在任何正在运行的事务, 所有事务均执行完毕, 该记录行的值对当前事务是可见的.
- 当 `m_up_limit_id <= DB_TRX_ID < m_low_limit_id` 时, 说明最新修改该行的事务在当前事务创建快照时处于活跃状态, 所以应在活跃事务列表 `m_ids` 中进行查找. 
	- 如果活跃事务列表中可以找到 `DB_TRX_ID`, 则说明在 `ReadView` 创建前该行数据被事务修改后未提交, 或在 `ReadView` 创建后该行数据被事务修改. 此时说明该记录值对当前事务是不可见的.
	- 如果活跃事务列表中不存在 `DB_TRX_ID`, 说明对应事务在修改了对应行记录后, 在 ReadView 快照创建前就进行了提交, 记录值对当前事务可见.
- 如果查到记录对事务不可见, 则在该记录行的 `DB_ROLL_PTR` 指针所指向的 `undo log` 中取出快照记录, 用快照记录的 `DB_TRX_ID` (对记录修改的次新事务) 重新开始判断, 直到找到满足条件的快照版本.

# RC与RR隔离级别
- RR(Repeatable Read) 和 RC(Read Committed) 是 InnoDB 的两个事务隔离级别, 默认情况下, MySQL 中 InnoDB 引擎使用 `RR` 隔离级别,, 通过 MVCC (非锁定一致性读) 实现事务隔离. 
- RR 和 RC 生成 ReadView 的时机不同. 对于 RC, 每次进行 select 操作时都会生成一个 ReadView, 而对于 RR, 只有事务内第一次 select 会生成 ReadView, 随后的 select 会使用第一次生成的 ReadView

# MVCC不可重复读
- 由于 RC 和 RR 生成 ReadView 的策略不同, 从而导致了 RC 策略下存在不可重复读的问题, 而 RR 解决了此类问题.
- 在 RC 中, 每次 select 都会产生一个 ReadView, 从而导致在事务内部如果有其他事务修改数据并提交, 则事务内部两次 select 的结果会产生差距, 从而导致不可重复读现象的出现
- 在 RR 中, 只在当前事务的第一次 select 时产生 ReadView, 后续过程中所有的 select 操作全都使用同一个 ReadView, 使得即使其他事务对表内字段产生了修改, 对当前事务来说都是不可见的, 从而实现可重复读.

# MVCC+临键锁防止幻读
- InnoDB 引擎在 RR 级别下通过 MVCC 和 next-key lock 解决幻读问题
- 当执行普通 select 时, MVCC 会通过快照读的方式读取数据. RR 隔离级别下只会记录第一次 select 查询时的 ReadView, 在 ReadView 生成后创建和修改的记录, 其版本号对当前事务的查询是不可见的. 从而实现了可重复读以及防止快照读下的幻读.
- 当执行当前读时, 读取的都是最新数据, 如果有其他事务在此过程中插入记录, 且刚好在当前读的查询范围内, 就会产生幻读现象. 解决方法是在查询时, 不光锁定查询到的记录, 同时锁定他们之间的间隙, 禁止其他事务在间隙内插入数据, 自然就不再会出现幻读.
