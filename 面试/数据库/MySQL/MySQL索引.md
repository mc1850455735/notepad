# 索引介绍

索引是一种用于快速查询和检索数据的数据结构，本质可以看作是一种排序好的数据结构。对于数据库表而言，索引相当于书的目录，通过目录可以快速检索书中的内容。

索引实现的底层数据结构存在多种类型，常见有 B树、B+ 树和 Hash、红黑树。在 MySQL 中，无论是 InnoDB 引擎还是 MyISAM 引擎，都使用了 B+ 树作为其索引结构。

# 常见索引类型

## 按应用维度

**MySQL 5.x**

- **主键索引**：表中用于唯一标识一行数据的索引。主键索引唯一且非空，一张表中只能存在一个主键索引。在存在主键索引的情况下，InnoDB 使用主键索引作为聚簇索引。
- **唯一索引**：保证索引列的值唯一。一个数据表中可以有多个，MySQL 中唯一索引允许存在多个 `NULL` 值。如果不存在显式主键，InnoDB 会选择第一个**非空唯一索引**作为聚簇索引。
- **普通索引**：最基本的索引，不做限制。使用最广泛，用于提升查询性能。
- **复合索引**：由多个列组成的索引，其最核心的规则是最左前缀原则。可以覆盖多个查询条件，使用时通常将等值查询条件和选择性较高的列在前，范围查询和排序字段在后。
- **覆盖索引**：覆盖索引，即查询字段全部包含在索引中，无需回表。极大减少 I/O，常用于高性能查询。
- **全文索引**：用于对字符串类型字段（`CHAR` / `VARCHAR` / `TEXT`）进行分词搜索。通常用于搜索文章、评论等。值得注意的是，现在通常不使用 MySQL 全文检索来查找文章内容，而是使用搜索引擎（如 ElasticSearch）。
- **前缀索引**：MySQL 中针对字符串类型字段的一种索引方式，用于对对字符串列的前 N 个字符建立索引。当字符串为长文本时，其索引 B+ 树节点中需要存储很长的字符串，会增大索引体积，占用磁盘空间, 浪费磁盘 IO。通过只将字符串的一部分前缀建立索引，节约索引空间, 提高索引效率。

**MySQL 8.x**

- 隐藏索引：也称为不可见索引，不会被优化器使用，但是仍然需要维护，通常会软删除和灰度发布的场景中使用。主键不能设置为隐藏索引（无论显式设置或隐式设置）。
- 降序索引：之前的版本就支持通过 desc 来指定索引为降序，但实际上创建的仍然是常规的升序索引。直到 MySQL 8.x 版本才开始真正支持降序索引。另外，在 MySQL 8.x 版本中，不再对 `GROUP BY` 语句进行隐式排序。
- 函数索引：从 MySQL 8.0.13 版本开始支持在索引中使用函数或者表达式的值，也就是在索引中可以包含函数或者表达式。

# 索引优缺点

## 优点

1. 通过索引，将数据库的全表扫描改为在 B+ 树上的扫描，大幅减少需要扫描的数据量，显著加速数据检索速度，减少磁盘 IO 次数
2. 通过创建唯一索引，可以保证表中某一列或几列组合的值是独一无二的，如用户ID、邮箱等。主键索引也是一种唯一索引。
3. 如果查询中的 `ORDER BY` 或 `GROUP BY` 子句涉及的列建有索引，数据库可以直接利用索引避免额外的排序操作，从而提升性能。

## 缺点

1. 创建和维护耗时，创建索引本身就需要时间，同时当表中数据进行增删改操作时，不仅需要修改数据本身，还需要根据相关索引的变化为 B+ 树进行更新和维护，这同样会导致 DML 操作效率降低。
2. MySQL 中的索引本质上是一种 B+ 树数据结构，需要以物理文件的形式存储，会额外占用一定的磁盘空间。
3. 如果索引设计不当或查询语句写的不好，数据库优化器可能不会选择使用索引或选错索引，反而导致性能下降。

用了索引不是一定可以提高查询性能的，在大多数情况下，索引查找确实快于全表扫描，但是当表中数据量很小，或查询结果集占比过大时，全表扫描效率都是优于索引查找的，因为全表扫描本身就是有成本的。同时如果索引维护不当或统计信息过时，也有可能导致优化器作出错误判断。

# 复合索引

复合索引，也叫组合索引或联合索引。其使用表中的多个字段创建索引，索引使用过程中需要参考**最左前缀匹配原则**。

## 优点

1. 复合索引通过一次索引，在符合最左前缀原则的情况下，可同时支持多个查询条件，相比多个单列索引数量更少、查询路径更清晰。
2. 复合索引在 B+Tree 中是按联合键排序，通常只选一个索引，避免了索引合并、多次扫描 B+ 树与临时结果集的创建。
3. 可以直接利用索引顺序同时优化 `WHERE` + `ORDER BY` / `GROUP BY`，避免了 `filesort`
4. 将查询字段放入同一个复合索引中可天然形成覆盖索引，实现联合过滤，做到不回表的查询。
5. 一个复合索引可替代多个单列索引，使索引数量更可控，减少索引管理成本。

## 缺点

1. 受最左前缀原则限制，查询时严格依赖列顺序，一旦查询模式变化，索引可能失效。
2. 索引设计难度高，设计时需考虑查询条件、过滤顺序、排序需求等要求，如果设计不当，会造成索引浪费，无法通过索引命中查询。
3. 相比普通索引，覆盖索引更宽，索引条目更大，会占用更多存储空间，对内存和磁盘不友好。
4. 在进行 `INSERT` / `UPDATE` / `DELETE` 时，需要同时维护所有复合索引，导致写性能下降。

# 常见索引失效情况

- 对于联合索引，不符合最左前缀法则时，联合索引只能部分使用或完全无法使用。
	- **最左前缀法则**：查询要从索引最左列开始, 并且不跳过中间的列（这里的中间的列和声明联合索引顺序有关，和查询条件顺序无关）。如果查询时跳过了某一列，该列索引之后的字段索引都将失效。

- 联合索引中，当自左向右匹配，直到遇到范围查询条件时，该范围查询条件右侧的列索引失效。但是对于 `>=`、`<=`、`BETWEEN`、`like 前缀匹配` 这四种范围查询，并不会停止匹配。
- 在索引列上进行运算操作（包括使用函数）时，索引列不再是可直接比较的有序值，从而无法进行有效的索引查找（MySQL 8.x 中的函数索引是例外）。
- 当查询条件中字段类型与索引列类型不一致，需要进行转换时（如字符串转整数或整数转字符串），可能导致索引列参与函数计算，从而同样无法利用索引，列索引失效。
- 进行模糊匹配时，若以通配符 `%` 开头（如 `%name`），无法利用 B+Tree 的有序性，索引无法使用；若仅在尾部使用通配符（如 `user%`），仍可利用索引进行范围扫描。
- 进行 or 连接时，如果 or 两侧存在没有索引或索引不生效的字段，优化器可能放弃索引而选择全表扫描；在部分场景下，也可能使用 `index merge`，但整体可预测性较差。
- MySQL 优化器会基于成本模型进行判断，依据包括 `CPU/IO` 成本、查找统计信息、行数与页数等。当索引成本高于全表扫描时，则索引不生效。通常来说，当结果数据占表中多数时，全表扫描速度优于索引。
- 用户可以使用 `FORCE INDEX` 强制 MySQL 优化器使用索引，但这种方式会绕过优化器的成本判断，存在性能退化风险，应谨慎使用。
