
# 如何理解 Agent 系统, Agent 的核心模块有哪些?

我理解 Agent 系统本质上是一个以大模型作为决策核心，通过工具与外部环境交互，并持续根据执行结果进行下一步决策的闭环系统。  
它和普通 LLM 应用最大的区别是，不只是一次 Prompt 到 Response，而是会不断执行 “模型决策 → Tool Calling → 工具执行 → 结果回传 → 再次决策” 的 Agent Loop，直到完成任务。

核心模块包括: 
- **Agent Loop**: 负责整个 Agent 的执行流程编排, 把模型调用、Tool Calling、工具执行、结果回传、再次决策串成一个闭环，直到任务完成。
- **LLM Provider**: 负责和底层大模型交互，并统一不同模型厂商的调用方式
- **Context/Memory**: 负责管理模型当前能看到的信息, 解决长会话中的上下文膨胀和关键信息保留问题
- **Tool System**: 负责给 Agent 提供操作外部环境的能力
- **Session/State**: 负责保存 Agent 当前运行状态，比如消息历史、当前任务、工具调用状态、权限审批状态等，用于支持会话恢复、任务取消和断点续跑。

# 如果用户的问题非常模糊或存在歧义，如何与用户进行澄清性对话? 

当用户问题模糊或存在歧义时，Agent 不应该直接猜测，而应该进入**澄清状态**，通过最少的问题补齐完成任务所必需的信息。

以下情况通常需要询问用户：
- 存在多个合理解释。
- 缺少必要参数。
- 不同选择会产生明显不同的结果。
- 涉及删除、发布、转账等高风险操作。
- Agent 没有权限替用户做决定。
- 即使继续检索也无法确定用户意图。

**如何提出澄清问题**
1. 一次只问最关键的问题，优先询问能够最大程度缩小方案范围的问题
2. 明确指出歧义在哪里
3. 提供少量互斥选项，选项最好控制在 2～3 个，并说明影响
4. 可以给出推荐项
5. 低风险场景可以声明假设后继续，如果选择不会造成明显风险，可以减少不必要的打断

原则是：
- 低风险、可逆 → 合理假设后继续
- 高风险、不可逆 → 必须澄清或确认

**Agent 中的实现**
可以将用户请求解析为“意图 + 槽位”，当必要槽位缺失时，Agent 暂停 Tool Call，同时保存原任务状态；确保用户确认意图后，Agent 可以知道当前需要进行的是哪个任务。

**为了避免无限澄清**
需要控制：
- 只询问必要信息。
- 设置最大澄清轮数。
- 用户不知道时提供默认方案。
- 用户明确表示“你决定”时采用推荐方案。
- 多次无法补齐时说明限制并停止。
- 不要重复询问用户已经回答过的信息。



# 什么是 Agent Loop, 一个 Agent 项目通常如何做 Agent Loop

Agent Loop 就是 Agent 的核心执行循环，Agent 接收目标后，不是只调用一次大模型，而是让模型不断在 “分析当前状态、选择下一步动作、执行工具、读取结果” 之间循环，直到完成任务或触发停止条件。

**Agent Loop 的组成**
1. **Model**
大模型根据用户目标、历史消息、当前任务状态、工具定义、工具执行结果，决定下一步的动作
2. **Tools**
对于 Agent 的一系列功能，模型本身不会真正执行这些操作，只会生成结构化 Tool Call。
3. **State**
包括：
	- 对话历史
	- 用户目标
	- 已完成步骤
	- 工具调用结果
	- 中间产物
	- Token 使用量
	- 重试次数
	- 当前任务状态
4. **Harness**
Harness 是 Agent 的运行框架。负责调用大模型、解析 Tool Call、执行工具、返回结果、控制权限、处理异常和重试，并且判断什么时候结束本轮执行。

**Agent Loop 通常的执行流程**
1. 根据环境配置，初始化 Agent 运行环境
2. 根据用户传来的描述，组装上下文
3. 将上下文传入模型，对模型进行调用
4. 校验并执行模型传回的工具调用
5. 返回工具调用结果给模型
6. 判断循环是否应该终止
