# 复杂工程的 AI Coding 如何做

第一步不是直接让 AI 写代码，而是理清问题空间和约束，避免边界不清、
模块职责不明、数据流不清 等情况。

可以让 AI 先整理需求和架构草图，并设置关键约束，同时人工审核。关键约束包括：模块边界、输入输出、存储设计、异常语义、并发模型、部署方式和可观测性。

同时可以先让 AI 生成 接口定义、目录结构、数据类、配置模板、单测骨架，再逐步填充核心逻辑。

# AI Coding 全栈开发经验

**工具**
- Trae
- Codex

**开发阶段**
- 项目框架初期构建
- 具体功能开发
- 前后端联调与问题修复

**AI Coding类型**
1. Vibe Coding
2. Plan模式
3. Harness模式

**VibeCoding**
适合小范围低风险的功能开发，如前端 UI 调整、简单 CRUD、局部样式优化。
- **优点**：开发速度快，Token消耗相对少，适合快速完成小功能和局部修改
- **缺点**：结果稳定性一般，容易误改或破坏其他功能代码，缺少完整任务记录，上下文压缩或切换对话后，AI 容易丢失历史背景。

**Plan 模式**
Plan 适合中等复杂度任务。AI 会先拆解任务，人工审查，再按照计划进行执行。
- **优点**：执行前会先规划任务，适合有明确目标但步骤较多的开发任务，同时比 VibeCoding 更容易控制修改范围；
- **缺点**：执行后不一定有明确的验收标准，如果计划本身不够详细，后续仍有可能偏离目标；对于复杂的跨模块任务，单纯使用 Plan 模式仍然容易遗漏上下文。

**Harness模式**
[参考项目：oh-my-codex](https://github.com/Yeachan-Heo/oh-my-codex)
Harness 模式适合复杂任务、跨模块任务和长期开发任务。他会记录任务运行时状态、计划、日志和记忆，把临时对话转为可追踪的工程过程。但是这种模式没有人工审查环节，更像是先斩后奏。

**优点**
- 可以存储任务状态、执行计划、日志和记忆；
- 能够根据实际执行情况动态调整任务图；
- 适合复杂功能、跨领域开发和长期任务；
- 有助于把 AI Coding 从临时会话转为工程化流程；

**缺点**：Token 消耗大、执行时间长，对于简单任务来说成本太高。


# 开发流程总结

**项目原型快速构建**
项目初期采用：人工设计+AI生成+人工 Review 的方式。
1. 分析项目需求，明确项目的基本功能和实现边界
2. 人工设计项目技术架构，选取技术栈
3. AI 辅助生成需求文档，由人工审查和纠正
4. 基于需求文档，让 AI 设计代码框架、分层结构和领域模型；
5. 使用 Agent 快速完成前后端原型搭建；
6. 人工 Review 代码结构、目录划分和核心抽象；

**具体功能开发**
涉及到具体功能开发时，会先判断任务规模
- 是否跨越多个领域模块；
- 是否设计数据库结构变更；
- 是否影响核心链路；
- 是否设计前后端协议变更；
- 是否需要补充测试或者文档。
对于小需求，使用 VibeCoding；对于代码改动范围较大，涉及多个模块或者需要长期上下文的工作，优先使用 Harness 模式。

**前后端联调**
前后端联调是全栈 AI Coding 中最容易出现问题的环节，常见于：
- API 字段未对齐
- WebSocket 协议未对齐
- 前端状态和后端返回结构不一致
- 多仓库上下文割裂，AI 只能看到一部分代码
为了解决这个问题：
- 在 Trae 中可以使用工作区功能把多个仓库合并到一个工作区，共享上下文；
- 在 Codex 中可以开启完整访问权限，使 Agent 可以跨项目读取和修改用户端、商家端、管理员端、后端和 Agent 代码。
