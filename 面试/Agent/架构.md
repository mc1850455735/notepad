
# 主流 Agent 设计架构

在现代 Coding Agent 中，三者不是完全替代关系，通常会结合使用：Spec 管目标，Plan 管步骤，ReAct Loop 管具体工具交互。

## **ReAct**

ReAct 的核心动作是让 LLM 在推理（Reasoning）和行动（Action）之间循环，根据工具返回结果继续调整下一步。

ReAct 不会提前规划完整的路线，而是使用类似于 “想一步做一步” 的执行策略；同时 ReAct 的回复强依赖于负责观察 (Observation) 的 Tool 的 Result；

**优点**
ReAct 由于采用 观察-执行-再观察 的行动路线，因此在实际执行过程中相对灵活，且对环境适应的能力强；

**缺点**
1. 长任务容易失控：模型在长上下文中不断调用和修改，可能会逐渐丢失较远的上下文，从而发生漂移、重复和遗漏等问题；
2. Token 消耗高：历史消息不断增长，会增大模型的 Token 消耗；
3. 行为难以预测：工具的调用由模型决定，调用次数不确定。

## **Plan-And-Execute**

Plan-And-Execute 的核心思想是：先让一个 Planner 制定完整计划，然后 Executor 按计划执行。

其与 ReAct 的核心区别是，ReAct 是一边想一边执行，而 Plan-And-Execute 是先规划再执行。

同时 Plan-And-Execute 还会检查每一步的执行结果；如果执行出错，则会检查 Plan 是否合理，并试图重新执行工具或者重新制定 Plan。

## **Spec**

Spec 架构是一种规范驱动的 Agent 设计方式，它不会让模型直接根据用户输入执行任务，而是先将用户需求转换成结构化 Specification，明确任务目标、约束条件、执行步骤和验收标准。

之后 Planner 根据 Spec 生成任务计划，Executor 调用工具完成任务，Verifier 根据 Spec 检查结果，不满足要求时触发重新规划。

相比 ReAct 这种边思考边执行模式，Spec 架构更适合长流程、复杂任务，例如 Coding Agent，因为它提高了任务可控性、可恢复性和可验证性。







第一类是 ReAct，边推理边行动，模型通过思考、调用工具、观察结果、再调用工具完成任务；

第二类是 Plan-and-Execute，先做规划，再按步骤执行任务，比纯 ReAct 更稳，适合长流程任务；

第三类是 Router 模式，先分类任务，再路由给不同的子 Agent 或工具链进行执行；

第四类是 Workflow + Agent，在 Workflow 的固定流程中镶嵌 Agent 进行局部自主决策。

多 Agent 中，还有 Supervisor 模式，由主 Agent 拆解任务，分派给多个子 Agent 执行；Blackboard 模式，多个 Agent 通过共享状态的方式进行协作。

# 调用大模型的过程中出现幻觉怎么办

大模型的幻觉无法完全消除，因此设计上不能直接相信模型生成的事实、工具参数和完成声明。我的处理方式是让模型负责规划和决策建议，让确定性程序负责参数校验、权限控制和工具执行，并通过数据库回查、测试或外部 API 结果验证任务是否真正完成。证据不足时允许拒答，执行失败时进行有限重试，高风险操作加入人工审批，同时只把经过验证的信息写入长期记忆。
