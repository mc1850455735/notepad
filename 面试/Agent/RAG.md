## 什么是RAG

RAG，Retrieval-Augmented Generation，**检索增强生成**，是一种将信息检索与文本生成相结合的 AI 架构，旨在让 LLM 在回答问题时可以动态引用外部知识库中最新最相关的信息，提升回答的准确性、时效性和可追溯性。通过 RAG，可以让模型先查资料再回答问题，而不是凭借记忆。

当前大模型尽管拥有不错的语言理解和生成能力，但是还存在许多局限：
1. 模型训练数据存在时间局限性；
2. 模型可能存在幻觉现象；
3. 模型无法访问企业内部文档、笔记、数据库等私有数据；
4. 模型回复缺乏依据，无法确定引用来源等问题

# Chunking 中文档的切分方式有哪些？

文档主要有 3 种切分方式
1. 按固定长度切分: 按照固定字符数或 Token 数切分文档，并设置一定重叠区域
2. 按语义切分: 先将句子或段落转换成向量，再计算相邻内容的语义相似度。当语义变化超过阈值时进行切分。
3. 基于结构的切分: 根据文档结构切分，如 Markdown 标题, HTML 标签, Java 类和方法, JSON 字段

# RecursiveCharacterTextSplitter 的原理是什么? 处理中文内容时要注意什么

**RecursiveCharacterTextSplitter** 的原理

`RecursiveCharacterTextSplitter` 可以理解成优先按**大语义边界**切；如果切出来仍然太大，就换更细的分隔符继续递归切；最后实在不行才按字符切。

默认的分隔符顺序是：
```
["\n\n", "\n", " ", ""]
```

RecursiveCharacterTextSplitter 具有递归的切分规则，也就是说先按照换行进行切分，如果换行切分后的块小于最大块大小 (如 500)，则按最大块大小合并后，作为合理的块直接向量化后加入数据库；
如果换行切分后的块大于默认最大块大小，则将其再按照换行符进行切分。依次类推，直到切分到最小也无法缩小到最大范围以内，才会按照字符进行切分。

同时，RecursiveCharacterTextSplitter 还会对切分后的块进行重新 Merge。比如 Chunk 1、2、3 大小分别为 100、200、100，则会拼接为一个最接近 Chunk Size 的总 Chunk 加入向量数据库。

同理，RecursiveCharacterTextSplitter 下的 OverLap 也不会按照精确的 LapSize 进行重叠，而是优先按照 `句子` -> `段落` -> `分隔符` 的顺序进行语义单元层面的合并。

**处理中文时可能遇见的问题**
对于中文问题，存在的最大问题就是默认的 separator 不合适；中文、日文等语言没有类似英文的单词边界。

对于中文应该添加一些中文特有的中文标点符号，如 `，`、`。`、`！`等；同时要注意新添加的符号在 separators 中的顺序，强语义边界应该大于弱语义边界。

同时，中文下对于 chunk_size，应该基于 Token 进行计算，由此才能和模型上下文限制真正对应起来，使用 Embedding 对应的 Tokenizer 计算。


# 一般怎么设计

不应为固定的先查再答 模式，而是作为一个决策节点，模型应该先判断该问题是否需要外部知识，再决定 query rewrite、query decomposition、召回、rerank 和 生成的顺序。

常见做法是把 rag 包装为一个工具，由 Agent 自行判断何时调用，对 RAG 检索结果应该进行去重、切片、排序和来源标注。

通常，还会要求模型必须按照检索到的证据进行回答，没有证据的情况明确回答不清楚，真正降低幻觉。

# RAG 检索流程

整体上来说，RAG 的检索流程可以分为两部分，分别是构建知识库和在线检索。具体流程如下：

1. 准备文档（知识库）
2. 文档切分
3. 文档块向量化
4. 保存向量并建立 ANN 索引
5. 接受用户问题，结合上下文进行 Query 改写
6. 查询 Query 向量化
7. Bi-Encoder 召回候选文档
8. 对召回结果进行 Cross-Encoder 重排
9. 将最终 Chunk 组装到上下文

# 如何进行 RAG 加速检索

1. 长文档切分，分别形成向量
2. 使用 ANN 索引，如 HNSW、IVF 等。
3. 先进行元数据过滤，再在剩余向量组中进行索引
4. 控制 RAG 召回数量，避免 Cross-Encoder 处理过多向量影响效率。
5. 数据特别多时，可以使用向量量化对向量进行压缩。
6. 可以进行向量数据库分片，按照业务维度对向量进行分区。
7. 增加向量化缓存，相同或者标准化后的查询不需要重复调用 Embedding 模型，降低向量化用时。

# 什么是 ANN 索引，有哪些 ANN 索引

ANN ，Approximate Nearest Neighbor，近似最近邻搜索。

ANN 有两种常用的具体算法，分别是 HNSW 和 IVF。

HNSW 全称是 **Hierarchical Navigable Small World**，即分层可导航小世界图。把向量组织成多层图结构，查询时不是遍历全部向量，而是：
1. 从最高层入口节点开始。
2. 沿着与查询向量更接近的节点移动。
3. 逐层向下搜索。
4. 在底层找到最相似的若干向量。

IVF 全称是 Inverted File Index，倒排文件索引。
构建索引时，先通过聚类算法把所有向量划分到多个分区，查询时：
1. 计算查询向量最接近哪些聚类中心。
2. 只搜索这些聚类中心对应的分区。
3. 不再扫描其他无关分区。

# 父子索引

RAG 检索过程中会遇到一个矛盾点
- **如果把文档切得太小（比如几句话一个分块）：** 向量检索（Embedding）虽然非常精准，但由于丢失了上下文背景，丢给大模型（LLM）时，模型可能会理解错意思，导致回答质量下降。
- **如果把文档切得太大（比如一整段、一整页）：** 文本里混杂了太多噪音，向量检索的准确度会急剧暴跌，容易召回一堆不相干的内容。

父子索引的核心思想是：“拿去检索的文本（子块），和最后喂给大模型的文本（父块），不是同一个东西。”

## 流程

**1.双层切分与关联：** 数据准备阶段。
首先将原始文档切成较大的父块，并为每个父块分配一个唯一的 parent_id。接着，将每个父块切成更小的子块，子块内部会显式记录它所属的 parent_id。

**2.混合存储：** 数据准备阶段。
-   向量数据库：只对小巧的子块计算 Embedding 并建立向量索引。
-   关系型/键值数据库（如 Redis/MySQL）：用来存放体积较大的父块实体，通过 parent_id 作为 Key 映射。

**3.精准搜索子块：** 在线检索阶段。
当用户提问（Query）时，系统直接去向量数据库里检索，由于子块语义单一、聚焦，能以极高的精度匹配到最相关的几个小子块。

**4.向上回溯父块：** 在线检索阶段。
系统抓取到中选的子块后，并不直接把子块喂给大模型。而是提取出子块身上的 parent_id，去键值数据库里顺藤摸瓜，直接捞出完整的父块文本。

## 作用

通过小块子块进行精确检索, 并返回子块所在的大块父块, 在保证了检索精度的同时, 保障检索结果上下文的完整性

## 优缺点

- **主要优势**：做到了“检索”和“理解”的双重极限。既保留了小文本的高召回率，又给了大模型充足的背景材料，能大幅减少大模型的**胡言乱语（幻觉）**。
- **额外开销**：你需要维护两套存储。同时，由于喂给大模型的父文档较长，每次对话消耗的 **Token 数量和推理成本会明显上升**。

# BM25

**BM25（Best Matching 25）** 是一种用来计算 **用户搜索词** 与 **文档** 之间相关性得分的经典算法, 是传统的 **关键词检索**（稀疏向量检索 / Sparse Retrieval）的最有效的方法之一。

**BM25** 在 **TF-IDF** 的基础上做出了两个最核心的升级：
- **词频饱和度**：对于一篇文章，BM25 会对其中关键词的分数贡献随着次数增加而趋于饱和。使得在同长度文章背景下，过多的频率差异不会产生过大的分差；
- **文档长度惩罚**：当文章中关键词出现的频度相同，但是文章长度不同时，长度更短的文章的分数显然应该更高。

## 为什么引入 BM25

在现代 RAG 系统中, 纯向量检索 (Dense Retrieval) 存在很多问题:
1. 关键词匹配
	- 向量模型（Embedding）在训练时被灌输了大量自然语言，导致它更关注句子的**语法结构和泛化语义**，而忽视了孤立的实体词, 对“专有名词、代码、数字”极度不敏感
	- 同时 BM25 实行**严格的字面精确匹配**, 全库极其罕见的稀有词（**IDF 逆文档频率极高**）。BM25 会赋予这个词极高的权重，任何只要包含了这个完整字符串的文档，得分都会瞬间飙升
2. 强行匹配与幻觉
	- 向量数据库可以匹配任何类似的条目, 导致返回给大模型的资料与用户问题可能完全不符, 直接误导后续的路由机制，让大模型开始编造答案
	- BM25 的打分完全建立在“有就是有，没有就是零”的硬性字面匹配上。如果知识库中完全没有这些核心关键词，BM25 算出来的得分会**断崖式下跌，直接趋近于 0**。
3. 冷启动成本高
	- 通用向量模型的语义空间是在通用语料上训练出来的。一旦面对极其专业的冷门领域，向量模型就会失去辨别力，必须依靠高成本的数据标注和模型微调才能恢复
	- BM25 完全不需要理解语义，天然具备极强的冷启动（Zero-Shot）能力。它凭借纯粹的统计学概率，就能在专业领域迅速建立起极高水准的基准检索线。
4. 词频累加引起的“长文欺诈”与“噪音过载”
	- 向量模型在将长文本（大 Chunk）压缩成几百维固定长度的向量时，不可避免地会发生“语义稀释”
	- BM25 通过 **词频饱和度** 和 **文档长度惩罚**，会根据关键词与全库平均长度的比值进行分值打折，天然更倾向于推荐那些短小精悍、主题聚焦的优质短内容。

# 什么是 Rerank，为什么需要 Rerank

Rerank 是对 RAG 初始召回结果的二次排序的步骤。初始检索主要负责召回数据，通常会通过 BM25、Embedding 以及 Hybrid Search 充分召回候选 Chunk，但是初始排序不一定足够准确；

为此，使用 Cross-Encoder 等 Reranker，将 Query 和 Document 混合输入模型后直接得出相关性评分，重新排序后，取 Top-k 提供给 LLM。

相比 Embedding 向量化 Query 后与向量数据库中的向量直接比较相似度的方式，Cross-Encoder 可以使 Document 与 Query 之间建立 Token 级别的交互，排序效果更好，但是同时计算成本更高。

因此，通常会选择 Hybrid Search 得到初始候选集后再精细排序。

# 向量数据库

向量数据库是一种专门用于存储、索引和搜索向量的数据库。通过向量数据库，可以实现通过相似度而非精确值查询数据。

对于传统数据库，如 MySQL、PostgreSQL、ES 等，其更擅长通过精确匹配和关键词搜索等获取需要的数据库，而藉由向量数据库，可以高效解决语义搜索、相似内容检索、知识召回等问题。

**常用向量数据库**

**Milvus**
- 定位：企业级分布式向量数据库
- 优点：原生分布式，支持高并发、大规模访问；工业级性能，社区成熟。
- 缺点：运维成本高。

**PostgreSQL + pgvector**
- 定位：小规模 RAG、初创产品。
- 优点：直接使用 SQL + 向量操作；简单易上手，可直接结合业务数据。
- 缺点：大规模性能有限。

**FAISS**
- 定位：向量检索库
- 优点：速度快，技术成熟；支持多种 ANN 算法；本地部署简单。
- 缺点：不支持分布式部署；无完整 DB 能力。

**Qdrant**
- 定位：轻量级、工程友好
- 优点：Rust 实现，性能稳定；具有强大的 Metadata Filter；易部署，对 RAG 友好。
- 缺点：超大规模性能略逊于 Milvus。

# 什么是 Graph RAG，为什么在已有向量/混合检索的基础上引入 Graph RAG？它主要解决哪些问题？

Graph RAG 是将**知识图谱**与 RAG 结合的检索增强生成技术。传统 RAG 主要检索语义相似的文本块，而 Graph RAG 会进一步抽取文本中的实体、关系、属性，并将它们组织成图结构。

查询时不仅检索相似文本，还会沿着图中的关系查找相关实体和证据，再交给大模型生成答案。

实际使用时，Graph RAG 不是完全替代向量 RAG，而是在原有的向量检索、关系词检索的基础上，进行混合检索。

**工作流程**

**1、构建知识图谱**
对原始文档进行切分，并抽取其中的实体和关系，对实体进行消歧与合并，最后构建知识图谱。通常还会保存知识图谱中对应的原始文本和来源，方便回答时引用证据。

**2、检索**
对于用户的 Query，单个文本块中可能没有直接答案，但 Graph RAG 可以进行多跳查询，根据图关系层层递进，最终找到答案。

**3、生成答案**
系统将检索到的图关系交给模型，包括：相关实体、实体之间的关系路径、图谱中的属性、对应原始文本、文档来源等。
最后由大模型生成带证据的答案。

**适用场景**
Graph RAG 比较适合：
- 企业股权和人物关系
- 风险分析
- 医疗知识关联
- 法律案件关系
- 推荐系统
- **代码调用链和依赖分析** （代码质量审查 Agent）
- 跨文档事件分析
- 需要多跳推理的问题
如果只是简单 FAQ 或单文档问答，传统向量 RAG 通常更简单、成本更低。
