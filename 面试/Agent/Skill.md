
# 大量 Skills 加载

当 Agent 拥有很多能力模块时，不能每次都把所有 Skill 的完整说明全部塞进上下文，否则会造成上下文膨胀、检索混乱、工具选择错误和推理成本上升等问题。

## 问题

1. 上下文占用太大
每个 Skill 往往包含：
```
Skill 名称
功能描述
输入参数
输出格式
使用条件
失败处理
示例
注意事项
```
当大量 Skills 同时被加载时，会占用大量上下文，挤压用户问题、历史对话和检索资料的位置。

2. 工具选择变差
Skill 太多时，模型容易出现：
```
选错 Skill
多个 Skill 混用
把不相关 Skill 当成可用工具
重复调用类似 Skill
```

如果同时把所有 Skills 的说明都放在 prompt 里，模型可能难以稳定判断当前应该用哪一个。

3. 推理成本增加
即使任务只需要一个 Skill，模型还是需要阅读所有的 Skill 描述，从而增加了成本、延迟和无关信息干扰。

## 解决

通过使用**渐进式披露**，分为三层处理。

Skills 不直接全部加载到上下文中，而是先读取每个 Skill 的名称和描述，再决定要不要加载完整内容。

Skill 的 Name 和 Description 可以看作是标题与摘要，提高 Skill 命中率，首先要提高 Skill 的 Description 的区分度，要重点描述其触发场景而不是作用；模型路由本质上是在做语义匹配，Skill 描述中意图越清晰，命中率越高。

建立 Skill 分层，通过建立 Skill Tree 提升 Skill 的检索精度。第一层可以分为多个大类，第二层再在第一层大类的基础上分子类。先找大类，再找子类，通过分层路由的方式缩减搜索空间，减少一次性全量匹配。

增加负样本描述。除了告诉模型什么情况下应该用以外，还要告诉模型哪种情况不应使用该 Skill。如：
```
仅用于生成 SQL 语句，不用于数据库设计和 SQL 语句性能优化；
仅用于前端代码生成，不负责后端接口开发。
```

召回 + 重排。类似 RAG，不直接将 Skills List 加入上下文供 LLM 选择，而是通过 Embedding 或 关键词检索召回 Top10，再交由大模型作判断。
