
# Gateway 起到什么作用

Spring Cloud Gateway 是微服务架构中的统一流量入口，主要负责路由转发、统一鉴权、限流、跨域和链路追踪。在我的项目中，我通过 Gateway 全局过滤器解析 JWT，并结合 Redis 校验登录状态和权限。校验成功后，将用户 ID 和 RequestId 写入请求头并转发给下游服务；下游服务通过拦截器解析请求头，并使用 ThreadLocal 保存当前请求的用户上下文，请求结束后及时清理。这样能够统一认证逻辑，减少重复代码，同时降低非法请求对下游服务的压力。

# 优惠券组合最优方案的实现是什么？线程池和CompletableFuture 并行计算是怎么用的？

**两级筛选的优惠券最优组合方案实现**
对于优惠券组合方案，我的实现方案是这样的。这套方案的核心优势是先通过两级筛选减少参与枚举的优惠券数量，再将相互独立的方案并行计算。

首先查询出用户当前所有的未使用且未过期的优惠券，并计算课程的总价格。

先对用户持有的所有优惠券进行两级筛选：
首先是**粗筛**，过滤掉一定不符合使用条件的优惠券，如未达到满减额度，或者该优惠券不能用于当前课程等。
随后对优惠券进行**细筛**，由于某些优惠券只能用于特定的课程，同时可能具有使用门槛，所以粗筛完毕后，会查询在使用范围中的课程的总金额，观察允许范围内的总金额是否也达到了优惠券的使用条件。
经过两级筛选后，得到一个 Map，对应每个优惠券实际适用的金额。

随后，进行组合枚举，对筛选后的优惠券进行排列组合。这一步的主要目的是得出所有可能的优惠券使用策略，因为不同的优惠券使用顺序可能导致最终的订单金额不同。
如先使用满减再使用打折可能比先使用打折再使用满减能省的钱更少，但是也有可能打折后不符合满减条件，反而产生更多金额，因此需要进行方案的设置。

对于所有的组合枚举方案，进行并行计算。把每个方案交给自定义线程池，并通过 CompletableFuture 异步计算。所有任务通过 CountDownLatch 等待汇总，结果保存到线程安全的集合中。

最后筛选最优解，对于最优解的选择，有两个规则：
- 对于金额不同的方案，选择金额最低的；
- 如果金额相同，那么选择使用优惠券数量最少的方案。
最后按照优惠金额降序返回候选方案集合。

**线程池和 CompletableFuture 的具体使用**
在项目中，线程池和 CompletableFuture 主要的作用是用来并行计算组合枚举的结果。线程池负责控制并发资源，`CompletableFuture`负责异步任务的编排和结果回调，两者结合后，可以把原本串行的多个方案计算并行化。

我的实现思路是，把每一种优惠券使用顺序都看作是一个相互独立的计算任务，将其提交到线程池中进行执行。

对于线程池的配置，使用的是自定义线程池，其中的核心线程数和最大线程数都是 12，这样设计的目的是为了不要让空闲线程被销毁后重建，有利于提高系统的速度；同时，线程池的等待队列容量为 99999，使用 `AbortPolicy`，也就是如果出现了超出线程池容量的情况直接报错。因为 99999 已经满足所有的计算可能了，如果超出这个容量，说明问题出现在优惠券排布的部分。

对于 CompletableFuture ，使用专用的线程池进行优惠券计算，可以不影响主线程池，同时更便于优惠券计算部分的监视和调参。

逐张计算优惠券后，需要将计算结果写入集合；使用 synchronizedList 同步列表保存计算结果，避免并发问题。
对于这一步，建立一个数量等于方案数的 CountDownLatch，每一个异步优惠券计算任务完成后都会调用 thenAccept 方法保存结果，并执行 countDown()。主线程最多等待 1s，随后对已完成的结果进行筛选。

# 问题

## 1) 项目总体与架构

### Q1：用一句话讲清楚地大智学的业务价值和核心链路？

**参考答：**  
地大智学是校内技能培训的在线教育平台，核心链路是“课程浏览/播放 → 领券/下单转化 → 互动（评论点赞）→ 成长体系（积分排行榜）→ AI 助手提升搜索与转化”，我主要负责高并发领券、优惠券推荐、积分排行、断点续播、AI Tool Calling + RAG、以及统一鉴权治理。

### Q2：系统整体架构是怎样的？为什么这么拆？

**参考答：**  
整体是 Spring Boot 微服务 + Gateway 统一入口，Redis 做缓存与排行榜，RabbitMQ 做异步削峰与延迟合并写，MySQL 做持久化，XXL-job 做批处理/快照任务。拆分上把高并发写路径（领券、进度上报）与查询路径（推荐、课程检索）隔离，避免互相拖垮。

### Q3：有哪些“最容易出问题”的关键链路？你怎么兜底？

**参考答：**  
领券秒杀、断点续播写入、排行榜快照、鉴权网关都是关键链路。兜底包括：限流+资格校验、分布式锁防超发、MQ 重试/死信、延迟合并写、任务分片+幂等、网关统一异常与降级策略、Redis/DB 双写一致性策略与补偿。

## 2) 异步领券、分布式锁、限流与防刷

### Q4：为什么用 Redisson 分布式锁？不用数据库乐观锁行不行？

**参考答：**  
秒杀/领券写入高峰时 DB 行锁/乐观锁会造成大量冲突与重试，容易把压力放大到数据库；Redisson 锁把竞争放到 Redis，延迟更低、吞吐更高，还能结合业务维度做细粒度锁（按券批次/用户/兑换码等），降低冲突面。

### Q5：你们锁的粒度怎么设计？锁名为什么要支持 SPEL 动态锁？

**参考答：**  
锁粒度按业务冲突域设计：比如“同一优惠券活动库存”用 `coupon:{activityId}`，“用户领取资格”用 `coupon:{activityId}:user:{userId}`。用 SPEL 动态锁名是为了让注解在不同方法复用，并能根据入参自动拼接锁 key，减少样板代码且避免开发误用统一锁导致性能下降。

### Q6：AOP + 分布式锁怎么保证“释放锁”和“异常场景”不出问题？

**参考答：**  
AOP 环绕通知里 try-finally 释放锁；对于 Redisson 的看门狗/租期：短任务用固定 leaseTime 防止忘记释放；长任务使用 watchdog 自动续期，确保业务执行期间锁不失效。异常直接抛出但保证 finally unlock。

### Q7：工厂 + 策略模式处理“锁竞争逻辑”具体解决了什么？

**参考答：**  
不同业务对竞争策略不同：有的希望立即失败（快速返回），有的允许自旋等待一定时间，有的需要排队/重试并做退避。工厂根据注解参数/业务类型选择策略实现（tryLock、阻塞 lock、带超时 lock、失败降级等），把竞争处理从业务代码剥离，提高复用与可维护性。

### Q8：固定窗口限流怎么做的？为什么不是滑动窗口/令牌桶？

**参考答：**  
固定窗口实现简单、Redis 原子自增即可（INCR + EXPIRE），对领券这种“秒杀高峰短、容忍一定边界误差”的场景足够。若后续出现窗口边界突刺明显，再升级滑动窗口（ZSet/HyperLogLog）或令牌桶（Lua 脚本原子扣减）。

### Q9：用户资格校验防刷怎么做？有哪些绕过风险？

**参考答：**  
资格校验包括：是否实名/是否在白名单/是否达到课程等级/是否已领过/是否在黑名单；同时做请求频次限制与设备指纹/账号风控标记。风险点是脚本换号、代理 IP、并发打穿缓存，所以会配合：网关层限流、接口幂等、Redis 记录短时行为、异常模式触发更严格策略。

### Q10：百万级兑换码兑换怎么设计，怎么避免一次性导入把系统打崩？

**参考答：**  
兑换码采用分批导入与校验：码表分片存储（按 hash 分库分表或按批次分表），兑换时先 Redis 快速校验（布隆过滤器/缓存热点批次），命中后再查 DB 做最终一致校验。兑换成功用异步通知/事件驱动更新订单或发券状态，避免强同步链路过长。

### Q11：秒杀“异步通知优化”具体指什么？

**参考答：**  
核心是把“发券成功后的后置动作”（发站内信/短信、积分变更、推荐刷新、日志上报）通过 MQ 异步化，主链路只做必要的资格判断与库存扣减/发券落库，减少 RT，提升峰值吞吐。

### Q12：库存扣减怎么做的？如何防止超卖/少卖？

**参考答：**  
常见做法是 Redis 预扣库存（Lua 原子判断+扣减）作为快速闸门，成功后异步/同步落库；DB 侧用唯一约束防重复领取、用版本号/行锁保证最终库存一致；若异步落库失败，会通过补偿任务回滚 Redis 预扣或重试落库，保证最终一致性。

## 3) 优惠券智能推荐、并行计算与决策链

### Q13：为什么要“全排列组合”？复杂度会不会爆炸？

**参考答：**  
因为用户可能有多张券/不同门槛叠加规则（满减、折扣、品类券、店铺券、平台券），要找全局最优就需要枚举可用组合。但确实会爆炸，所以做了初筛（过滤不满足门槛/不可叠加）+ 细筛（按券类型分组、限制组合长度、剪枝）来控制规模。

### Q14：你提到 MapReduce 思想，怎么落地的？

**参考答：**  
Map 阶段把券按规则映射到可用集合/分组（如可叠加组、互斥组），Reduce 阶段在每组内生成组合并做剪枝，然后对跨组组合做合并计算，避免全量笛卡尔积直接爆。

### Q15：并行计算用 FutureTask + CompletableFuture，怎么避免线程池被打满？

**参考答：**  
使用自定义线程池（核心线程数与队列容量可控），对任务数做上限保护（超过阈值退化为串行/分批），并使用 `CompletableFuture.allOf` 汇聚结果。高峰期配合缓存：同一用户/同一价格区间短时间内复用计算结果，减少重复计算。

### Q16：推荐的“最优解”如何定义？只看优惠金额吗？

**参考答：**  
一般是多目标：优先最终支付最低，其次优惠券消耗策略（避免浪费高价值券）、再考虑券有效期（快过期优先）、用户偏好（某类券优先）。这些通过“决策链/打分模型”实现，可配置权重，方便运营调参。

### Q17：你们的“80% 查询速度提升”主要来自哪几块？

**参考答：**  
主要来自：1）初筛/细筛剪枝减少组合数；2）并行计算缩短 CPU 密集阶段；3）对券规则与券详情做缓存（如券门槛/适用范围预热）；4）对重复请求做短期结果缓存与请求合并。

### Q18：怎么验证推荐结果正确性？有没有线上对账/回放机制？

**参考答：**  
离线用规则回放：采样历史订单与券包，跑推荐引擎并与实际优惠对账；线上灰度期间对一部分请求双算（旧逻辑/新逻辑）比对差异，记录异常组合；同时对推荐结果做可解释输出（命中规则、优惠明细），方便排查。

## 4) 积分排行榜、ZSet、快照与任务分片

### Q19：为什么用 Redis ZSet 做排行榜？不用 MySQL 排序？

**参考答：**  
MySQL 排名需要频繁排序/分页，积分实时变化会导致大量写与查询互相影响；ZSet 天然支持按 score 排序与 range 查询，适合实时排行与 TopN，延迟低且成本可控。

### Q20：赛季排行榜怎么设计数据结构？

**参考答：**  
每个赛季一个 key：`rank:season:{seasonId}`，member 存 userId，score 存积分；额外维护用户积分明细/变更流水用于追溯。查询 TopN 用 `ZREVRANGE`，查询用户排名用 `ZREVRANK`。

### Q21：月初快照为什么要落库？落到“按赛季拆分表”的原因？

**参考答：**  
快照落库是为了长期存档、历史赛季查询与报表分析，避免 Redis 长期存太久造成成本与运维压力。按赛季拆表减少单表膨胀，也利于归档与冷热数据分离。

### Q22：XXL-job 分片并行 + 子任务串联怎么做？难点是什么？

**参考答：**  
分片并行：每个分片处理一段用户区间或 ZSet 分段扫描；子任务串联：先导出 Redis 排行快照，再写入 DB，再做汇总统计。难点是幂等与失败重试：每个分片有唯一任务标识，写库用唯一键/版本号保证重复执行不产生脏数据；最终用聚合任务检查分片完成度。

### Q23：排行榜数据一致性：Redis 实时分数 vs DB 快照差异怎么解释？

**参考答：**  
Redis 是实时态，DB 是月初（或定点）的快照态，本来就允许存在差异。产品上明确“实时榜/历史榜”两个视图；若需要“某一时刻榜单可复现”，就以快照为准。

## 5) 断点续播：上报、延迟合并写、误差控制

### Q24：为什么前端 15 秒上报一次？误差 30 秒怎么来的？

**参考答：**  
15 秒是体验与流量的折中：太频繁浪费带宽与写入压力，太稀疏会丢失进度。服务端采用 Redis 实时覆盖最新进度，MQ 延迟合并写 MySQL（例如 30 秒合并窗口），所以最坏情况下进度落库会比真实播放落后一个合并窗口，误差控制在 30 秒内。

### Q25：为什么要 RabbitMQ 延时合并写？直接写 MySQL 不行吗？

**参考答：**  
进度上报属于高频写，直接写 MySQL 会产生大量小事务与 IO，且热点用户会造成更新争用。通过 MQ 延迟，把同一用户同一视频的多次上报合并成一次写库，极大减少写放大，提升 DB 稳定性。

### Q26：延迟合并写如何避免消息乱序或重复导致回退？

**参考答：**  
写库时按“更大的播放进度优先”做幂等：只有当消息携带的进度 > DB 当前进度才更新，确保乱序不会回退；重复消息也不会产生副作用。必要时消息体带时间戳/版本号辅助判断。

### Q27：跨设备无缝续播怎么实现？以哪个数据为准？

**参考答：**  
读取时优先 Redis 最新进度（实时），若 Redis 失效则回源 MySQL 进度（持久）。用户在新设备打开视频时，先拉取进度并设置播放器 seek；同时会把 DB 进度回填 Redis 做热启动。

## 6) AI 智能助手：Tool Calling + RAG + 业务闭环

### Q28：你们为什么选 Spring AI？Tool Calling 的价值是什么？

**参考答：**  
Spring AI 能把大模型调用与工具编排融入 Spring 生态。Tool Calling 让模型不是“只会聊天”，而是能调用后端能力（课程查询、推荐、预下单），从“回答”升级为“完成任务”，并把结果以结构化卡片返回，提升可用性与转化。

### Q29：你们的工具有哪些？如何做参数校验与安全控制？

**参考答：**  
工具包括课程检索、课程详情、优惠券推荐、预下单等。安全上：工具层做严格参数校验（白名单字段、范围限制）、鉴权校验（用户身份/权限）、以及限流与审计；模型输出只作为“意图”，不直接执行敏感动作，敏感操作必须二次确认或走业务规则。

### Q30：RAG 知识库怎么构建？向量库里放什么？

**参考答：**  
以课程介绍、章节大纲、常见问题、学习路径等文本为语料，做清洗切分（chunk）、生成 embedding 入向量库，检索时根据用户问题召回 topK 片段，拼接到 prompt 作为上下文。对课程更新会触发增量更新 embedding。

### Q31：如何评估 RAG 的效果？如何处理幻觉？

**参考答：**  
评估用：命中率（召回是否包含答案）、回答准确率、引用一致性（回答是否来源于检索片段）。降低幻觉：强制引用检索内容、无命中时让模型明确“不确定并建议查询”、对关键查询走“工具优先”而不是纯生成。

### Q32：预下单卡片展示怎么做？前端怎么渲染？

**参考答：**  
工具返回结构化 JSON（课程ID、价格、券组合、应付金额、按钮文案等），前端根据 schema 渲染卡片。这样模型只负责选择与组织信息，不负责拼 HTML，保证稳定性与安全性。

## 7) 统一权限治理：注解+AOP、网关鉴权、会话共享

### Q33：为什么要做“自定义权限注解 + AOP”？不直接写在业务里？

**参考答：**  
直接写会导致业务侵入严重、重复代码多且难统一改动。用注解+AOP可以把鉴权逻辑标准化（登录校验、角色校验、资源权限），业务只声明“需要什么权限”，实现解耦与统一治理。

### Q34：Gateway + Redis 做统一鉴权的链路是怎样的？

**参考答：**  
请求到网关后先做 token 解析/验签，再去 Redis 获取会话/权限信息（或缓存的权限集合），校验通过才转发到后端服务；网关统一处理异常码与未登录/无权限响应，并做日志追踪与限流。

### Q35：分布式会话共享为什么选 Redis？有哪些一致性问题？

**参考答：**

### Q40：如何保证“Redis 写成功但 DB 写失败”的一致性？

## Redisson+AOP分布式锁

为什么要用 AOP 封装 Redisson？因为如果直接在业务代码中书写分布式锁逻辑，会产生大量重复代码，且业务代码与锁逻辑耦合严重。

加锁逻辑中，整个业务执行过程包裹在 `try-finally` 块中。无论业务执行成功还是抛出异常，`finally` 块中都会执行 `lock.unlock()`。

通过**自定义注解**，注解中设置参数，在方法上添加注解将自动**环绕**添加分布式锁逻辑。如果 AOP 层面尝试加锁失败（达到 `waitTime` 未获取到锁），抛出自定义的“系统繁忙”异常，由全局异常处理器捕获并返回给前端，保证用户体验。

## 异步通知优化秒杀

传统的同步领券流程包含：查询资格 -> 扣减库存 -> 生成券码 -> 写入数据库。在百万级并发下，数据库压力极大，响应时间长。

配合 Redisson 的可靠性，确保了“库存扣减”与“异步通知”的联动，解决了同步请求导致的接口超时和高连接占用的问题。

## XXL-JOB 分片并行与补偿

### 分片处理实现

分片处理的核心目标是：将全量数据拆分，让多个执行器（Executor）节点同时干活，缩短总耗时。
 
**A. 调度配置**

在 XXL-JOB 管理后台，任务的“路由策略”选择 **“分片广播”**。这样每次触发任务时，调度中心会向所有注册在该 AppName 下的执行器节点发送调度请求。

B. 逻辑代码实现

每个节点在执行时，可以通过 `XxlJobHelper` 获取当前分片信息：
-   **index**：当前执行器序号（从 0 开始）。
-   **total**：总执行器个数。
每一个执行器（Executor）启动时会获得 `shardIndex`（当前分片序号）和 `shardTotal`（总分片数）。

**关键的数据分拆逻辑（Data Routing）**：

为了保证多个节点不会处理重复的数据，通常有两种做法：
1. **基于 Redis ZScan 的分片**：每个节点都遍历 ZSet，但只处理 `userId % total == index` 的数据。
	- 优点：逻辑简单，各节点负载相对均匀。
	- 缺点：每个节点都要遍历全量 Redis Key，有一定冗余开销。
2. **基于 Rank 范围的分片（推荐）**：先获取 ZSet 总数 `totalSize`，计算每个分片的步长 `step = totalSize / total`。
	- 节点 $i$ 只处理排名在 $[i \times step, (i+1) \times step - 1]$ 之间的数据。
	- 使用 `zrangeWithScores` 分页获取，效率最高。

### 子任务串联

持久化完成后，通常需要进行一些后续操作（如：清理 Redis 旧数据、计算本赛季奖励、生成汇总报告）。为了解耦，我们不把这些逻辑全写在一个大方法里，而是使用“子任务”。

**A. 配置方式**
在 XXL-JOB 的“主任务”（持久化任务）配置界面，有一个 **“子任务 ID”** 输入框，填入后续逻辑任务的 ID。

**B. 触发机制**
1. **主任务完成：** 当所有分片节点都返回“成功”状态后，调度中心会自动触发子任务。
2. **执行顺序：** 保证了“先落库、再后续处理”的严格顺序。

### 如何判断“所有分片都成功”？

这是分布式调度中的一个难点。XXL-JOB 默认的子任务触发逻辑是：**只要主任务的触发请求发送成功，或者任意一个分片成功，就可能触发子任务。** 但在持久化场景下，我们需要 **“所有分片全部成功写入 MySQL”** 才能执行后续逻辑。针对这一点，你可以在项目中做了如下增强：

- **计数器方案（Redis Counter）：**
	1. 主任务启动时，在 Redis 记录一个计数器，初始值为分片总数 `total`
	2. 每个分片执行完落库逻辑后，执行 `DECR` 操作。
	3. **最后一个完成的分片**（计数器减到 0 的那个）通过代码手动调用 XXL-JOB 的 API 触发子任务，或者直接在当前节点执行后续清理逻辑。
- **状态检查逻辑：** 子任务被触发后的第一件事，是先查询数据库的赛季表，校验数据量是否符合预期。如果校验不通过，直接终止并报警，防止错误扩散。

### 故障补偿机制

- **子任务串联**：任务执行完后通过 XXL-JOB 的“子任务”功能触发校验逻辑。
- **重试机制**：开启 XXL-JOB 的失败重试策略（如重试 3 次）。
- **幂等性保障**：数据库端使用 `ON DUPLICATE KEY UPDATE` 或 `赛季 ID + 用户 ID` 作为联合唯一索引，确保分片重试时不会产生重复的赛季记录。

## 断点续播功能

**核心流程：分层存储与异步合并**
- **第一层：Redis 实时写（高速缓冲）**：前端每 15 秒上报进度时，服务端优先更新 Redis。Redis 存储格式通常为 `Hash`（Key: `user_video_progress`, Field: `videoId`, Value: `progress`）。这一步保证了极高的并发响应能力。
- **第二层：RabbitMQ 延时通知（削峰）** 在更新 Redis 的同时，并不立即写数据库，而是向 RabbitMQ 发送一条**延时消息**。

**“延时合并”的具体逻辑**
- **合并触发**：延时消息设定为 30 秒后消费。
- **逻辑校验**：当消费者接收到消息时，去 Redis 查出该用户最新的进度值。
	- **比对时间戳：** 如果 Redis 中的最后更新时间与当前时间差值小于 30 秒，说明用户还在持续观看且有更新的上报，此时**丢弃**当前旧消息（或者说合并了），等待下一条更新的消息来触发写入。
	- **最终写入：** 只有当消息到期且 Redis 中记录的更新时间已经**超过一定阈值**，或者**达到强制刷盘频率**时，才将数据同步到 MySQL。

**误差控制与用户体验**
- **误差 30 秒的来源：** * 前端 15s 上报 + 消息队列处理延迟。即使系统突然宕机，由于 Redis 挂了或消息丢失，用户下次回来时，进度条最多倒退 30 秒（上一次持久化成功的点），这在业务上是完全可以接受的。
- **跨设备无缝续播：** * 当用户切换手机或平板打开同一视频时，服务端优先查询 Redis。如果 Redis 没有（说明已过时），再查 MySQL。这保证了用户看到的进度永远是最新的。

## 自定义权限注解 + Spring AOP 实现非侵入式接口鉴权

**设计维度：自定义注解 + 切面拦截**
定义了一个通用的权限注解 `@RequiresPermissions`，支持传入权限标识符（如 `course:upload`）。
- **AOP 切入点（Pointcut）**：拦截所有标注了该注解的方法。
- **环绕通知（Around Advice）**：
	1. **获取 Token**：从 `HttpServletRequest` 的 Header 中获取 JWT 或 Session ID。
	2. **身份解析**：调用封装好的 `SecurityContext` 获取当前用户信息。
	3. **权限比对**：将注解要求的权限与用户拥有的权限列表进行匹配。

**多条件支持与逻辑组合**
为了支持复杂的权限逻辑（如“拥有 A 权限 **或** B 权限”），我在注解中引入了 `logical` 属性：
- **AND 模式**：必须拥有全部列出的权限。
- **OR 模式**：拥有其中之一即可放行。
- **SpEL 支持**：借鉴了分布式锁的经验，权限注解也支持 SpEL。例如 `@RequiresPermissions("#userId == principal.id")`，可以实现 只能修改自己的资料 这种数据级权限控制。

**性能优化：Gateway + Redis 分布式会话**
为了避免 AOP 成为性能瓶颈，我采取了**两级校验策略**：
- **第一级（网关层 Gateway）**：使用全局过滤器（GlobalFilter）校验 Token 的合法性及基础黑白名单。由于网关层离用户最近，在这里拦截非法请求能极大**减轻后端微服务的压力**。
- **第二级（应用层 AOP）**：用户信息和权限列表不再实时查询数据库，而是存储在 **Redis** 中。
	- 用户登录后，权限集合以 `Set` 结构存入 Redis。
	- AOP 切面通过 `redisTemplate.sIsMember` 快速判断用户是否拥有权限。
	- **一致性保证：** 当管理员修改了用户权限时，通过 **Redis Pub/Sub** 或直接删除缓存 Key，强制用户下次请求时重新加载权限。

## 库表拆分

**拆分维度：物理表 vs 逻辑表**
我们通常采用**水平切分**，将数据按时间维度（赛季）分散到不同的物理表中。
- **表名规则：** `points_record_202601`、`points_record_202602` ...
- **结构一致：** 所有的物理表结构完全相同，包含 `user_id`、`score`、`rank_time` 等字段。

**核心流程：从 Redis 到 MySQL 的快照持久化**
由于排行榜在 Redis 中是实时更新的，持久化的核心逻辑如下：

A. 动态表名生成
在 XXL-JOB 触发持久化任务时，程序根据当前日期计算出对应的表名。

B. 自动建表逻辑
为了保证系统健壮性，在执行写入前，系统会先检查目标表是否存在，如果不存在则自动创建：

持久化细节：分片并行处理

针对你简历中提到的 **XXL-JOB 分片并行**，具体拆分逻辑如下：
1.  **分片广播：** 假设有 10 个执行器节点，XXL-JOB 会给每个节点分配一个 `shardIndex` (0-9)。
2.  **数据路由：** 每个节点只负责 Redis ZSet 中特定范围的用户。
	-   **方案一（按排名分片）：** 节点 0 处理排名 1-10000 的数据，节点 1 处理 10001-20000。
	-   **方案二（按用户 ID 取模）：** 这是更稳健的做法。节点通过 `ZSCAN` 遍历 Redis，只处理 `user_id % 10 == shardIndex` 的数据并写入数据库。

**为什么要这么拆？**

- **冷热数据隔离：** 用户通常只关心“当前赛季”的排名（热数据）。将旧赛季（冷数据）拆分出去，可以保证当前赛季表的索引极小，查询几乎都在内存中完成。
- **运维便利性：** 当几年前的旧数据不再需要时，可以直接 `DROP TABLE`，这比在大表里执行 `DELETE`（会产生大量碎片和锁竞争）效率高得多。
- **水平扩展：** 如果未来单月数据量依然巨大，这种架构可以无缝演进到分布式数据库（如 ShardingSphere），只需改变分片算法即可。
