### HTTP V.S. HTTPS

- **端口**: HTTP 为80，而 HTTPS 为443.
- **URL前缀**: `http://` 和 `https://`
- **传输层**：HTTP 直接运行于 TCP 之上，而 HTTPS 先经过 TLS，再走 TCP；TLS1.3 已经与 QUIC 融合到 HTTP/3
- **加密：HTTP 直接明文传输，但 HTTPS 经过**对称加密 ( AES / ChaCha20 )
- **身份认证**：HTTP 无任何身份认证，而 HTTPS 有服务器证
- **安全性**: HTTPS **安全性较高**，但 HTTP **效率更高**
- **SEO**: 搜索引擎通常更青睐使用 HTTPS 协议的网站, 因为 HTTPS 能够提供更高的安全性和用户隐私保护.

### HTTPS 密钥交换+证书校验流程

### TLS中的加密算法

HTTPS 里一般同时用了三类加密算法
- **非对称加密**（RSA / ECDHE）用来安全地交换会话密钥、验证身份；
- **对称加密**（AES / ChaCha20）用来加密实际传输的数据；
- **哈希算法**（SHA-256 等）用来校验完整性；
- 此外还会使用 **数字签名**（RSA/ECDSA）保证证书和身份可信。

### HTTPS 握手过程

HTTPS 握手过程基本分为 5 步:
1. 客户端发送 ClientHello 包, 其中包括: TLS 版本, 密码套件, 客户端的随机数, SNI (要访问的域名, Server Name Indication, 服务器名称指示)
2. 服务端返回 ServerHello 包. 服务端根据客户端传来的信息, 返回选择使用的 TLS 版本 和 密码套件, 服务端随机数, 并发送数字证书, 证书中包含公钥.
3. 客户端检查证书: 是否由可信 CA 签发, 证书是否过期, 访问域名是否与证书匹配, 证书签名是否正确, 证书是否被吊销
4. 使用 ECDHE, 服务端和客户端交换临时公钥, 计算出相同的共享秘密, 并结合双方随机数派生出对称加密密钥.
5. 双方发送 Finished, 切换到加密通信, 并发送握手校验数据, 确定密钥协商成功, 且握手过程没有被篡改
6. 建立加密通道完成后, 在加密信道上进行 HTTP 请求与响应的传输.

**ECDHE 加密的生效原理**
HTTPS 的 ECDHE 加密是基于数学难解问题实现的, 虽然中间攻击者可以看到所有的随机数和公钥 A, B, 但是无法看到由客户端或服务端本身生成的私钥 a, b. 
而客户端和服务端本身并不需要知道对方的私钥, 只需要通过自己的私钥 a 和对方的公钥 B, 通过函数 f(a, B) 进行信息加解密. 而函数具有性质 f(a, B) = f(A, b), 从而实现不传输私钥的情况下实现对称加密密钥的计算.
最终双方使用对称加密密钥进行通信，同时 Finished 消息保证握手过程未被篡改。

**为什么ECDHE是完全前向保密的**
ECDHE 每次根据随机数生成双方的对称加密密钥并根据对称加密密钥进行数据的加解密. 
即使本次的私钥泄露, 以前传输过程中的私钥与现在也不同, 对称加密密钥完全不同. 
所以至多泄露一次对话内容.

### 输入 URL 到展示页面流程

1. 在浏览器中输入指定网页URL。
2. 地址栏解析。
	-  URL 组成
	- 浏览器缓存
	- Service-Worker 拦截
	- HSTS 强升 HTTPS
3. DNS解析：浏览器使用DNS协议，获取域名对应的IP地址。
	- 递归/迭代
	- 根/TLD/权威
	- DoH/DoT
	- DNS Cache
	- edns-client-subnet
5. 建立连接：浏览器根据IP地址和端口号，向目标服务器发送TCP连接请求。
	- TCP 三次握手
	- TLS 1.3/QUIC 0-RTT
	- SYN 丢包/重传
	- SYN Cookies
6. 发送请求：浏览器在建立好的TCP上，向服务器发送HTTP请求报文，获取网页内容。在这个过程中，cookies 也会随请求发送给服务器。
	- HTTP 1.x/2/3
	- 长连接&队头阻塞
	- 代理链
7. 服务器响应：服务器收到 HTTP 请求报文后，处理请求，组织 HTTP 响应报文返回给浏览器。
	- CDN 缓存
	- 负载均衡
	- 状态码
	- 压缩
	- Cookie/Set-Cookie
	- ETag
8. 浏览器渲染：浏览器收到HTTP响应后，解析响应体中的HTML代码，渲染网页的结构和样式，同时根据HTML中其他资源的URL，继续发起HTTP请求解析资源。
	- HTML Parser
	- CSSOM
	- JS 执行
	- Layout→Paint→Composite
	- CLS/LCP
9. 关闭连接：浏览器不需要与服务器通信时，可以主动关闭TCP或等待服务器关闭。
	- TCP 四次挥手
	- TIME_WAIT
	- Keep-Alive
	- HTTP/2 复⽤无需挥手

### HTTP 状态码

![[面试/计算机网络/Inbox/Pasted image 20251125094703.png]]

常见状态码：
- 200
- 304
- **401**：**Unauthorized（未认证）**- 请求没有提供有效的身份凭证，例如 Token 缺失、无效或已过期。通常需要重新登录或刷新 Token。
- **404**：**Not Found（资源不存在）**- 服务器找不到请求的接口或资源，可能是 URL 错误、路由不存在，也可能是业务数据不存在。
- **503**：**Service Unavailable（服务不可用）**- 服务器暂时无法处理请求，常见原因包括服务过载、停机维护、线程池耗尽或下游服务不可用。
- **504**：**Gateway Timeout（网关超时）**- 网关或代理调用上游服务时，在规定时间内没有收到响应。说明请求已经转发，但上游服务响应过慢或发生网络异常。

### HTTP/1.0与HTTP/1.1

- **连接方式**: `HTTP/1.0` 只支持短连接, `HTTP/1.1` 支持长连接.
- **状态响应码**: `HTTP/1.1` 中新添加了大量状态码.
- **缓存机制**: `HTTP/1.0` 中主要使用 `Header` 中的 `If-Modified-Since`, `Expires` 作为缓存的判断标准, 而 `HTTP/1.1` 引入了更多缓存策略, 如 `Entity tag`, `If-Unmodified-Since`, `If-Match`, `If-None-Match` 等.
- **带宽**: `HTTP/1.0` 中存在浪费带宽现象, 当客户端只需要部分对象时, 服务器只能传输全部对象, 且 `HTTP/1.0` 不支持断点续传功能; `HTTP/1.1` 在请求头中加入 range 头域, 允许只请求资源的某个部分, 方便开发者充分利用带宽和连接
- **Host 头**: `HTTP/1.1` 引入了 Host 头段, 用于标记域名, 允许同一个 IP 地址上托管多个域名, 支持虚拟主机的功能, 而 `HTTP/1.0` 没有 host, 不支持虚拟主机.

### HTTP/1.1与HTTP/2.0
- 多路复用: `HTTP/2.0` 在同一连接上可以同时传输多个请求和响应, 互不干扰; 而 `HTTP/1.1` 只能使用串行方式, 对每一对请求和响应都需要独立连接, 而浏览器为控制资源对 `TCP` 连接数量有限制. 这使得 `HTTP/2.0` 在处理多个请求时更加高效, 减少了网络延迟.
- 二进制帧: `HTTP/2.0` 使用二进制帧进行数据传输, 对数据传输更加紧凑高效; 而 `HTTP/1.1` 使用文本格式的报文, 需要传输的数据量更大.
- 队头阻塞: `HTTP/2.0` 引入多路复用技术, 运行多个请求和响应在单个 `TCP` 连接上并行交错传输, 在应用层解决了 `HTTP/1.1` 的队头阻塞问题, 但仍受到 `TCP` 层队头阻塞的影响.
- 头部压缩: `HTTP/1.1` 支持 `body` 压缩不支持 `header` 压缩; `HTTP/2.0` 中, 支持 `Header` 压缩, 使用了专门为 `Header` 压缩设计的 `HPACK` 算法, 减少了网络开销.
- 服务器推送: `HTTP/2.0` 支持服务器推送, 可以在客户端请求资源时, 将其他相关资源一并推送给客户端，减少了客户端的请求次数和延迟. 而 `HTTP/1.1` 中需要客户端自己发送相关请求.
