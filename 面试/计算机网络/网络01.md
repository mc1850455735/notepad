
# IP协议

IP ( Internet Protocol，网际协议 )。它负责解决一个核心问题：互联网中的一台设备，怎么找到另一台设备。网络通信中，需要地址表示不同机器的位置，这个地址就是 IP 地址。

## IPv4

IPv4 是第 4 版互联网协议，也是目前最早大规模普及的一代 IP 协议。IPv4 使用 32 位地址，地址总数理论上有 `2^32` 个，约 42.9 亿。IPv4 地址通常写成十进制点分格式，由 4 段组成，每段 8 位，总共 32 位。

**特点**
- 历史最久，应用最广
- 大多数网络都兼容
- 地址资源紧张
- 需要依赖 NAT 等技术缓解地址不足问题

## IPv6

**IPv6** 是第 6 版互联网协议，是为了解决 IPv4 地址不足等问题而设计的新一代 IP 协议。它使用 **128 位**地址，通常写成冒号分隔的十六进制，且支持简写规则。128 位地址总数理论上有 `2^128` 个，远超 IPv4。

**特点**
- 地址空间极大
- 设计上更适合未来互联网发展
- 减少对 NAT 的依赖
- 在路由、自动配置、安全等方面做了很多改进

## IPv4 vs IPv6

| 对比项   | IPv4         | IPv6                 |
| -------- | ------------ | -------------------- |
| 地址长度 | 32 位        | 128 位               |
| 表示方式 | 点分十进制   | 冒号分隔十六进制     |
| 地址数量 | 约 42.9 亿   | 极其巨大             |
| NAT      | 大量依赖     | 依赖较少             |
| 报文头   | 较复杂       | 更简洁固定           |
| 广播     | 支持广播     | 不支持广播，使用组播 |
| 地址配置 | 手动 / DHCP  | SLAAC / DHCPv6       |
| 地址解析 | ARP          | NDP                  |
| 发展定位 | 传统主流协议 | 新一代协议           |

## IP 版本过渡

### 双栈策略

双栈就是让设备同时支持 IPv4 和 IPv6，同时有 IPv4 地址和 IPv6 地址。通信时，系统会根据目标地址类型来决定走哪套协议：
- 如果目标支持 IPv6，就优先走 IPv6
- 如果目标不支持 IPv6，就退回 IPv4

**优点**
- 兼容性最好
- 过渡最平滑
- 不需要复杂封装或转换
- 便于逐步迁移业务

**缺点**
- 同时维护两套网络，复杂度高，运维成本高

**适用场景**：企业网络、操作系统、数据中心逐步升级到 IPv6

### 隧道策略

最常见的方法是把 IPv6 报文封装在 IPv4 网络里传输，或者反过来。适用于两端支持 IPv6，而中间网络只支持 IPv4 的情况。通过该策略，即使中间基础设施未升级到 IPv6，也能让两端 IPv6 网络互通。允许网络逐步升级到 IPv6。

**常见类型**
- 手工隧道：管理员手动配置隧道两端地址。
- 自动隧道：系统自动推导隧道端点，减少人工配置。
- GRE / IP 隧道：借助 GRE 等通用隧道机制承载 IPv6。

**优点**：不要求中间网络马上升级，可以快速打通 IPv6 孤岛，适合渐进式部署

**缺点**
- 增加封装开销，MTU 处理更复杂
- 配置和排障更复杂；
- 自动隧道方案已不太主流

**适用场景**
- 两个 IPv6 网络之间跨 IPv4 骨干互联
- 运营商或企业网络临时过渡
- 旧网络环境下测试 IPv6 连通性

### 协议转换策略

因为 IPv4 和 IPv6 报文格式不同、地址长度不同，所以让 IPv4 和 IPv6 之间通过翻译设备互通，比如 NAT64、DNS64 等协议。适合 IPv6-only 和 IPv4-only 网络互通。

IPv6 客户端发请求，中间转换设备把 IPv6 请求转成 IPv4 请求，发给 IPv4 服务器，IPv4 响应回来后，再转换成 IPv6 响应返回给客户端。

**常用协议**
- NAT64：让 IPv6-only 客户端访问 IPv4-only 服务器，中间通过 NAT64 做地址和协议转换，将 IPv6 地址转为 IPv4 地址。
- DNS64：与 NAT64 配合使用。DNS64 的作用是为 IPv6 only 的客户端捏造一个可用于访问 IPv4 only 服务端的 IPv6 地址，再由 NAT64 转为 IPv4 地址。

**优点**
- 可以让纯 IPv6 网络继续访问 IPv4 资源
- 有助于推动 IPv6-only 部署
- 适合 IPv4 地址紧张的环境

**缺点**
- 协议转换增加复杂度
- 兼容性相对比较一般
- 增加排障复杂度
- 影响端到端透明性

**适用场景**
- IPv6-only 接入网络
- 数据中心逐步去 IPv4 化

### 平稳过渡策略

**1. 双栈部署**  
让核心设备、服务器、操作系统同时支持 IPv4 和 IPv6。为最常见的方案，兼容性最好，业务可以逐步迁移。

**2. 分阶段改造**  
先改网络基础设施，再改服务器和应用，最后改终端接入。降低一次性变更风险。

**3. 隧道技术**  
如果部分网络暂时还不支持 IPv6，就用隧道把 IPv6 流量封装在 IPv4 网络中传输，用来打通过渡期链路。

**4. 协议转换**  
当 IPv6-only 和 IPv4-only 系统需要通信时，会用 NAT64、DNS64 这类转换技术保证互通。

**5. 先外围、后核心业务**  
企业通常会先让官网、公共服务、测试环境支持 IPv6，再逐步扩展到内部核心系统。

**6. 做好测试和回退方案**  
上线前会做兼容性、性能、安全测试；上线时保留 IPv4 回退能力，避免影响业务连续性。

**7. 配套改造运维和安全体系**  
包括 DNS、负载均衡、防火墙、监控、日志、ACL、漏洞扫描等，都要同时支持 IPv6。

### 过渡挑战

**现存网络结构兼容性复杂，迁移无法一刀切**
企业网络里同时存在老旧系统和新业务平台，部分系统可能只支持 IPv4，导致必须考虑使用双栈等 IP 过渡策略。然而，兼容性越复杂，过渡周期越长，管理难度也更高。

**业务连续性要求高，需避免迁移风险影响生产**
迁移过程中可能影响业务可用性，必须避免服务中断。因此需要优先考虑低风险、可回退的方案，从而影响技术推进速度。

**使用双栈策略，导致运维成本上升**
使用双栈时，需要同时维护 IPv4 和 IPv6 两套体系，意味着配置更复杂，运维人员学习成本更高，故障定位难度增加。

**地址规划和网络架构需要重新设计**
企业在过渡时通常要重新思考地址规划是否分层、是否便于路由汇总、如何统一编址各个部门地址、是否适配自动配置和未来扩展等问题，需要重构网络设计思路。

**安全体系需要同步升级**
IPv6 环境下与 IPv4 环境安全策略存在不同，安全人员的经验可能不足，从而导致IPv6 ACL 和防火墙策略不完善、对各个协议的安全理解不足等问题。

**应用系统和中间件改造成本高**
企业应用程序中可能固定依赖 IPv4 地址和协议，同时数据库连接字符串、接口配置、白名单等信息都依赖 IPv4。所以企业选择过渡策略时，还需要进行应用、数据库、中间件和外围依赖的联动升级。

**外部生态不一致，导致企业不能独立完成迁移**
外部合作伙伴可能只支持 IPv4，决定了企业往往不能只看内部条件，而要看上下游生态成熟度。生态不成熟时，只能长期保留双栈或依赖协议转换。

# 代理服务器

## 概念

代理服务器本质上是一个“中间人”。

客户端不直接和目标服务器通信，而是先把请求发给代理，再由代理代替它去和另一端通信，最后把结果转回来。这个“中转层”可以带来很多能力，比如隐藏身份、访问控制、缓存加速、负载均衡、安全防护等。

## 基本机制

一次典型的代理过程是这样的：

1.  客户端先连接代理服务器
2.  代理服务器接收请求，按规则决定是否转发
3.  如果允许，代理服务器再去访问目标服务器
4.  目标服务器把响应返回给代理
5.  代理再把响应转交给客户端

所以代理的核心不是“替你存数据”，而是“替你建立连接、转发请求、控制流量”。

可以把它理解成两种视角：
-   **替客户端出面**：这就是正向代理
-   **替服务器出面**：这就是反向代理

## 作用

- **隐藏真实 IP**：目标网站看到的是代理服务器的 IP，不是你的真实 IP。
- **访问控制**：公司或学校会用代理统一管理员工/学生的上网权限，比如屏蔽某些网站。
- **缓存加速**：代理可以把常访问的内容先存起来，下次别人再访问时会更快。
- **安全过滤**：有些代理会检查流量，拦截恶意网站、病毒内容或不合规请求。
- **转发请求**：在网络架构里，代理还能帮后端服务分担压力、做负载均衡或隐藏内部服务器。

## 正向代理

正向代理服务的是客户端，帮助客户端去访问本来无法直接访问或不方便直接访问的资源，目标服务器通常感知到的是代理，而不是实际用户。

当客户端**没有配置正向代理时**，用户直接访问目标网站。目标网站直接收到用户请求，也直接把响应返回给用户。

当**有正向代理时**，客户端先把请求发给代理服务器，再由代理服务器将请求转发给目标网站，拿到响应后返回给客户端。

在正向代理过程中，目标网站能够看到的请求来源 IP 是代理服务器 IP，但目标网站不一定能直接知道真实用户 IP， 除非代理主动加一些头，比如 `X-Forwarded-For`。

### 作用

#### 请求转发

客户端可能因为网络策略、地域限制、公司网络限制，不能直接访问某些资源。正向代理可以帮助客户端访问原本因网络拓扑、权限策略或地域原因而无法直接访问的服务。

#### 隐藏客户端身份

目标服务器只能看到代理服务器的 IP，看不到真实客户端 IP。不过正向代理只能降低直接暴露，而不能做到绝对匿名，因为很多场景下仍然能结合日志、账户、Cookie、指纹等方式识别用户。

**作用**
- 隐藏真实来源
- 做匿名访问
- 避免直接暴露内部网络结构

#### 访问控制

通过代理，可以控制客户端能访问什么、不能访问什么。如：
-   禁止访问某些网站
-   限制某些时间段访问外网
-   限制下载某类文件
-   按用户、IP、部门做权限策略

#### 日志和审计

很多企业内网机器不允许直接访问互联网，而是必须统一经过代理服务器。

好处：
- 统一审计
- 统一权限控制
- 统一日志记录
- 统一安全策略

#### 缓存和加速

代理服务器可以缓存热门资源。如多个客户端频繁访问同一个文件、网页、镜像包，代理先缓存一份，后续直接从本地返回。

优点：
- 减少带宽消耗
- 提升访问速度
- 降低外网请求次数

#### 协议转发与统一管理

代理可以帮客户端处理某些复杂网络逻辑，比如：
- DNS 解析转发
- 协议适配
- 认证
- 日志记录
- 流量控制

### 缺点

- 增加链路复杂度：多了一跳，系统更复杂，增加排障难度。
- 可能带来性能损耗：代理本身会增加转发开销，代理可能成为性能瓶颈。
- 单点问题：单点代理挂了，所有客户端都可能无法访问外网。
- 安全和隐私风险：如果代理不可信，会提高使用网络通信的风险，导致通话内容被泄密。
- 兼容性问题：有些协议或者应用对代理支持不好，需要额外适配。

### HTTP & HTTPS 工作过程

对 HTTPS 来说，很多正向代理只是建立隧道，不直接解析业务明文；如果企业要做 HTTPS 审计，通常需要配合受信任证书做 TLS 中间人代理。

#### HTTP 请求代理

客户端把**完整 URL** 发给代理，而不是只发路径。

例如平时直接请求服务器时可能是：

```
GET /index.html HTTP/1.1  
Host: www.example.com
```

而走 HTTP 代理时，客户端可能会发给代理：

```
GET http://www.example.com/index.html HTTP/1.1  
Host: www.example.com
```

代理服务器收到后，再代替客户端去请求目标站点。

#### HTTPS 怎么代理

HTTPS 因为有 TLS 加密，HTTP 代理一般使用 `CONNECT` 方法建立隧道。

比如客户端会发：

```
CONNECT www.example.com:443 HTTP/1.1  
Host: www.example.com:443
```

代理如果允许，就建立一条 TCP 隧道。之后客户端和目标服务器在这条隧道里做 TLS 握手，代理通常只转发字节流。

如果不做中间人解密，代理看不到 HTTPS 明文内容

### 常见类型

#### 透明代理

客户端可能甚至不知道自己正在经过代理。

特点：
- 请求经过代理
- 目标服务器有时还能知道真实客户端 IP
- 常用于企业网关、内容过滤

#### 匿名代理

隐藏客户端真实 IP，但会告诉目标服务器“我是代理”。

#### 高匿名代理

尽量不暴露自己是代理，也不暴露真实客户端信息。不过现实里“高匿名”不是绝对的，只是减少暴露特征。

### 应用场景

- 企业内网统一外网出口
- 爬虫代理池
- 开发调试
- 安全审计与内容过滤
- 软件包镜像和缓存

### 客户端主动配置正向代理

正向代理是替客户端访问目标资源，所以客户端必须知道请求先发给谁。也就是说，客户端需要显式配置代理地址和端口，或者通过 PAC 文件、系统策略、浏览器设置等方式自动使用代理。

而反向代理之所以不需要客户端配置，是因为它对外就是目标服务本身的一部分。

### 正向代理 vs VPN

#### 正向代理
- 主要代理特定**应用层**请求，常见是 HTTP、HTTPS、SOCKS
- 通常需要应用或系统配置代理
- 不一定加密全部流量

#### VPN
- 更偏网络层或隧道层，建立一条虚拟专用网络隧道
- 通常接管整机或整段网络流量
- 往往会加密整个通信过程

## 反向代理

通过配置反向代理服务器，客户端访问的其实不是后端真实服务器，而是先访问反向代理，再由反向代理把请求转发给后面的一个或多个真实服务器。客户端可能以为自己访问的就是目标网站，但实际上真正处理请求的，可能是由反向代理指向的一台或多台应用服务器。

反向代理代理的是**服务端**，不是客户端。它站在服务器这一侧，帮后端服务器接收请求，再把请求分发给后端真实服务器，最后把结果返回给客户端。客户端通常不知道后面到底有几台服务器，也不知道请求最终落到了哪一台。

当有反向代理时，客户端**访问流程**一般是
1.  客户端发请求给反向代理
2.  反向代理根据配置决定转发给哪台后端服务器
3.  后端服务器处理请求
4.  后端把响应返回给反向代理
5.  反向代理再返回给客户端

### 作用

#### 隐藏后端服务器

通过反向代理，使客户端只能看到反向代理，看不到后端真实服务器。这样做不暴露内部服务器地址。不暴露内部网络结构。利于提高安全性，便于统一管理入口。

#### 负载均衡

这是反向代理最经典的用途。反向代理作为流量入口，把请求转发到后端服务集群，实现负载均衡，从而分摊流量压力，提高系统吞吐量，避免单台服务器被打爆，提高整体可用性。

常见反向代理负载均衡策略：
- 轮询
- 加权轮询
- IP 哈希
- 最少连接

#### SSL/TLS 终止

很多系统会把 HTTPS 证书配置在反向代理层。

当客户端和反向代理建立 HTTPS 连接后，反向代理完成 TLS 握手和解密，随后由反向代理把请求转发给后端服务。

通过反向代理的转发，后端服务不需要都配置证书，且统一管理 HTTPS，减轻后端加解密开销，便于运维。

这就是常说的 **SSL 终止** 或 **SSL 卸载**。

#### 统一入口和路由转发

反向代理可以根据不同路径、域名把请求**转发到不同服务**，常见于微服务和网关架构。

#### 缓存静态内容

反向代理可以缓存热点资源，通过缓存，可以减少后端压力，提升响应速度，降低重复计算消耗。

#### 高可用和故障隔离

如果某台后端服务器挂了，反向代理可以把流量切到其他正常节点。这样系统不至于因为单台机器故障就整体不可用。

#### 安全防护

反向代理通常是很多安全策略的落点，如限流、黑白名单、防刷、防攻击、请求过滤、WAF 接入、Header 处理等。反向代理不仅是转发器，还是安全边界的一部分。

### 常用组件

常用反向代理软件如下：
- **Nginx**（常见）
- **HAProxy**
- **Envoy**
- **Apache HTTP Server**
- 云厂商的 **负载均衡器**
- Kubernetes 里的 **Ingress Controller**

### 缺点

- **增加系统复杂度**：多了一层转发，配置和排障更复杂。
- **可能成为瓶颈**：如果反向代理本身性能不足，会变成系统瓶颈。
- **可能成为单点**：如果只部署一个反向代理节点，它挂了整个入口都不可用。

一般会通过多实例部署、Keepalived / VIP、云负载均衡、集群高可用等方式避免反向代理的缺点。

## 正向代理 vs 反向代理

正向代理解决的是“客户端怎么出去”的问题，反向代理解决的是“请求怎么进来并分发给后端”的问题。

| 类型     | 正向代理                               | 反向代理                                     |
| -------- | -------------------------------------- | -------------------------------------------- |
| 本质区别 | 代理客户端                             | 代理服务器                                   |
