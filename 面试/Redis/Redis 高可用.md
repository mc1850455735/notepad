## 概要

实现Redis高可用主要通过以下方式：
1. 主从复制架构实现数据冗余备份；
2. 哨兵模式（Sentinel）监控主节点并自动故障转移；
3. 集群模式（Redis Cluster）通过数据分片和节点互备提供分布式高可用；
4. 配合持久化机制保障数据安全；
5. 部署多机房容灾架构应对网络分区。

## 主从复制

**主从复制 ( Replication ) 原理**：通过异步复制实现主节点和从节点之间的**数据同步**。主节点负责写操作，从节点负责读操作和备份。 **适用于**对可用性要求不高的**小规模场景**，或作为其他高可用方案的基础。

**优点**
- 配置简单，支持读写分离。
- 数据冗余备份，避免单点故障导致数据丢失。

**缺点**
- 不自动处理故障转移，主节点宕机后需要手动将从节点切换为主节点。
- 主节点是唯一的写入点，存在写操作单点瓶颈。

## 哨兵模式

**哨兵模式 ( Redis Sentinel ) 原理**：由多个 Sentinel 节点组成监控集群，自动检测主节点和从节点的健康状态，并在主节点发生故障时进行故障转移，自动选举新主节点并更新客户端配置。**适用于**中小规模场景，需要**自动故障切换**但**无需切片**的情况。

**核心功能**
- 监控 ( Monitoring )：实时检查节点状态。
- 通知 ( Notification )：通过 API 或脚本告知管理员故障。
- 自动故障转移 ( Automatic Failover )
- 客户端配置发现：客户端通过 Sentinel 获取当前主节点地址。

**优点**
- 自动化故障转移，减少人工干预。
- 支持水平扩展的 Sentinel 集群，提高监控可靠性。

**缺点**
- 写操作效率仍受限制于单主节点性能。
- 客户端需要支持 Sentinel 协议。

## 集群模式

**集群模式 ( Redis Cluster )**：Redis 官方提供的分布式解决方案，通过分片将数据分散到多个主节点，每个主节点对应多个从节点，支持故障转移和数据迁移。**适用于**大规模数据、高并发、需要横向扩展的分布式环境。

**核心特征**
- 数据分片：利用**哈希槽**，将数据分配到不同的节点。
- 高可用：每个分片的主节点至少有一个从节点，当主节点故障时从节点自动升级为主节点。
- 去中心化架构：节点间通过 Gossip 协议通信，客户端可连接任意节点。

**优点**
- 支持水平扩展，适合大规模数据和高并发场景。
- 自动故障转移和数据迁移。

**缺点**
- 由于哈希槽的存在，部分相关命令受限。
- 客户端需要兼容集群协议。

## 第三方代理

**Twemproxy (Nutcracker)**
-  代理中间件，将客户端请求分片到多个Redis实例。
-  优点：简化客户端分片逻辑，支持一致性哈希。
-  缺点：不支持自动故障转移，需配合 Sentinel 或 Cluster 使用。

**Codis**
-  开源的分布式 Redis 解决方案，支持动态扩缩容和故障转移。
-  通过代理层 (Codis Proxy) 和 ZooKeeper/Etcd 协调分片信息。
-  **适用于**需要透明分片和动态扩展的企业级应用 (但社区活跃度较低)。

## 云托管

**AWS ElastiCache、Azure Cache for Redis、阿里云Redis**
-  基于Redis Sentinel或Cluster的托管服务，提供自动故障恢复、备份、监控等功能。
-  优点：免运维，适合云原生环境。
-  缺点：依赖云厂商，成本较高。
