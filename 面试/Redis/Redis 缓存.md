
# 延迟双删问题

对于 Redis 和 MySQL 之间的数据同步，通常会出现这样的一种问题：
MySQL 修改数据后，为了保障数据一致性，选择先删除 Redis 中的内容，然后更新数据库中的记录，然后有线程访问对应的项目时，由于 Redis 中的内容已经被删除，所以直接访问 MySQL 中的内容，并依据 MySQL 中的内容，对 Redis 内容进行重建。

但是，上述过程可能遇到这样一个问题：
假设线程 A 需要进行数据修改，于是线程 A 先删除 Redis 中的内容，然后试图对 MySQL 中的数据进行修改；
然而此时，线程 B 在 Redis 被删除，MySQL 未修改的时机，对 Redis 进行访问，发现没有对应 Redis 条目后，使用 MySQL 中的数据对 Redis 进行重建，此时 Redis 中消息又被重建为 old 消息。

## 延迟双删的策略

因此，采用延迟双删的方式进行数据一致性的处理：
首先将 Redis 中的缓存删除，然后将 MySQL 中的数据进行更新，等待一定时间（延迟时间 > 查数据库 + 回写缓存的最长耗时）后，再次删除 Redis 中的缓存。
通过这种方式，即使删除 Redis 后又被其他线程重建了 Redis 中的记录，也可以通过一定时间后的延迟删兜底。

不过，延迟双并不能保证强一致性，因为第二次删除可能会失败。实际生产环节中，还会加入 MQ 重试机制，TTL，或者 Binlog / Canal 等机制提高延迟双删的可靠性。

# 缓存问题

### 击穿

**缓存击穿** 也叫 **热点 Key 问题**，就是一个被高并发访问且缓存重建业务较复杂的 Key 突然失效，导致大量请求访问瞬间给服务器带来巨大冲击。

对于热点 key 问题，核心解决思路就是避免对热点 key 的访问直接打到数据库中，可以通过以下方式解决： 

1. **互斥锁**：当热点 key 失效时, 通过**互斥锁**，只允许一个线程查询并重建缓存，其他并发线程 **阻塞等待** 或 **返回默认值**。分布式锁必须设置过期时间，且过期时间需要大于数据库查询 + 缓存写入的最大耗时之和。同时设置最大重试次数，避免无限等待。适用于可以接受短暂请求阻塞，对数据一致性高要求的同时热点 key 更新频繁的场景。

2. **逻辑过期**：热点 key 是系统核心高频访问的数据。通过业务逻辑而不是 Redis 过期时间控制，实现 key 逻辑过期。逻辑过期时，直接取已过期数据。适用于热点 key 相对稳定，同时可以接受**短期不一致**，以及对**性能**有高要求的场景。

3. **缓存预热**：对于某些可预测的热点 key (如秒杀商品, 节日活动等)，在系统启动时主动将热点 key 加载到 Redis 中，避免首次访问为空导致大量数据库请求；适用于可提前得知的热点 key，且系统启动时无大量用户访问；但无法应对突发热点 (如突发新闻等)。

逻辑过期和互斥锁的策略，都需要分布式锁。对于逻辑过期，需要分布式锁用于重建锁，第一个拿到锁的线程负责重建缓存，其他线程发现锁被占用后，直接拿旧缓存；对于分布式锁互斥方案，拿不到分布式锁的其他线程，会阻塞等待互斥锁过期或被释放。逻辑过期方案可以在高并发环境下获得低延迟和高可用，代价是一段时间内的不一致。

### 穿透

**缓存穿透** 指的是客户端请求的数据在缓存中和数据库中都不存在, 这样的缓存永远都不会生效，所有请求都会直接打到数据库，对数据库造成压力。

**解决策略**

1. **缓存空对象**：对数据库中不存在的数据，在 Redis 中缓存一个空值，并设置一个**较短的过期时间**，短时间内后续相同请求会直接打到缓存中。实现简单，但可能占用过多内存空间，同时对于短时间内 id 不同的假请求没有较好的防御能力。

2. **布隆过滤器**：是一种概率性数据结构，可以用来判断某元素是否可能存在于集合中，且空间占用极小。缺点是存在误判可能，标准布隆过滤器一定让真实存在的数据通过，但可能把部分不存在的数据也放过去。即使如此也大大降低了打到数据库中的假请求数量。

3. **加强请求参数合法性校验**：通过配置过滤规则, 过滤明显非法的请求, 如格式错误, 超出合理范围等. 从请求入口处拦截非法请求, 避免无效请求到达缓存或数据库.

4. **限流熔断**：对于单个IP/用户/接口的请求频率进行限制, 防止短时间内恶意高频请求冲击.

### 雪崩

**缓存雪崩**是指在同一时间段内大量的缓存 key 同时失效或者 Redis 服务器直接宕机，导致大量请求直接到达数据库，为数据库带来巨大压力。

**解决策略**

- **打散过期时间**：雪崩的主要原因就是大量 key 同时过期。通过给每个 key 过期时间都添加随机偏移量，打散过期时间，避免瞬间集体失效，将数据库压力进行平摊。

- **构建 Redis 集群**：通过构建 Redis 集群提高缓存层的可用性，确保缓存服务层不宕机，不丢失数据，防止单体 Redis 因服务器宕机导致的缓存层整体不可用，核心是数据冗余+故障自动切换。

- **添加熔断降级策略**：当 Redis 集群出现故障导致缓存层不可用时，通过熔断降级策略，直接 **拒绝部分请求** 或 **返回默认值**，避免所有请求直接穿透导数据库，保护数据库不被压垮。

- **配置合理淘汰策略**：Redis 内存满后会触发提前配置好的内存淘汰策略，如果淘汰策略不合理，则可能导致大量热点 key 被批量淘汰。

# Caffine 和 Redis的区别

Caffeine 是进程内的 JVM 本地缓存，Redis 是独立部署、多个服务实例共享的分布式缓存。

Caffeine 官方将其定位为高性能 Java 内存缓存，其数据存储在 JVM 内存中，读取数据时不需要经过网络，因此读取速度极快。然而，Caffeine 缓存空间大小受单个 JVM 内存限制，且每个服务实例各有一份 Caffeine 缓存，多实例之间容易出现数据不一致。

因此，Caffeine 更适合存储一些数据量比较小，数据只需要在单个实例中使用，且对访问延迟要求极高的数据。实际项目中可以把 Caffeine 作为一级缓存、Redis 作为二级缓存，但需要通过失效消息和合理 TTL 解决两级缓存一致性问题。
