
### 概念

Redis 持久化是指将内存中的数据保存到磁盘, 以便在服务重启或故障后可以恢复数据的机制. 
Redis 本质是内存数据库, 内存中数据在服务器宕机后都会丢失. 持久化用于保证数据不会因进程退出或机器重启而丢失.

Redis 中主要有 RDB 和 AOF 两种持久化存储方式. `RDB` 通过快照的形式进行持久化存储, 恢复速度快, 对性能影响小, 但是可能丢失最近一次快照记录; `AOF` 通过追加日志实现持久化存储, 数据恢复最完整, 丢失可控制在秒级, 但文件更大, 性能开销相对较高.

通常情况下会同时使用 `RDB` 和 `AOF` 两种持久化方法，即**混合持久化模式**. 让 `RDB` 用于数据备份, `AOF` 用于数据恢复.

### RDB

**原理**
- 定时快照：在指定时间间隔内，将内存中数据集生成二进制快照 `snapshot` (dump.rdb) 并写入磁盘中。`RDB` 的快照规则可以自定义，`Redis` 重启时, 通过读取 `.rdb` 文件恢复数据。
- 触发方式：
	- 自动触发：通过配置文件设置时间策略
	- 手动触发：执行 `SAVE` (阻塞主线程) 或 `BGSAVE` (后台异步) 命令。
- `.RDB` 文件的保存位置是在 `Redis` 配置文件中指定的.

**优点**
- 二进制文件紧凑，加载速度快远于 `AOF`。
- `RDB` 文件是某个时间点的完整数据副本，适合冷备份和灾难恢复。
- 后台异步生成快照，对主线程的影响较小。

**缺点**
- 最近操作可能不会被持久化，从而导致两次快照之间的数据丢失。
- 数据集较大时，`BGSAVE` 的 fork 操作可能阻塞主线程，耗费服务器性能。

### AOF

**原理**
- **日志追加**：记录 `Redis` 的每个写操作，`Redis` 重启时，重新执行命令以恢复数据。`AOF` 文件的保存位置是在 `Redis` 配置文件中指定的。
- **同步策略**：
	- **appendfsync always**：每个命令都同步到磁盘 (最安全)
	- **appendfsync everysec**：每秒同步一次 (默认)
	- **appendfsync no**：由操作系统决定何时同步 (最快)

**优点**
- 数据安全性高，最多丢失 1 秒数据 (every second 下)。
- `AOF` 文件为文本格式，便于人工分析或修复
- 进行了自动重写优化，通过 `BGREWRITEAOF` 压缩冗余命令。

**缺点**
- 对于相同数据, `AOF` 文件体积通常比 `RDB` 文件体积更大。
- 高写入负载下，频繁同步可能影响吞吐量。
- 根据选用的 `fsync` 策略不同，`AOF` 在某些配置下可能比 `RDB` 更慢一些.

### 混合持久化

Redis 4.0 + 后，支持结合了 RDB 和 AOP 优势的混合持久化，生成一个包含 RDB 数据头和 AOF 增量命令的混合文件。
- 触发条件：在 AOF 重写时，先以 RDB 格式保存当前数据集，后续增量命令以 AOF 格式最佳。
- 恢复流程：先加载 RDB 快照，再重放后续 AOF 命令。
- 优点：
	- 快速恢复：RDB 提供基础数据，减少恢复时间。
	- 数据完整性：AOF 记录增量操作，降低数据丢失风险。

### 持久化方案选择 

- 允许分钟级数据丢失：RDB。因为其恢复速度快，适合备份和快速重启。
- 不允许数据丢失：AOF (everysec)。最多丢失 1 秒，安全性高。
- 高吞吐量场景：RDB 或混合持久化。减少 AOF 的同步开销。
- 数据恢复优先级：混合持久化。兼顾恢复速度和数据完整性。

### 数据恢复流程
1. 重启 Redis：自动按以下**优先级**加载持久化文件：
	1. 仅存在 AOF：加载 AOF。
	2. 仅存在 RDB：加载 RDB。
	3. 同时存在 AOF 和 RDB：加载 AOF，因其记录更完整。
2. 手动恢复
	- 将备份的 RDB/AOF 文件放入配置目录，重启 Redis。
