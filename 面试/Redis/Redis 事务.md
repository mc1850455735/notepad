
## 一句话总结

Redis 事务通过 `MULTI`、`EXEC` 命令组合多个操作按顺序执行，保证**原子性**（整体执行但**不支持回滚**）。若命令入队时出现语法错误，整个事务会被拒绝；运行时**错误不影响**其他命令执行。支持 `WATCH` 命令实现**乐观锁机制**，监视键值变化时自动中断事务，适用于并发控制场景。

通常，工程中不会使用 Redis 的事务，而是使用 Lua 脚本保证 Redis 命令的原子性。

## 详细解析

### 概念

Redis 中事务的本质就是通过命令 (`MULTI`, `EXEC`, `WATCH`) 一次性、顺序性地执行一组命令地机制。事务中所有命令都会被打包后按顺序执行，不会被其他客户端的命令插入，从而保证系列操作一定程度的原子性。

总结来说，事务就是**一次性、顺序性、排他性**的执行一个队列中的一系列命令。

### 事务的基本命令

Redis 事务通过以下几个命令实现：

|命令|描述|
|-|-|
|MULTI|开启事务。后续命令会被暂存到事务队列中，不会立即执行|
|EXEC|提交事务。将队列中的所有命令按顺序执行，并返回所有命令的执行结果|
|DISCARD|取消事务。清空事务队列，放弃执行所有命令|
|WATCH key...|监控一个或多个键。如果被监控的键在事务执行前被其他客户端修改，事务会失败（乐观锁机制）|
|UNWATCH|取消所有键的监控（通常在DISCARD后自动触发）|

### 事务执行步骤

1. 使用 `Multi` 命令开始一个事务。事务开始后，在使用 `Exec` 执行事务之前，所有命令都不会立即执行，而是被存入**事务队列**。
2. 事务模式下，客户端可以连续发送多个命令，这些命令会被依次加入队列当中。
3. 通过 `Exec` 执行队列中的所有命令，按顺序返回每个命令的结果。`Exec` 执行后，整个事务被视为已完成，不做任何操作即可结束事务。
4. 执行 DISCARD 命令，可以清空整个命令队列，事务终止且不执行任何命令。

Redis 中事务不支持回滚，Exec 执行开始后，即使事务执行过程中出现失败，也不会终止，而是继续向下执行。

### 乐观锁：WATCH的使用

如果需要保证事务执行期间某些键**未被其他客户端修改**，可以用 WATCH 实现**乐观锁**。

**流程**
1. 执行 `WATCH key1 key2...` 监控目标键。
2. 执行 `MULTI` 开启事务。
3. 提交命令到事务队列。
4. 执行 `EXEC` 时，Redis 会检查被监控的键是否被其他客户端修改：
    - 如果未修改，正常执行事务。
    - 如果被修改，事务**失败**（返回nil），所有命令不执行。

### Redis 事务 ACID 分析

Redis 事务的行为与传统数据库（如 MySQL）的事务有显著差异，其 ACID 特性区别如下：

- **原子性 (Atomic)**：传统数据库事务支持 ACID 中的**原子性**，但 Redis 事务的原子性有限。Redis 中单条命令是满足原子性的，但是事务整体不保证原子性，且没有回滚操作。
	- 事务中存在**语法错误**时，整个事务都会被拒绝，所有命令都不执行。
	- 当运行事务过程中出现**运行时错误**时，只有出现错误的命令失效，其余操作依然会继续向下执行。
	- Redis 事务不支持**回滚**。即使事务中某个命令失败，已执行的命令也无法撤销。设计原因是为了保持简单和高性能，避免回滚带来的复杂性。
	- 事务中的命令按入队顺序**串行执行**，执行期间不会被其他客户端命令打断，这是由 Redis 的单线程模型保证的。
- **一致性 (Consistency)**：Redis 的数据模型不存在复杂的一致性约束，但是可以藉由单个命令的原子性和 Lua 脚本复杂原子操作，在业务层面保持一致性。
- **隔离性 (Isolation)** : Redis 是单线程模型, 命令之间串行执行, 事务之间互不影响, 满足隔离性需求
- **持久性 (Durability)** : 事务只要执行成功, 就可以被通过 RDB 或 AOF 持久化到磁盘中.
