
# 分布式锁的概念

**说明**
锁在程序中的作用就是同步工具，保证资源在同一时刻只能被一个线程访问，Java中的锁，比如 synchronized、Lock 等都是我们经常使用的，但是 Java 的锁只能保证单机的时候有效，分布式集群环境就无能为力了，因为 Java 的这些锁都是在同一个 JVM 中发挥作用的，如果是在分布式的服务中，会有多个虚拟机下的服务进行并发访问，这些锁是发挥不了作用的，这个时候我们就要用到**分布式锁**，可以用来控制分布式系统之间同步访问共享资源。 

分布式锁的思路是：在整个系统中提供一个**全局、唯一**的获取锁的东西，然后在每个系统都需要加锁时，都去用这个东西拿到一把锁，这样不同的系统拿到的就可以认为是同一把锁，这个东西，可以是 Redis、Zookeeper，也可以是数据库，只要是能储存数据的数据库都可以实现分布式锁。 

一般来说，分布式锁要满足以下几个条件：一是**互斥性**，在任何时候，对于同一条数据，只有一台应用可以获取到分布式锁。二是**高可用性**，在分布式场景下，一小部分服务器宕机不影响使用，这种情况下就需要将提供分布式锁的服务以**集群**的方式部署。三是**防止锁超时**，如果客户端没有主动释放锁，服务器会在一段时间之后自动释放锁，防止客户端宕机或者网络不可达时产生死锁。四是**独占性**，加锁解除必须由同一台服务器进行，也就是锁的持有者才可以释放锁，不能出现你加的锁，被别人解锁了。

常见的分布式锁的解决方案有三种：基于关系型数据库，如 MySQL、Redis、Zookeeper 的方案。基于关系型数据库实现分布式锁依赖数据的唯一性来实现资源锁定，比如主键和唯一索引等。

基于 Redis 实现简单，理解逻辑简单，性能好，可以支撑高并发的获取和释放锁的操作，缺点是 Redis 容易单点故障，集群部署，并不是强一致性的，锁不够健壮，key 的过期时间设置多少不明确，只能根据实际情况调整，需要自己不断的去尝试锁，比较消耗性能。

基于 Zookeeper，天生设计定位就是分布式协调，强一致性，很健壮，如果获取不到锁，加一个监听器就可以了，不用一直轮询，性能消耗小，但是在高请求高并发下，系统疯狂的加锁释放锁，最后 zk 承受不住这么大的压力，可能会存在宕机的风险。 

基于 MySQL 的分布式锁：主要有两种，一种是悲观锁，一种是乐观锁。悲观锁主要用 select...where...for update 对所查进行锁定和操作，name 字段必须要走索引，否则会锁表。优点是实现简单，由 MySQL 去解决争抢问题，架构相对简单，不再需要多余的三方组件，使整个系统更加简单；缺点是性能较差，并且有锁表的风险，非阻塞操作失败后，需要轮询，占用 cpu 和 MySQL 数据库资源，长时间不提交或者长时间轮询，会占用过多的 MySQL 连接资源。 

基于 Redis的分布式锁主要依靠三个命令：`SETNX`、`expire`、`delete`。`SETNX` 为 set if not exists 的缩写，使用方式为 `SETNX key value`，若 key 不存在，则存入键值对，返回1，该线程成功得到了锁，若key存在，则什么也不做，返回0，该线程抢锁失败；`expire key <timeout>` 为key设置一个超时时间，单位为秒，超过这个时间锁会自动删除 key，避免因宕机引起死锁；`delete key` 删除指定key。

实现思想为：获取锁时，使用 setnx 加锁，key 为锁名，value 值为一个随机生成的 UUID，获取锁成功后，使用 expire 命令为锁添加一个超时时间，若超过这个时间则放弃获取锁，释放锁的时候，通过 UUID 判断是不是该锁，若是该锁，则执行 delete 进行琐释放。

优点是依赖于 Redis 的高并发特性，性能极佳；缺点是过期时间不好控制，需要考虑续锁的问题，实现相对复杂，操作过程非阻塞，操作失败后需要轮询，占用cpu资源，主节点挂掉未成功同步的情况下，可能导致多个节点同时获取锁。

在具体实现时，需要考虑一下几个问题：因为宕机引起死锁问题，通过设置过期时间解决。业务时间长于过期时间时，可以开一个守护进程，为锁续期，即看门狗。为避免锁被别人释放，可以用锁写入唯一标识，释放锁先检查标识，再释放。这些问题实现起来太麻烦，可以用别人封装好的库 **Redisson**。Redisson 实现方法：一是 try-Lock，二是看门狗续锁机制，三是使用 Lua 脚本。Redisson 默认将锁的时间设置为 **30s**。

上述的分布式锁是建立在单节点之上的，有可能会违背锁的唯一性原则，无法保证高可用，若是要保证分布式锁的高可用，则可以采用多个节点的实现方案，可以采用 **RedLock 算法**来实现，Redisson 也完成了对 RedLock的封装，具有以下特性：互斥访问，避免死锁和容错性，只要大部分 Redis 节点存活，就可以正常提供服务。  

# 讲讲 Redisson 分布式锁原理和实现

Redisson 分布式锁的核心就是使用 Redis Hash + Lua 脚本保证加解锁操作的原子性，并通过一个后台线程进行锁的自动续期（看门狗机制）。

首先是**加锁**。
加锁时，Redisson 会执行一段 Lua 脚本进行原子操作，分三层进行判断：
- 如果锁不存在，直接创建 Hash 结构，field 是线程标识，value 设为 1，并设置过期时间（默认 30s），加锁成功；
- 如果锁已经存在，且 Hash 中的 field 表示匹配当前线程，说明当前是锁重入，value + 1 并刷新过期时间，加锁成功；
- 如果锁已经存在但是 Hash 中的 field 不匹配当前线程，说明锁已经被占用，返回锁的剩余存活时间，加锁失败。

当加锁成功后，通过**看门狗机制**重置锁的过期时间。
Redisson 会启动一个后台线程，默认每隔 10 秒设置锁的过期时间为 30 秒。只要当前业务线程还存在并持有锁，后台线程的续期就会一直执行，所以锁永远都不会过期。
当业务线程调用 unlock 操作或挂掉时，续期线程才会停止；即使线程挂掉没来得及解锁，由于看门狗线程失效，锁自然过期。

最后是**解锁**。
解锁时，Redisson 同样执行一段 Lua 脚本进行原子操作，分三层进行判断：
- 如果要解锁的锁不存在或者不属于当前线程，则直接返回；
- 如果 field 匹配，则 value - 1，如果减完以后大于 0，说明存在未退出的重入，刷新过期时间后返回。
- 如果 field 匹配且 value - 1 后为 0，则删除 key，同时 publish 一条消息通知其他等待中的线程。


# Redis 分布式锁

使用 Redis 的 SET 命令配合 NX（不存在时设置）、EX（过期时间）参数创建唯一键作为锁，并生成**随机值**标识客户端。获取锁失败时**重试或退出**，业务处理完成后**校验随机值**，并用 Lua 脚本原子化删除键释放锁。需注意设置合理**超时时间**防止死锁。高可用场景可采用 **RedLock 算法**增强可靠性。通常生产环境中会直接使用 Redission。

**实现演进**
- 实现1: 直接使用 `SETNX` 加锁, `del` 释放锁. 加锁没有过期时间, 且 `del` 时不区分锁的主人, 可能出现**死锁**现象或**误删锁**等情况.
- 实现2: 使用 `SETNX` 加锁, `del` 释放锁. 通过 `setnx` 加锁后通过 `expire` 设置过期时间, 确保不会出现死锁现象. 设置锁时同时在 `value` 设置锁的拥有者, 防止误删锁的现象发生. 但这种方法加锁和设置过期时间是两条命令, 不是原子操作, 存在中间状态.
- 实现3: 使用 Set 命令/ Lua 脚本同时实现加锁和过期时间的设置, 保证操作的原子性, 同时使用 Lua 可以实现复杂的原子操作. 但当业务执行时间大于锁的过期时间是, 锁会自动过期解锁, 其他客户端可以得到本不应释放的锁, 导致多个客户端同时进入临界区
- 实现4: 在客户端设置看门狗线程, 负责定期给当前客户端持有的锁延长过期时间, 业务结束后, 正常使用 Lua 脚本释放锁.

### 基础分布式锁

使用单一 Redis 实例，通过原子性 Set 同时获取锁和设置锁过期时间，避免非原子性条件下死锁的发生；同时设置客户端唯一标识，删除锁时，使用**客户端唯一标识 + Lua 脚本**的方式，保证原子性的同时防止误删除。

**优点**
- 实现方法简单, 易实现且性能较好

**缺点**
- 依赖单一 Redis 实例的可靠性，安全性差。若实例宕机，Redis 锁丢失。
- 主从切换的不一致可能导致短时间内锁异常。
- 业务执行时间超过锁存活时间可能造成锁提前被删除。

### RedLock分布式锁

**RedLock 红锁**是 Redis 作者提出的一种基于 Redis 的分布式锁算法。

部署 N 个 ( N为大于等于5的奇数 ) 相互独立的 Redis 实例节点，客户端依次尝试在每个 Redis 节点中获取同名锁，统计在时间窗口内成功获得的锁的数量，如果获取锁成功的节点数超过一半，则认为获取锁成功。释放锁时通过 Lua 脚本对所有节点执行解锁操作。

**作用**
- 通过多个实例提高锁的可用性与安全性, 避免单个节点宕机导致锁失效。
- 是提高锁可靠性的方案，但不是银弹。如果对锁可靠性有严格要求，还需要进行高幂等的业务设计等额外方案。

**看门狗**，即**锁续期机制**，是防止因业务超时而导致的锁提前失效的一种解决办法。其核心思想是设立一个后台线程，用于定期续期锁的有效期，避免在业务结束前超时释放锁。

### 增强式分布式锁

**锁可重入性**
- 在客户端标识中添加线程信息，通过线程 ID 实现锁的持有者绑定。
- 加锁时若锁已被使用，则根据线程 ID 确定该线程是否可重入锁。
- 释放锁时，通过线程 ID 校验线程一致性，避免误释放锁。

**分段锁设计**
- 按照业务类型，将不同业务进行分片，不同业务使用不同的锁。
- 通过分段锁，可以降低单锁竞争，提升并发能力。

**公平锁实现**
- 当等待锁时，使用有序集合维护等待队列。
- 锁空闲后，严格按请求队列中顺序获取锁。

### Redisson 框架或其他第三方

**Redisson 框架**
**特性**：内置看门狗、支持异步锁、公平锁模式

**监控与告警**

## 分布式互斥锁作用

- 防止接口因并发重复执行
- 控制对共享资源的访问
- 确保分布式任务的单实例执行
- 使用互斥锁控制热点key重建, 防止缓存击穿
- 控制分布式系统操作互斥



# Redis 排行榜

使用 Redis 的 Sorted Set（有序集合）实现排行榜：  
1. 用 ZADD 命令添加成员及其分数  
2. 通过 ZREVRANGE 获取分数从高到低的排名  
3. ZRANK 可查询成员具体排名  
4. 结合 ZSCORE 获取成员具体分数  
5. 相同分数默认按字典序排序，可用时间戳作为辅助排序条件

Redis  ZSET 支持按 Score 排序，并提供了丰富的命令用于动态更新、查询排名、获取 Top-N 等操作，非常适合实现实时排行榜。

ZSET 的每个元素由 Member 和 Score 组成，Redis 会根据 Score 对成员进行升序排序（默认）或降序排序（通过命令参数控制）。
排行榜的核心操作（如更新分数、查询排名、获取 Top N）都可以通过 ZSET 的命令高效完成。

**处理同分排名**

ZSET 中若多个成员分数相同，Redis 会按 member 的字典序排序（升序）。

若需避免同分按字典序排序（如希望先达到该分数的用户排名更前），可以将分数设计为**复合值**，例如：  
$分数 = 主积分 * 10^6 - 时间戳$（时间戳用于区分先后）。

这样，主积分相同的用户，时间戳更小，也就是更早达到的用户分数更高，排名更前。
