# 基础概念

`select`、`poll` 和 `epoll` 都是 Linux 下的 I/O 多路复用机制，目的是让一个线程同时监听多个文件描述符，当某个文件描述符就绪时再进行读写，避免为每个连接都创建一个线程。

它们的核心区别主要体现在三个方面：监听集合如何传递、内核如何检测就绪事件，以及就绪结果如何返回

## `select`

`select` 使用 `fd_set` 位图保存需要监听的文件描述符。每次调用 `select` 时，用户程序都需要把完整的**文件描述符集合**从**用户态复制到内核态**。内核会遍历整个集合，检查哪些文件描述符已经就绪，调用结束后再把结果写回用户态。

因此，`select` 有几个明显的问题。

第一，它通常存在文件描述符**数量限制**，常见的 `FD_SETSIZE` 是 1024。

第二，每次调用都要复制完整集合。

第三，内核需要线性遍历所有文件描述符，时间复杂度是 `O(n)`。

第四，`select` 会修改传入的集合，所以每次调用之前都需要重新设置。

## `poll`

`poll` 和 `select` 的工作原理基本相同，也需要把所有监听的文件描述符传入内核，内核依次遍历并检查事件是否就绪，时间复杂度同样是 `O(n)`。

它相对于 `select` 的主要改进是使用 `pollfd` 数组保存文件描述符，不再使用位图，因此没有 `FD_SETSIZE` 这种固定的 1024 限制。它能够监听的文件描述符数量主要受进程文件描述符上限和系统资源限制。

但是，`poll` 并没有解决性能上的核心问题。即使只有一个连接就绪，内核仍然要遍历整个数组；调用返回后，用户程序也需要遍历整个数组，才能找到哪些文件描述符产生了事件。因此，当连接数量很大但活跃连接较少时，性能仍然比较差。

## `epoll`

`epoll` 是 Linux 针对**大量并发连接**设计的 I/O 多路复用机制。它通常通过三个系统调用使用：

```c
epoll_create();
epoll_ctl();
epoll_wait();
```

首先通过 `epoll_create` 创建一个 epoll 实例，然后通过 `epoll_ctl` 把需要监听的文件描述符注册到内核中，最后通过 `epoll_wait` 等待就绪事件。

`epoll` 和前两者最大的区别是，监听集合不需要在每次等待时完整传递。文件描述符只需要通过 `epoll_ctl` 注册一次，之后由内核维护。

文件描述符就绪时，内核会通过回调机制将其加入就绪队列，`epoll_wait` 只需要把已经就绪的事件返回给用户程序。

所以，`epoll` 不需要每次遍历全部文件描述符，也不需要每次复制完整监听集合。在大量连接、少量活跃的场景下，性能明显优于 `select` 和 `poll`。

不过，严格来说，不能简单地说 `epoll` 的时间复杂度永远是 `O(1)`。`epoll_wait` 获取就绪事件的开销主要与实际就绪事件数量有关，可以近似理解为 `O(k)`，其中 `k` 是本次就绪的文件描述符数量；而文件描述符的添加、删除和修改还涉及红黑树操作。

`epoll` 还支持两种触发模式。

第一种是水平触发，也就是 LT。只要文件描述符仍然可读或可写，`epoll_wait` 就会持续返回该事件。LT 是默认模式，使用简单，不容易遗漏事件。

第二种是边缘触发，也就是 ET。只有文件描述符的状态发生变化时才通知一次。例如，从不可读变成可读时通知一次。如果一次没有把数据读取完，之后可能不会再次通知，所以 ET 模式通常需要配合非阻塞 I/O，并循环读取，直到返回 `EAGAIN`。

## 总结

| 对比项         | select      | poll        | epoll         |
| ----------- | ----------- | ----------- | ------------- |
| 数据结构        | 位图          | `pollfd` 数组 | 内核红黑树和就绪队列    |
| 文件描述符数量     | 通常有 1024 限制 | 无固定 1024 限制 | 无固定 1024 限制   |
| 是否每次复制完整集合  | 是           | 是           | 否             |
| 是否遍历全部文件描述符 | 是           | 是           | 通常只处理就绪事件     |
| 时间开销        | `O(n)`      | `O(n)`      | 主要与就绪事件数有关    |
| 触发模式        | 水平触发        | 水平触发        | 水平触发和边缘触发     |
| 适用场景        | 少量连接、兼容性要求高 | 连接数一般       | Linux 高并发网络服务 |

如果在面试中做一句话总结，我会说：

`select` 和 `poll` 都是把完整的文件描述符集合交给内核，由内核线性扫描；`poll` 主要解决了 `select` 文件描述符数量受限的问题，但没有解决遍历问题。`epoll` 则通过注册机制和就绪队列避免反复复制和全量扫描，更适合大量连接、少量活跃的高并发场景。
