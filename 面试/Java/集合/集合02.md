# Map

## HashMap

### HashMap与HashTable区别
- 线程安全性: HashMap 是**线程不安全**的, HashTable 是**线程安全**的; 因为 HashTable 内大多数方法都使用 synchronized 关键字进行了修饰. 但是如果需要线程安全的 Map, 请选择 `ConcurrentHashMap`
- 效率: 由于不需要进行线程安全判断, HashMap 比 HashTable 效率更高, 且 HashTable 基本上已被淘汰, 尽量不要使用.
- `Null Key` 和 `Null Value`: `HashMap` 允许 `null key` 和 `null value`, `null key` 只能有一个, `null value` 可以有多个; `HashTable` 不允许存在 `null key` 和 `null value`, 否则会抛出异常.
- 扩容策略: HashMap 初始大小为16 (第一次从0直接扩到16), 而 HashTable 默认初始大小为11. HashMap 每次扩容时为 2n, HashTable 每次扩容为 2n+1. 若初始化时给定了初始容量, 则 HashTable 直接使用给定的容量, HashMap 会将给定容量扩充为最近的2的幂次方大小.
- 数据结构: HashMap 会在链表长度大于阈值时, 将链表转换为红黑树以减少搜索时间, 而 HashTable 没有这种操作.
- 哈希函数: HashMap 中的哈希函数对哈希值进行了高位和低位的混合扰动处理, 以减少哈希冲突; HashTable 没有相关处理, 直接使用哈希值.

### HashMap与HashSet区别
- `HashSet` 底层就是基于 `HashMap` 实现的, 基本直接调用 `HashMap` 中的方法. `HashSet` 中以成员对象本身作为key计算哈希值, 实现 `Set` 接口, 仅存储对象.

### HashMap与TreeMap区别
- `HashMap` 和 `TreeMap` 都继承自 `AbstractMap`, 但是 `TreeMap` 还额外实现了 `NavigableMap` 接口和 `SortedMap` 接口. 相比于 `HashMap` 来说, `TreeMap` 主要多了对集合中元素根据键排序的能力以及对集合内元素的搜索能力.
- 通过实现 `NavigableMap` 接口, 使 `TreeMap` 具有对集合内元素搜索的能力, 该接口内提供了丰富的方法检索和操作键值对, 这些方法都是基于红黑树的数学实现的, 红黑树保持平衡状态, 从而保证了各类操作的时间复杂度为 O(logn), 使 `TreeMap` 可以很好的处理有序集合搜索问题.
	1. 定向操作:  `ceilingEntry()`, `floorEntry()`, `higherEntry()`, `lowerEntry()` 用于定位大于等于,小于等于,严格大于,严格小于给定键的最接近键值对.
	2. 子集操作: `subMap()`, `headMap()`和 `tailMap()` 方法可以高效创建原集合的子集视图, 无需复制整个集合
	3. 逆序视图: `descendingMap()` 方法返回逆序的 `NavigableMap` 试图, 使得可以反向迭代整个 `TreeMap`
	4. 边界操作: 通过 `firstEntry()`, `lastEntry()`, `pollFirstEntry()` 和 `pollLastEntry()` 方法可以方便地访问和移动元素.
- 通过实现 `SortedMap` 接口, 使 `TreeMap` 具有对集合内元素根据键排序的能力. 默认是按照 key 的升序排序, 也可以指定排序比较器.

### HashSet重复检查
- 当在 `HashSet` 中加入对象时, 会计算加入对象的 `hashCode()` 决定对象插入的位置. 如果插入位置已存在对象, 则向下遍历链表/红黑树, 依次使用 `equals()` 判断, 检查 `hashCode` 相等时对象是否相同. 若相同则插入失败.

### HashMap底层实现

#### JDK1.8之前
- 在 JDK1.8 之前, HashMap 底层通过数组和链表组合在一起实现, 即通过拉链法的方式实现哈希表.
- `HashMap` 通过 key 的 `hashcode` 经过扰动函数处理后得到 hash 值，然后通过 `(n - 1) & hash` 判断当前元素存放的位置

#### JDK1.8及之后

##### 变动
- 从 JDK1.8 开始, HashMap 在解决哈希冲突时, 同时引入链表和红黑树进行冲突解决. 当两个元素 hash 哈希值相同时, 会先创建链表并将节点加入链表中, 当链表长度大于阈值(默认8)时, 将链表转为红黑树进行存储. 
- 这样做的目的是为了减少搜索时间: 红黑树查询的时间复杂度为 `O(logn)`, 而链表查询时间复杂度为 `O(n)`

##### 扩容与红黑树转换时机
- 在进行链表转换前会先进行判断, 如果当前数组长度小于64, 则优先进行**数组扩容**, 而不是转为红黑树. 数组扩容能减少哈希冲突发生的概率, 在大多数情况下比直接转换为红黑树更加高效; 红黑树需要保持自平衡, 维护成本高, 且过早引入红黑树反而会增加代码复杂度.

##### 阈值选择
1. 泊松分布表明, 链表长度达到8的概率极低, 绝大多数情况下链表长度都不会超过8. 阈值设为8可以保证性能和空间效率的平衡性.
2. 经实践验证, 数组长度阈值设为64是最好的选择. 在小数组中, 扩容成本低, 优先扩容可以避免过早引入红黑树, 提高维护成本; 数组长度大于64后, 冲突概率较高, 此时红黑树性能优势开始显现.

### HashMap长度2次幂原因
- 为提高 HashMap 存取效率, 减少碰撞, 应确保数据尽量均匀分布. 由于 int 值相对大而哈希数组相对小, 所以需要对元素经哈希函数得出的散列值进行取余操作. 当除数是2次幂时, 对 hash 的取余操作等价于 `(length - 1) & hash` 位运算, 可以提高运算效率.
- 扩容时, 可以使 `HashMap` 扩容更加均匀. 范围内最低位为0或1的概率相同, 可以最大概率保证在扩容后的新数组中, 新旧范围内数的比例大致相同 (如果原哈希数组分布均匀). 同时, 只需要判断最低位的大小, 就可以决定元素应该留在原地或者被移动到新数组中.

### HashMap多线程死循环问题
- JDK1.7 及之前, HashMap 在多线程操作情况下, 扩容操作时可能出现死循环问题. 这是因为 JDK1.7 及之前拉链链表采用头插法构建, 多线程同时操作时可能导致链表节点中的next指针指向错误的位置形成环路, 使查询操作出现死循环.
- JDK1.8 开始, 将 HashMap 的插入改为尾插法, 插入节点永远置于链表末尾, 不会出现环路. 但在多线程条件下, 虽然不会出现环路, 但是还是有可能出现对节点的覆盖情况, 因此不建议在多线程中使用 HashMap

### HashMap线程不安全原因
- 如上述, 在多线程条件下对 `HashMap` 的并发写操作可能导致以下问题:
1. 数据覆盖: 先写入的值被后写入的值覆盖. 两个线程可能同时准备在链表内添加节点, 且同时找到链表末尾. 在同一个位置两个线程前后完成了节点的插入操作, 导致后加入的节点被先加入的节点覆盖
2. 无限循环: 在 JDK1.7 及之前, 可能因多线程头插导致链表成环, 从而在 get 操作时引发无限循环.

## ConcurrentHashMap

### 具体实现

#### JDK1.8之前
- JDK1.8 之前, 采用 `Segment数组 + HashEntry数组 + 链表` 的形式实现, `Segment` 数组默认元素数量为16个, 一旦确定就不能变化. `Segment` 是一种可重入锁, `HashEntry` 用于存储键值对. `ConcurrentHashMap` 将加入的元素按照哈希值分配到不同 `Segment` 中, 当试图对对应的 `HashEntry` 修改时, 必须先获得对应的 `Segment`. 不同 `Segment` 可以并发写入, 同一 `Segment` 并发写入会导致阻塞.
![[面试/Java/集合/Inbox/Pasted image 20251127115727.png]]

#### JDK1.8及之后
- JDK1.8 及之后, 对 `ConcurrentHashMap` 进行了彻底重写. 不再使用 `Segment` 分段锁, 改为 `Node + CAS + synchronized` 保证并发安全; 同时采用类似于新版 `HashMap` 的数据结构, 使用 `数组 + 链表 + 红黑树` 的形式, 在链表长度大于8是进行红黑树转换. 这种实现方式锁粒度更细, synchronized 只锁当前链表或者红黑树的首节点, 只要不发生 hash 冲突的并发访问就不会锁节点, 不影响其他 Node 的读写, 大大提升读写效率.

### 和HashTable区别

#### ConcurrentHashMap
- JDK1.7中, 底层采用**分段的**数组+链表实现. `ConcurrentHashMap` 对整个桶数组进行分割分段, 分为多个 `Segment` 可重入锁, 每个锁只锁容器内部分数据. 多线程访问容器内不同数据段的数据时就不存在锁竞争, 提高了并发访问效率.
- JDK1.8中, 底层数据结构与 HashMap 一致. 摒弃 `Segment` 概念, 改用 Node 数组 + 链表 + 红黑树, 并配合使用 `synchronized` 和 `CAS` 进行并发操作. 类似优化后且线程安全的 HashMap, 虽然 JDK1.8 中还可以看到 Segment, 但已简化属性, 只是为了兼容旧版本.
- `ConcurrentHashMap` 中使用 `TreeNode` 存储红黑树节点, 并使用 `TreeBin` 对节点进行包装, TreeBin 使用 waiter 维护红黑树根节点, 阻止其他线程进入, 预防红黑树旋转过程中由于根节点变化导致其他线程读写红黑树异常.

#### HashTable
- 底层采用数组+链表的形式实现. 类中所有方法都使用 `synchronized` 关键字进行修饰以确保线程安全, 效率非常低下. 当多个线程同时访问时, 只能有一个线程进行操作, 导致越来越多线程阻塞, 效率越来越低.

### key和value不能为null
- 在 `ConcurrentHashMap` 中, 无论 `key` 还是 `value` 都不能置为空, 这是因为 `null` 作为 `key` 或者 `value` 时存在二义性, 单线程下可以该容忍歧义, 而多线程下无法容忍. 以 `null` 作为 `k/v` 的二义性主要体现在 `get(k)` 返回 `null` 时, 无法确认实际情况: 1. `key=null` 不存在 2. `key=null` 存在但是 `value=null`.
- 在 HashMap 中, 这种二义性可以通过 get(k) 后的 `containsKey(k)` 方法进行二义性的消除, 但在 `ConcurrentHashMap` 中, 两次操作之间可能插入其他线程对 `ConcurrentHashMap` 的修改, 使 `containsKey(k)` 方法结果不可信.
- 如果确实需要在 `ConcurrentHashMap` 中使用 null, 可以由使用者手动定义特殊的静态空对象 (如 `NULL = new Object()` ) 替代 null

### 复合操作原子性
- `ConcurrentHashMap` 是线程安全的, 意味着多线程情况下同时进行读写操作时不会出现数据不一致情况, 也不会导致如 JDK1.7 及之前 HashMap 的多线程操作链表死循环问题. 但只能确保单个操作的安全, 不意味着复合操作也是原子性的. 在两个基本操作之间, 其他线程可能执行, 从而导致结果改变.
- 为保证部分复合操作的原子性, `ConcurrentHashMap` 提供了一些原子性的复合操作, 如 `putIfAbsent`, `compute`, `computeIfAbsent` , `computeIfPresent`、`merge`等. 通过单个方法调用, 根据给定的 `key` 和 `value` 在内部进行一系列操作
- 虽然复合操作也可以通过加锁的方式实现同步, 但这种方式效率相对低, 且违背了使用 `ConcurrentHashMap` 的初衷, 尽量使用提供的原子性的复合方法.
