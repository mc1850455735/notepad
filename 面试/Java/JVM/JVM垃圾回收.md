
# 什么是 Stop The World？

在执行某些 GC 逻辑时（如初始标记），必须暂停所有的用户线程，确保在分析过程中引用关系不再发生变化。这个停顿过程就叫 **STW**。

**调优目标**：
所有的 GC 优化（如使用 G1、ZGC 收集器），本质上都是为了**缩短 STW 的时间**。

# 引用类型

## 强引用

被强引用关联的对象不会被回收。

使用 new 创建对象的方式创建一个强引用。
```java
Object obj = new Object();
```

## 弱引用

被弱引用关联的对象一定会被回收。他将会存活到下次垃圾回收之前。

通过 `WeakReference` 类实现弱引用。
```java
Object obj = new Object();
WeakReference<Object> wf = new WeakReference<Object>(obj);
```

## 软引用

被软引用关联的对象只有在堆中内存大小不够的情况下才会进行垃圾回收。

通过 SoftReference 类创建软引用。
```java
Object obj = new Object();
SoftReference<Object> wf = new SoftReference<Object>(obj);
// 使对象只被软引用关联
obj = null;
```

## 虚引用

又称为幽灵引用或幻影引用。一个对象是否有幽灵引用的存在，对其生存时间完全不构成影响，也无法通过虚引用获取一个对象。

设置其的唯一目的就是能在这个对象被回收时收到一个系统通知。

使用 PhantomReference 类实现虚引用。
```java
Object obj = new Object();
PhantomReference<Object> wf = new PhantomReference<Object>(obj);
```

# 对象可回收的判断

## 引用计数法

给对象添加一个引用计数器，当对象增加一个引用时计数器加 1，引用失效时计数器减 1。引用计数为 0 的对象可被回收。

两个对象出现**循环引用**的情况下，此时引用计数器永远不为 0，导致无法对它们进行回收。正因为循环引用的存在，因此 Java 虚拟机不使用引用计数算法。

## 可达性分析法

通过 **GC Roots** 作为起始点进行搜索，能够到达到的对象都是存活的，不可达的对象可被回收。

**GC Roots**
- 虚拟机栈（栈帧中的局部变量表）引用的对象
- 本地方法栈中 JNI（Native 方法）引用的对象
- 方法区中 **类静态属性** 引用的对象
- 方法区中 常量 引用的对象
- 所有被同步锁synchronized持有的对象

# 垃圾回收算法

## 标记-清除

将存活的对象进行标记，然后清理掉未被标记的对象。

**缺点**
- 标记和清除过程效率都不高；
- 会产生大量不连续的内存碎片，导致无法给大对象分配内存

## 标记-整理

让所有存活的对象都向一端移动，然后直接清理掉端边界以外的内存。

## 复制

**概述**
将内存划分为大小相等的两块，每次只使用其中一块，当这一块内存用完后，将该区域存活对象复制到另一块上，再清理使用过的内存空间。

**缺点**
- 只使用了一半内存

**演化**
现在的商业虚拟机都采用这种收集算法来回收新生代，但是并不是将新生代划分为大小相等的两块，而是分为一块较大的 Eden 空间和两块较小的 Survivor 空间，每次使用 Eden 空间和其中一块 Survivor。在回收时，将 Eden 和 Survivor 中还存活着的对象一次性复制到另一块 Survivor 空间上，最后清理 Eden 和使用过的 Survivor。

HotSpot 虚拟机的 Eden 和 Survivor 的大小比例默认为 8:1，保证了内存的利用率达到 90%。如果每次回收有多于 10% 的对象存活，那么一块 Survivor 空间就不够用了，此时需要依赖于老年代进行分配担保，也就是借用老年代的空间存储放不下的对象。

## 分代收集

现在的商业虚拟机采用分代收集算法，它根据对象存活周期将内存划分为几块，不同块采用适当的收集算法。

一般将堆分为新生代和老年代。新生代使用复制算法，老年代使用 `标记 - 清除` 或 `标记 - 整理` 算法。

# 垃圾收集器

## CMS收集器

### 概述

CMS（Concurrent Mark Sweep）垃圾收集器是 Java 的并发低停顿垃圾回收器，通过 **初始标记-并发标记-重新标记-并发清除 四阶段实现**，减少停顿时间。缺点包括内存碎片、浮动垃圾问题，且无法处理并发失败。已在 JDK9 被标记废弃，JDK14 正式移除。

CMS 是 JVM 中一种以 **低延迟** 为目标的垃圾回收器，主要用于老年代的垃圾回收。它通过 **并发标记-清除算法** 减少垃圾回收时的 STW，适合对响应速度敏感的应用（如 Web 服务、实时系统）

### 设计目标

- **最小化 STW 时间**：通过**并发执行**大部分回收阶段，减少用户线程的停顿。
- **适用场景**：适合内存较大、对延迟敏感的老年代回收（JDK 9 后已不推荐使用，逐渐被 G1、ZGC 等替代）。

### 工作流程

1. 初始标记 ( STW )
	- 标记 GC Roots 直接关联的对象（速度极快）。
2. 并发标记
	- 从 GC Roots 出发，**遍历老年代** 所有存活对象（与用户线程并发执行）。
3. 重新标记 ( STW )
	- 修正并发标记阶段 因用户线程运行导致的标记变动（增量更新或原始快照）。
4. 并发清除
	- 清除未被标记的垃圾对象（与用户线程并发执行）。

### 优缺点

**优点**
- **低延迟**：大部分阶段与用户线程并发执行，STW 时间短。
- **适用大内存**：适合老年代较大的堆内存（如 4GB 以上）。

**缺点**
- **内存碎片**：使用标记-清除算法，不整理内存，可能导致 Full GC 时触发压缩（STW 时间长）。
- **CPU 敏感**：并发阶段占用 CPU 资源，可能影响应用吞吐量。
- **浮动垃圾**：并发清理阶段用户线程可能产生新垃圾，需预留空间
- **并发失败（Concurrent Mode Failure）**：若回收速度跟不上对象分配速度，会退化为 Serial Old 收集器（Full GC）。

## G1收集器

### 一句话总结

G1（Garbage-First）是 Java HotSpot 虚拟机的低延迟垃圾收集器，采用分 Region 堆内存布局，兼顾年轻代和老年代回收。它通过并发标记和优先回收垃圾最多的 Region（Garbage-First原则），实现**可控的停顿时间预测**（通过-XX:MaxGCPauseMillis参数）。适用于大内存、低延迟场景，替代了传统的CMS收集器，支持压缩整理避免内存碎片。

### 设计目标

- **低延迟与可预测停顿**：G1 以可控的停顿时间（默认 200ms）为核心目标，通过分区回收和启发式算法实现，适合大内存堆。
- **全堆管理**：无需区分新生代与老年代的物理边界，所有堆内存被划分为多个等大小的 **Region**（默认 2048 个），每个 Region 可动态扮演 Eden、Survivor 或老年代角色。

### 核心机制

- **分区回收**：优先回收垃圾比例高的 Region（Garbage-First 原则），避免全堆扫描，减少回收范围。
- **Remembered Set（RSet）**：记录跨 Region 的引用关系，避免全堆扫描。例如，YGC 时仅需扫描年轻代 Region 的 RSet，无需遍历老年代。
- **SATB（Snapshot-At-The-Beginning）**：通过快照解决并发标记阶段的漏标问题，确保标记准确性。

### 工作流程

1.  **初始标记（STW）**：标记 GC Roots 直接关联的对象，耗时极短。
2.  **并发标记**：与用户线程并发标记存活对象。
3.  **最终标记（STW）**：合并并发标记期间的引用变更（通过 RSet 和 SATB 快照修正）。
4.  **筛选回收**：根据 Region 的回收价值排序，按用户设定的停顿时间选择回收区域，存活对象复制到空闲 Region（局部整理）。

### 适用场景
-   大内存堆且对延迟敏感的应用（如实时数据处理）。
-   需要避免长时间 Full GC 的场景（如高并发服务）。

### 与 CMS 区别

| 对比维度     | G1收集器                                                     | CMS收集器                                                    |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 适用范围     | 全堆                                                         | 仅老年代，需配合新生代收集器                                 |
| 内存模型     | 逻辑分代，物理分区（Region），动态调整区域角色               | 物理分代（固定 Eden、Survivor、老年代），连续内存块          |
| 回收算法     | 标记-整理（整体） + 复制（局部），减少碎片                   | 标记-清除，产生内存碎片，需 Full GC 时整理                   |
| 停顿时间控制 | 可通过参数设定，可预测，混合回收（Mixed GC）降低影响         | 无法预测，依赖并发标记，可能因浮动垃圾导致的 Concurrent Mode Failure 触发 Full GC |
| 处理大对象   | 大对象可跨多个 Region 存放，避免直接晋升老年代               | 大对象直接进入老年代，可能加剧碎片问题                       |
| 内存碎片     | 局部复制整理，碎片较少                                       | 标记-清除导致碎片，频繁 Full GC 时需压缩                     |
| 并发阶段     | 仅初始标记和最终标记需 STW，并发标记和筛选回收与用户线程并行 | 初始标记和重新标记需 STW，并发标记和清理与用户线程并行       |
| CPU消耗      | 较高（RSet 维护和并发标记开销），但可通过参数调优平衡        | 高（并发标记和清理占用 CPU，默认线程数(CPU核数+3)/4）        |
| 漏标处理     | 原始快照（SATB），保留标记开始时的引用快照                   | 增量更新，重新标记阶段修正新增引用                           |
| JDK版本      | JDK 7 引入，JDK 9+ 默认                                      | JDK 5 引入，JDK 9 后废弃，JDK 14 移除                        |

### 关键问题

-   浮动垃圾处理
    -   **CMS**：并发清理阶段用户线程产生的垃圾需下次 GC 回收，易引发 Concurrent Mode Failure，退化为 Serial Old 收集器。
    -   **G1**：通过 Mixed GC 动态回收部分老年代 Region，结合 SATB 减少漏标，避免 Full GC。
-   **内存碎片影响**
    -   **CMS**：频繁 Full GC 时需压缩碎片（-XX:+UseCMSCompactAtFullCollection），增加停顿时间。
    -   **G1**：每次回收均整理部分 Region，整体碎片率低，适合长期运行的系统。
-   **三色标记与漏标**
    -   **CMS** 使用增量更新（记录新增引用），重新标记阶段需遍历变更对象。
    -   **G1** 使用 SATB（记录删除的引用），通过快照保留标记开始时的对象图，减少重新标记工作量。

# 内存分配与回收策略

## GC回收概述

JVM 在进行 GC 时，并非每次都对堆内存中的所有区域进行回收，大部分时间回收都只对新生代进行。

在 Hotspot VM 的实现中，GC 按照回收区域分为两类：部分收集(Partial GC) 和整堆收集(Full GC)：
- 部分收集(Partial GC)：不完整的收集整个 Java 堆。
	- 新生代收集(Minor GC)：只对新生代进行的垃圾收集。
	- 老年代收集(Major GC)：只对老年代进行的垃圾收集。
		- 目前只有 CMS GC 会有单独收集老年代的行为。
		- 很多时候 Major GC 和 Full GC 会混合使用，需要具体判断是 Major GC 还是 Full GC。
	- 混合收集(Mixed GC)：收集整个新生代和部分老年代的垃圾收集。
		- 目前只有 G1 GC 会有该行为。
- 整堆收集(Full GC)：收集整个 Java 堆和方法区的垃圾。

## 内存分配策略

 1. 对象优先在 Eden 区分配
	- 大多数情况下，对象直接在 Eden 区分配.
	- Eden 区空间不足时，发起 Minor GC。
 2. 大对象直接进入老年代
	 - 大对象是指需要大量连续内存空间的对象，如长字符串。
	 - 大对象的出现，会导致提前触发垃圾收集，以获取足够的连续空间，用来存储大对象。
	 - 通过 `-XX:PretenureSizeThreshold` 参数进行设置，大于该值的对象直接在老年代进行分配，避免 Eden 区与 Survivor 区之间的大量内存复制。
 3. 长期存活的对象进入老年代
	 - 对于年轻代对象，每经过一次 Minor GC，年龄就增长1岁，到达一定年龄后移动到老年代中。
	 - `-XX:MaxTenuringThreshold` 用来定义年龄的阈值。
 4. 动态对象年龄判定
	 - 在进行 Minor GC 时，如果从某年龄段起，累计存活对象占内存大小达到 `TargetSurvivorSize` (通常为 Survivor 的一半)，则将该年龄记为动态阈值，年龄大于该阈值的对象直接晋升老年代。
 5. 空间分配担保
	- Minor GC 执行前，JVM 检查老年代最大可用连续空间是否大于新生代所有对象总空间。若条件成立，则 Minor GC 可以确认是安全的。
	- 如果不成立，则虚拟机检查 `HandlePromotionFailure` 参数，确认是否允许分配担保失败。如果允许失败，则继续检查老年代最大可用连续空间是否大于历次晋升到老年代对象的平均大小。
	- 如果大于，则尝试进行一次 Minor GC；如果小于或参数不允许担保失败，则执行 Full GC。

## FullGC触发条件

1. 调用 System.gc()
	- 建议虚拟机执行 Full GC，但虚拟机不一定真正执行。
	- 不建议使用这种方式，而是让虚拟机管理内存。
2. 老年代空间不足
	- 老年代空间不足的常见原因是大对象直接进入老年代和长期存活对象进入老年代等。
	- 为避免 Full GC，应该尽量避免创建过大的对象和数组。
	- 可以通过虚拟机参数调节新生代大小，让对象尽可能在新生代被回收掉，不进入老年代；也可以通过虚拟机参数提高对象进入老年代的年龄，让对象在新生代多存活一段时间。
3. **空间分配担保失败**
	- 执行 Minor GC 时，需要进行分配担保。如果担保失败，执行一次 Full GC。
4. JDK 1.7 及以前永久代空间不足
	- 在 JDK 1.7 及之前，HotSpot 虚拟机中的方法区在永久代中进行实现。当系统中加载的类、反射类、调用的方法较多时，永久代可能被占满。
	- 当永久代被占满时，执行 Full GC 进行回收。如果空间仍不足，则抛出 OOM 异常。
5. 并发模式失败 Concurrent Mode Failure
	- 执行 CMS GC 过程中同时有对象放入老年代，而此时老年代空间不足，报 Concurrent Mode Failure 错误，同时触发 Full GC。
6. 内存碎片化

# Java 内存泄漏

### 概念

在 Java 中，虽然有自动 GC，但如果 长生命周期的对象 持有了 短生命周期的对象 的引用，导致后者无法被 GC Roots 断开，就会产生内存泄漏。长期内存泄漏必然导致内存溢出。

### 常见的内存泄漏场景

- **静态集合类（Static Collections）**：
	- **现象**：使用 `static` 修饰的 `HashMap` 或 `List`。由于静态变量是 GC Root，只要类不被卸载，集合里的对象就永远不会被回收。
	- **对策**：及时 `clear()` 集合，或者不使用静态集合。
- **未关闭的资源（Resources not closed）**：
	- **现象**：数据库连接（`Connection`）、网络连接（`Socket`）、IO 流等。如果不手动 `close()`，它们占用的内存和句柄就不会释放。
	- **对策**：使用 **try-with-resources** 语法。
- **ThreadLocal 导致的泄漏**：
	- **现象**：`ThreadLocalMap` 的 **Key** 是弱引用，但 **Value** 是强引用。如果线程不结束（如线程池中的常驻线程），Value 就一直存在。
	- **对策**：使用完后必须 **显式调用 `remove()`**。
- **不合理的内部类引用**：
	- **现象**：非静态内部类默认持有外部类的引用。如果内部类的生命周期比外部类长，外部类就无法被回收。
- **Hash 值改变**：
	- **现象**：对象存入 `HashSet` 后修改了参与 `hashCode` 计算的字段，导致 `remove` 时找不到对象，该对象永久留在集合中。

### 排查思路与工具

当线上出现 OOM 或频繁 Full GC 时，通常按以下步骤排查：

1. **生成堆转储文件 (Heap Dump)**：
	- 启动参数加上：`-XX:+HeapDumpOnOutOfMemoryError`（崩溃时自动抓取）。
	- 手动抓取：使用 `jmap -dump:format=b,file=heap.hprof <pid>`。
2. **使用分析工具**：
	- MAT (Memory Analyzer Tool)
	- JProfiler / VisualVM
3. **定位代码**：
	- 查看 **Retained Heap（深堆）** 最大的对象是谁。
	- 顺着引用链（GCRoot Path）向上找，看哪个业务类持有了这个对象。

### 内存溢出（OOM）与内存泄漏（Memory Leak）

- **内存泄漏**：该回收的没回收（代码逻辑问题）。
- **内存溢出**：内存不够用了（结果）。

持续的内存泄漏一定会导致内存溢出，但内存溢出不一定是泄漏造成的（也可能是内存分配太小或瞬间并发量过大）。
