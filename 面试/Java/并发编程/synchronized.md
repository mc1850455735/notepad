
# 介绍一下 synchronized 关键字，其修饰方法和代码块时有什么不同？

**synchronized 关键字介绍**
synchronized 关键字主要用于解决多个线程之间的资源同步问题, 其修饰的方法或代码块在任意时刻只能有一个线程执行。

构造方法本身不能使用 synchronized 进行修饰, 但是可以在构造方法内部使用 `synchronized` 代码块。构造方法本身是线程安全的，但是如果构造方法中涉及到对**共享资源**的操作，则需要采用合适的同步措施。

早期版本中, synchronized 属于重型锁，其实现依赖操作系统底部的 Mutex Lock，对线程的挂起或唤醒都需要操作系统完成，在用户态和内核态的切换过程需要较多时间，效率相对较低。

Java 6 之后，对 synchronized 关键字引入了大量优化，如自旋锁、适应性自旋锁、锁消除、锁粗化、偏向锁、轻量级锁等，减少了 synchronized 的锁开销，使其足够在实际项目中使用。对于偏向锁，JDK15 中默认关闭，JDK18 中彻底废弃。

**synchronized 修饰**
synchronized 可以用来修改方法和代码块，修饰方法时，又分为实例方法和静态方法两种，对于静态 `synchronized` 方法和实例 `synchronized` 方法，其调用不存在冲突，因为二者需要的锁不相同。

具体来说：
1. 修饰实例方法时，进入同步代码前要获得当前**对象实例**的锁；
2. 修饰静态方法时，进入同步代码前要先获取**当前类对象**的锁，这是因为静态方法属于整个类所有，不依赖于特定实例；
3. 修饰代码块时，即可以选择将当前实例作为锁，也可以选择将当前类作为锁，具体选择依代码块作用不同而不同。

尽量不要使用字符串作为锁对象，因为字符串具有缓存功能。

# JDK 6 以后，对 synchronized 都进行了哪些优化？

Java6之后, synchronized 引入了大量优化, 如自旋锁、适应性自旋锁、锁消除、锁粗化、偏向锁、轻量级锁等, 减少了所操作开销, 提高了 synchronized 锁效率.
 

# HotSpot 为什么逐渐禁用并移除了偏向锁？

对于偏向锁，在 JDK 15 中默认关闭，JDK18 中彻底废弃，主要存在两个原因：

首先，随着机器性能的提升，偏向锁带来的性能收益不明显。偏向锁主要由早期 Java 集合 API 使用，负责保证早期多线程集合的正确执行，这种多线程集合可能存在大量的只有单线程使用的情况，偏向锁可以带来较高的收益。
随 JDK 发展，逐渐设计出更高性能的集合类，不再需要 synchronized 关键字的硬约束，降低了偏向锁的性能收益；同时偏向锁只在单线程访问同步代码块场景下有收益，多线程竞争时就需要撤销偏向锁，性能开销较昂贵。且随着机器的发展，CAS 的调用成本逐渐降低。

其次，偏向锁的使用也导致 JVM 内部维护成本高。偏向锁的复杂实现，将复杂代码引入到 JVM 的同步子系统中，并对其他 HotSpot 组件也具有入侵性，为理解代码、重构系统带来了困难。

# JVM 如何识别和执行 `synchronized`？

**修饰同步语句块**
当 synchronized 关键字修饰同步语句块时，其底层实现依靠的是 monitorenter 和 monitorexit 指令。前者指示同步代码块的开始，后者指示同步代码块的结束。同时，源码中至少存在两个 monitorexit 指令，以确保锁在正常结束和出现异常情况下都可以被正常释放。

当执行 monitorenter 时，线程试图获取锁，即 monitor 对象监视器的持有权。执行 monitorenter 时，如果锁的计数器为0，说明锁可获取，将锁计数器设为1，相同线程再次进入后，锁计数递增；执行 monitorexit 时，递减锁计数器直到计数器为 0，说明线程释放锁；当锁被其他线程持有时，当前线程无法直接进入同步代码块，HotSpot 可能通过自旋等方式尝试获取锁，竞争无法解决时，线程可能进入阻塞状态，等待后续唤醒并重新竞争锁。

HotSpot 中重量级 Monitor 由 C++ 的 `ObjectMonitor` 实现。此外, notify/wait 方法也依赖于 ObjectMonitor 对象，只有在同步的块或方法中才能调用。

**修饰同步方法**
synchronized 关键字修饰方法时，不添加 monitorenter 和 monitorexit 指令，而是向方法声明中添加 `ACC_SYNCHRONIZED` 标识，如果存在该标识，则说明该方法是一个同步方法。

当 JVM 调用方法时，如果方法中存在此标识，则根据方法类型进行同步调用。对于实例方法, 使用实例对象；对于静态方法, 使用当前类；不论同步语句块还是同步方法, 其实现的本质都是对 monitor 的获取。

# synchronized 锁升级过程以及对象头 Mark Work 的变化是什么？

**锁升级过程**
以 JDK 8 为例，synchronized 的锁升级过程分为四步：无锁 -> 偏向锁 -> 轻量级锁 -> 重量级锁。
JDK 15 开始，默认禁用偏向锁，并在 JDK 18 中彻底废弃偏向锁；JDK 23 中又采用了新的轻量锁实现。

首先是偏向锁。偏向锁主要是解决一个锁一直被同一个线程使用的场景，在这种情况下，没有必要每次加解锁都使用 CAS。
当对象处于可偏向状态，Mark Word 的最低 3 位为 `101`，线程指针为 0。
当线程第一次设置锁时，通过 CAS 设置 Mark Word 中的 `JavaThread*` 记录为自己的线程指针；当再次获取锁时，线程率先判断 `JavaThread*` 中的指针是否为自己。
偏向锁释放时，通常不会清除 Mark Word 中的线程指针，这是它能够减少重复加锁开销的原因。

如果另一个线程也开始竞争这把锁，JVM 就会开始检查并处理偏向锁的状态；如果发现不能继续偏向原来的线程且适合采用轻量级锁时，JVM 就会撤销偏向锁并进入轻量锁机制。
试图加锁的线程会在自己的栈上创建对应锁的锁记录 (Lock Record)，并通过 CAS 将对象的 Mark Word 替换为自己的锁记录；如果成功，则获取轻量级锁，原本的 Mark Word 保存在锁记录中；如果失败，则需要根据锁持有者和锁的竞争状况，决定重试、识别重入或者进一步膨胀。

此时对象的 Mark Word 不再保存对象的 HashCode 和 GC 年龄等信息，而是保存锁记录指针。当线程释放轻量级锁时，JVM 会试图通过 CAS 操作恢复对象的原始 Mark Word 信息。

当多个线程同时竞争同一把锁，轻量级锁无法解决竞争时，就会进行锁膨胀 (Lock inflation)，使用 ObjectMonitor 管理同步。此时原本 Mark Word 中指向 Lock Record 的指针就会变成指向 ObjectMonitor 的指针，ObjectMonitor 中包含所有者、重入计数以及用于管理竞争线程的机制。
获取不到锁的线程可能进行自旋，但是必要时会阻塞等待，而不是一直消耗 CPU。

**Mark Word 的变化**
一个 Java 对象在 HotSpot 虚拟机上的内存结构主要由三部分组成，分别是：对象头( Object Header，内含 Mark Word 和 Klass Pointer 两部分 )、实例数据 ( Instance Data )、对齐填充 ( Padding )。[[面试/Java/JVM/JVM内存结构#Java 对象内存结构|Java 对象内存结构]]

其中 Mark Word 是实现 synchronized 锁管理的重要组成部分。Mark Word 总长度为 64 bits，当对象处于不同的锁状态时，Mark Word 中相同位的含义也会发生变化。

以 JDK 8 为例，不同的状态下，Mark Word 的位含义如下：
```
普通无锁：
| unused:25 |    hash:31   | unused:1 | age:4 | 0 | 01 |
偏向锁：
| JavaThread*:54 | epoch:2 | unused:1 | age:4 | 1 | 01 |
轻量级锁：
|               Lock Record 指针:62                | 00 |
重量级锁：
|               ObjectMonitor 指针:62              | 10 |
GC 标记：
|               GC 使用的特殊信息                    | 11 |
```

在 Mark Word 中，对于无锁和偏向锁的状态，主要靠后 3 位进行区分；轻量级、重量级和 GC 标记主要靠后两位进行区分。

# 与volatile区别

`volatile` 是线程同步的轻量级实现，性能较 `synchronized` 好。但是 `volatile` 只能由于变量而 `synchronized` 可以用于修饰方法和代码块。

与此同时，`volatile` 只能保证数据的可见性而无法保证执行的原子性，而 `synchronized` 二者都可以实现。`volatile` 解决的是变量在多个线程之间的可见性, 而 `synchronized` 关键字解决的是多个线程之间访问资源的同步性。
