
# synchronized

## 概念

synchronized (同步) 是 Java 中的一个关键字, 主要用于解决多个线程之间的资源同步问题, 被他修饰的方法或代码块在任意时刻只能有一个线程执行。

构造方法不能使用 synchronized 进行修饰, 但是可以在构造方法内部使用 `synchronized` 代码块. 构造方法本身是线程安全的, 但是如果构造方法中涉及到对共享资源的操作, 则需要采用合适的同步措施.

早期版本中, synchronized 属于重型锁, 其实现依赖操作系统底部的 Mutex Lock, 对线程的挂起或唤醒都需要操作系统完成, 在用户态和内核态的切换过程需要较多时间, 效率相对较低。

Java6 之后，对 synchronized 关键字引入了大量优化, 如自旋锁、适应性自旋锁、锁消除、锁粗化、偏向锁、轻量级锁等，减少了 synchronized 的锁开销，使其足够在实际项目中使用。对于偏向锁, JDK15 中默认关闭，JDK18 中彻底废弃

## 使用

synchronized 主要用于：
1. 修饰实例方法：进入同步代码前要获得当前**对象实例**的锁
2. 修饰静态方法：进入同步代码前要先获取**当前类**的锁, 这是因为静态方法属于整个类所有, 不依赖于特定实例
3. 修饰代码块：可以选择将当前实例作为锁, 也可以选择将当前类作为锁；具体选择依代码块作用不同而不同。尽量不要使用字符串作为锁对象, 因为字符串具有缓存功能

对于静态 `synchronized` 方法和实例 `synchronized` 方法, 其调用不存在冲突，因为二者需要的锁不相同

## 底层原理

#### 同步语句块

synchronized 底层实现依靠的是 monitorenter 和 monitorexit 指令。前者指示同步代码块的开始，后者指示同步代码块的结束。
源码中存在两个 monitorexit 指令，这是为了确保锁在正常结束和出现异常情况下都可以被正常释放.

当执行 monitorenter 时, 线程试图获取锁, 也就是 monitor 对象监视器的持有权。
如果锁的计数器为0, 说明锁可获取, 将锁计数器设为1；执行 monitorexit 时, 如果锁的计数器为1，则将锁计数器设为0；如果获取锁对象失败, 则当前线程阻塞等待, 直到锁被另一个线程释放为止。

在 Hotspot 虚拟机中, monitor 是基于 C++ , 由 ObjectMonitor 实现的, 每个对象中都内置了一个 ObjectMonitor 对象. 此外, notify/wait 方法也依赖于 ObjectMonitor 对象, 只有在同步的块或方法中才能调用.

#### 同步方法

在 synchronized 修饰的方法中不存在 monitorenter 和 monitorexit 指令, 而是 `ACC_SYNCHRONIZED` 标识, 该标识指明了该方法是一个同步方法。

JVM 调用方法时, 如果方法中存在此标识, 则根据方法类型进行同步调用。

对于实例方法, 使用实例对象；对于静态方法, 使用当前类；不论同步语句块还是同步方法, 其实现的本质都是对 monitor 的获取。

## Java6之后优化

Java6之后, synchronized 引入了大量优化, 如自旋锁、适应性自旋锁、锁消除、锁粗化、偏向锁、轻量级锁等, 减少了所操作开销, 提高了 synchronized 锁效率.
 
synchronized 锁主要存在四种状态, 分别是: 无锁状态, 偏向锁状态, 轻量级锁状态, 重量级锁状态, 随着锁竞争的激烈程度逐渐升级. 锁状态只可以升级, 不可以降级, 这是为了提高获得锁和释放锁的效率

##### 偏向锁的禁用
- 对于偏向锁, JDK15中默认关闭, JDK18中彻底废弃, 主要存在两个原因
1. 性能收益不明显. 偏向锁主要由早期 Java 集合 API 使用, 随 JDK 发展出现更高性能的集合类, 降低了偏向锁的性能收益; 同时偏向锁只在单线程访问同步代码块场景下有收益, 如存在多线程竞争就需要撤销偏向锁, 性能开销较昂贵
2. JVM内部维护成本高. 偏向锁将复杂代码引入同步子系统, 并对其他 HotSpot 组件也具有入侵性, 为理解代码, 重构系统带来了困难.

## 与volatile区别

`volatile` 是线程同步的轻量级实现, 性能较 `synchronized` 好。

但是 `volatile` 只能由于变量而 `synchronized` 可以用于修饰方法和代码块.

`volatile` 只能保证数据的可见性而无法保证原子性, 而 synchronized 二者都可以实现

`volatile` 解决的是变量在多个线程之间的可见性, 而 `synchronized` 关键字解决的是多个线程之间访问资源的同步性.



# CAS

CAS（Compare-And-Swap）是 Java 中基于硬件的无锁并发机制，通过比较内存值与预期值进行原子更新。

核心方法包含内存地址、预期值和新值，若匹配则更新，否则重试或放弃。常用于 AtomicInteger 等原子类实现线程安全操作，避免加锁开销。

存在ABA问题（可通过版本号标记解决），适用于低竞争场景。

## 核心思想

**CAS** ( Compare And Swap ) 是一种基于硬件的无锁并发机制，用于在多线程环境下实现**变量的**线程安全修改。核心思想是通过比较内存值与预期值进行**原子操作**，两值相等时才会进行更新。

CAS 操作是一个**原子操作**，依赖于底层 CPU 保证指令的原子性。通过 CAS，避免了传统锁带来的线程阻塞和上下文切换开销。

**CAS** 包含 3 个关键参数：**V：要更新的变量值，E：预期值，N：拟写入的新值**。
当 `V = E` 时，将 V 更新为 N；如果 `V != E`，说明在执行 CAS 前有其他线程更新了 V， 则当前线程放弃更新。

整个 CAS 过程由 CPU 指令保证原子性，不可被中断。多个线程同时尝试更新一个变量时，只有一个会成功，剩下的继续尝试更新或放弃本次操作。

## Java中CAS支持

Java 中 CAS 的底层实现依赖于 `sun.misc` 包下的 Unsafe 类。该类提供了一系列 CAS 方法，直接调用 CPU 的原子指令确保操作的原子性。

Unsafe 类中的方法大多低级别且不安全操作，通常用于需要极高性能或底层访问的情况，常用于 JDK 内部，不建议普通开发者使用。

Unsafe 类实现了对 Object、int、long 等一系列类型的 CAS 操作，其内部是使用 C++ 代码实现的原子操作，使用 JNI 调用 C++ 编写的内联代码实现 CAS。

`java.util.concurrent.atomic` 包下定义了一些用于提供原子操作的 `Atomic` 类，这些类利用底层的原子指令，确保在多线程环境下操作的线程安全。以整数的 `AtomicInteger` 为例，其底层通过 Unsafe 类的 compareAndSwapInt 方法循环尝试更新 V 直到执行完成，即其底层是**自旋锁机制**。

## 问题

### ABA问题

如果一个变量初次读取时值为A，且在准备赋值时值仍为A，但这不能代表该变量一定没有被修改过，因为这段事件可能被修改为了其他值后又改为A。这个问题即为 ABA 问题。

**解决思路**
1. 版本号机制：通过维护一个**版本号**（或时间戳），每次修改值的同时**递增版本号**。CAS 操作需同时校验**值和版本号**，确保值未被其他线程修改过。
2. `AtomicStampedReference` 类：该类是 Java 利用版本号思想作出的实现，将值与一个 int 类型版本号绑定，每次更新时递增版本号。
3. `AtomicMarkableReference` 类：使用一个boolean标记代替版本号，标记值是否被修改过。适用于只需简单标记的场景。

### 自旋开销大

在 CAS 操作中使用自旋操作进行重试,，不成功则循环，直到成功为止。长时间不成功会对 CPU 带来很多负担。

**解决思路**
如果 JVM 可以支持 pause 操作, 则自旋效率可以得到提升, pause 指令可以延迟指令的执行, 减少CPU资源损耗, 同时可以在退出时避免内存顺序冲突而导致的CPU流水线被清空

### 仅支持单一变量

CAS 只对单个变量，不能同时操作多个变量。

**解决思路**
- 直接使用锁解决多个变量操作的原子性。
- 多个变量合并为一个变量，然后使用 CAS 操作合并后的变量。
- 从JDK1.5 开始，Java 提供 AtomicReferrence 类，允许将多个变量整合成为一个对象进行 CAS 操作。


# 死锁

**死锁**是多线程中，线程互相等待资源而导致无法继续执行的现象。
- 产生条件：互斥、占有且等待、不可剥夺、循环等待，缺一不可。  
- 预防方法：资源排序、一次性申请资源、使用可中断锁、加锁超时。  
- 检测方法：jstack、监控工具等。

## 产生条件

产生死锁有四个条件，四条件必须同时成立才会产生死锁。如果需要破坏死锁，只需要破坏四个条件之一即可。
1. 互斥：资源一次只能被有限线程占用。
2. 占有且等待：线程持有互斥资源后，等待获取其他线程持有的资源。
3. 不可剥夺：已分配给线程的资源不能剥夺。
4. 循环等待：存在线程环，每个线程等待其他线程持有的资源。

## 死锁解决策略

根据死锁的产生条件，可以得出死锁存在 4 种解决方法：
1. 破坏互斥条件（不可能）
	- 不可能在 Java 中完全破坏，资源通常必须互斥
2. 破坏占有且等待条件
	- 一次性申请所有资源
	- 申请不到就释放已占有资源重试
3. 破坏不可剥夺条件
	- 可设计可中断锁，Java 提供 `ReentrantLock.lockInterruptibly()`
4. 破坏循环等待条件（最常用）
	- 对资源进行全局排序
	- 按固定顺序加锁，避免循环等待

## 实际避免死锁

1. 在程序设计阶段对资源进行排序，并避免写出嵌套锁代码，从而避免死锁。
2. 为线程设置超时等待机制，规定时间内尝试加锁，超时则直接失败。
3. 中断等待。Java 提供可中断锁 `ReentrantLock.lockInterruptibly()。
4. 使用 jstack、监控工具等发现死锁并重启线程，进行人工干预。
