
JMM (Java Memory Model) 定义了对于一个共享变量, 另一个线程对这个共享变量执行写操作后, 这个线程对这个共享变量的可见性

# CPU缓存模型

- CPU 缓存是为了解决 CPU 处理速度和内存处理速度不对等的问题, 内存缓存硬盘数据是为了解决硬盘访问速度过慢的问题.
- 现代 CPU 缓存通常分为三层, 分别为 L1, L2, L3 Cache; 在多CPU环境下使用 Cache 进行缓存, 可能存在缓存不一致的问题, 为解决缓存不一致问题, 可以通过指定缓存一致协议, 如 MESI 协议等.
- 由于操作系统屏蔽了底层硬件的操作细节, 将各种硬件资源虚拟化, 所以操作系统也需要解决内存缓存不一致问题, 操作系统通常使用 `Memory Model` 内存模型定义一系列规范解决这个问题.

# 指令重排序

### 概述
- 为了提升执行速度/性能, 计算机在执行程序代码时, 会对指令进行重新排序.
- 常见指令重排序有以下2种情况:
	- 编译器优化重排: 编译器在不改变**单线程**程序语义的前提下, 重新安排语句的执行顺序
	- 指令并行重排: 现代处理器采用了指令级并行技术 (ILP), 使多条指令同时执行; 当指令之间不存在数据依赖性时, 通过改变指令顺序进行并行执行
- 同时, 内存也可能出现类似重排序的情况, 即为了保证执行的高效, 主存和本地内存的内容可能存在不同, 导致程序在多线程下执行可能出现问题
- 重排序的过程可以保证串行语义的一致性, 但无法保证多线程间语义也一致

### 流程
- 编译器优化重排->指令并行重排->内存系统重排

### 禁用重排序
- 对于编译器, 通过禁止特定的编译器重排序的方式避免重排序
- 对于处理器, 通过插入**内存屏障/栅栏**的方式禁止特定类型的处理器重排序
- 内存屏障: 是一种CPU指令, 通过插入内存屏障禁止处理器指令重排序. 同时会在处理器写值时强制将新值刷新到主存; 在读值时强制从主存中读取最新值

# JMM

### 概述
- Java 是最早尝试提供内存模型的编程语言, 原本的内存模型存在缺陷. 从Java5 开始, 使用新的内存模型. 虽然每个操作系统都提供了内存模型, 但 Java 是一个跨平台的编程语言, 需要自己提供内存模型以屏蔽操作系统差异.
- JMM 可以被认为是 Java 定义的一种并发编程规范, 主要目的是简化多线程编程, 增强程序的可移植性. 为解决其中的指令重排序问题, JMM 抽象了 `happen-before` 原则.
- 即, JMM 定义了解决问题的规范, 使 Java 开发者不需要关心底层原理, 直接使用提供的关键字和类就可以开发线程安全的程序.

### 线程与主内存关系抽象

- JMM 抽象了线程与主内存之间的关系, 比如共享变量必须存储在主内存中

**主内存与本地内存**
- 主内存: 所有线程创建的实例对象都存放在主内存中, 无论该实例对象的类型. 为了优化运行速度, JVM以及硬件可能让工作内存优先存储在寄存器和 Cache
- 本地内存: 每个线程都有一个私有本地内存, 本地内存中存储了该线程已读/写共享变量的副本, 线程只能操作自己本地内存中的变量而无法访问其他变量的本地内存. 如果线程间需要铜棍

**线程间通信步骤**
- 对于两个线程, 在通信时需要经历以下2个步骤
	1. 线程1把本地内存中修改过的共享变量副本的值同步到主内存中.
	2. 线程2到主内存中读取对应的共享变量的值.
- 然而, 在多线程环境下, 对主内存中共享变量的修改可能出现安全问题, 即无法保证每个操作的原子性.

**同步操作**
- 对于主内存与工作内存之间的具体交互协议, 即变量从主内存拷贝到工作内存, 以及从工作内存同步到主存的过程, 主要依靠8种同步操作
	- 锁定(lock), 解锁(unlock), 读取(read), 载入(load), 使用(use), 赋值(assign), 存储(store), 写入(write)
- 同时, 还规定了一系列同步规则
	- 不允许一个线程无原因地（没有发生过任何 assign 操作）把数据从线程的工作内存同步回主内存中。
	- 一个新的变量只能在主内存中 “诞生”，不允许在工作内存中直接使用一个未被初始化（load 或 assign）的变量，换句话说就是对一个变量实施 use 和 store 操作之前，必须先执行过了 assign 和 load 操作。
	- 一个变量在同一个时刻只允许一条线程对其进行 lock 操作，但 lock 操作可以被同一条线程重复执行多次，多次执行 lock 后，只有执行相同次数的 unlock 操作，变量才会被解锁。
	- 如果对一个变量执行 lock 操作，将会清空工作内存中此变量的值，在执行引擎使用这个变量前，需要重新执行 load 或 assign 操作初始化变量的值。
	- 如果一个变量事先没有被 lock 操作锁定，则不允许对它执行 unlock 操作，也不允许去 unlock 一个被其他线程锁定住的变量。

### JVM内存区域与JMM
- JVM 内存区域与 Java 虚拟机的运行时区域有关, 定义了 JVM 在运行过程中如何对程序数据进行分区存储.
- JMM 和 Java 并发编程相关, 抽象了线程和主内存之间的关系, 规定了从 Java 源码到 CPU 指令的过程中, 要遵循的并发相关的原则和规范. 主要目的是简化多线程编程, 增强程序可移植性.

# happens-before原则

### 介绍
- `happens-before` 原则于 `JSR133` 引入, 用于描述两个操作之间的内存可见性. 
- 如果一个操作 `happens-before` 另一个操作, 说明第一个操作对第二个操作可见且在第二个操作之前执行; 但是即使一个操作 `happens-before` 另一个操作, 也不代表不可以对其进行**重排序**, 如果重排序后的执行结果与在 `happens-before` 关系要求下的结果**一致**, 则 `JMM` 同样允许其进行重排序.
- `happens-before` 原则的诞生是为了程序员和编译器, 处理器之间的平衡. 程序员追求的是易于理解的高可读的**强内存模型**, 只需遵循编码规则即可; 编译器和处理器追求的是较少的约束的**弱内存模型**, 使能够有最大的空间优化性能.
- `happens-before` 原则的设计思想主要有两点
	1. 对编译器和处理器的约束尽可能少. 只要在单线程程序或正确执行的多线程程序中可以保持结果不变, 中间可进行任意的重排序优化.
	2. 对可能改变执行结果的重排序, `JMM` 要求编译器与执行器必须禁止.
	- 即 `happens-before` 对外暴露的接口是禁止所有重排序操作, 但实际上只对会影响结果的重排序进行了制止, 不改变执行结果的重排序不作操作
- `happens-before` 实际表达的是前一个操作对后一个操作是可见的, 无论两个操作之间是否处于同一个线程.

### 常见规则
- happens-before 规则共8条. 如果两个操作不满足任何一个 happens-before 规则, 则二者没有顺序要求, JVM 可以随意对两个操作进行重排序.
- 常见规则为以下5条:
1. **程序顺序规则**: **线程内部**顺序书写的代码, 书写在前面的操作 happens-before 书写在后面的操作.
2. **加锁解锁规则**: 加锁操作 happens-before 解锁操作.
3. **volatile 变量规则**: volatile 变量的写操作 happens-before 任意线程中后面的 volatile 变量的读操作. 即 volatile 变量的写操作的结果对于其后发生的任何读操作都是可见的.
4. **传递规则**: 如果 A happens-before B, 且 B happens-before C, 那么 A happens-before C
5. **线程启动规则**: `Thread` 对象的 `start()` 方法 `happens-before` 线程内每个操作

# 并发编程特性

### 原子性
- 一次或多次操作, 要么所有的操作全部得到执行而不被中断, 要么所有操作都不会被执行.
- `synchronized` 和 `Lock` 类可以保证任意时刻只有一个线程访问该代码块, 而原子类中通过 `CAS` 操作(也可能用到 `volatile` 或者 `final`) 确保原子操作.

### 可见性
- 当一个线程修改了某共享变量, 其他线程都可以立即看到修改后的值.
- Java 中可以用 `synchronized`、`volatile` 以及各种 `Lock` 实现可见性
- 如果将变量声明为 `volatile` 的, 说明指示 `JVM` 该变量共享且不稳定, 每次使用时需要到主存中进行读取

### 有序性
- 由于指令重排问题, 有时代码的执行顺序未必就是编码时的顺序. 
- Java 中 `volatile` 可以禁止对指令进行重排序优化.
