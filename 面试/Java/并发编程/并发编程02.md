# volatile

- volatile 关键字可以用来声明变量事共享且多线程可见的, 使用该关键字修饰的变量, 每次使用时**都要到主存中**进行读取. volatile 只能保证数据的**可见性**而不能保证数据的原子性, 但 synchronized 关键字可以同时做到保证数据的可见性和原子性.
- volatile 还可以用来防止JVM的指令重排序. 一行代码在 JVM 中可能对应多段操作, 如果多段操作的执行顺序不影响最终结果, 则可能发生指令重排序. 在单线程情况下不会出现问题, 但是多线程情况下, 可能导致另一个线程获得数据时数据未赋值, 从而使用未赋值的数据.
- volatile 只保证取数据时的可见性, 不保证操作数据时的原子性, 所以 volatile 关键字不能保证数据的原子性

# 乐观锁和悲观锁

乐观锁假设操作冲突少，只在提交时检查数据是否被修改（如版本号机制），适用于读多写少场景；悲观锁预先加锁（如行锁、表锁），确保独占操作，适合写多场景，但影响并发性能。前者减少锁竞争，后者保证强一致性。

## 悲观锁

**悲观锁**总是假设最坏的情况，设定每次访问数据一定会出现共享问题，于是要求每次访问资源前必须上锁，直到资源使用完毕释放锁，转让给其他线程使用。**悲观锁**在**高并发情况**下会导致激烈竞争，从而造成线程阻塞，系统上下文频繁切换，增加系统性能开销，同时还存在**死锁问题**。

synchronized 关键字和 ReentrantLock 类都是悲观锁思想的实现。

## 乐观锁

乐观锁总是假设最好的情，设定每次访问数据时一定不会出现共享问题，线程不需要停止等待，可以一直执行，只需要在提交时验证对应的资源是否被其他线程修改。

高并发场景下，乐观锁相比于悲观锁，不存在锁竞争导致的线程阻塞，性能相对更高，但是若**冲突频繁发生**，也会导致频繁重试的系统**开销飙升**。可以使用某些方式解决这个问题，比如 `LongAdder`。

Atomic 系列类就是乐观锁的 CAS 思想实现的。

## 乐观锁实现

### 版本号机制

在数据库表中加入**版本号字段**，标识数据被修改的次数，被修改时版本号+1。当客户端试图更新数据值时，同时会设定对版本号的要求，只有当版本号与读取时版本号**一致**时，才允许修改更新，否则要重试更新操作，直到成功。

### CAS算法

**CAS** ( Compare And Swap ) 是一种基于硬件的无锁并发机制，通常用于实现乐观锁。其核心思想是通过比较**内存值**与**预期值**进行**原子操作**，两值相等时才会进行更新。该操作是一个**原子操作**，底层依赖于CPU的原子指令。
