# volatile

- volatile 关键字可以用来声明变量事共享且多线程可见的, 使用该关键字修饰的变量, 每次使用时**都要到主存中**进行读取. volatile 只能保证数据的**可见性**而不能保证数据的原子性, 但 synchronized 关键字可以同时做到保证数据的可见性和原子性.
- volatile 还可以用来防止JVM的指令重排序. 一行代码在 JVM 中可能对应多段操作, 如果多段操作的执行顺序不影响最终结果, 则可能发生指令重排序. 在单线程情况下不会出现问题, 但是多线程情况下, 可能导致另一个线程获得数据时数据未赋值, 从而使用未赋值的数据.
- volatile 只保证取数据时的可见性, 不保证操作数据时的原子性, 所以 volatile 关键字不能保证数据的原子性

# 乐观锁和悲观锁

总体而言, 通常来说, 悲观锁用于写多读少的情况, 乐观锁用于读多写少的情况, 但是也可能使用其他机制解决问题, 以实际情况决定

### 悲观锁
- 悲观锁总是假设最坏的情况, 设定每次访问数据一定会出现共享问题, 于是要求每次访问资源前必须上锁, 直到资源使用完毕释放锁, 转让给其他线程使用
- synchronized 和 ReentrantLock 都是悲观锁思想的实现
- 悲观锁在高并发情况下会导致激烈竞争, 从而造成线程阻塞, 系统上下文频繁切换, 增加系统性能开销, 同时还存在死锁问题

### 乐观锁
- 乐观锁总是假设最好的情况, 设定每次访问数据时一定不会出现共享问题, 线程不需要停止等待, 可以一直执行, 只需要在提交时验证对应的资源是否被其他线程修改.
 - Atomic系列类就是乐观锁思想的CAS机制实现的
- 高并发场景下, 乐观锁相比于悲观锁, 不存在锁竞争导致的线程阻塞, 性能相对更高, 但是若冲突频繁发生, 也会导致频繁重试的系统开销飙升. 可以使用某些方式解决这个问题, 比如 `LongAdder`

#### 乐观锁实现

##### 版本号机制
- 在数据库表中加入版本号字段, 标识数据被修改的次数, 被修改时版本号+1, 数据试图更新数据值时, 同时会设定对版本号的要求, 只有当版本号与读取时版本号一直的才允许修改更新, 否则要重试更新操作, 直到成功

##### CAS算法
- CAS, 即 Compare And Swap, 用于实现乐观锁. 核心思想是使用预期值与要更新的变量值进行比较, 两值相等时才会进行更新, 该操作是一个原子操作, 底层依赖于CPU的原子指令.
- CAS涉及三个数: **V-要更新的变量值, E-预期值, N-拟写入的新值**. 仅当V等于E时, 使用N更新V的值, 如果不等, 说明有其他线程更新了V, 则当前线程放弃更新. 多个线程同时尝试更新一个变量时, 只有一个会成功, 剩下的继续尝试更新或是放弃操作.
- Java 中对 CAS 的支持是通过 C++ 代码实现的, 使用 JNI 调用 C++ 编写的内联代码实现 CAS, 因此 CAS 的具体实现和操作系统以及CPU都有关系
- Java 中的 `sun.misc` 包下定义了 Unsafe 类, 这个类是用来提供一些低级别, 不安全操作的类, 通常用于需要极高性能或底层访问的情况, 不建议普通开发者使用; Unsafe 类实现了对 Object, int, long 的 CAS 操作, 其内部是使用 C++ 实现的原子操作, 与操作系统以及CPU密切相关
- `java.util.concurrent.atomic` 包下定义了一些用于提供原子操作的 `Atomic` 类, 这些类利用底层的原子指令, 确保在多线程环境下操作的线程安全. 以整数的 `AtomicInteger` 为例, 其底层通过 Unsafe 类的 compareAndSwapInt 方法循环尝试更新 V 直到执行完成, 即其底层是**自旋锁机制** 

##### CAS问题

###### ABA问题
- 如果一个变量初次读取时值为A, 且在准备赋值时值仍为A, 但这不能代表该变量一定没有被修改过, 因为这段事件可能被修改为了其他值后又改为A. 这个问题即为 ABA 问题
- 解决思路是在变量前面追加版本号或时间戳.  `AtomicStampedReference` 类就是使用标志法解决ABA问题的一种实现.

###### 循环时间长开销大
- 在 CAS 操作中使用自旋操作进行重试, 不成功则循环到成功为止, 长时间不成功会对 CPU 带来很多负担
- 如果 JVM 可以支持 pause 操作, 则自旋效率可以得到提升, pause 指令可以延迟指令的执行, 减少CPU资源损耗, 同时可以在退出时避免内存顺序冲突而导致的CPU流水线被清空

###### 只能一个共享变量
- CAS 只对单个变量, 不能同时操作多个变量. 为变相实现多个变量操作, 从JDK1.5 开始, Java 提供的 AtomicReferrence 类允许将多个变量整合成为一个对象进行 CAS 操作

# synchronized

### 概述
- synchronized (同步) 是 Java 中的一个关键字, 主要用于解决多个线程之间的资源同步问题, 被他修饰的方法或代码块在任意时刻只能有一个线程执行
- 构造方法不能使用 synchronized 进行修饰, 但是可以在构造方法内部使用 `synchronized` 代码块. 构造方法本身是线程安全的, 但是如果构造方法中涉及到对共享资源的操作, 则需要采用合适的同步措施.
- 早期版本中, synchronized 属于重型锁, 其实现依赖操作系统底部的 Mutex Lock, 对线程的挂起或唤醒都需要操作系统完成, 在用户态和内核态的切换过程需要较多时间, 效率相对较高
- Java6 之后引入了大量优化, 如自旋锁、适应性自旋锁、锁消除、锁粗化、偏向锁、轻量级锁, 减少了 synchronized 的锁开销, 使其足够在实际项目中使用
- 对于偏向锁, JDK15中默认关闭, JDK18中彻底废弃

### 使用
- synchronized 主要用于修饰 1.实例方法 2.静态方法 3.代码块. 
- 对于实例方法, 进入同步代码前要获得当前对象实例的锁; 
- 对于静态方法, 进入同步代码前要先获取当前类的锁, 这是因为静态方法属于整个类所有, 不依赖于特定实例; 
- 对于静态 `synchronized` 方法和实例 `synchronized` 方法, 其调用不存在冲突, 因为二者需要的锁不相同.
- 对于修饰代码块的情况, 可以选择将当前实例作为锁, 也可以选择将当前类作为锁, 具体选择依代码块作用不同而不同
- 尽量不要使用字符串作为锁对象, 因为字符串具有缓存功能

### 底层原理

#### 同步语句块
- synchronized 底层实现依靠的是 monitorenter 和 monitorexit 指令, 前者指示同步代码块的开始, 后者指示同步代码块的结束. monitorexit 会存在两个, 这是为了确保锁在正常结束和出现异常情况下都可以被正常释放.
- 当执行 monitorenter 时, 线程试图获取锁, 也就是 monitor 对象监视器的持有权. 如果锁的计数器为0, 说明锁可获取, 将锁计数器设为1.
- 执行 monitorexit 时, 如果锁的计数器为1, 则将锁计数器设为0.
- 如果获取锁对象失败, 则当前线程阻塞等待, 直到锁被另一个线程释放为止.
- 在 Hotspot 虚拟机中, monitor 是基于 C++ , 由 ObjectMonitor 实现的, 每个对象中都内置了一个 ObjectMonitor 对象. 此外, notify/wait 方法也依赖于 ObjectMonitor 对象, 只有在同步的块或方法中才能调用.

#### 同步方法
- 在 synchronized 修饰的方法中不存在 monitorenter 和 monitorexit 指令, 而是 `ACC_SYNCHRONIZED` 标识, 该标识指明了该方法是一个同步方法. JVM 调用方法时, 如果方法中存在此标识, 则根据方法类型进行同步调用.
- 对于实例方法, 使用实例对象; 对于静态方法, 使用当前类
- 不论同步语句块还是同步方法, 其实现的本质都是对 monitor 的获取.

#### Java6之后优化
- Java6之后, synchronized 引入了大量优化, 如自旋锁、适应性自旋锁、锁消除、锁粗化、偏向锁、轻量级锁等, 减少了所操作开销, 提高了 synchronized 锁效率.
- synchronized 锁主要存在四种状态, 分别是: 无锁状态, 偏向锁状态, 轻量级锁状态, 重量级锁状态, 随着锁竞争的激烈程度逐渐升级. 锁状态只可以升级, 不可以降级, 这是为了提高获得锁和释放锁的效率

##### 偏向锁的禁用
- 对于偏向锁, JDK15中默认关闭, JDK18中彻底废弃, 主要存在两个原因
1. 性能收益不明显. 偏向锁主要由早期 Java 集合 API 使用, 随 JDK 发展出现更高性能的集合类, 降低了偏向锁的性能收益; 同时偏向锁只在单线程访问同步代码块场景下有收益, 如存在多线程竞争就需要撤销偏向锁, 性能开销较昂贵
2. JVM内部维护成本高. 偏向锁将复杂代码引入同步子系统, 并对其他 HotSpot 组件也具有入侵性, 为理解代码, 重构系统带来了困难.

#### 与volatile区别
- `volatile` 是线程同步的轻量级实现, 性能较 `synchronized` 好. 但是 `volatile` 只能由于变量而 `synchronized` 可以用于修饰方法和代码块.
- `volatile` 只能保证数据的可见性而无法保证原子性, 而 synchronized 二者都可以实现
- `volatile` 解决的是变量在多个线程之间的可见性, 而 `synchronized` 关键字解决的是多个线程之间访问资源的同步性.

# ReentrantLock

### 概述
- `ReentrantLock`, 可重入锁, 是一个可重入且独占式的锁, 实现了 Lock 接口. 其与 synchronized 关键词类似, 但是更灵活更强大, 增加了轮询, 超时, 中断, 公平锁, 非公平锁等高级功能.
- `ReentrantLock` 中定义了 Sync 内部类, 该内部类中实现了大部分添加锁和释放锁的操作, 该类有 FairSync 公平锁和 NonfairSync 非公平锁两个子类; 可重入锁 `ReentrantLock` 的底层是由 [[面试/Java/并发编程/AQS|AQS]] 实现的.
- `ReentrantLock` 默认使用非公平锁, 也可以使用构造器参数指定使用公平锁.

### 公平锁与非公平锁的区别
- 公平锁: 锁被释放以后, 先申请的线程先得到锁. 为保证时间上的公平, 性能相对较差一些, 上下文切换更频繁.
- 非公平锁: 锁被释放以后, 后申请的线程也有可能先得到锁; 得到锁的顺序是随机或者按线程优先级排序的. 由于不需要考虑时间, 性能更好, 但是可能存在线程一直无法获取到锁的情况出现.

### 与synchronized区别
- 两者都是**可重入锁**. 可重入锁又称递归锁, 指**线程**获得了一个锁后, 如果该锁还没有释放, 可以再次获取自己的内部锁. JDK 提供的所有 Lock 实现类都是可重入的.
- synchronized 在 JVM 虚拟机的层次进行实现; 而 ReentrantLock 在 JDK API 的层次进行实现, 需要手动进行 `lock()` 和 `unlock()`, 并且可以查看源码
- ReentrantLock 比 synchronized 增加了一些高级功能: 
	1. 等待可中断: ReentrantLock 提供了一种中断等待锁的线程的机制, 通过提供的 `lockInterruptibly()` 方法实现该机制. 如果阻塞等待过程中其他线程中断了当前的线程, 会抛出线程中断异常 `InterruptedException`, 可以捕获该异常进行处理
	2. 可实现公平锁: ReentrantLock 提供了公平锁的实现, 而 synchronized 关键字提供的锁只能是非公平锁.
	3. 可实现选择性通知: synchronized 关键字通过 `wait()` / `notify()` 机制可以实现等待/通知机制, 而 ReentrantLock 的实现需要借助 Condition 接口与 `newCondition()` 方法
	4. 支持超时: ReentrantLock 允许设定超时时间, 锁等待最长时间后仍未获得, 则直接失败, 不会一直等待

### 补充

#### 等待可中断
Java 中的线程在执行 `interrupt` 中断操作时, 只有当特定情况下, 才会响应中断, 并抛出 `InterruptedException` 异常. 其中包括当线程通过执行 `lockInterruptibly()` 方法执行加锁情况. 当执行该方法时, 检查是否存在中断标志, 存在中断标志则抛出异常. 否则尝试加锁, 加锁成功继续向下执行, 否则阻塞等待; 如果等待过程中出现了对该线程的中断, 则抛出异常

#### Condition 接口
Condition 接口在JDK1.5加入, 可以实现多路通知功能, 即一个 Lock 中可以创建多个 Condition 实例. 线程对象可以注册到某个特定的 Contidion 实例中, 从而有选择性的进行线程通知. 对于 synchronized, 执行 notify() / notifyAll() 时, 只能通知随机一个等待线程或全部等待线程, 而通过 ReentrantLock 中持有的某个 Condition 的 signalAll() 方法, 可以有选择性的只唤醒注册在这个 Condition 中的线程.
