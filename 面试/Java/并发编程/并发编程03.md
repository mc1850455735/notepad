
# ThreadLocal

### ThreadLocal的作用
- ThreadLocal 允许每个线程绑定自己的值, 用于存储私有数据, 确保各线程之间互不干扰. ThreadLocal 变量创建时, 每个访问该变量的线程都会有一个独立的副本, 可以通过 `set()` 设置副本中的值, `get()` 获取副本中的值

### ThreadLocal实现原理
- `ThreadLocal` 类中存在一个名为 `ThreadLocal` 的子类, 每个线程类中都含有这个类; 对于一个特定的 `ThreadLocal` 实例, 线程调用 set() 时, 就是以该 `ThreadLocal` 实例为键, 向当前线程的 `ThreadLocalMap` 中插入值; 读取时, 就是以该实例为键, 获取 `ThreadLocalMap` 中的值.
- 如果在一个线程中定义了两个 ThreadLocal 对象, `Thread` 内部用的都是存在于线程对象内部的 `ThreadLocalMap` 存放数据, 其 key 就是 ThreadLocal 对象, 其 `value` 是调用 `set()` 方法设置的值
- 所以, 最终变量是存放在了当前线程的 `ThreadLocalMap` 中, 而不是存在于 `ThreadLocal` 类上, `ThreadLocal` 可以被看作是对 `ThreadLocalMap` 的封装.

### 内存泄漏问题
- 在线程使用 ThreadLocal 存储值时, 实际上是将值存储到当前线程中的 `ThreadLocalMap` 中, 该对象使用 `ThreadLocal` 实例作为 key, 通过哈希算法计算索引, 并最终存储于 `Entry extends WeakReference<ThreadLocal<?>>` 类型的数组中.
- 也就是说, ThreadLocalMap 的 key 是 ThreadLocal 的弱引用. 如果 ThreadLocal 不被任何值指向, 则该对象会在 GC 的下一次回收时被直接回收, 但是 value 是强引用存在的, 当 ThreadLocal 弱引用被回收是, Map 中仍然强引用存在 value, 导致无法被垃圾回收. 当 ThreadLocal 不被强引用而回收时, 若线程长期存活导致其中的 ThreadLocalMap 持续存在, 就会造成内存泄漏.
- 为避免内存泄漏, 在不再使用某个 ThreadLocal 后, 务必调用 remove() 方法移除其中的 value, 再对 ThreadLocal 进行释放; 同时, 在线程池等线程复用的场景下, 尽量使用 `try-finally` 块, 确保即使出现异常也可以执行 remove() 方法

### 跨线程传递ThreadLocal值

为实现异步场景下, 父子线程之间传递 `ThreadLocal` 值, 有两种解决方案: 
- `InheritableThreadLocal` : 该类为 JDK1.2开始提供的工具类, 继承自 `ThreadLocal` 类, 使用该工具类时, 会在创建子线程时令子线程继承父线程当中的 `ThreadLocal` 值, 但是不支持线程池场景下的 `ThreadLocal` 值传递
- `TransmittableThreadLocal` : 阿里巴巴开源的工具类, 继承并加强了 `InheritableThreadLocal` 工具类, 允许在线程池场景进行 `ThreadLocal` 值传递

#### InheritableThreadLocal原理
- 在线程中, 同时存在两个 ThreadLocalMap, 一个 map 用来进行存储线程中数据, 另外一个 map 名为 InheritableThreadLocal , 用来进行跨线程传递
- inheritableThreadLocals 就表示可以传输给子线程的线程持有的数据或由父线程传输而来的线程持有的数据
- 子线程由父线程创建, 创建时父线程调用 init() 方法指定 ThreadLocal 的继承逻辑. 方法调用时, 传入参数 inheritThreadLocals, 如果为 true, 说明需要继承, 则将父线程的 inheritableThreadLocals 直接传给子线程即可

#### TransmittableThreadLocal原理
- JDK默认不支持线程池场景下的 ThreadLocal 传递, TTL 实现了该功能. 由于无法改动 JDK 源码, 该类通过装饰器模式在原有功能上实现了增强.
- TTL 共改造两处: 1. 实现了自定义的 Thread, 在 run 方法内部做 ThreadLocal 的赋值操作 2. 基于线程池进行装饰, 向 `execute()` 方法提交时, 不提交 JDK 内部的 Thread, 而是提交自定义的 Thread

# 线程池
- 线程池是管理一系列线程的资源池, 当有任务需要处理时, 直接从线程池中获取, 线程处理完任务后不会被立即销毁, 而是等待处理下个任务.

### 线程池优点
- 降低资源消耗: 通过重复利用线程, 避免了频繁创建和销毁线程的开销
- 提高响应速度: 线程池内通常会维护一定数量的常驻线程, 任务来后可以直接交给空闲线程进行处理, 省去了创建线程的时间开销.
- 提高线程可管理性: 通过线程池统一管理池中的线程, 可以配置池的大小, 任务队列大小和拒绝策略等, 控制并发线程的总量, 防止系统资源耗尽, 保证系统的稳定性; 同时, 线程池也为监控系统状态提供了接口.

### 创建线程池
- 首先, 线程资源使用时, 应尽量保证由线程池提供 (阿里巴巴规范要求必须通过线程池获取线程), 否则随意创建和销毁大量同类线程会加大时间和系统开销, 同时可能导致内存好进或系统"过度切换"的问题出现
- 同时, 应尽量避免通过 `Executors` 获取内置线程池, 而是通过构造函数获取.

#### 构造函数创建
- **推荐使用**, 因为 `ThreadPoolExecutor` 构造函数方式允许开发者明确指定线程池的核心参数, 对线程池的运行行为有更精确的控制, 从而避免资源耗尽的风险.

#### 工具类创建
- 不推荐. 通过 Executors 工具类提供的方法创建线程池
- 可以通过给定的 `FixedThreadPool`, `SingleThreadExecutor`, `CachedThreadPool`, `ScheduledThreadPool` 四种方法创建指定类型的线程池.

#### 内置线程池缺点
- 对于 `FixedThreadPool` 和 `SingleThreadExecutor`, 其阻塞队列使用的是 `LinkedBlockingQueue`, 且任务队列最大长度设置为 `Integer.MAX_VALUE`, 可以视为是无界的, 可能堆积大量请求, 导致出现 OOM.
- 对于 `CachedThreadPool` , 其阻塞队列使用同步队列 `SynchronousQueue`, 且线程池内允许创建线程数量为 `Integer.MAX_VALUE`, 可以看作是无界的. 当线程数量较多且执行速度较慢时, 可能导致大量线程堆积, 从而导致 OOM
- 对于 `ScheduledThreadPool` 和 `SingleThreadScheduledExecutor` , 其使用物件的延迟阻塞队列 `DelayedWorkQueue`, 队列最大长度为 `Integer.MAX_VALUE`, 可能堆积大量请求导致 OOM

#### 线程池常见参数

##### 最重要三个参数
- `corePoolSize` : 任务队列未达到队列容量时, 最大可以同时运行的线程数量
- `maximumPoolSize` : 任务队列中存放任务达到最大容量时, 当前可同时运行的线程数量变为最大线程数. 队列已满且超过 `corePoolSize` 后, 新加入的线程先执行, 队列中的线程继续等待线程出现空闲.
- `workQueue` : 任务队列, 新任务到达时会先判断当前运行的线程数量是否到达核心线程数量, 如果达到则新任务存入该任务队列

##### 其他参数
- `keepAliveTime` : 当线程池中的线程数量大于 corePoolSize 时, 即存在非核心线程时, 非核心线程在空闲后不会立刻销毁, 而是等待, 直到超过等待时间.
- `unit` : 等待时间参数的时间单位
- `threadFactory` : executor 创建新线程时会用到.
- `handler` : 拒绝策略

### 核心线程默认不回收
- `ThreadPoolExecutor` 默认不会回收核心线程, 即使核心线程空闲
- 这样做的目的是为了减少线程创建时的开销, 因为核心线程通常需要保持长期活跃, 以应对可能的任务的到来.
- 如果线程池被用作周期性的场景, 且频率不高, 则通过 `allowCoreThreadTimeOut` 设置其参数为 `true`, 可以允许回收空闲的核心线程

### 空闲核心线程状态
- 核心线程无存活期: 在核心线程空闲时, 会一直处于 `WAITING` 状态, 等待获取任务, 核心线程一直存活于线程池中.
- 核心线程有存活期: 核心线程空闲时, 会切换到 `WAITING` 状态等待获取任务, 如果阻塞等待的时间超过了核心线程存活时间, 则线程退出工作, 将该线程从线程池中移除, 线程状态改为 `TERMINARED`

### 线程池拒绝策略

#### 概述
- 当当前线程池线程数量已经达到最大值且队列中也被放满了任务时, 应当为线程池对象 `ThreadPoolExecutor` 定义一些策略处理新来的任务.
- `AbortPolicy` : 直接抛出 `RejectedExecutionException` 异常拒绝新任务的处理
- `CallerRunsPolicy` : 若线程数量已满, 则会使用执行者自身线程执行该任务. 如果此时执行者已关闭, 则丢弃该任务. 该策略会降低新任务提交速度, 影响程序整体性能, 适合对执行要求高的任务.
- `DiscardPolicy` : 不处理新任务, 直接丢弃
- `DiscardOldestPolicy` : 加入新任务, 丢弃最早未处理的任务

#### CallerRunsPolicy详解
- 如果要求保证任何一个任务请求都要被完成, 则 `CallerRunsPolicy` 拒绝策略是最适合的方式. 
- 然而如果走到 `CallerRunsPolicy` 的任务是一个非常耗时的任务, 且处理该任务的线程为主线程, 则可能导致主线程阻塞, 影响程序正常执行. 严重情况下可能由于主线程阻塞而导致线程池阻塞, 甚至最终导致 OOM.
- 如果能够在阻塞任务队列无法容纳的情况下, 主动扩展阻塞任务队列的大小, 则可以实现在内存允许的情况下调整堆内存, 在队列中容纳更多任务, 确保任务可以被准确执行.
- 为了确保CPU利用率, 还可以在阻塞等待队列满时, 增加线程池的最大线程数 `maximumPoolSize` , 提高任务的处理速度; 同时也可以避免消息队列中任务数量过多导致内存耗尽.
- 如果在内存和CPU全部都达到极限的情况下还是无法做到不丢弃, 则可以使用任务持久化的思路进行任务的存储. 实现方案包括但不限于: 1. 使用 MySQL 数据库进行未执行任务存储; 2. 使用 Redis 缓存任务; 3. 将任务提交到 MQ 中间件中. 通过实现 `RejectedExecutionHandler` 接口自定义拒绝策略.
- 在某些框架中, 还可能会直接临时创建新 Thread 直接处理无法加入队列的任务, 但是需要服务器有良好的硬件条件, 且临时创建线程无法被准确监控

### 常用阻塞队列

以内置线程池为例, 常用的阻塞队列如下
- 容量为 `Integer.MAX_VALUE` 的 `LinkedBlockingQueue` (有界阻塞队列) : 常用于 `FixedThreadPool` 和 `SingleThreadExecutor` . `FixedThreadPool` 最多只能创建核心线程数的线程, 即核心线程数和最大线程数相等; `SingleThreadExecutor` 只能创建一个线程. 二者任务队列大小都极大, 可看作 OOM 前永远不会放满
- `SynchronousQueue` (同步队列) : 常用于 `CachedThreadPool`. 同步队列没有容量,不存储元素. 对于提交过来的任务, 如果有空闲线程, 则直接使用空闲线程; 否则新建线程用来处理任务. 因此, 可以看作 `CachedThreadPool` 的线程数是可以无限扩展的, 但是可能因线程数过多导致 OOM 问题.
- `DelayedWorkQueue` (延迟队列) : 常用于 `ScheduledThreadPool` 和 `SingleThreadScheduledExecutor`. 延迟队列的内部任务不是按照加入队列时间排序的, 而是按照预先设置的执行时间长短排序. 内部数据结构是一个基于数组的小根堆, 保证每次出队的任务都是执行时间最短的. 延迟队列是一个无界队列, 底层数组容量不足时会自动进行扩容. 随着任务不断提交, 任务会全部被添加到队列中, 队列永远不会满, 所以线程池内的线程数量永远不会超过其核心线程数, 最大线程数参数对于使用该队列的线程池来说是无效的.
- `ArrayBlockingQueue` (有界阻塞队列) : 底层使用数组, 容量固定.

### 线程池处理任务流程

当接收到一个任务时: 
1. 如果当前运行的线程数小于核心线程数, 则新建一个线程执行任务.
2. 如果当前运行的线程数大于等于核心线程数, 但小于最大线程数, 则将该任务放入任务队列中等待执行.
3. 如果任务队列已满, 且当前运行的线程数小于最大线程数, 则新建线程 (非核心线程) 对传入任务进行处理
4. 如果当前运行线程数等于最大线程数, 且任务队列已满, 则当前线程应被拒绝, 调用线程池的拒绝策略方法
- 可以调用 `prestartCoreThread()` 方法启动一个核心线程等待任务. 如果核心线程数已满, 则方法返回 false, 否则返回 true.
- 可以调用 `prestartAllCoreThreads()` 方法启动所有的核心线程等待任务. 方法返回值为启动成功的核心线程数量.

### 线程异常处理
- 需要分为 `execute()` 和 `submit()` 两种情况进行讨论.
- 二者的主要区别在于对异常的处理策略不一致.

#### execute()
- 任务通过 execute() 提交到线程池, 在执行过程中抛出异常时, 如果这个异常没有在任务内被捕获, 则该异常会导致线程终止, 异常会被打印到控制台上. 线程池会检测到线程终止后, 会创建一个新线程替代, 以保持线程总量不变.

#### submit()
- 任务通过 submit() 提交到线程池, 在执行过程中抛出异常时, 该线程不会被打印出来, 而是会将异常封装到 Future 类型的返回值对象中. 当调用对应的 `Future.get()` 方法时, 可以捕获到 `ExecutionException` 异常.
- 这种情况下, 线程不会因异常结束, 而是继续存在于线程池中等待复用.
- 这允许 submit() 提供更灵活的错误处理机制, 调用者可以获取异常并自行决定如何处理异常. 而 execute() 适合不需要关注执行结果的场景.

### 线程池命名

#### guava
- 使用 guava 的 ThreadFactoryBuilder 类, 可以指定线程池中线程的命名策略.

#### 实现ThreadFactory
- 通过继承 ThreadFactory 线程工厂类, 并在其中重写对应的 newThread() 方法, 在 newThread 方法中定义对新建线程的命名方式.

### 线程池大小设定

#### 概述
- 线程池的大小必须根据任务的特征和大小来指定. 
- 线程池过小, 如果同一时间内有大量任务需要处理, 则会导致任务在任务队列中堆积, 以及任务队列满后面临的任务无法正常处理的情况. 严重情况下还可能导致OOM问题, 且在这个过程中 CPU 没有得到充分利用.
- 线程池过大, 大量线程可能同时争抢CPU资源, 导致大量的不必要的上下文切换, 从而增加了线程的执行时间, 影响整体执行效率

#### 计算
- CPU 密集型任务: N+1. 这种任务主要消耗 CPU 资源, 可将线程数设为 CPU核心数+1. 多出来的一个线程是为了防止线程偶发的线程中断或者其他原因导致的任务暂停. 一旦暂停, 多出的一个线程就可以充分利用 CPU 空闲时间.
- IO 密集型任务: 2N. 这种任务的大部分时间会用来处理 IO 交互, 而在线程处理 IO 的过程不会占用 CPU, 此时就可以将 CPU 交由其他线程使用.

#### 上下文切换
- 多线程中一般线程个数都大于 CPU 个数, 而一个 CPU 核心在同一个时间段内只能被一个线程使用. 为保证每个线程都能被执行, CPU 需要为每个线程分配时间片并在他们之间轮转.
- CPU 切换线程时, 需要保存上一个线程状态并加载下一个线程状态, 这个保存并加载的过程就叫做 CPU 的一次上下文切换.
- 上下文切换通常是计算密集型的, 这个过程中需要消耗大量的 CPU 时间.

### 动态修改线程池参数
- 线程池参数中, 最重要的就是 `corePoolSize` , `maximumPoolSize` , `workQueue` 三个参数, 其中 `corePoolSize` , `maximumPoolSize` 在 `ThreadPoolExecutor` 中提供了对应的 set 方法
- 修改 `corePoolSize` 时, 如果修改后的核心线程数小于当前工作线程数, 则会回收当前的工作线程.
- `ThreadPoolExecutor` 默认不提供修改 `workQueue` 的方法, 可以通过自定义或者映入相关队列依赖的方式, 实现一个长度可变的任务阻塞队列.

### 优先级线程池
- 想要实现优先级线程池, 实际上就是要实现一个使用优先级队列的线程池
- 对于优先级队列, 可以使用 Java 提供的 `PriorityBlockingQueue` 优先级阻塞队列作为任务队列, 该队列是一个支持优先级的无界阻塞队列, 可以看作是一个线程安全的 `PriorityQueue`, 但 `PriorityQueue` 不支持阻塞操作.
- `PriorityBlockingQueue` 的使用必须为其设定比较功能, 可以选择为传入的任务类实现 `Comparable` 接口, 或者定义一个 `Compator` 对象指定任务对象的排序规则.
- `PriorityBlockingQueue` 存在一些问题: 1. 优先级阻塞队列是无界的, 可能堆积大量请求导致 OOM 问题; 2. 低优先级的任务可能长期得不到执行, 出现饥饿问题; 3. 由于需要对队列中的元素进行排序以及保证线程安全性 (优先级阻塞队列采用的是可重入锁 `ReentrantLock`), 因此会导致性能降低
- 解决: 1.可以通过继承 `PriorityBlockingQueue` 并重写其中的 offer 方法, 手动限制队列大小解决; 2. 可以通过优化设计解决, 比如将等待时间纳入考虑, 采用高响应比优先调度算法等, 但实现困难; 3.只能改善, 无法解决, 且性能影响对整个系统来说通常可接受.

# Future

### 作用
- Future 类是异步思想的典型运用. 在程序执行过程中, 可以将能够并行的任务交由子线程并行执行, 主线程执行其他任务, 待其他事情执行完毕需要获取并行任务执行结果时, 通过 Future 类获取耗时任务的结果.
- 这是多线程中的 Future 设计模式, 其核心思想是**异步调用**, 主要用于多线程领域, 并非 Java 独有. 简单来说, 就是将一个任务交由 Future 处理, 在此期间可以做任何其他事情, 也可以取消任务, 或者获得任务的执行状态. 一段时间后, 需要使用结果时, 直接到 Future 处获取执行结果.
- 在 Java 中, Future 类是一个泛型接口, 位于 `java.util.concurrent` 包下, 其中定义了5个方法, 分别包含: 1.`取消任务`; 2.`判断任务是否取消`; 3.`判断任务是否已经执行完成`; 4.`获取任务执行结果` 4个功能.

### 与Callable关系
- `Future` 接口与 `Callable` 接口的关系体现在 `FutureTask` 实现类
- `FutureTask` 提供了 `Future` 接口的基本实现, 同时也实现了 `Callable` 接口, 常用来封装 `Callable` 和 `Runnable`, 可以作为一个任务直接被线程执行. 
- `ExecutorService.submit()` 方法返回的就是一个 `FutureTask` 类型的对象. 
- FutureTask 有两个构造方法, 可以分别接收 `Runnable` 接口的实现和 `Callable` 接口的实现. 实际上传入的 `Runnable` 接口实现也会在构造方法内部转换为 `Callable` 接口实现.
- `FutureTask` 相当于对 `Callable` 进行了封装, 管理着其中任务的执行情况, 并且存储着 `Callable` 的 `call()` 方法的执行结果.

### CompletableFuture类

#### 概述
- 在 `Future` 的实际使用过程中存在一些局限性, 如 不支持异步任务的编排组合, 获取计算结果的 `get()` 方法为阻塞调用.
- 为解决 `Future` 缺陷, 在 Java8 中引入 `CompletableFuture` 类. 该类中提供了函数式编程, 异步任务编排组合等能力. 该类同时实现了 `CompletionStage` 和 `Future` 两个接口. 
- `CompletionStage` 描述了一个异步计算的阶段. 很多计算可以分为多个阶段, 通过该类可以将所有步骤组合起来, 形成异步计算的流水线. 该接口中声明了很多方法, 其中大量使用了 Java8 中引入的函数时编程, `CompletableFuture` 类的函数式编程能力就是这个接口赋予的

#### 任务依赖关系
- 如果存在一个任务, 需要依赖另外两个任务执行完后再执行, 这种场景适合通过 CompletableFuture 类进行实现. 
- 使用 CompletableFuture 类的 allOf() 静态方法, 可以并行运行前两个任务. 待前两个任务都完成后, 再执行第三个任务.

#### CompletableFuture异常处理
- 使用  `CompletableFuture` 类时, 对于不同的方法有不同的异常处理策略, 应该以正确的方法进行异常处理, 避免异常丢失或者出现不可控问题.

下面是一些建议: 
- `whenComplete()` 方法可以在任务完成时触发回调函数, 并正确的处理异常, 而不是让异常被吞噬或丢失
- `exceptionally()` 方法可以处理异常并重新抛出, 以便异常可以传播到后续阶段, 而不是使异常被忽略或终止.
- `handle()` 方法可以处理正常的返回结果和异常, 并返回一个新结果, 而不是让异常影响正常的业务逻辑.
- `allOf()` 方法可以组合多个 `CompletableFuture`, 并统一处理所有任务异常, 而不是让异常处理过于冗长或重复.

#### 自定义线程池原因与目的
- `CompletableFuture` 默认使用全局共享的 `ForkJoinPool.commonPool()` 作为执行器, 所有未指定执行器的异步任务都会默认使用该线程池. 
- 虽然 `ForkJoinPool` 效率较高, 但是当同时提交大量线程时, 可能导致资源竞争和线程饥饿, 进而影响系统性能.
- 为避免这些问题, 建议提供 `CompletableFuture` 自定义线程池. 
- `CompletableFuture` 自定义线程池将带来以下优势: 
1. 隔离性: 为不同任务分配独立线程池, 避免全局线程池资源争夺; 
2. 资源控制: 根据任务特性动态调整线程池大小和队列类型, 优化性能表现; 
3. 异常处理: 通过自定义的 `ThreadFactory` 可以更好的处理线程异常情况.
