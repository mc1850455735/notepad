
## 生产者阶段（发送端）

- **确认机制**：使用 MQ 提供的确认机制。生产者发送消息后，必须收到 MQ 服务端的确认应答（ACK），才认为发送成功。
- **重试机制**：网络抖动可能导致发送失败，应在代码中包含重试逻辑。


**幂等机制**
由于重试机制的出现，消息可能出现重发发送给消费者的情况。因此，需要通过幂等机制，避免重复发送导致的问题。

**幂等实现方案**
- **数据库唯一主键**：利用数据库主键唯一性避免重复插入。
- **去重表**：利用 Redis 或 数据库 记录已经处理过的消息 id，每次处理消息前先确认该 id 是否存在。

## MQ 服务端阶段（存储端）

- **持久化**：确保消息不仅存在于内存中，还要刷到磁盘上。在 RabbitMQ 中需要将队列（Queue）和消息（Message）都设置为 `durable`。
- **多副本容灾**：使用**集群部署**。例如在 Kafka 或 RocketMQ 中，主节点接收到消息后，会同步给从节点，只有多个副本**都写入成功**，才返回成功给生产者。

## 消费者阶段（接收端）

- **手动确认（Manual ACK）**：**这是最关键的一点**。消费者不应在接收到消息后立即自动确认，而应在业务逻辑执行完毕并成功入库后，再手动向 MQ 发送确认。
- 如果执行失败，可以利用 MQ 的**重试机制**，将消息放回队列重新消费。
