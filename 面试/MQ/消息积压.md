
# 为什么会出现消息积压，如何处理大量消息积压？

当生产速度大于消费速度时，就会出现消息积压。常见的出现消息积压的**原因**如下：
- 生产流量突然增加：秒杀、大促等场景
- 消费者性能不足：消费者处理慢，CPU 性能不足 
- 下游服务响应慢：慢 SQL、Redis 响应慢、外部 API 延迟
- 消费者发生故障：消费者宕机，网络故障等
- 消费频繁失败：消费失败后持续重试，阻塞后续消息
- 分区数量不足：Kafka Partition 较少，限制了消息并行度
- Kafka 中频繁 Rebalance

在 Kafka 中，消息积压主要靠 Consumer Lag 消息进行判断，如果 Partition 中的最新 Offset 已经达到了 10w 但是 Comsumer 已提交 Offset 只达到了 7w，说明存在 3w 的滞后。
**预防**消息积压，主要通过三方面进行：
1. **容量规划**：根据业务峰值设计 Partition 数量、Consumer 实例数量和数据库处理能力；
2. **监控告警**：监控 Kafka Consumer Lag、消息等待时间、消费速率、失败率以及 Rebalance 次数；
3. **限流与弹性扩容**：在消费者能力不足时限制上游流量，并根据积压情况增加消费者实例；

对于消息积压，可以通过以下方式进行**处理**：
- 增加消费者数量：消费者数量的提升会导致消费并行度的提升，进而导致消费能力的提升，从而加速消息处理，缓解消息积压；
- 优化消费者处理逻辑：通过提升消费者的处理速度，减少与数据库的交互次数，排查满查询等操作，提升消息的处理速度；
- 对消费失败的消息进行隔离：通过添加隔离机制，避免消费者反复重试已失败的消息；同时失败的消息也不能简单丢弃，而是使用死信队列进行后续补偿处理；
- 临时扩容：如果消息积压过多，临时进行扩容，处理完积压消息后再回缩，如果现有 Kafka 分区不足，可以评估增加分区；
