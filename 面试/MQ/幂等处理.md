
# 常见的幂等处理方式有哪些

1. 数据库唯一索引：常用于创建
2. 幂等 Key / Request ID：
3. Redis SETNX
4. 状态机控制
5. 乐观锁
6. 数据库去重表
7. 一次性 token

**数据库唯一索引**
借助 MySQL unique key 的唯一性，以订单表为例，可以将 order_id 设为唯一索引，当第一次订单插入成功后，如果有第二次相同 order_id 的订单被试图插入，会出现 insert 失败，从而保证幂等。

**幂等 Key / Request ID**
客户端每次操作时，生成唯一 id，服务端先判断对应的唯一id是否处理过。如果处理过，直接返回第一次的结果，否则执行操作，保存对应唯一 id 的结果，并将结果进行返回。

**Redis `SETNX`**
客户端发送请求时，利用 Redis 的 SETNX 操作进行幂等判断。如果成功则执行业务；失败说明对应业务正在执行或者已经被执行过，适合做高并发条件下的简单防重。

**状态机控制**
以订单支付为为例，一个订单对应的状态只能是固定的线性的，不能重复执行，也不能违反顺序，如： `待支付 → 已支付 → 已发货 → 已完成`。
可以在 SQL 中将上一个状态作为 UPDATE 的条件，判断对应语句的 affected_rows，如果为 1，说明更新成功；为 0，说明已经被处理过或状态不允许处理。

**乐观锁**
将版本号作为条件，适合 `库存扣减、余额更新、状态修改` 等操作，本质上属于 CAS 思想。

**防重表**
在 MySQL 等数据库中定义一个特殊的表，对每一个消息，都给予一个 message_id，MySQL 中的表用于记录对应的消息是否已经消费。如果对应 message_id 插入成功，那么执行相关的业务；如果插入失败，则视为已消费，直接 ACK。
这是一种常见的 MQ 至少消费一次的解决策略。

**一次性 token**
客户端执行前，先申请 token，并带着 token 提交业务请求，服务端执行相关请求，并删除对应的 token。如果对应请求重复执行，由于对应的 token 已经被删除，无法执行从而拒绝。
