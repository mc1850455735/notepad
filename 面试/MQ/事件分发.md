
# 讲一下事件分发，事件分发的原理是什么？

事件分发就是通过事件类型建立生产者和消费者之间的订阅关系，当事件发生时，由 Dispatcher 或 Broker 根据路由规则找到对应的 Handler，并同步或异步执行，从而实现业务模块之间的解耦。

具体流程可以大致理解为：
```plain
事件产生
   ↓
事件分发器
   ↓
根据事件类型找到订阅者
   ↓
调用对应 Handler
```

事件分发的核心步骤为三步：
1. 注册事件监听
2. 路由事件到不同的服务
3. 执行对应接口处理事件

对于一个有多个服务关心的事件，如用户注册，通过事件分发不需要串行触发相应服务的接口，而是直接通过分发事件通知对应的服务。通过事件分发，不需要直接改动事件产生的代码，减少了模块之间的耦合度，使每个服务专注于自身，这就叫 事件驱动架构 (Event-Driven Architecture)。

以 go 举例，一个**基础的事件分发**可以分为添加事件监听和分发事件两个部分：
添加事件监听的过程可以看作是向一个 map 数据结构添加 handler 的过程，map 负责管理对应 event 发生时，应该通知哪些 handler；
分发事件的过程可以看作根据 map 中的 event 类型 key 和 handler 类型 value 调用接口的过程。

对于事件分发的实现，尤其是分发事件的过程，有同步和异步两种分发方法。**同步分发**比较简单，当事件被触发时，可以视作使用一个 for 循环遍历 map 对应 key 中的每一个 handler；**异步分发**可以使用 goroutine 等异步方式，从而一次性触发多个 handler。

对于大型系统，并不会简单的只使用 goroutine 和 map 等方式实现事件分发，还会结合比如 **Channel、消息队列、Event Bus** 等，提高系统的可用性。
以基于 Channel 的事件分发为例，当生产者产生了事件时，只负责将对应事件添加到 Event Channel 当中，消费者不断从 Channel 中拉取事件信息并消费，此时的结构就是在生产者和消费者之间添加了一个队列。
```
Producer
   ↓
Channel (Queue)
   ↓
Consumer
```

在**分布式系统**中，一个服务产生的事件会需要分发到多个不同的服务中，此时可以借助 Kafka / RocketMQ 等消息队列，此时的 Broker 就承担事件分发器的功能。以 Kafka 为例，Porducer 生产消息后，根据 Topic 选择不同的队列，决定消息要发给谁，并由不同的 Consumer Group 进行消费。也就是说，消息队列实际上就可以看作是事件分发的一种**分布式实现**。

事件分发有**两种典型的模型**：
- 发布订阅模型：有一个事件发布者，事件被一系列订阅者订阅，事件发出后，所有订阅了这个事件的人都可以收到。比如订单创建后，修改库存，通知用户，分析状态等一系列服务都执行。
- 竞争消费模型：一个消息发送后，一系列消费者进行竞争，最终只有一个消费者消费消息。比如处理 1000 张图片，每张图片都只能被处理一次。

# Kafka 中的事件分发是怎么实现的？

Kafka 的事件分发，本质上是通过 Topic + Partition + Consumer Group 实现的。
与普通的事件分发不同，Kafka  收到事件后不会主动调用 Handler，而是先将事件根据 Topic 持久化到 Partition 中，由 Consumer 主动拉取 Partition 中的消息进行处理。

具体来说，Kafka 事件分发的流程如下，以用户下单为例：
用户创建订单后，订单服务发布一个事件，包含事件类型、订单号、用户号等信息；随后，Kafka 通过 Topic 对事件进行分类，随后将事件发送到 Partition 中存储具体消息。
选择 Partition 时，如果指定了业务 key，可以通过哈希分区策略使同一个订单的事件进入同一个 Partition，从而保证同类事件在同一个 Partition 中的存储顺序。

进入 Partition 中的消息，Kafka 通过 Partition 和 Consumer Group 两个机制控制，决定使用发布订阅机制还是竞争消费机制。
对于不同的 Consumer Group 之间，遵从的是**订阅/发布机制**，同一个消息可以反复被不同的 Consumer Group 消费，每一个 Consumer Group 拥有不同的 Offset；
对于同一个 Consumer Group 之内的 Consumer，遵从的是**竞争消费机制**，同一个 Partition 在同一个时刻内只能分配给一个 Consumer，因此同一条消息不会被组内的 Consumer 反复消费。
如果 Partition 少，Consumer 多，那么 Partition 就成了决定最大消费并行度的关键因素。

通过 [[Kafka Rebalance]]，在 Partition 或 Consumer Group 中 Consumer 数量发生变化时，可以重新分配 Partition，从而支持扩容和故障恢复。
