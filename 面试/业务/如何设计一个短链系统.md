
短链系统就是在用户访问时短链接时，系统自动重定向到原始的长链接
短链系统的特征就是：读多写少。

在架构上，可以分为：
客户端 - 网关 - 实例 - Redis & MySQL - MQ - 服务统计 等模块

主要技术有：
- 数据库
- 缓存
- 分布式 ID
- 消息队列
- 网关

# 短码生成

通常采用 base62 生成短码。本质上是把一个整数转位一个固定长度的 62 位字符串。理论上，一个 6 位的 Base62 编码可以表示约 568 亿种组合。

不能使用 Hash，因为 HashCode 有可能发生冲突，同时 Java 的 hashCode 只有 32 位，无法保证大规模下映射的唯一性。

实际中，通常使用分布式 id + base62，完成从长码到短码的映射。
用户提交长 URL 后，通过分布式 ID 生成器，得到唯一 id，并将该唯一 id 通过 base62 进行编码，得到一个短码。最后将分布式 id 和完整URL存入 MySQL。

数据库表可以这样设置：
```sql
CREATE TABLE short_url (
    id BIGINT PRIMARY KEY,
    short_code VARCHAR(16) NOT NULL,
    long_url TEXT NOT NULL,
    user_id BIGINT,
    expire_time DATETIME,
    status TINYINT NOT NULL DEFAULT 1,
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_short_code (short_code)
);
```
最重要的是，必须对 short_code 建立**唯一索引**。

# 高并发访问支持

当用户访问量较大时，如果每次短链访问都直接打到 MySQL，会对 MySQL 造成很大的压力，因此采用 Redis+MySQL 的 **Cache Aside 模式**进行高并发的支持。具体主要与 Redis 的缓存使用有关。

短链系统返回时，通常使用 302 状态码返回网站的原始地址。因为 301 作为永久重定向，客户端中很可能会长期缓存目标 URL 的地址，影响网站统计短链服务数据。

对于这些状态码，含义如下：

| 状态码 | 含义               | 对短链系统的影响               |
| --- | ---------------- | ---------------------- |
| 301 | 永久重定向            | 客户端可能长期缓存，后续访问不再经过短链服务 |
| 302 | 临时重定向            | 更适合目标可修改、需要访问统计的短链     |
| 307 | 临时重定向，保留 HTTP 方法 | 适合需要严格保留请求方法的场景        |

# 访问统计

如果需要统计每个短链的 UV、PV、时段访问量、访问来源等数据，通常采用消息队列异步处理。用户请求短链后，系统通过 Redis + MySQL 查询其对应的长链，这一过程中会产生访问事件，对应事件会被加入消息队列中（如 Kafka），通过特定的 Consumer 进行计数，聚合到 Redis，最后写入 MySQL 数据库中固定。
